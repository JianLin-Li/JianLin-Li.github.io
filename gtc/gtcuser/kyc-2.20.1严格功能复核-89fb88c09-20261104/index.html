3. 已复现的 9 类问题

D1 / P1：迁移后的进行中流程，可能新旧接口都不能继续提交

产品要求： PRD 6.1.2、FR-OV-01—04 和监管切换验收要求，有当前流程时能够进入并继续办理；无历史的首次 KYC 应直接进入表单。

实际调用链：

  • 迁移 insertProcess 只插 process、关联旧 content，不初始化 kyc_member_other.kyc_link_json 中的 __process_v1.target。
  • 注册 setKycNode 只分配 member.kyc_id 和旧状态记录，也不创建该目标上下文。
  • context 和 readTargetContext 只读取已有控制节点。
  • shouldUpgradeLegacyWrite 因为查到当前本人 process，要求改用新接口；旧 Controller 因此拒绝提交。
  • saveInfo 又要求必须有匹配的目标上下文。

隔离执行结果： 构造已有本人进行中 process、没有控制节点的状态，context.current!=null、target=null、can_continue=true，myinfo 能返回 4 个步骤；旧写入口升级判断为 true，新 saveinfo 返回 KYC_TARGET_CHANGED。这不是缺字段或版本传错，客户端根本拿不到有效 target_context_id。

同一缺口也影响没有 process、没有目标节点的首次办理：新接口 context 返回 current=null,target=null,can_continue=false，myinfo.steps=[]。此时旧接口可能仍能办理，但当前新页面契约没有声明并覆盖这条首次办理分流，且旧链路不能自动获得全部新校验。

最小方案： 在既有流程 Service 增加受锁保护、幂等的“缺失上下文补齐”，不创建空 process、不创建 content。仅允许两种情况：已有进行中本人流程时绑定其 process/config；从未办理且已有服务端分配的有效 member.kyc_id 时，建立未提交目标。已有生效档案且没有新目标时不自行创建另一轮，也不覆盖后台已存在的目标或损坏节点。首屏入口及契约需同步说明这个准备动作；并发进入只能得到同一目标。无需改 process 表结构，也无需让客户传监管或规则 ID。

D2 / P1：Sumsub 总审核拒绝，可被新流程按子步骤通过处理

产品要求： FR-NA-01、范围文档 2.2.3 的前置条件都是第三方审核通过后才做平台附加检查；第三方不通过应展示第三方原因。

代码证据： Sumsub 新流程回调 把总结果 GREEN 和 RED 放入同一个分支，然后直接用 IDENTITY/POA 子步骤的 reviewAnswer 生成 passed/rejected。总结果 RED 没有优先阻断。对照同文件 旧处理，旧代码明确在总 RED 时进入拒绝处理。

隔离执行结果： 模拟总 RED（人脸不匹配）而 IDENTITY 为 GREEN，新绑定被写成 passed，refresh.required_action=poi_name_confirm_required；继续正常确认姓名并调用 saveinfo(mode=verification)，实际写入 status=9,audit_method=sumsub。复现只模拟供应商返回，没有调用真实第三方。

影响： 第三方已经拒绝的结果可能进入平台通过链路，拒绝原因也被丢失。这属于审核结果正确性问题，不是 request check 功能。

最小方案： 只修新流程适配分支的拒绝优先级：总 RED 优先转拒绝并复用已有原因解析；只有满足通过前提才解析为通过、做国籍和姓名检查、绑定关联候选。保留原验签、业务号、SDK 链接、供应商调用和旧业务号逻辑。补总 RED/子 GREEN、总 RED/无子结果两类行为测试。

D3 / P1：旧版分组快照的历史详情，会丢掉真实字段且误报完整

产品要求： FR-HD-02、FR-HD-21 和历史验收要求展示当时 schema、值和状态；不能用当前资料替代，也不能把缺资料误报为完整。

真实旧结构： 旧 buildKycFormDetail 返回 [{分组信息, child:[实际字段...]}]。迁移会把旧 kyc_form_detail_snapshot 原样放入流程快照。

新接口问题： normalizeHistoryFields 把每个顶层分组当成一个字段，没有展开 child。于是生成的 field 是空字符串；数组却非空，history_incomplete 被判为 false。进行中旧内容在 resolveFields 中也可能直接返回分组快照，而新接口文档约定的是平铺字段。

隔离执行结果： 用旧代码实际生成结构构造“一个分组、三个字段”的已完成历史，history/detail 返回 fields 数量 1、field_keys=[""]、history_incomplete=false，但 values 仍有三个真实字段。前端拿不到正确的字段定义来展示这些值。

最小方案： 在既有快照转换处同时兼容平铺字段和旧 child 分组，仅使用历史快照中的叶子字段，保留原顺序、标题、类型及 extra；不能去查当前 schema 补历史。无法解析出真实字段时，才标记不完整。当前旧内容读写也复用同一受限转换。无需回写全部历史数据或重新迁移。

D4 / P2：新表单增加必填字段后，myinfo 仍允许直接复用提交

产品要求： FR-RU-07、RU-16—17 和 9.1.1 第 9—11 条明确要求：旧值反显，新必填字段为空，未补齐时提交置灰，进入修改补齐后仅当前步骤重审。

代码证据： myInfo 的复用判断与权限 只根据是否找到旧通过 content；resolveUiState 没有检查它是否满足当前必填字段。写入口倒是会调用当前字段校验。

隔离执行结果： 同 form ID，旧通过资料缺少新必填字段：接口已经返回该新字段，但同时返回 mode=reuse,can_submit=true,can_reuse=true；直接复用提交又报 KYC_FIELD_REQUIRED。

影响： 后端不会因此误通过，但前端若按当前契约渲染，按钮状态与产品要求相反，客户需要点击后才知道缺字段。

最小方案： 读取阶段用现有字段定义检查旧资料完整性，区分“可反显来源”与“可直接继承通过”。缺必填时保留旧值、返回提交不可用和缺失字段，允许进入修改；正式提交仍执行原有校验。只处理当前步骤。

D5 / P2：已经进入重提编辑，刷新后仍返回不可编辑、不可提交

产品要求： FR-RU-10—11 要求服务端持久化编辑态，刷新或返回后继续编辑；驳回重提也必须能完成重新提交。

代码证据： resubmitInfo 调用 enterEdit 持久化 edit_entered；myInfo.mode 使用这个标记，但 UI 状态和 permissions 仍只按旧 content 状态计算。resolveUiState(-1) 固定返回 rejected、can_edit=false,can_submit=false。

隔离执行结果： 对拒绝 content 调用 resubmitinfo，成功拿到 edit_context_id，随后读 myinfo 得到 mode=edit，但 ui_state=rejected、can_edit=false、can_submit=false、动作仍是 resubmit。

影响： 用 resubmitinfo 的局部响应强制进入编辑可能暂时可用，但刷新、换设备或按 permissions 恢复页面时会回到旧状态。不能要求前端自行篡改服务端权限来补救。

最小方案： 对本人进行中流程，把有效编辑上下文、重提标记纳入页面状态计算；返回可编辑/可提交状态。旧 content 的 -1、驳回原因和审核证据保留，正式提交成功后才清编辑标记。历史和已结束流程继续只读。

D6 / P2：驳回后表单定义变化，编辑入口返回旧字段，却按新字段校验

触发条件： 当前流程某表单已经提交并被拒绝，之后后台在相同 form ID 中新增必填字段，客户重提。

代码证据： resolveFields 只要旧 content 有快照就优先返回旧快照；enterEdit/resubmitinfo 继续使用该结果。正式提交的 validateSaveValues 则查询实时 system_form_detail。

隔离执行结果： 重提响应不包含 new_required，客户按返回字段提交得到 KYC_FIELD_REQUIRED。与 D4 不同，这里编辑入口根本没返回必须填写的字段。

最小方案： 进行中表单的编辑/重提使用本次提交将校验的有效 schema，旧值按兼容字段预填，新字段为空；历史详情和只读已提交证据继续用当时快照。不要全局取消快照，也不要通过关闭必填校验解决。

D7 / P2：普通表单姓名没有继承旧的去空白校验

产品依据： FR-RU-03 要求按新规则校验资料完整合法；旧链路已有姓名去空白及非空约束，本次也没有要求移除该能力。

代码证据： 新 validateSaveValues 只检查 null/''/[]，不处理字符串空白；旧 saveInfoGtc 对 first_name/last_name/firstname/lastname 会 trim 后再次拒绝空值。

隔离执行结果： 在自动规则下提交 first_name=" "，实际返回 submitted=true,status=9，数据库保存了三个空格。此处是普通个人信息提交，不是第三方姓名拆分，后者已有不同的校验。

最小方案： 在现有新提交规范化中恢复四个姓名字段的字符串、trim 和空值检查，复用与编辑都采用同一口径；仅补旧链路已有的必要约束，不另造通用表单校验框架。是否还有其他字段合法性约束，应按现有字段类型逐个确认，不能据此大范围重写。

D8 / P2：流程已终止，refresh 仍可能返回可继续姓名确认

产品要求： PRD 5.1 和 9.5 第 7 条要求旧流程链接和旧认证失效；结束流程不能再引导客户办理。

代码证据： 回调和正式写入口已经校验 process_status=1，但 refresh 只检查目标、审核代次、provider、process ID 是否仍匹配，没有检查绑定流程当前生命周期。

隔离执行结果： 保留匹配的控制节点及 passed 认证，把 process 改为 -2；refresh 仍返回 state=passed,required_action=poi_name_confirm_required。后续写入口会拒绝，因此这里不是已证实能恢复资格，而是读接口给出了不可执行的动作。

最小方案： refresh 在计算动作前核对本人流程生命周期，终止/归属不符/不存在返回失效态并清空办理动作；正常完成且已提交的回执仍可只读返回，不能把合法完成记录全部误标为失败。真实管理端终止若已经换了目标，该场景会被现有代次检查拦住；缺口针对终止后控制节点仍保留的状态。

D9 / P2：姓名保留并转人工后，重新读页面显示的仍是第三方审核

产品要求： FR-NM-12—13 要求保留第三方证据、POI 转人工，而不是继续第三方审核；页面和真实审核方式需要一致。

代码证据： 正式提交正确写成 kyc_audit_method=manual,status=1，但 myInfo 的 review_selection 随后被 applyFormStateToReviewSelection 中保留的 method=third_party,provider=sumsub 覆盖。重读响应没有独立的“当前人工待审”字段来区分证据来源。

隔离执行结果： 姓名不一致，选择 keep_current_name_manual 并正式提交：数据库 audit_method 为 manual，但 myinfo 返回 review_selection.method=third_party,provider=sumsub，verification 为 submitted。

最小方案： 已正式提交的当前待审内容以真实 kyc_audit_method 作为当前审核方式；第三方 provider 留在 verification 中作为证据来源。若处于尚未重新提交的方式切换编辑态，再使用控制节点的选择。供应商字段缺失转人工的同类路径一起用窄测试验证。

4. 部分实现和边界问题，不与已复现缺陷混算

4.1 “兼容表单资料预填”实际仅支持相同 form ID

PRD 6.3 原则及 FR-RU-12 描述相同或兼容资料可预填，兼容预填不继承审核状态。目前 findReusableProcessContents 只接受相同 form ID；不存在另一套受控的兼容字段预填逻辑。

隔离场景使用两个不同 ID、相同类型、相同三个字段的个人信息表单，新表单 values=[]，没有预填。这证明当前覆盖止于相同 ID；但产品没有把“兼容”明确为仅字段同名、同类型，还是必须有复制来源关系，所以不能直接按标题、sort 或 form_type 猜来源。

最小建议：先把本期必须支持的兼容来源落实为明确的表单对照。已有可证明复制关系时，只预填语义和类型兼容的字段，新增字段留空，始终重新审核；没有唯一来源时保持空值。无需建设通用迁移引擎，也不建议无条件按同类型跨表单复制。若产品本期只要求相同 ID，应明确收窄 FR-RU-12 的验收口径，不能继续声称已经支持任意兼容表单。

4.2 新流程不支持 Zoloz，而 Web 审核方式图里包含它

reviewSelection、allowedReviewProviders 目前只开放 Sumsub、IDWise；旧 /api/kyc/kyc_link 对已进入新流程的客户又会返回升级要求。所以旧 Zoloz 不能仅靠“旧逻辑还在”就在新流程中继续使用。

这是确定的渠道覆盖边界，是否构成本期阻断取决于实际目标规则是否还配置并要求提供 Zoloz。不能为了让选项显示就直接放开新渠道，因为其结果尚未有同等可信的流程绑定。最小处理是先核对本期部署规则与前端选项：若必须保留，单列兼容任务；若不在本期支持范围，产品、配置和 UI 明确一致。本轮没有修改第三方发起和回调。

4.3 POI 地址开关关闭时，独立第三方 POA 应否自动通过，产品原文有张力

范围文档 2.2.2 同时写了：

前置条件：优先使用第三方 POA 结果回写；若没有 POA 信息，再使用该逻辑。

开关关闭：不区分第三方如何返回，客户都需要独立完成 POA 步骤，提交后进入人工审核。

当前实现把开关限定在“无独立 POA 的 POI 地址补齐”；正常独立第三方 POA 通过后，仍可以 status=9。这个实现符合前置条件的窄解释，但不符合把“开关关闭”那句理解为全部 POA 都转人工的解释。不能给它一个无条件“完全符合”的结论。

建议由产品明确此开关仅控制地址补齐，还是也覆盖独立第三方 POA 的最终审核方式。确认前维持现状，不扩改供应商逻辑或把所有 POA 一刀切转人工。

4.4 姓名转人工后的页面动作，以最新 PRD 的直接提交要求为准

最新 FR-NM-13 写明：回填第三方资料后，系统直接提交人工审核并定位下一步骤。App 原型仍有人工表单及提交按钮的画面。

当前接口可以完成该行为：name_preview → name_confirm → saveinfo(mode=verification)。其中后两次请求应由前端在用户点击同一个确认按钮后自动串联，不能额外要求客户再点击一次“提交”。name_confirm 单独成功只保存决策；如果 saveinfo 失败，前端不得跳下一步，应保留输入和决定并允许重试。

因此，“拆为两个请求”本身不等于后端缺功能；实际前端是否自动串联尚未验收。最小方案是把一个用户动作的调用与失败恢复明确给 App/Web，不为此新增一套姓名提交服务或合并大事务。

7. 时间、历史和 SQL 口径

PRD 把开始时间称为 created_at，现有 SQL 使用 create_time、对外返回 started_at。本轮核对到新提交和迁移均把 create_time、started_at 设置为同一个开始值，因此字段命名不同本身不要求加列，也没有发现用审核时间代替开始时间。前端应明确把 started_at 映射到 PRD 的开始时间并格式化为 YYYY-MM-DD HH:mm:ss。

ended_at 的 SQL 定义是完成或终止时间。若产品要展示的是“被下一份档案替代的失效时刻”，那是另一种业务时间，不能擅自拿 update_time 代替；本轮没有依据要求增加字段。

当前 SQL 已有 poi_address_auto_pass，最后两步关联认证和地址补齐并非仍然完全未开发。旧接口文档开头及旧复核报告中的笼统“复合认证未完成”需要区分为“本地关联已实现、真实报文及双端验收未完成”。

本轮没有新增 SQL。process 历史查询按 member_id 缩小范围，再按生效状态/时间排序并分页，现有版本 SQL 有 member_id 索引；没有访问资金或返佣大表。单会员 process 数量较大时，排序和 count 成本仍需实际规模/EXPLAIN 判断，不能凭本次功能复核承诺性能。

9. 建议的最小修补顺序

每一步可以独立审核和提交，不需要大范围重构，不新增 process 表字段。

顺序 范围 具体动作 关键验收
1 D1，入口 受控补齐缺失目标，覆盖迁移进行中和首次办理；不生成空流程 首次进入、迁移后继续、两次进入幂等、旧生效无新目标不多建一轮
2 D2，拒绝优先级 只修 Sumsub 新流程适配对总 RED 的判断 总 RED/子 GREEN 不能过，保留拒绝原因；正常 GREEN 不回归
3 D3，旧快照 转换旧 child 分组，保留历史字段；正确标记不完整 新平铺、旧分组、缺 schema、本人终止详情、跨会员拒绝
4 D4—D6、D9，页面契约 修复复用资格、进入编辑后的权限、编辑 schema 和实际审核方式 前后端字段一致；刷新可重提；人工与第三方来源可区分
5 D7，旧校验 仅补姓名 trim/非空等已有约束 空白姓名拒绝，合法姓名保留；其他表单不扩大校验

7 第 4、8 节 明确兼容/渠道/开关口径，执行双端真实联调 不用未经确认的假设扩大第三方或管理端改动

步骤 2 是本次需求的“第三方拒绝不能当通过”修正，和新建 request check、重写第三方认证流程不同；实施时仍应只改必要适配判断。此表是审查建议，本轮没有执行这些业务修补。
