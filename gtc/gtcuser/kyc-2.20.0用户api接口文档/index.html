Kyc 2.20.0用户 api接口文档

2026-11-13 项目：gtcuser

KYC 流程用户 API 契约

最新前端联调文档：KYC 2.20.1 用户 API 最新接口文档（2026-11-05）。已按 36167d0c6 及合入后的 test 核对完整路径、参数、响应码与调用顺序。下文保留原实施过程，当前接口以新文档为准。

版本：2.20.1 状态：当前功能分支实施契约；协议、证件约束、生效资料、客户文件、日志、回调生命周期、成功通知及个人信息重提改国家后的 POA 重认证已分步补齐。本轮另补 Sumsub 失败后 request check，见 4.7。供应商及双端真实环境验收尚未完成，不能据此认定整项需求已上线就绪。实施与提交记录见同目录《KYC-2.20.1用户API分步实施与验收记录-20261103.md》。

最新收尾基线：b9e26dc26。本次修正第三方正式提交重放时的会员资格返回，完成 15 个 KYC 行为脚本及 15 项单元测试复核；完整结果与剩余外部依赖见同目录《KYC-2.20.1用户API最终收尾复核-20261104.md》。

1. 通用约定

  • 基础路径：/api/kyc/process。
  • 除第三方回调外，所有接口使用现有 TokenMiddleware。
  • 当前会员 ID 从登录态取得，客户端不能传 member_id。
  • process_id、content_id、form_id、verification_id 对外按字符串处理，避免 JavaScript 大整数精度丢失。
  • target_context_id 是未正式提交前的目标上下文，不是 process_id。
  • source_type=1 表示客户本人流程；source_type=2 表示后台代客流程。
  • 用户 API 只允许编辑 source_type=1 且 process_status=1 的流程。
  • 每个会员最多一条未完成 source1 流程和一条未完成 source2 流程。
  • 没有正式提交前不创建 t_kyc_process，不创建状态为 0 的空流程。

统一成功响应仍使用项目现有 Result 包装，以下示例均为 data 内容。

正式提交后的 review_selection.method/provider 展示当前内容实际审核方式，姓名保留或资料不足转人工时显示 manual/null；第三方证据来源仍在 verification.provider。进入新编辑或切换后，审核选择展示待重提方式。

显式请求 source2、已完成或已终止流程作为当前编辑流程时，返回对应错误；历史详情使用 POST /api/kyc/process/history/detail。

POA 步骤增加 country_consistency={personal_country,hint_key}，hint_key=POA_COUNTRY_CONSISTENCY_HINT 对应常驻文案“与个人信息居住国家需保持一致”。POA 尚无资料时默认国家取本轮个人信息国家；人工不一致校验同时在服务端执行。

4. 表单操作

4.1 进入表单编辑（POST /api/kyc/process/enter_edit）

1{
2  "target_context_id":"ctx-uuid",
3  "process_id":"10001",
4  "form_id":"12",
5  "expected_version":3,
6  "source_content_id":"8102"
7}

只记录编辑意图，不创建流程、不创建 content、不改变审核状态。返回 edit_context_id、可编辑字段和 values。source_content_id 可选；传入时必须是当前生效档案中本人相同 form ID 的通过来源，不能指定其他表单或其他会员资料。

进入编辑成功后，POST /api/kyc/process/myinfo 对应步骤会持续返回相同的 edit_context_id 和 mode=edit。重复调用会复用已有编辑上下文。本轮尚无提交内容时，即使省略来源 ID，也会用服务端已核定的同 ID 可信历史资料预填 values，刷新后仍可反显；新增字段保持空值。已有本轮提交或重置/第三方预填时优先显示本轮数据。不同 form ID 不按类型、标题或 UUID 猜测预填。

预填不继承历史审核状态；进入编辑后即使值全部改回，也须按本轮规则正式重审，不能再调用 mode=reuse 绕过。只读复用的数据仍从 reuse.preview_values 读取，缺新增必填时先显示 reuse_incomplete，由客户修改补齐。

普通编辑提交沿用旧配置：个人客户 setting.auto=1 时，个人信息、问卷、协议（form_type=1/3/4）按自动审核为 status=9；公司客户仍待人工，人工 POA 不因 auto=1 直接通过。协议编辑提交必须完成下述正式签署链路，签署失败不能推进步骤。

本轮全通过时，用户 API 在提交事务中投影最终个人信息姓名、国家和规则到会员，冻结档案，并同步 member_other 的监管类型与档案快照；失效当时实际生效的流程。新流程尚未全通过时保持旧生效会员资料。

mode=verification 还需提供 verification_id，请求中的 values 不参与认证资料落库。服务端只读取已验签回调绑定的供应商资料，并再次核对目标、表单、审核代次和流程版本。POI 须先完成姓名确认，POA 国家不一致须先完成国家决策。供应商资料或证明文件不齐全时新 content 为 status=1，交人工审核；资料齐全且附加校验通过时为 status=9。verification 提交成功后返回 verification_id，重复 request_id 返回原回执。成功响应中的 process_id、content_id 均为字符串；首次正式提交才创建流程记录。

member_kyc_status 表示请求返回时的会员整体资格，与当前步骤 status 分开。新流程未完成但旧档案仍生效时为 9；首次办理尚未完成时通常为 1。第三方提交重放保留原提交的 content_id/status/version，对 member_kyc_status 重新做只读查询：不返回旧回执中的占位值，也不因重放恢复已终止流程或写回资格。完整页面的生效档案仍通过 POST /api/kyc/process/context 重读。

正式提交包含 idno 时，人工、第三方及历史复用都复用旧 TMemberService::checkIdOfUserNum 的注册限制开关、正常会员/总账号数量规则；以本轮个人信息国家为上下文。数量拒绝沿用业务码 10004 及旧翻译文案，网关异常保持原异常。失败不创建内容或回执；已提交请求重放不重复检查。此步没有增加证件号唯一约束，也未改变旧跨会员并发口径。

协议字段正式签署（仍使用 POST /api/kyc/process/saveinfo）

myinfo.steps[].fields 中 type=agrement 的 extra 保留服务端配置的 PDF 模板 URL。编辑提交把对应字段值设为 true（兼容 1、"1"），例如 values={"contract":true}，字段名以实际表单为准。不能把前端上传的 PDF URL 作为签署结果。

服务端复用旧 PDF 签署服务，使用本流程个人信息姓名、居住国家、会员可信邮箱以及本次请求 IP/设备，生成签名文件；正式内容保存生成后的 URL，并创建既有 contract_agreements 记录和 kyc_agreement 安全活动。表单、签署记录、活动、流程和提交回执在同一事务保存；失败全部回滚。相同 request_id 和相同请求重放返回原回执，不重复签署。

mode=reuse 从服务端当前生效来源读取已签署 URL，不重新生成协议；来源没有签署 URL 或本轮姓名变化要求重签时拒绝复用，需进入编辑重新确认。旧 PDF 服务未重构：文件生成期间持有会员事务锁，文件上传成功后数据库失败可能留下孤立文件，需在 staging 验证耗时和失败恢复。

先按普通 mode=edit 提交。姓名一致按当前配置提交；不一致且没有 personal_name_decision 时，外层仍为正常 Result，但 data 表示本次未提交：

4.2.2 个人信息重提改国家后重认证 POA（POST /api/kyc/process/saveinfo）

用户于 2026-11-03 确认：本轮个人信息被驳回后允许重提变更居住国家；若本轮已通过 POA 的国家与新国家不一致，将该 POA 恢复待提交，要求重新认证。无需新增请求参数或路由，仍按 saveinfo 提交个人信息；姓名同时不一致时，先完成 4.2.1 的姓名决策，未正式提交不重置 POA。

处理仅限同一会员、同一进行中本人流程、目标规则内 form_type=5,is_last=1,kyc_status=9 的不一致 POA。CN/CHN/China 统一比较，同国表示变化不触发；未通过 POA、其他流程和会员、姓名/国家规则未涉及的步骤保持原状。

成功响应新增 reset_form_ids，仅列出本次国家变更触发重认证的 POA 表单 ID，按字符串数组返回。例如个人信息重提成功后返回 "reset_form_ids":["13"]，普通提交返回 []；请求重放返回首次相同结果，不重复重置或写日志。前端按 reset_form_ids ?? [] 兼容升级前保存的旧回执。

前端收到非空数组后，使用响应中的新 version 调用 POST /api/kyc/process/myinfo 刷新整个流程，不能沿用此前 POA 已通过卡片。对应 POA 为 status=0,content_id=null,mode=edit，审核选择中 requires_resubmission=true；旧普通资料可预填，国家覆盖为新国家，证明文件清空。保留原配置可选的人工/第三方方式：人工重新提交进入待审；第三方需发起新的认证并取得可信结果，旧认证、迟到回调和历史只读复用均不能直接恢复通过。重新正式提交成功后清除重提标记。

原 POA 审核记录与客户文件保留作证据，原内容仅退出 is_last，不创建状态 0 的空内容。重置、个人信息新内容、流程版本、日志和回执同事务，失败全部回滚。重置后整轮保持进行中，旧生效资格和会员国家不提前改变；待重新认证且本轮全部通过后再切换。

4.3 准备驳回表单重提（POST /api/kyc/process/resubmitinfo）

只允许本人 source1 进行中流程中当前 kyc_status=-1 的表单。接口返回编辑上下文，正式保存仍调用 POST /api/kyc/process/saveinfo。

接口会保留原拒绝 content_id 作为 base_content_id 和只读基线，并在控制节点标记 requires_resubmission=true；不会修改旧 content，也不会提前创建新 content。

4.4 切换表单审核方式（POST /api/kyc/process/switch_method）

用于在人工和第三方审核方式之间切换。未提交和待审核允许切换；已通过、source2、已终止不允许切换。

3  "form_id":"12",
4  "method":"third_party",
5  "provider":"idwise",
6  "expected_version":3,

4.5 创建第三方认证链接（POST /api/kyc/process/kyc_link）

创建第三方认证链接。请求必须指定本人可编辑的 process_id 或有效 target_context_id、form_id、provider 和 request_id。客户端不能传 level、回调地址或审核结论。

没有正式提交时可以生成认证链接，但不创建流程或表单记录；认证结果先绑定控制上下文，首次正式提交时再绑定流程。

新流程按规则配置开放 sumsub、idwise、zoloz；Zoloz 沿用旧版仅支持 POI（form_type=2）的范围，不在 POA 中展示或接受选择。Zoloz 的发起和结果查询复用旧 Identify/SDK/定时任务，尊重原 kyc.kyc_identy 的人脸实名/证件实名配置。服务端保存本次实际 bizId、transactionId 与认证上下文的对应关系，前端仍只使用 verification_id，不自行传供应商业务号或交易号。

链接申请失败返回 KYC_PROVIDER_LINK_FAILED；打开链接或收到前端回调不会直接产生通过结论，正式提交仍需调用 saveinfo。Zoloz 成功也必须经过平台国籍校验及姓/名确认；保留原姓名或材料缺失时进入人工审核，不能因供应商成功直接修改会员姓名或通过表单。

4.6 查询第三方认证状态（POST /api/kyc/process/refresh）

1{"verification_id":"verify-uuid"}

返回 pending、passed、rejected、submitted、superseded 或 expired，以及 form_id、target_context_id、verification_id、provider、process_id、version 和可展示原因。passed 时的 required_action 为 poi_name_confirm_required、poa_country_decision_required 或 submit_verification；平台国籍拒绝为 nationality_rejected。仅返回完整证件姓名和国家等展示字段，不返回证件号或供应商原始资料。只有服务端验证过的第三方结果才可用于正式提交，前端不能自行声明认证完成。

认证摘要及本接口增加 can_request_check 和 request_check_status。前者只在当前有效 Sumsub 失败绑定上为 true；平台国籍拒绝、失效或已提交绑定不可重审。后者取值见 4.7。

绑定流程已终止、丢失、归属其他会员或代客来源时，返回 state=superseded 并清除 required_action；不返回可确认或可提交动作。已完成流程的 submitted 回执仍可只读查询，未绑定流程的首次认证按正常状态返回。

管理端联调前提： 如果 saveinfo(mode=verification) 因供应商字段或证明文件缺失、或因用户选择保留当前姓名而产生 status=1 的人工待审内容，管理端审核通过后须按该 source1 流程规则重算全部表单状态。达到全通过时，管理端须冻结流程档案、切换生效流程，并落实本轮已确认的姓名及目标国家投影；否则用户 API 只会看到单步通过，流程不会自动生效。此项需与 Eric 的管理端实现联调验收。

4.7 申请 Sumsub 重新审核（POST /api/kyc/process/request_check）

作用： 客户在 POI/POA 的 Sumsub 自动审核失败后，主动要求 Sumsub 用同一申请人重新审核。根据范围文档 2.2.5 实施，不创建新 applicant、不生成新认证业务号、不改变认证等级。客户端不传 applicantId、第三方业务号、审核结论或任意重审原因。

1{
2  "target_context_id":"ctx-uuid",
3  "process_id":"10001",
4  "form_id":"12",
5  "verification_id":"verify-uuid",
6  "selection_generation":1,
7  "expected_version":3,
8  "request_id":"recheck-uuid"
9}

selection_generation 取 myinfo.steps[].review_selection.generation。首次正式提交前 process_id=null、expected_version=0；不会因此创建流程或表单记录。同次 Sumsub 认证附带的失败 POA 也复用原申请人重审，已提交的 POI 结果保持原状。

返回 refresh 的当前认证状态，并增加 request_replayed，例如：

 1{
 2  "verification_id":"verify-uuid",
 3  "form_id":"12",
 4  "target_context_id":"ctx-uuid",
 5  "provider":"sumsub",
 6  "state":"pending",
 7  "request_check_status":"accepted",
 8  "can_request_check":false,
 9  "request_replayed":false,
10  "required_action":null,
11  "process_id":"10001",
12  "version":3,
13  "retry_after":5
14}
request_check_status 含义与前端动作
not_started 本绑定尚未发起 request check
preparing 服务端正在查询原申请人与审核状态；重复请求使用同一 request_id。准备进程中断超过 60 秒后，同一请求可以安全接管准备阶段
sending 已预留发送操作；继续查询，不能换新请求重复送审

规则：

  • 只接受本人当前目标、source_type=1 进行中流程，且表单属于当前规则、当前审核方式为 Sumsub、版本与选择代次一致。已正式通过表单、已完成/终止流程、代客流程及平台国籍拒绝不可重审。
  • 同一 request_id 与相同参数只执行一次发送；重复请求返回当前状态、request_replayed=true。同一幂等键改参数返回 KYC_REQUEST_REPLAY_MISMATCH。重审进行中禁止另起请求。
  • 发送前查询原申请人及当前审核状态。供应商 pending、queued、prechecked 等未完成状态不再次送审；缺少可核对的审核轮次信息时也不发送。当前整体 RED，或整体 GREEN 但目标步骤明确 RED 时才送审，已通过的当前结果不再额外送审。
  • 回调及查询补偿只采纳同一 applicant 已完成的新审核轮次，旧 RED 晚到不能结束本轮重审。只有准备阶段允许租约接管，发送阶段中断不能自动重发。
  • 重审通过仍需执行平台国籍检查、POI 姓名确认、POA 国家一致性判断，之后才可正式 saveinfo；不会直接修改会员资格、生效档案或创建通过表单。
  • 前端按 can_request_check=true 或步骤 available_actions 中的 request_check 展示重新审核入口。本文不增加业务重审次数或冷却时间限制；供应商实际是否接受以返回为准。

产品“同一流程只产生一笔第三方费用”的目标通过复用原申请人落实；供应商真实账单和套餐计费仍需联调核实。

 4  "form_id":"12",
 5  "verification_id":"verify-uuid",

 8  "last_name":"ZHANG",

值 处理
use_confirmed_name 采用确认后的姓名；后续正式保存时满足证据条件才自动通过

6. POA 国家处理

6.1 校验人工提交及历史复用 POA 的国家一致性（POST /api/kyc/process/saveinfo）

人工提交及历史复用 POA 在 POST /api/kyc/process/saveinfo 内以本轮个人信息国家优先、会员国家兜底做服务端校验。两者不一致时返回业务错误键：

1{
2  "error_key":"POA_COUNTRY_MISMATCH"
3}

此时不创建 content、不更新会员资料、不生成通过状态。两个国家由页面正在编辑的个人信息和 POA 字段展示，错误响应本身不附带国家值。

6.2 处理 POA 国家不一致（POST /api/kyc/process/verification/poa_country_decision）

第三方 POA 返回后发现国家不一致时调用。

1{
2  "process_id":"10001",
3  "form_id":"15",
4  "verification_id":"verify-uuid",
5  "decision":"keep_personal",
6  "expected_version":4,
7  "request_id":"poa-country-uuid"
8}

decision：

值 处理
keep_personal 保留个人信息国家，POA 要求重新上传并转人工审核
use_poa 使用 POA 国家，终止当前 source1 流程，从个人信息重新开始

首次提交前 process_id 可为 null、expected_version=0。keep_personal 使当前 POA 内容退出本轮有效记录，将第三方资料预填到人工编辑态、把国家改为个人国家并清空旧证明文件；saveinfo(mode=edit) 要求上传新文件，旧第三方证明 URL 不得混入新提交。新人工提交创建新的 content 并待审核；本次重交期间切换第三方会拒绝 KYC_POA_RESUBMIT_REQUIRED。第三方认证保留为只读历史绑定，不能再作为本轮通过凭证。服务端确认同次认证覆盖 POI＋POA 时，关联 POI 同时恢复待提交，清除原姓名确认并使旧认证失效；独立 POI 不受影响。

成功响应新增 reset_form_ids 字符串数组：保留国家时为 POA 及实际退回的关联 POI，如 ["15","12"]；独立 POA 为 ["15"]；更新国家时为目标规则全部表单。前端按 reset_form_ids ?? [] 刷新步骤，并重新读取 POST /api/kyc/process/myinfo，不得继续显示旧 POI 通过状态或沿用旧姓名确认。幂等重放返回首次相同的受影响表单。

use_poa 将已存在的当前流程标记为 process_status=-2，原因固定为 poa_country_reset；若还没有流程则只重置目标。接口生成新的 target_context_id、递增目标代次，并在 target.personal_country_override 保存 POA 国家供个人信息预填和重提。全部当前步骤及认证绑定失效，旧生效流程继续有效；新流程在下一次个人信息正式提交时创建。会员国家直到新一轮完整生效才更新。

重置响应还包含 next_process_id=null,next_version=0。响应原 process_id/version 指向被终止流程；前端切换到新 target_context_id，用 next_version 办理新目标，不能带旧版本。新目标会预填相同表单已通过的兼容资料，个人国家用 POA 新国家覆盖；全部当前步骤仍为待提交，个人信息不能直接复用旧国家的通过状态。当前目标规则保持不变，用户并未选择或更改监管类型。

服务端只接受 verification 状态中的可信国家结果，决策时重新读取本轮个人信息国家，并按 request_id 幂等；不会由客户端直接修改 t_member.country 或旧生效流程。

6.3 复合认证与身份含地址的范围

POST /api/kyc/process/kyc_link 仍按单个 form_id 生成独立 business_id。同次 Sumsub 成功认证确有另一类唯一已审核材料时，服务端在既有控制 JSON 绑定具体 POI/POA 表单；不按“同会员、同供应商”或相同 applicantId 合并独立认证。关联结果仅是候选，POI 仍需姓名确认及正式提交，POA 仍需国家一致性检查及正式提交。多份同类材料或图片不能唯一定位时，不推断关联。真实供应商样本仍待联调验证。

身份含地址补齐 POA 已接入 POST /api/kyc/process/saveinfo，无需新增请求参数或接口。处理条件为：当前规则自动审核且 poi_address_auto_pass=1、本次 Sumsub POI 通过国籍及姓名附加校验并正式提交、没有独立 POA 信息、能够唯一定位本次通过证件的地址及图片、目标 POA 必填字段齐全。POI 仅在第三方通过或仅确认姓名时，不生成正式 POA 内容。

供应商映射采用当前通过步骤对应的 info.idDocs[].address；若地址带 source，仅接受 proofOfIdentity。居住国家使用该地址的 country 经现有国家映射转换，不能使用证件签发国；图片复用该 POI 本次 imageIds 已下载的正反面。申请人通用 info.addresses、历史同类多份证件、未能定位的材料均不能直接触发补齐。出现任何 PROOF_OF_RESIDENCE 步骤（含待审、拒绝）或独立 POA 资料时，保持第三方 POA 优先，不用身份证地址绕过。

国家一致时，与 POI 提交在同一事务创建已通过 POA content、字段快照、客户文件和自动填充/审核日志，纳入既有额度及整轮状态计算；额度或落库失败整体回滚。成功响应 auto_passed_form_ids 如 ["15"]；未发生补齐为 []。前端按 auto_passed_form_ids ?? [] 刷新对应步骤，并重读 POST /api/kyc/process/myinfo，无需另行提交该 POA；请求重放不重复创建。

国家不一致时只保存同源 POA 候选，不创建通过内容；页面通过既有 poa_country_decision_required 引导调用 POST /api/kyc/process/verification/poa_country_decision。保留个人国家时按 6.2 退回 POA 和关联 POI；使用 POA 国家时重置全部步骤。姓名选择保留个人信息转人工时，不自动补齐 POA。

按范围文档 2.2.2 的前置条件及 Eric 用户 API 实施方案 8.5，该开关控制“无 POA 信息时用 POI 地址补齐”，关闭时不填充、客户需独立完成 POA。可信的独立 POA（包括同次明确的 PROOF_OF_RESIDENCE）在开关开/关时均可于材料齐全、国家一致且正式提交后通过；缺证明转人工、国家不一致先决策、供应商拒绝不采纳。人工提交在两种开关状态下都进入人工审核；已通过独立 POA 不被后到身份证地址覆盖。未将该开关扩为独立第三方 POA 的总审核开关。

该矩阵已有 70 项隔离行为检查。范围文档“关闭后提交进入人工”一行应结合上述“无独立 POA”前提阅读，建议产品补全前提文案；这不是本轮取得的新产品确认。真实 Sumsub 样本的文档地址、字段覆盖、图片归属及 MySQL 两端锁仍需 staging 联调，缺少证据保持独立 POA 路径。

已绑定流程的回调仅接受会员本人 source_type=1,process_status=1：完成、终止、来源不符或记录不存在时不拉取供应商详情，迟到的新业务号仍被消费，不能落入旧链路写入。回调写入前与后台共用会员行互斥，重新核对状态，防止查询详情期间被终止。首次正式提交前允许尚未绑定流程的认证，只保留可信结果，不创建流程、表单或变更资格。旧业务号继续沿用原供应商链路。

整轮生效资料同步

只有本流程全部必需步骤通过后，才在同一事务切换资格并投影会员资料：最终姓名以本轮个人信息为准；生日、证件类型和国籍优先本轮已通过 POI；地址优先已通过 POA；公司名称仅更新公司会员。居住国家仍取本轮个人信息，国籍与居住国家分别存储。

非空证件号激活前重新检查旧数量限制，并通过 MemberSensitiveIdentityService 的现有本地敏感字段链路写入，参与同连接嵌套事务，禁止直接明文更新。失败时新提交、敏感值、普通资料和生效切换一起回滚，旧生效档案继续有效。member_other 证件图片只做局部更新，不覆盖密文影子或监管/档案字段。

邮编保留在本轮内容、快照及客户文件 metadata；当前数据字典没有 member.zipcode，未增加字段。超过旧 member_other.front/back 255 字节限制的 URL 保留在目录及快照，不截断写入图片列。

客户提交导致整轮首次自动生效后，事务提交完再调用现有 EmailNotificationEventService 的 KycSuccessNotify 事件。通知协议链接只来自本流程已通过表单的签署 URL，排重并转义；不混入会员其他轮次协议。部分通过、事务回滚和请求回放均不触发。通知异常不回滚资格，不在用户接口内直接发送邮件。

投递保障沿用现有事件/异步队列：提交后进程退出、通知派发或既有异步入队失败仍可能漏通知，没有新增 outbox、自动补发或精确一次投递承诺。失败日志仅含会员 ID、流程 ID 和异常类型；重复业务提交不会补发。此类失败需人工核对并安排补发，本次未新增补发接口。后台最后人工通过的通知由 Eric 管理端链路负责，需分别联调。

客户文件与 POA 额度（无新增用户接口）

正式 POI / POA 提交将已有文件写入 customer_file，来源固定为 kyc_user_content + content_id，POI 为类型 2、POA 为类型 1，保留文件正反面与会员附件原名。审核状态与本次内容一致，暂无文件的第三方待审资料不生成空目录。重投影同一来源只更新原目录，重复提交回执不会重复建目录。历史复用提交仍形成新流程内容和对应来源目录，计数沿用 Eric 的业务记录口径，不自行改成全局 URL 去重。

myinfo.poa_quota 和正式 POA 提交统一按后台 CustomerFile::poaFileTotal 计算：有效目录 + 尚未投影的历史 KYC，按来源排重，不再查询废弃 address_proof。后台上传、历史已通过和最新待审核按既有规则计数；已迁移来源不重复加旧表。对缺失历史目录不做自动迁移。

POA 提交与后台共用 MySQL 命名锁 customer_file_poa_{member_id}，覆盖完整事务；新增目录后的总数超 15 时，表单、目录、流程、日志、回执全部回滚。KYC_FILE_BUSY 表示未取得锁，可使用同一未成功请求重试；KYC_FILE_LIMIT 表示超额；KYC_FILE_INVALID 表示文件值无效。不改变旧版 KYC 接口的统计实现。本项 SQLite 测试无法验证真实 MySQL 锁竞争，发布前需双端并发联调。

流程日志（服务端副作用，无新增用户接口）

正式提交在同一事务写入既有 kyc_process_log：客户提交/只读复用使用 operator_type=1；系统自动审核和第三方通过使用 operator_type=5。姓名保留导致 POI 转人工、协议失效待重签、POA 保留国家重交/更新国家终止、整轮生效记录固定事件原因，不存输入资料、证件或第三方报文。

已完成请求重放不重复写日志；日志失败则整个业务事务回滚。首次正式提交前不为记录日志创建主流程。表结构沿用 Eric 已有版本 SQL，数据字典仅补齐缺失定义，没有新增发布 SQL。后台仍使用 Eric 的查询接口。

10.5 POI 姓名确认弹窗

当 ui_state=poi_name_confirm_required 时，前端展示第三方姓名及姓/名输入。先调用 POST /api/kyc/process/verification/name_preview；只有 name_mismatch=true 才展示两个选择：

1POST /api/kyc/process/verification/name_confirm
2decision=use_confirmed_name
3POST /api/kyc/process/verification/name_confirm
4decision=keep_current_name_manual

最终选择调用 name_confirm 后，用返回的 version 调用 POST /api/kyc/process/saveinfo（mode=verification、同一 verification_id、新 request_id），成功后重新读取 POST /api/kyc/process/myinfo。单独 name_confirm 成功不代表 POI 已正式提交。

前端应把这两个调用串在同一次确认按钮操作中：姓名不一致时默认“更新个人信息姓名”，另一项为“保留当前姓名并转人工审核”；客户选定后无需再点击第二个提交按钮。只有 saveinfo.submitted=true，或查询到同一认证 refresh.submission_confirmed=true，才结束本次提交。转人工的提交成功须显示待审核，不能显示认证通过；下一步位置由重新读取的步骤顺序、阻断和权限决定。

同一次操作分别固定 name_confirm 与 saveinfo 的两个不同 request_id。断网重试保留原参数和原 ID；已经取得姓名确认响应时直接重试正式提交，不重复创建姓名选择。确认的幂等回执可能是过去的版本，遇到版本/目标变化必须重读上下文，不能把新版版本号直接塞进旧请求绕过校验。

页面刷新后先读 POST /api/kyc/process/context、POST /api/kyc/process/myinfo，再对当前步骤的 verification_id 调用 POST /api/kyc/process/refresh：submitted 显示已提交；passed + submit_verification 显示“继续提交”，沿用服务端已保存的姓名决策；passed + poi_name_confirm_required 才重新确认拆分。恢复页面本身不自动发起写操作。

完整请求、返回示例、串联代码及逐项联调检查见同目录《KYC-2.20.1姓名确认前端对接与联调清单-20261104.md》。当前工作区未提供用户 App/Web 前端仓库，此处为对接要求，不能视为前端页面已完成。
