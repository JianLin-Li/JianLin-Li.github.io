KYC 2.20.1 用户端 API 最新接口契约

版本：2.20.1
整理日期：2026-11-05
适用项目：gtcuser
代码基线：feature/v2.20.1/kyc_process-jalen / c0fba8bc331df1015fda414114b79ebb8c606b52。
本版已包含认证链接重试、国家覆盖值生命周期、失效选项校验和姓名确认基准四项修复。接口可用性以对应环境部署该分支后的结果为准。
文档性质：给 Web/App 前端联调使用的接口契约，依据当前路由、参数接收、Service 返回结构及既有测试/复核记录整理。本文描述实际实现，不能作为真实环境验收通过证明。域名由各环境配置提供。

本文只描述用户端接口。管理端接口、第三方供应商回调内部协议和 SQL 发布步骤不属于前端调用范围。旧接口仍保留兼容，但新 KYC 页面必须使用本文的 /api/kyc/process/* 接口。

1. 调用约定

1.1 API 地址和鉴权

所有新流程接口的完整地址格式为：

1POST https://{API_HOST}/api/kyc/process/{action}

例如：

1POST https://{API_HOST}/api/kyc/process/context

API_HOST 替换为当前环境的 API 主机名，不含协议或重复的 /api。本文 14 个流程接口全部使用 POST，全部需要登录鉴权。会员 ID 由服务端从登录态读取，前端不能自报 member_id、监管 ID 或规则 ID。

JSON 请求 Header：

1Authorization: Bearer {ACCESS_TOKEN}
2Content-Type: application/json
3Accept: application/json

沿用项目已有请求层的语言和设备 Header；token Header 为旧兼容方式，新接入建议统一使用 Authorization，不在 URL 中携带 token。

统一成功响应：

1{
2  "code": 200,
3  "message": "success",
4  "data": {}
5}

注意：业务成功值为 code=200。下面各接口的响应示例均为统一包装内的 data，不再重复外层包装。message 可能随语言变化，成功不依赖固定的 "success" 文本。

典型业务拒绝：

1{
2  "code": 10000,
3  "message": "KYC_VERSION_CONFLICT",
4  "data": []
5}

本模块大部分错误共用数值码 10000，第 10 节的错误键通常位于 message；没有独立的 error_key 字段。证件占用校验使用 10004。业务异常可能仍返回 HTTP 200，前端须先检查业务 code，再处理 data；登录错误沿用现有统一拦截器。

1.2 字段类型

以下 ID 对外统一按字符串处理：

  • process_id
  • content_id
  • form_id
  • verification_id
  • edit_context_id
  • target_context_id

process_id=null 表示本轮还没有正式提交。首次正式提交使用 expected_version=0。

kyc_config_id、generation、version、状态及分页字段为整数；权限为布尔值。所有 *_at 时间为秒级 Unix 时间戳，0 表示尚未发生，前端不要渲染成 1970 年。config_revision 是不透明字符串，原样回传。

字段值 values、reuse.preview_values 非空时通常是键值对象，PHP 空数组可能序列化为 []，前端兼容 {} 和 []，不把空数组当作表单列表。本文示例 ID、字段名及国家仅作说明，实际以接口返回定义为准。

1.3 流程和权限边界

字段 值 含义
source_type 1 客户本人流程，可由用户端办理
source_type 2 后台代客流程；进行中只给提示，已完成可看历史，均不能编辑
process_status 1 进行中
process_status 9 已完成
process_status -2 已终止
review_status 10 尚未全部提交或当前没有待审核项
review_status 11 必需表单已提交且至少一项待审核
review_status 20 存在拒绝
review_status 9 本轮全部通过
effect_status 1 当前生效
effect_status 0 未生效或已失效
step.status 0 尚未提交
step.status 1 待审核
step.status -1 拒绝
step.status 9 通过

同一会员允许本人和代客各有一条未完成流程；用户 API 只把 source_type=1 作为本人可办理流程。

member_kyc_status 是整体资格：0 未提交、1 进行中、2 未认证、9 已认证。旧生效档案仍有效时，即使本轮未完成也可保持 9，不要用它定位新流程步骤。

1.4 本次对旧文档的整理

以本文作为最新接口联调入口；同目录旧接口文档和逐步实施记录保留用于追溯。本文逐一给出接口的新旧属性、名称、完整路径、请求参数表、返回字段表、示例和调用顺序，并补齐姓名确认后自动正式提交、国家冲突后刷新目标、Sumsub request check 及旧接口边界。动态表单、上传及协议签署见第 3.3 节。

1.5 新旧接口和参数表的读法

  • 新接口（本次新增）：本次流程方案新增的 /api/kyc/process/* 共 14 个路由；包括 Eric 先前已提交的接口，并非仅指最近一次提交新建的方法。
  • 旧接口（本次继续复用）：上传图片、上传文件和公共国家列表；新 KYC 页面仍可调用。
  • 旧接口（兼容保留）：第 11 节的旧 /api/kyc/* 路由。用来辨认旧调用和迁移，新页面使用对应的新流程接口。
  • 下文除明确标注 multipart/form-data 或 GET Query 外，请求参数均放在 JSON 请求体；参数表列出前端可使用的字段，不接受客户端自报会员、监管或审核结果。
  • “条件必填”以说明列为准；例如首次无流程使用 process_id=null,expected_version=0，已有流程必须使用当前版本。服务端允许部分字段省略，不代表前端可以用过期上下文提交。
  • 返回字段表描述统一包装中的 data。null、空数组、字段省略分别标明，不能混用。动态表单的业务字段以当前 fields 为准，公共嵌套结构详见第 14 节。
  • 无请求参数表示无需传业务参数；POST 可以不传请求体，也可以由请求库发送 {}。鉴权、语言和设备 Header 不算业务请求参数。

3.3 动态表单、上传及协议

3.3.1 表单分类和字段结构

form_type 表单分类 提交方式
1 个人信息 saveinfo(mode=edit/reuse)
2 身份信息 POI 人工、复用或第三方；第三方通过后必须确认姓/名

4 客户协议 编辑时明确同意，服务端生成签署文件；或在允许时复用

fields[] 返回平铺数组，常用定义：

字段 类型 用途

desc string 提示或协议说明

响应中 fields=[] 仅是结构示例，真实可提交表单会有字段。前端用 values[field.field] 反显，并保留字段原类型。当前字段未填写时显示空值；不要将完整 fields 数组作为 values 传入。问卷选项沿用已有组件对 extra 的解析和取值方式，不提交翻译后的展示文案替代原业务值。

确认会绑定当时参与比较的个人姓名。正式提交前若个人信息姓名已变化，myinfo/refresh 会重新返回 poi_name_confirm_required，saveinfo 返回 KYC_NAME_CONFIRM_REQUIRED。保留原第三方通过结果和图片，重新执行 name_preview 与 name_confirm，使用新的确认 request_id 和当前版本，再正式提交。重放旧确认请求只能得到旧回执，不能恢复已失效的决策。仅其他步骤更新版本，或姓名只有既有比较规则忽略的空白/大小写差异，不会要求重确认。旧未提交决策缺少比较基准时同样补一次确认；已正式提交的 POI 不受影响。

6.4 POI 地址自动补齐 POA

当前实现复用 Sumsub 结果：没有独立 POA 内容/认证、规则开启自动审核与“身份含地址自动通过 POA”、同源地址资料完整且国家一致时，POI 姓名确认并正式通过可在同次事务补齐 POA，响应 auto_passed_form_ids。不覆盖已有独立 POA，也不省略 POI 姓名确认。国家不一致仍交给第 6.2 节决策；材料不足不自动补齐。

前端无需新增专用请求，只在 saveinfo 后重读步骤。独立第三方 POA 材料完整且国家一致时仍可按原第三方结果提交。

产品范围文档中“独立 POA 优先”与“关闭开关都进入人工”的表述存在既有冲突，尚无统一确认；本节如实记录当前实现，没有将关闭开关解释为强制所有独立第三方 POA 人工审核。前端据实际返回状态展示，该口径仍需产品验收确认。

1switch_method(method=third_party) -> 使用返回版本/代次调用 kyc_link
2-> 打开 url -> refresh 轮询
3   pending：等待后继续 refresh
4   rejected：按可用动作 request_check / 重认证 / 切换人工
5   passed + poi_name_confirm_required：姓名预检/确认 -> saveinfo
6   passed + poa_country_decision_required：国家决策 -> 重读目标和步骤（本次不提交原认证）
7   passed + submit_verification：saveinfo(mode=verification)
8   submitted：重读 context + myinfo，展示实际待审/通过状态
9   superseded/expired：丢弃旧页面操作，重读 context + myinfo

8.5 姓名确认按钮

前端一次按钮操作应按以下顺序串联：

1name_preview
2-> name_confirm
3-> 使用新 version 调用 saveinfo(mode=verification)
4-> 刷新 context + myinfo

name_confirm 成功不代表 KYC 已提交或已通过。

8.6 国家冲突

1myinfo.blocking_action
2-> poa_country_decision
3-> 使用返回的 target_context_id / next_version
4-> context + myinfo

国家冲突处理前，后续步骤不能提交、编辑或切换审核方式。

9. 幂等、重试和版本

  • request_id 必须由前端为每次业务动作生成并持久保留到拿到结果。
  • 需要幂等 ID 的接口：saveinfo/switch_method/kyc_link/request_check/name_confirm/poa_country_decision。读取、enter_edit/resubmitinfo/name_preview 不接收该字段。
  • 请求超时且结果未知时，优先使用原 request_id 重放。
  • 更换业务参数必须生成新的 request_id。
  • expected_version 来自最近一次成功响应；版本冲突后重新读取 context 和 myinfo，不能把旧版本自动带回。
  • target_context_id 变化后，清理旧页面编辑状态和第三方链接。
  • 第三方认证窗口关闭不代表成功；必须以 refresh 的服务端状态为准。
  • 页面禁止通过本地缓存自行修改 status、process_status、effect_status 或 member_kyc_status。
超时或中断位置 恢复方式
姓名确认未拿到响应 原参数、原 ID 重放 name_confirm；取返回版本继续正式提交
姓名确认成功、正式提交尚未发送 使用已返回版本及预先生成的提交 ID 自动续接 saveinfo
确认后个人姓名发生变化，或旧确认没有比较基准 按 poi_name_confirm_required 重新预检/确认，确认使用新 ID；无需重做第三方认证
正式提交响应丢失 第三方先查 refresh 的 submission_confirmed，也可原参数、原 ID 重放 saveinfo；普通表单原请求重放后重读页面
收到 KYC_VERSION_CONFLICT/KYC_TARGET_CHANGED 停止重试，先重读 context，按第 8.1 节决定读取 myinfo 或只读详情；不能把新版本直接套进旧业务请求
Sumsub 重审 unknown/sending/accepted 继续 refresh，不重新建 applicant 或换 ID 再次送审

重放返回的 content_id/status/version 是原动作回执，未必是此刻流程最新版本；以重读页面为准。member_kyc_status 可能按当前状态重新计算，不应要求两次回执所有字段逐字相同。
