2.1 R1：姓名确认后个人姓名发生变化，旧确认仍可覆盖最新个人信息

需求依据： PRD §6.5 要求先以个人信息姓名与客户确认的证件拆分姓名比较，一致自动通过，不一致由客户选择更新个人姓名或保留个人姓名转人工。§6.6 另行定义“POI 已通过后个人信息驳回重提”，不能用该分支替代 POI 尚未正式提交时的姓名判断。

复现顺序：

  1. 本轮个人信息被驳回，姓名为测试值 Old Name，客户通过 resubmitinfo 进入重提编辑。
  2. 本轮第三方 POI 结果通过，证件拆分也是 Old Name。
  3. 调用 verification/name_confirm，返回 name_mismatch=false，流程版本由 3 变为 4。此时还没有正式提交 POI。
  4. 客户在另一个页面或恢复的个人信息页面，将姓名改为 New Name 并正式提交，版本变为 5。
  5. 重读 myinfo 与 refresh 恢复 POI 页面，服务端仍返回 can_submit=true、required_action=submit_verification；按这个恢复结果使用版本 5 调用 saveinfo(mode=verification)。这不是直接把新版本套入未经重读的旧请求。
  6. 结果：POI 返回通过 9；刚提交的本轮个人信息姓名从 New 被改回 Old，没有要求针对这次差异重新选择。

实际输出：

1{"scenario":"stale_name_decision","confirmed_mismatch":false,"restored_action":"submit_verification","restored_can_submit":true,"before":"New","after":"Old","poi_status":9}

代码原因： nameConfirm 比较并保存 name_mismatch、确认拆分和决策，但没有保存被比较的个人姓名基线；saveInfo 只要看到 name_confirmation=confirmed 就调用 updateProcessPersonalName 覆盖当前个人信息。流程版本能拒绝旧请求，却不能证明旧姓名决策在新版本下仍有效。

影响边界： 已观察到本轮个人信息内容被覆盖；没有观察到旧生效流程被修改。不把它扩大描述为历史档案或会员旧资格已经被破坏。

最小修复方案：

  • 姓名确认时，在现有表单状态 JSON 中保存当时比较的规范化个人姓/名。
  • POI 正式提交事务内，重新读取本轮个人姓名；与确认时基线不同，则在插入内容和更新个人姓名前拒绝，要求重新预览/确认。
  • 保留第三方已通过的认证结果与文件。客户只需重新选择，不重新调用供应商认证。
  • 只比较影响决策的姓名，不因其他步骤或个人地址变化强制重做姓名确认。

验收： 旧版本拒绝；换成最新版本仍不能使用失效的姓名决策；重新确认后的两条选择均可完成；姓名未变、仅其他步骤变化时仍可提交；失败时不写 POI、不覆盖姓名。

2.2 R2：当前配置已不接受的历史选项，仍能只读复用为通过

需求依据： PRD §6.3 正文明确将“当前步骤资料不合法”列为不满足直接复用条件；FR-RU-03 要求按新规则检查当前步骤，FR-RU-05、RU-16—17 要求不满足复用条件时仅当前步骤按新规则重新审核。FR-RU-01、验收 §9.1.1 已明确来源是当前生效档案的相同表单 ID，不要求扩大到任意历史流程。

复现顺序：

  1. 当前生效流程有一张已通过表单，字段 answer=retired-option。
  2. 新流程仍使用同一个 form_id；该字段当前是 select，extra 中只允许 allowed，历史值已不在可选范围。
  3. myinfo 仍返回 reuse.available=true。
  4. 调用 saveinfo(mode=reuse,source_content_id=历史记录)，返回 status=9，新内容仍保存 retired-option。

实际输出：

1{"scenario":"invalid_choice_reuse","reusable":true,"status":9,"saved_values":{"answer":"retired-option"}}

复现配置使用项目模型支持的 score/value/value_ori 结构，未将异常配置或翻译文字冒充合法业务选项。

代码原因： myInfo 只检查缺必填和空姓名；validateSaveValues 检查必填、姓名和协议同意，但没有根据当前单选/多选选项检查值是否合法。复用提交 调用了它，因此非空但已失效的值仍可被标记为通过。字段选项来源见 SystemFormDetail；字典也明确 extra 用于提供单选/多选数据。

最小修复方案：

  • 在现有字段校验范围内，补项目已有 radio/select/checkbox 的当前选项合法性检查，使用真实业务值 value_ori，避免以多语言展示文字比较。
  • myinfo 发现非法来源值时保留历史预览，但禁止直接复用提交，允许进入修改；不要把非法值伪装成“缺少必填字段”。
  • 普通编辑和 mode=reuse 的写入口均重新校验，防止只修页面按钮后仍可直接请求继承通过。
  • 不改旧生效档案，也不增加评分规则或通用校验引擎；仅当前步骤补正并按当前规则审核。

验收： 已删除选项不可复用；有效原始选项可复用；多选只要含一个非法选项就不直接继承；补正后按规则审核；历史详情仍保留原值；非选项字段不受这次修复影响。

2.3 R3：采用 POA 国家重置后，后续被驳回的个人信息无法再次变更国家

需求依据： FR-RU-15 和验收 §9.1.1 第 8 条允许进入修改后编辑并提交个人信息居住国家；§6.7 的“采用 POA 国家”要求本次更新国家并重置 KYC，没有规定以后被驳回重提仍永久锁定该国家。会话中也已明确允许个人信息被驳回重提时改国家，并重置不一致的本轮已通过 POA。

复现顺序：

  1. 本轮个人信息国家是中国；第三方 POA 返回德国。
  2. 调用 verification/poa_country_decision(decision=use_poa)，旧流程终止，新目标的 personal_country_override=Germany。
  3. 新目标首次正式提交个人信息，国家是德国，创建新流程。
  4. 模拟后台驳回这张个人信息并增加流程版本；客户通过 resubmitinfo 获得编辑上下文。
  5. 客户将国家改回中国，携带正确目标、流程、最新版本及编辑上下文提交。
  6. 结果：页面 can_edit=true，提交却返回 KYC_TARGET_CHANGED。覆盖值依旧是德国；刷新重试不会消除它。

实际输出：

1{"scenario":"country_after_reset","error":"KYC_TARGET_CHANGED","override":"Germany","can_edit":true}

代码原因： poaCountryDecision 保存目标国家覆盖值；saveInfo 对这个目标下每次个人信息提交都强制等于覆盖值，没有区分“重置后首次承接国家”与“后续被驳回后的合法编辑”。已有 个人国家变化重置 POA 逻辑因此无法走到。

最小修复方案： 让覆盖值仅用于新目标的默认预填和首次个人信息正式提交；首次承接成功后，在同一事务内消费该临时覆盖，或仅在尚无本轮个人信息时执行覆盖校验。后续国家依据本轮已提交个人信息读取，重提沿用现有国家变化与 POA 重置逻辑。不得提前把新国家写回旧生效会员投影。

验收： 重置后默认国家仍正确；首次提交不回退为旧国家；之后被驳回可以改为合法新国家；不一致的本轮已通过 POA 需要重交；旧回调无法恢复原 POA；旧生效资格不变。

2.4 R4：首次取第三方认证链接失败，相同请求重试丢失业务号

性质： 这是接口恢复和认证关联缺陷，不把它包装成 PRD 新增了一种供应商审核规则。

复现顺序： 选择 Sumsub，第一次 kyc_link 使用服务端业务号调用供应商；模拟供应商调用抛出异常。状态中保留 reserved。相同 request_id、目标、流程、版本和认证代次重试，命中已有预留结果，却没有返回内部 business_id。

实际输出：

1{"scenario":"link_retry","provider_calls":2,"first_has_id":true,"second_has_id":false}

同时出现 Undefined array key "business_id"。此处供应商完全由替身代替，没有发起真实认证或产生费用。真实供应商可能拒绝空业务号；当前隔离验证只证明平台第二次传入的业务号为空，不声称已经观察到供应商错绑客户。

代码原因： kycLink 的已有预留返回分支 漏掉该字段，而 供应商调用 需要读取它。首次创建预留的返回分支包含该字段。

最小修复方案： 已有预留分支从服务端已保存认证绑定补回业务号及后续恢复所需的内部字段，继续校验当前目标/表单/供应商/代次。业务号不对前端暴露；不生成新的业务号来掩盖原请求失败，不修改供应商验签、审核结果和回调协议。

验收： 首次失败后相同请求使用同一非空业务号恢复；已有 URL 时直接返回；失效目标或代次不能复活；错误请求不能借其他表单预留；未恢复成功时不产生正式 KYC 表单。

4. 一处仍需区分的产品材料冲突

改动范围 2.2.2 的前提写：

优先使用第三方POA结果回写；若没有POA信息，再使用该逻辑。

同表关闭“身份含地址自动通过 POA”开关的描述又写：

不区分第三方如何返回，客户都需要独立完成POA步骤，提交后进入人工审核。

当前实现：开关只控制无独立 POA 时用 POI 地址和图片替代 POA；独立可信 POA 的国家、材料等条件满足时仍可按第三方通过。

若前提约束整个表格，当前行为成立；若关闭项要覆盖所有第三方独立 POA，则当前行为不满足关闭项。两种解读会改变真实审核结果，不能靠代码单方面选一个再宣布“没有差异”。这与已经按正文解决的 §6.6 姓名默认选项冲突是两件事。

本报告保留这一项为材料口径问题，不计入上文四个已确认缺陷。本轮不改审核规则。若最终要求“关闭时所有独立 POA 也必须人工”，最小影响位置应是 POA 最终审核状态判断及对应测试，不应重写供应商回调或删除原认证能力。

用户前端仍要落实或验收的内容：
