Gtcuser服务器 docker部署与启动说明

2026-10-22 项目：gtcuser

gtcuser 项目架构与服务器部署手册

适用范围：服务器 8.218.218.58 上的正式、开发、预发三个 Docker Compose 环境。部署配置以 2026-10-22 的服务器只读核查为依据；应用结构以 gtcuser 代码仓库为依据。运行中的镜像、代码版本和服务状态应按第六节命令重新核验。本文不包含密钥或环境变量值。

一、整体关系

gtcuser 是基于 Hyperf 3.1、MineAdmin 3.0 的 PHP 后端，承载客户 API、后台接口、WebSocket、定时任务和异步队列等能力。业务涉及 CRM、交易账户、MT、跟单、PAMM、IB、返佣、KYC、出入金和报表；各业务域的具体接口以仓库 docs/apis/ 和代码为准。

1请求 / WebSocket 连接
2    -> 宿主机端口（前置域名和反向代理链路待核实）
3    -> Docker Compose 创建的 Hyperf 容器
4    -> 容器 /opt/www 中的应用代码（宿主机目录绑定挂载）
5    -> Controller -> Service -> Repository / Model
6    -> MySQL / Redis / 外部系统（连接地址由环境配置决定）
7
8同一个容器启动流程还会加载定时任务调度和 Redis 异步队列消费进程；
9具体任务是否执行，取决于代码、开关和环境配置。

这个部署方式要区分三层：

层次 来源 作用
运行环境镜像 服务器以 /www/wwwroot/Dockerfile.php8235 作为构建文件，Compose 通过 image: 引用标签 提供 PHP、Swoole、Composer 和扩展；服务器 Dockerfile 不复制项目源码
应用代码与依赖 各环境宿主机 gtcuser* 目录，绑定挂载到容器 /opt/www 提供 composer.json、bin/、app/、config/、vendor/ 等运行文件
容器配置 各环境的 Compose 文件和应用运行配置 指定用户、端口、挂载、入口命令、重启策略及环境变量

因此，改动宿主机代码目录与重新制作运行环境镜像是两条不同的变更路径。gtcuser/hyperf 只是镜像名称，不能据此推断镜像包含项目代码或已经发布到镜像仓库。

二、应用代码在哪里

仓库入口与常用目录如下；这是开发时定位功能的地图，不表示服务器上每个环境都处于同一代码提交。

路径 职责
bin/hyperf.php、composer.json CLI 启动入口与 composer start 脚本
config/autoload/server.php、config/routes.php、config/autoload/middlewares.php HTTP/WebSocket 监听、路由和请求中间件
app/Http/Admin、app/Http/Api 后台与客户侧接口入口
app/Service 按业务域编排业务规则、事务与外部调用
app/Repository、app/Model 数据访问，以及表结构、关系和属性转换
app/Task、app/Jobs、app/Command 定时任务、异步任务和 CLI 命令
config/autoload、.env.example 数据库、Redis、队列、日志和其他配置的代码入口及变量名示例
runtime/ 进程文件和应用日志；是挂载代码目录下的运行时数据

常见调用路径是 Controller -> Service -> Repository/Model。HTTP 服务经 config/autoload/middlewares.php 进入路由和控制器；队列、定时任务则从对应进程和任务入口进入业务 Service。项目规范与业务细节见仓库 AGENTS.md、docs/项目开发规范.md 和 docs/apis/。

代码仓库根目录也有一个 Dockerfile，使用 PHP 8.1 基础镜像并包含 COPY . /opt/www；仓库自带 Compose 还写着 hyperf/hyperf:8.2-alpine-v3.18-swoole。它们与本次核实的服务器 /www/wwwroot/Dockerfile.php8235 和服务器 Compose 不同。理解当前服务器部署时，应以后者和实际容器为准，不能把仓库文件当作生产配置。

三、运行环境镜像

服务器 Dockerfile 基于 php:8.2.35-cli-alpine3.24，安装 Swoole 6.0.0、Redis、rdkafka 等扩展，并从 composer:2 复制 Composer。其唯一 COPY 不涉及 gtcuser 源码，也没有安装项目 vendor。仓库要求新增代码保持 PHP 8.1 兼容；这里的 PHP 8.2.35 是本次服务器运行镜像版本。

服务器 root Shell 历史中出现过以下构建命令，可用于理解镜像标签如何产生；历史没有可信的执行时间和操作者，不能把它当作某次发布的完整审计记录：

1cd /www/wwwroot
2docker build --pull --no-cache --progress=plain -f Dockerfile.php8235 -t gtcuser/hyperf:php-8.2.35-swoole-6.0.0 .

-f 指定 Dockerfile，-t 指定镜像标签，末尾 . 是构建上下文；--pull 更新基础镜像，--no-cache 不复用构建缓存。同一标签可被新镜像覆盖，镜像 ID 才能区分具体版本。

服务器 Dockerfile 的 2026-10-22 快照全文见文末附录（151 行、4543 字节，SHA-256：4bdcd1d3fe9a68916de870712bde6fba439c3d41f8c1a2a49bda4dc06c25ab24）。今后构建前应直接读取服务器现文件，不把此快照视为永久不变的源文件。

Dockerfile 不设置项目自己的 WORKDIR、ENTRYPOINT 或 CMD；这些由 Compose 提供。镜像设 TZ=UTC 和 date.timezone=UTC，而 Compose 另设 TIMEZONE=Asia/Shanghai 应用变量。两者用途不同，不应将应用变量直接等同于 PHP 的默认时区。

四、服务器部署拓扑与 Compose

三个环境各有独立的宿主机代码目录和 Compose 文件，共用同一个镜像标签。正式环境的有效 Compose 配置如下；省略了注释和未启用的 Redis、watch 示例：

 1version: '3'
 2services:
 3  hyperf:
 4    hostname: node1
 5    image: gtcuser/hyperf:php-8.2.35-swoole-6.0.0
 6    user: "1000:1000"
 7    restart: always
 8    environment:
 9      - "TIMEZONE=Asia/Shanghai"
10      - "APP_PROJECT=hyperf"
11      - "APP_SYSTEM_ENV=docker"
12    working_dir: "/opt/www"
13    ports:
14      - 9505:9505
15      - 9506:9506
16      - 9507:9507
17    volumes:
18      - ./:/opt/www
19    entrypoint: ["composer", "start"]
20    logging:
21      driver: "json-file"
22      options:
23        max-size: "500m"
24        max-file: "5"

开发、预发的 hyperf 服务也使用相同的镜像标签、用户、工作目录、挂载目标、入口和日志轮转设置。环境差异如下：

环境 Compose 文件 容器名 hostname 宿主机代码目录挂载到 /opt/www 宿主机:容器端口
正式 /www/wwwroot/gtcuser/docker-compose.yml gtcuser-hyperf-1 node1 /www/wwwroot/gtcuser 9505:9505、9506:9506、9507:9507
开发 /www/wwwroot/gtcuser-dev/docker-compose-dev.yml gtcuser-dev-hyperf-1 node2 /www/wwwroot/gtcuser-dev 9502:9505、9503:9506、9504:9507
预发 /www/wwwroot/gtcuser-staging/docker-compose-staging.yml gtcuser-staging-hyperf-1 node2 /www/wwwroot/gtcuser-staging 9508:9505、9509:9506、9510:9507

开发和预发文件还在服务上显式声明 networks: [gtcuser_default]；该网络的实际连接对象未核实。hostname 是容器内主机名，不代表有三台服务器。volumes: - ./:/opt/www 中的 . 相对各 Compose 文件所在项目目录解析；三个运行容器的挂载源已通过 docker inspect 核对为上表绝对路径。

正式环境的 config/autoload/server.php 明确配置 HTTP 0.0.0.0:9505 和 WebSocket 0.0.0.0:9507。Compose 虽然还映射了容器端口 9506，但这份服务配置没有对应的监听服务；不能因为端口映射存在就认定 9506 上有应用。域名、Nginx 和负载均衡如何转发到这些端口尚未核实。

Compose 的 image: 只引用标签，不执行 Dockerfile。重新构建并覆盖同一标签不会改变已创建容器底层的镜像 ID；容器需要重新创建，才可能采用新 ID。restart: always 只负责进程退出后的重启，不负责镜像升级。

五、容器启动、配置与依赖

Compose 创建 hyperf 容器后，以 UID:GID 1000:1000 在 /opt/www 工作目录执行 entrypoint: ["composer", "start"]。完整启动链路为：

1宿主机 gtcuser / gtcuser-dev / gtcuser-staging 代码目录
2    -> Compose 绑定挂载 ./ 到容器 /opt/www
3    -> 以 UID:GID 1000:1000、工作目录 /opt/www 启动
4    -> entrypoint: composer start
5    -> composer.json 的 scripts.start
6    -> rm -rf runtime/container
7    -> php bin/hyperf.php start
8    -> Hyperf 载入配置，启动 HTTP/WebSocket、定时任务和队列等已配置进程
9    -> Docker 将容器端口映射到各环境的宿主机端口

正式环境 /www/wwwroot/gtcuser/composer.json 的 start 脚本为：

1"start": [
2  "Composer\\Config::disableProcessTimeout",
3  "rm -rf runtime/container",
4  "php bin/hyperf.php start"
5]

composer start 不执行 composer install。由于 /opt/www 是绑定挂载，项目的 vendor/ 必须在宿主机代码目录中可用；源码和依赖如何发布到各目录，本次未找到可确认的 Git、CI 或同步命令。宿主机文件的更改会反映到挂载目录，但常驻的 Swoole 进程不会因此自动完成一次受控发布，仍需按实际变更评估重载或重建。

应用配置分工如下：

配置入口 影响
Compose environment 提供 TIMEZONE、APP_PROJECT、APP_SYSTEM_ENV；不包含本项目全部运行配置
config/autoload/server.php HTTP/WebSocket 监听和 Swoole 进程设置
config/autoload/databases.php、redis.php 数据库和 Redis 连接，使用 DB_*、REDIS_* 等环境变量
config/autoload/processes.php、crontab.php、async_queue.php 定时任务调度进程、Redis 队列消费进程及队列配置；还受应用开关影响
config/autoload/logger.php、runtime/logs/ 应用文件日志；容器标准输出另由 Docker json-file 日志驱动保留
.env.example 变量名和开发示例，不是服务器实际密钥来源的证明

bin/hyperf.php 明确设置默认时区为 UTC。MySQL、Redis 以及部分交易、报表和第三方系统是代码中的依赖，但生产连接地址、凭据和网络路径不在本文列出，也未核查生产配置来源。开发时可从仓库 .env.example 查看所需变量名，不能将其值视为服务器值。

六、部署和排障时如何核查

先确认目标环境的宿主机代码目录、Compose 文件和当前镜像 ID。以下命令是只读核查，可在服务器终端执行：

1docker image inspect gtcuser/hyperf:php-8.2.35-swoole-6.0.0 --format '{{.Id}} {{.Created}}'
2docker inspect -f '{{.Name}} {{.State.Status}} {{.Image}} {{range .Mounts}}{{.Source}}:{{.Destination}}{{end}}' \
3  gtcuser-hyperf-1 gtcuser-dev-hyperf-1 gtcuser-staging-hyperf-1
4docker compose -f /www/wwwroot/gtcuser/docker-compose.yml ps
5docker compose -f /www/wwwroot/gtcuser/docker-compose.yml logs --tail=100 hyperf

排查时还应查看目标环境的 runtime/logs/；目录随代码挂载位于宿主机，不能只看 docker logs。上面的 docker compose ... ps/logs 以正式环境为例，开发和预发需换成表中的各自 Compose 文件。docker inspect .Image 是容器真正使用的不可变镜像 ID，docker ps 显示的标签不能代替它。

更新过程按变更对象区分：

  1. 代码或依赖变更：先确认目标环境的代码提交、vendor/、运行配置和数据库变更均已就绪，再按既定发布流程重载或重建容器。当前代码交付方式与实际执行过的发布命令尚未核实。
  2. PHP、Swoole 或扩展变更：由服务器 Dockerfile 构建新环境镜像，记录新旧完整镜像 ID。复用同名标签只改变标签指向，不会升级已运行容器。
  3. 容器更新：使用目标环境的 Compose 文件重新创建 hyperf 服务，核对新容器 .Image 是否等于预期镜像 ID，并检查服务状态、日志、HTTP 与 WebSocket。docker compose -f <目标文件> up -d --no-deps --force-recreate hyperf 是 Compose 的标准操作形式，不是本次已核实的历史部署命令。
  4. 回滚：预先保留旧镜像 ID、旧代码版本和配置。运行环境回滚需要使 Compose 再次引用旧镜像并重建容器；代码回滚需要恢复相应宿主机目录。只重启现有容器不会切换镜像。
