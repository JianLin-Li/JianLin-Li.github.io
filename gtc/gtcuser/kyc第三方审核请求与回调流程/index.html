KYC 第三方审核请求与回调流程

本文承接 kycdsf.md 中的旧 /api/kyc/* 主链路，继续说明 Sumsub、IDWise、Zoloz 的请求构造、认证链接生成、审核结果回传和本地落库过程。

结论以当前仓库代码为准；本次只新增分析文档，未修改业务代码，也未调用真实第三方接口。文中的密钥、Token、证件资料均使用占位符或字段名表示。

一、先给结论

  1. 三个渠道都从 POST /api/kyc/kyc_link 进入，由 KycService::kycFormDataSave() 按 form_type + audit_method 分流。
  2. Sumsub 当前主链路不是先创建 applicant，再创建链接，而是直接请求 WebSDK Link 接口，以 externalUserId + levelName 让 Sumsub 建立或定位认证上下文。
  3. IDWise 创建的是 Journey 验证链接。第三方返回原始 URL 和 journey_id 后，本地会把 URL 转成本站短链，并把 journey_id 作为 transactionId 返回给前端。
  4. Zoloz 先写本地 t_identify，再调用 initialize。它返回 transactionId + clientCfg，本地分别生成 H5 长链和本站 zoloz_redict 跳转链。
  5. Sumsub 和 IDWise 的 Webhook 更像是“审核已完成通知”：收到通知后，本地还会再次调用第三方查询接口，获取申请人/Journey 的完整结果，不会只凭 Webhook 中的 GREEN 或 Complete 直接落库。
  6. Zoloz 没有走服务器结果 Webhook。completeCallbackUrl、interruptCallbackUrl 是前端完成/中断跳转地址；真正审核结果由 ZolozTask 定时调用 checkresult 拉取。
  7. 三个渠道最后都落到 t_kyc_user_content，身份对应 form_type=2，地址对应 form_type=5；单张表单通过后，再统一计算整个会员的 KYC 总状态。
  8. Sumsub、IDWise 重提时可能使用 memberId_N 作为第三方业务 ID；回调时再去掉 _N 找回本地会员。Zoloz 使用独立的雪花 bizId + transactionId，不是这套 memberId_N 规则。

二、统一入口与渠道分流

2.1 接口入口

KYCController::kycLink() 接收：

1{
2  "form_type": 2,
3  "audit_method": "sumsub"
4}
  • form_type=2：身份认证。
  • form_type=5：地址证明。
  • audit_method：sumsub、idwise 或 zoloz。
  • 接口有 TokenMiddleware，会员 ID 来自当前登录上下文，不由请求体指定。

代码位置：

  • app/Http/Api/Controller/V1/KYCController.php:184：路由和参数接收。
  • app/Service/crm/KycService.php:2826：统一业务分流。

2.2 发起前的共同检查

kycFormDataSave() 依次执行：

  1. 查询会员，会员不存在则报错。
  2. 企业会员直接返回空数组，不走这里的第三方自动审核。
  3. 根据 member.kyc_id 查询 t_kyc_setting。
  4. 从 audit_method_json 取出全部 kyc_channel，检查本次 audit_method 是否被允许。
  5. 读取本次渠道的第三方业务 ID。
  6. 只有 auto=1 且 form_type 为 2 或 5 时才进入相应分支。
flowchart TD A["POST /api/kyc/kyc_link"] --> B["TokenMiddleware 获取 memberId"] B --> C["kycFormDataSave(memberId, formType, auditMethod)"] C --> D{"会员存在且为个人会员？"} D -- "否" --> E["报错或返回空数组"] D -- "是" --> F["读取 t_kyc_setting"] F --> G{"audit_method 在 audit_method_json 中？"} G -- "否" --> H["auth_method_not_exist"] G -- "是" --> I{"auto=1 且 formType=2/5？"} I -- "否" --> J["返回空数组"] I -- "是" --> K{"audit_method"} K -- "sumsub" --> L["生成 Sumsub WebSDK Link"] K -- "idwise" --> M["创建 IDWise Journey Link"] K -- "zoloz 且 formType=2" --> N["初始化 Zoloz 实名交易"] K -- "zoloz 且 formType=5" --> J

2.3 level_name 的取值并不完全相同

场景 实际取值
Sumsub 身份认证 当前渠道在 t_kyc_setting.audit_method_json 中的 level_name；缺失时回退到旧的 t_kyc_setting.level_name
Sumsub 独立地址认证 全局 kyc.kyc_service_config.Sumsub.location，不是当前渠道 JSON 中的 level_name
IDWise 身份、地址认证 当前渠道 JSON 中的 level_name，作为 IDWise flow_id；缺失时回退旧字段
Zoloz 不使用 level_name，由 kyc.kyc_identy 决定 Real ID 或证件识别

对应代码：app/Service/crm/KycService.php:1046、app/Service/crm/KycService.php:1073、app/Service/crm/KycService.php:2867、app/Service/crm/KycService.php:2894。

2.4 返回给前端的结构

身份分支统一返回：

1{
2  "kycUrl": "认证或跳转地址",
3  "h5": "H5 地址",
4  "transactionId": "第三方交易号；Sumsub 为空",
5  "type": "1=Zoloz，2=Sumsub，3=IDWise"
6}

地址分支只返回 kycUrl、h5、transactionId，没有 type。

三、Sumsub：请求如何构造

3.1 请求时序

sequenceDiagram autonumber participant FE as 前端 participant C as KYCController participant S as KycService participant A as KycApiService participant SC as SumsubClient participant SS as Sumsub FE->>C: POST /api/kyc/kyc_link<br/>form_type + audit_method=sumsub C->>S: kycFormDataSave(memberId, formType, auditMethod) S->>S: 校验规则并取得 businessId、levelName S->>A: getWebSdkLink(businessId, levelName, "", lang) A->>SC: getWebSdkLink(...) SC->>SC: 规范化语言、拼接 path/query、生成 HMAC 签名 SC->>SS: POST /resources/sdkIntegrations/levels/{levelName}/websdkLink SS-->>SC: {"url": "https://..."} SC-->>S: 第三方 WebSDK URL S-->>FE: kycUrl/h5=URL，transactionId="" FE->>SS: 打开 WebSDK URL，提交身份或地址材料

3.2 第三方 HTTP 请求

代码位置：

  • app/Common/Lib/Kyc/KycApiService.php:92：Sumsub 客户端入口。
  • app/Common/Lib/Kyc/lib/SumsubClient.php:81：WebSDK URL 构造。
  • app/Common/Lib/Kyc/lib/SumsubClient.php:284：签名头和请求发送。
  • app/Common/Lib/Kyc/lib/SumsubClient.php:309：HMAC 签名原文。

请求形态：

1POST {base_url}/resources/sdkIntegrations/levels/{levelName}/websdkLink?ttlInSecs=1800&externalUserId={businessId}&lang={lang}
2Content-Type: application/json
3X-App-Token: {app_token}
4X-App-Access-Ts: {timestamp}
5X-App-Access-Sig: {hmac_signature}

请求体为空。主要参数含义：

参数 来源与作用
levelName 身份来自规则渠道配置；独立地址来自全局 location；进入客户端后做 rawurlencode
ttlInSecs=1800 WebSDK 链接有效期，代码固定为 1800 秒
externalUserId 本地 businessId，首次通常是 memberId，重提后可能是 memberId_N
lang 当前系统语言，经 normalizeSdkLang() 转成 Sumsub 支持的语言码
externalActionId 当前 kyc_link 主链路传空，不出现在最终 query 中

签名算法：

1signature = HMAC_SHA256(
2    timestamp + UPPERCASE(HTTP_METHOD) + requestUri + requestBody,
3    secret_key
4)

其中：

  • requestUri 包含路径和 query。
  • 当前生成链接的 requestBody 为空字符串。
  • 签名使用 secret_key，app_token 放在 X-App-Token。
  • Guzzle 使用配置中的 base_url 发送请求；只接受 HTTP 200/201 为成功。

配置来源有一个容易忽略的点：

  • app_token、secret_key 由 KycApiService::getKycFactory() 从 crm.kyc_service_config.Sumsub 读取并注入客户端，见 app/Common/Lib/Kyc/KycApiService.php:49。
  • base_url、webhook_secret_key 由 SumsubClient 自己从 kyc.kyc_service_config.Sumsub 读取，见 app/Common/Lib/Kyc/lib/SumsubClient.php:33。
  • 因此 outbound 请求签名和 inbound Webhook 验签不是完全来自同一个配置数组。

3.3 当前主链路没有显式调用 createApplicant

SumsubClient 虽然提供 createApplicant()，但当前 kyc_link 链路没有调用它；Controller 和 Service 中旧的申请人创建代码也已注释。因此理解当前流程时，应以“直接生成 WebSDK Link”为准，不要把旧流程拼接进来。

3.4 回调地址不在该请求中

生成 WebSDK Link 的请求没有传服务器 Webhook URL。Sumsub 必须能把审核事件发送到：

1POST /api/kyc/kyc_webhook

该地址需要由 Sumsub 侧的 Webhook 配置保证，而不是由 kyc_link 请求动态指定。

四、Sumsub：回调和落库逻辑

4.1 Webhook 入口与验签

入口：KYCController::kycCallback()，见 app/Http/Api/Controller/V1/KYCController.php:323。

该接口没有会员 TokenMiddleware，依靠 Sumsub Webhook 摘要验证来源：

  1. 读取原始请求体，并在可 seek 时 rewind，保证后续还能再次读取。
  2. 从 x-payload-digest-alg 读取算法。
  3. 支持 HMAC_SHA1_HEX、HMAC_SHA256_HEX、HMAC_SHA512_HEX。
  4. 用 webhook_secret_key 对原始请求体计算 HMAC。
  5. 与 x-payload-digest 比较，不一致则抛出 Invalid signature。
  6. 验签通过后才 json_decode。

代码：app/Common/Lib/Kyc/lib/SumsubClient.php:236。

4.2 事件过滤

Controller 只处理：

1type = applicantReviewed 或 applicantActionReviewed
2且 reviewStatus = completed

其他事件验签后不再进入业务处理。满足条件后调用：

1SumsubService::handleSumsubReviewedWebhook()

4.3 完整回调时序

sequenceDiagram autonumber participant SS as Sumsub participant C as KYCController participant SC as SumsubClient participant S as SumsubService participant K as KycService participant DB as 本地数据库 SS->>C: POST /api/kyc/kyc_webhook C->>SC: callback(rawBody + digest headers) SC->>SC: 按声明算法计算 HMAC 并验签 SC-->>C: 解码后的 Webhook 数据 C->>C: 过滤事件类型和 completed C->>S: handleSumsubReviewedWebhook(data) S->>S: externalUserId 还原 memberId S->>S: 仅接受 reviewAnswer=GREEN/RED<br/>按 memberId 加锁 S->>DB: 查询会员；总 KYC 已为 9 则跳过 S->>SS: getApplicantsInfo(businessId) SS-->>S: 申请人详情和 applicantId S->>SS: getApplicantRequiredIdDocsStatus(applicantId) SS-->>S: IDENTITY / PROOF_OF_RESIDENCE 各步骤结果 alt 整体 RED S->>K: 分别拒绝命中的身份/地址表单 else 整体 GREEN S->>K: 同步步骤为 GREEN 的身份/地址表单 end K->>SS: 下载本次步骤的证件或地址材料 K->>DB: 更新 kyc_user_content、会员资料、材料文件 K->>K: checkUserKycStatus() K->>DB: 刷新会员 KYC 总状态及全通过副作用 C-->>SS: success

4.4 GREEN 和 RED 的实际判断

整体 GREEN

本地不会只处理一个 idDocs[0] 就结束，而是：

  1. 调 getApplicantsInfo(businessId) 获取申请人完整资料。
  2. 调 getApplicantRequiredIdDocsStatus(applicantId) 获取每个步骤的结果。
  3. 找出 IDENTITY 系列步骤中 reviewResult.reviewAnswer=GREEN 的项。
  4. 按步骤的 idDocType + country 从申请人历史资料中匹配本次证件。
  5. 找出 PROOF_OF_RESIDENCE 系列中结果为 GREEN 的项，匹配地址或地址证件。
  6. 分别同步身份和地址，因此一个组合 Journey 可以同时完成两张本地表单。
  7. 至少同步成功一项后调用 checkUserKycStatus()。

整体 RED

  • 从 Webhook 的整体 reviewResult、步骤 reviewResult、图片级 imageReviewResults 中提取拒绝原因。
  • 优先把 rejectLabels 映射为本地用户提示，其次使用 moderationComment/clientComment，最后使用通用拒绝提示。
  • IDENTITY 存在则拒绝身份；PROOF_OF_RESIDENCE 存在则拒绝地址。
  • 驳回时也会合并第三方已解析的 kyc_content，并尝试保存相应材料。
  • 最后调用 checkUserKycStatus()。

4.5 回调后还会发起哪些 Sumsub 请求

请求 用途
GET /resources/applicants/-;externalUserId={businessId}/one 获取申请人资料、applicantId
GET /resources/applicants/{applicantId}/requiredIdDocsStatus 获取身份/地址各步骤审核结果和本次图片 ID
GET /resources/applicants/{applicantId}/metadata/resources 获取材料资源元数据
GET /resources/inspections/{applicantId}/resources/{imageId} 下载具体材料内容

这些请求也统一经过 sendRequest()，使用与生成链接相同的 Sumsub HMAC 请求签名。

4.6 “我已完成”主动刷新是另一条补偿链路

POST /api/kyc/refresh_kyc_info 会主动查询 Sumsub，不经过 Webhook 验签：

  • 入口：app/Http/Api/Controller/V1/KYCController.php:307。
  • 主逻辑：app/Service/crm/KycService.php:3112。
  • 查询 applicant 和 status 后，GREEN 走 kycAuditReviewedAllNew()，RED 走 kycAuditReviewedRejected()。
  • 它和 Webhook 成功/拒绝处理共用 sumsubKycSync_{memberId} 锁，降低并发重复落库概率。

注意：主动刷新能否执行还受个人会员、auto=1、旧单渠道字段 kyc_channel=sumsub、存在未通过表单等条件限制，见 app/Service/crm/KycService.php:3255。

  • app/Common/Lib/Kyc/lib/IdwiseClient.php:92：Basic 认证和 HTTP 发送。

5.3 本地短链不是新的第三方认证

第三方返回的 url 会写入 short_url.long_url，前端拿到的是：

1{PC_SITE_URL}api/open/short_url_redirect?short_code={short_code}

访问该短链后，ShortUrlController 再 302 到 IDWise 原始 URL。代码：

  • app/Service/crm/ShortURLService.php:16
  • app/Http/Api/Controller/Open/ShortUrlController.php:28

journey_id 会同时：

  • 作为 transactionId 返回前端；
  • 写入短链记录的 remark；
  • 通过 markLatestKycLinkContent() 写到最新身份/地址表单的 journey_id，供后续人工审核回调核对。

六、IDWise：Webhook 和落库逻辑

6.1 入口和来源校验

入口：POST /api/kyc/idwise_kyc_webhook，见 app/Http/Api/Controller/V1/KYCController.php:402。

处理过程：

  1. Controller 读取并 rewind 原始 body。
  2. KycService::idwiseCallback() 创建 IdwiseClient 并调用其 callback()。
  3. IdwiseClient::callback() 比较请求 Authorization 与代码中配置的固定 Bearer 凭证。
  4. 不一致抛出 Invalid signature；一致则解析 JSON。

代码：app/Common/Lib/Kyc/lib/IdwiseClient.php:136。

这里不是对原始 body 做 HMAC，也不是使用创建 Journey 时的 Basic 凭证，而是单独的 Webhook Bearer 校验。本文不展示具体凭证值。

6.2 Finished Journey

Webhook 中主要使用：

1body.referenceNo  -> 还原本地 memberId
2body.journeyId    -> 再查完整 Journey
3body.systemDecision
4event

分支：

event / systemDecision 实际处理
Finished Journey / Incomplete 不处理
Finished Journey / Complete 查询完整 Journey，再按 documents 判断
Finished Journey / Refer 同样查询完整 Journey，不直接整体拒绝
Finished Journey / Rejected 同样查询完整 Journey
Updated Journey 进入 IDWise 后台人工审核结果处理

完整 Journey 查询：

1GET {base_url}/journey/v2/get/{journeyId}
2Authorization: Basic ...

代码：app/Common/Lib/Kyc/lib/IdwiseClient.php:68。

6.4 单个 document 的通过条件

代码要求两个条件同时成立：

1validation_result.validation_outcome = Passed
2且 has_passed_rules = true

身份步骤 step_title=ID Document 还有人脸检查：

  • 如果返回了 selfie.status，且该状态不是 Complete，即使证件 document 通过，也会按人脸核验失败拒绝身份。
  • 地址步骤使用 step_title=Proof of Address。

驳回原因来源：

  1. 文件校验失败：读取 validation_result.validation_checks 中未通过项。
  2. 规则失败：根据 documents.step_id 去顶层 rule_results 找引用该步骤的失败规则。
  3. 保存 message 到 kyc_replay，保存校验/规则名到 reject_check_type。

6.5 旅程级 Refer 的兜底

当完整结果没有 documents，且 system_decision=Refer 时：

  • 根据当前规则需要哪些身份/地址表单，以及本地各表单最新状态，判断应拒绝身份还是地址。
  • 能定位到表单则写入通用驳回原因。
  • 无法定位则只记录日志。

7.5 RSA 请求签名

公共发送方法：app/Common/Lib/Identify/ZolozTool.php:523。

请求头：

1Content-Type: application/json; charset=UTF-8
2Accept: application/json
3Client-Id: {client_id}
4Request-Time: {ISO8601 time}
5Signature: algorithm=RSA256, keyVersion=v1, signature={signature}

签名原文：

1POST {path}
2{client_id}.{Request-Time}.{jsonData}

即第一行是 HTTP 方法和路径，第二行是 client_id、请求时间、完整 JSON body 用点号连接。处理步骤：

  1. 使用配置的商户私钥做 SHA256withRSA 签名。
  2. 对二进制签名做 Base64。
  3. 再做 URL encode 后放入 Signature 头。

这里读取的是私钥文件路径配置，文档不展示证书内容。

十、幂等、异常和回调响应的实际行为

渠道 防重复/并发措施 处理异常后的 HTTP 行为
Sumsub sumsubKycSync_{memberId} 锁；会员总状态 9 跳过；表单 9 或人工待审核跳过 验签失败会抛错；验签后的业务处理异常被 Controller 捕获并记录，最后仍返回 success
IDWise 表单 9 或人工待审核跳过；人工审核还核对驳回状态和 journey_id Bearer 校验和业务处理都在 Controller 的 try/catch 内，异常被记录后仍返回 success
Zoloz 定时任务 singleton；终态写 has_cached=1；表单 9 或人工待审核跳过 没有第三方 Webhook 应答；任务外层捕获异常并记录

需要特别注意：

  1. Sumsub 的会员级锁不代表 IDWise 也有相同锁。 当前 IDWise 回调没有看到相同的会员锁或按 eventId 去重。
  2. Sumsub/IDWise 业务失败仍 success，意味着第三方不一定能根据 HTTP 失败响应识别“本地处理失败并重试”。排查时不能只看 Webhook HTTP 200，还要看渠道日志和本地表单状态。
  3. ZolozTask 的 try/catch 包住整个批次；某条记录抛出异常时，会中断本次后续记录处理，未成功的记录等待后续任务再试。
  4. markLatestKycLinkContent() 的方法注释提到写实际审核方式，但当前 kyc_audit_method 赋值被注释，实际只会在 journeyId 非空时保存 journey_id，见 app/Service/crm/KycService.php:4351。实际审核渠道主要在结果落库时写入。
  5. Zoloz 成功和拒绝分支写入的是 kyc_audit_method='zolzo'，不是配置和请求分支使用的 zoloz，见 app/Service/crm/KycService.php:1283、:1340、:1348。按审核渠道排查历史数据时需要考虑这个现存拼写。
  6. 当前代码会记录部分 Webhook 原始 body、认证详情或凭证头。本文仅描述行为，不复制其中的敏感信息。
