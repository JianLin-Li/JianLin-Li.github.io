KYC 2.20.1 用户端 UI、第三方认证与 kyc_link_json 全流程说明

日期：2026-11-11
用户端代码：/Users/jalen/www/local/gtcuser
核对分支：feature/v2.20.1/kyc_process-jalen，提交 bccca6e73
说明：本文是对用户端流程的解释文档，不修改业务代码、不执行数据库写入。

1. 本文怎样对应 UI 原型

本次核对的原型入口是：

  • Web：https://www.figma.com/design/J4AHANi5NviHO1a4wyPQoV/web-gtcgo--Copy---Copy-?node-id=6276-10292&p=f
  • App：https://www.figma.com/design/1skETB8Ish6I9KOFmfnuL8/GTC-GO-app--Copy-?node-id=5205-53284

侧边浏览器可以看到 Web 文件中的 2.20.0 画板及其 KYC 页面组。匿名 Figma 账号只能读取画板概览，点击 Present 会要求登录，所以本文以画板中已经确认的页面类型、交互说明，以及当前分支返回的页面状态字段为依据；按钮的最终文案和像素布局仍由前端按 Figma 实现。

UI 的主线可以理解为：

 1KYC 总览
 2  ├─ 当前办理目标 / 当前步骤
 3  ├─ 生效档案（只读）
 4  └─ 历史记录（生效、失效、本人终止）
 5       ↓
 6个人信息 → 身份信息 POI → 地址证明 POA → 问卷 → 客户协议
 7       ↓              ↓               ↓
 8     人工/自动       人工/第三方       人工/第三方
 9                       ↓               ↓
10                 姓名确认弹窗       国家不一致弹窗
11                       └──────→ 正式提交 → 全部必填通过 → 生效

这里的“步骤”是用户在 UI 看到的表单卡片；form_id 是服务端保存和校验的真实表单 ID。典型配置如下，具体标题由 t_system_form.title 返回：

UI 卡片 常见 form_id form_type 用户看到的内容

Identity Information / 身份信息 17 2 国籍/证件国家、证件类型、证件图片、证件姓名、证件号、生日
Proof of Address / 地址证明 18 5 居住国家、地址、邮编、地址证明文件
Questionnaire / 问卷 19 3 风险或客户问卷字段
Client Agreement / 客户协议 20 4 协议展示和签署确认

不要让前端用标题或 form_type 猜 form_id；前端应使用 myinfo.steps[] 返回的 form_id、title、fields、sort。

2.1 target：UI 当前办理哪一个目标

target 对应 UI 顶部显示的当前 KYC 目标/监管方案。它由服务端准备，会员不能自行传一个监管类型来替换它。

  • target_context_id：当前页面上下文 ID；旧页面提交时不一致会被拒绝。
  • kyc_config_id：当前规则配置，决定需要哪些表单和审核渠道。
  • generation：目标代次；使用 POA 国家重置时会递增。
  • process_id：已经创建的本人 source_type=1 进行中流程；首次填表前可为 null。
  • config_revision：规则版本；前端只回传服务端给出的版本。
  • personal_country_override：用户选择采用第三方 POA 国家后，给新目标的临时个人居住国家。它不是立即更新会员资料。

因此，UI 看到“重新开始 KYC”时，服务端实际做的是创建新的 target_context_id，而不是让前端自行把旧 process_id 清空后继续提交。

2.2 forms：每个 UI 表单当前采用什么审核方式

键是 <target_context_id>:<form_id>。值保存当前表单的审核方式和代次：

  • method=manual：用户填写并提交人工审核。
  • method=third_party：用户需要走第三方链接。
  • provider：sumsub、idwise 或 zoloz。
  • selection_generation：每次切换审核方式/渠道递增，旧认证结果不能覆盖新选择。
  • name_confirmation、country_decision、requires_resubmission 等：UI 弹窗完成后的服务端决策。

UI 的“人工审核/第三方审核”单选框只改变这里；switch_method 本身不创建 t_kyc_process，也不写正式 t_kyc_user_content。

2.3 verifications：一次第三方认证的本地绑定

verifications 的对象键就是前端拿到的 verification_id。它把五件事固定在一起：

1当前会员 + 当前 target + 当前 form_id + 当前审核代次 + 当前供应商认证

其中：

  • verification_id：本地 UUID，供 refresh/name_preview/name_confirm/saveinfo 使用。
  • business_id：本次供应商业务号，例如 730103797_8...；Sumsub 回调的 externalUserId 就是它。
  • journey_id：Sumsub applicantId、IDWise journeyId 或 Zoloz transactionId 等供应商侧标识。
  • state：reserved → pending → passed/rejected → submitted，也可能变成 superseded/expired。
  • provider_values：服务端从供应商结果解析出的候选表单值；前端不能自行伪造这些值。
  • provider_result_at：服务端采纳供应商结果的时间，不是供应商原始审核时间。
  • content_id：正式 saveinfo(mode=verification) 后写入的 t_kyc_user_content.kyc_id。

“本地绑定”就是这条映射：

1verification_id
2  ↕ t_kyc_member_other.kyc_link_json.state.verifications
3business_id
4  ↕
5Sumsub externalUserId / IDWise referenceNo

它不是 t_kyc_process.id，也不是 t_kyc_user_content.kyc_id。生成链接时 process_id 可以为空；只有用户正式提交第三方结果时，才需要创建或关联流程。

2.4 receipts：防止 UI 重复点击产生重复业务

前端每个写操作都要生成 request_id。后端在 receipts 中保存已提交动作的摘要和响应：

  • 同一请求超时重试，返回原响应。
  • 请求参数换了但继续使用旧 request_id，返回重放不匹配。
  • 姓名确认、POA 国家决策、第三方正式提交等动作不会因为用户双击而重复写内容。

3. UI 页面逐屏对应后端处理

3.1 KYC 总览页：先读取上下文，不直接创建流程

UI 目的：显示当前办理入口、生效档案、是否存在代客流程以及历史入口。

调用顺序：

1POST /api/kyc/process/context
2POST /api/kyc/process/myinfo

context 返回：

  • current：本人 source_type=1 的进行中流程，可编辑。
  • target：当前目标上下文；首次正式提交前 process_id 可以为空。
  • effective：当前生效档案，只读。
  • delegated：代客 source_type=2 流程摘要，只读，不能作为用户编辑流程。
  • permissions：是否可以继续办理、是否可以查看历史。

myinfo 返回每张 UI 表单卡片的 steps[]：

1form_id / form_type / title / sort
2content_id / status / values / fields
3ui_state / available_actions / permissions
4reuse / verification / review_selection

前端应该以 ui_state 和 available_actions 决定按钮，不要只根据 status=9 或 verification.state 自行推断页面。

3.2 个人信息页：先编辑，首次正式提交才创建流程

UI 目的：填写姓名、电话、生日和居住国家。它是 POI 姓名比较和 POA 国家比较的基准。

  1. 用户点击“编辑”或进入个人信息卡。
  2. 前端调用 POST /api/kyc/process/enter_edit，得到 edit_context_id、fields、values。
  3. 用户填写后调用 POST /api/kyc/process/saveinfo，参数 mode=edit。

首次提交：

  • process_id=null、expected_version=0。
  • 服务端在事务内创建 t_kyc_process，固定 source_type=1。
  • 写入一条 t_kyc_user_content，并回写 process_id。
  • target.process_id 更新为新流程 ID。
  • 写入 t_kyc_process_log 的客户提交事件。

后续编辑：

  • 锁定本人进行中流程并校验 version。
  • 原内容 is_last=0，新内容 is_last=1。
  • 居住国家如发生变化，会检查本轮已通过 POA；若冲突，则恢复 POA 待提交并要求重新认证/上传。

UI 上“保存个人信息”与“开始第三方认证”是两个动作。前者是否创建流程，取决于是否是第一次正式保存；后者只创建认证绑定。

3.3 身份信息页：选择人工或第三方

UI 目的：展示身份资料表单和审核方式选择。

用户选择人工：

 1POST /api/kyc/process/switch_method
 2{
 3  "target_context_id": "...",
 4  "process_id": "3812",
 5  "form_id": "17",
 6  "method": "manual",
 7  "provider": "",
 8  "expected_version": 1,
 9  "request_id": "..."
10}

之后在身份信息页上传证件并用 saveinfo(mode=edit) 提交。可信资料由用户输入，状态通常是人工待审 kyc_status=1。

用户选择第三方：

  1. switch_method(method=third_party, provider=sumsub) 写 state.forms[target:17]。
  2. 前端调用 POST /api/kyc/process/kyc_link。
  3. 后端在 verifications 中预留绑定，先写 reserved，再调用供应商生成 URL。
  4. URL 成功后更新为 pending，返回 verification_id + url。

kyc_link 不直接写 t_kyc_user_content，也不代表身份信息已通过。UI 应进入“认证中”卡片，使用 refresh 等待结果。

3.4 第三方认证页：资料先在供应商，回调才更新本地绑定

用户打开 kyc_link.url，在 Sumsub/IDWise 页面上传证件、进行人脸或地址认证。此时：

  • 浏览器打开/关闭第三方页面，不会把本地状态改成通过。
  • 供应商先保存 applicant、审核步骤、OCR 和图片。
  • 认证完成后由供应商服务器回调旧入口，Sumsub 为 POST /api/kyc/kyc_webhook，IDWise 为 POST /api/kyc/idwise_kyc_webhook。

Sumsub 回调的关键关联是：

1回调 externalUserId
2  = verifications[verification_id].business_id

后端还要继续校验目标、表单、审核方式、provider、selection_generation、流程生命周期和重审 attempt，防止旧链接或旧回调覆盖当前 UI。

回调写回 kyc_link_json：

字段 UI 用途
state 认证中、失败、通过
rejection_reason 失败原因弹窗
document_name 姓名确认弹窗的证件姓名
document_country 国籍允许性及身份信息展示
poa_country POA 国家分歧弹窗
personal_country 与 POA 国家比较的基准
provider_values 正式提交时服务端使用的可信资料
provider_result_at 本地收到并采纳结果的时间

回调完成后仍没有正式 t_kyc_user_content。用户必须回到 UI 继续确认和提交。

3.5 认证中/失败/通过：refresh 决定下一张 UI 卡片

1POST /api/kyc/process/refresh
2{
3  "verification_id": "verification-uuid"
4}

服务端只按“当前登录会员 → t_kyc_member_other → 同一个 verification_id”查询，不使用会员最近一条表单替代绑定。

返回值重点：

state required_action UI 行为
pending null 显示认证中，按 retry_after 继续 refresh
rejected null 展示供应商失败原因；若 can_request_check=true 显示 request check，否则允许重新认证/切人工
rejected 且 rejection_reason=KYC_NATIONALITY_NOT_ALLOWED nationality_rejected 显示国籍不支持提示，重新选择人工或其他允许渠道
passed，POI 未确认姓名 poi_name_confirm_required 打开姓名拆分/确认弹窗
passed，POA 国家不一致 poa_country_decision_required 打开两国选择弹窗并阻断后续步骤
passed，前置决策完成 submit_verification 允许调用 saveinfo(mode=verification)
submitted null 认证结果已正式进入流程，重新读取 myinfo

因此 required_action=null 不是“没有数据”，必须与 state 一起解释。

3.6 POI 通过后的姓名确认弹窗

UI 画面：显示第三方证件识别出的完整姓名，让用户确认姓和名的拆分；姓名不一致时展示两个选择。

调用顺序：

1POST /api/kyc/process/verification/name_preview
2POST /api/kyc/process/verification/name_confirm
3POST /api/kyc/process/saveinfo   // mode=verification

name_preview 只读比较：

  • 用户填写 first_name、last_name 后，按证件国家规则拼出完整姓名。
  • 必须覆盖第三方证件姓名的全部字符；中点、连字符和内部顺序不能被静默删除。
  • 再与本轮个人信息姓名比较，返回 name_mismatch。

name_confirm 的两个分支：

UI 选择 decision forms[target:17] 正式提交结果
更新个人信息姓名并自动通过 use_confirmed_name name_confirmation=confirmed，保存确认姓/名和比较基准 服务端把本轮个人信息姓名同步为确认值；资料完整时 POI 可为 9
保留当前姓名并转人工审核 keep_current_name_manual name_confirmation=manual_review，requires_manual_review=true POI 正式入库但 kyc_status=1、kyc_audit_method=manual

这个弹窗确认本身不改 t_member，也不把绑定直接改为 submitted。必须用相同 verification_id 再调用 saveinfo(mode=verification)，服务端才把 provider_values 写入正式内容。

3.7 POA 页面和国家不一致弹窗

人工 POA：

  • UI 在国家字段旁常驻展示“必须与个人信息居住国家一致”。
  • saveinfo(mode=edit) 服务端规范化国家名称/代码后比较。
  • 不一致直接返回 POA_COUNTRY_MISMATCH，不写新内容。

第三方 POA：

  • refresh 或 myinfo 返回 poa_country_decision_required、个人国家和证明国家。
  • 决策前，myinfo.steps[] 后续步骤为 blocked_by_poa_country，前端应禁用导航；后端也拒绝绕过调用。

弹窗两个选择：

选择“保留当前个人国家并重交 POA”

1POST /api/kyc/process/verification/poa_country_decision
2{
3  "decision": "keep_personal"
4}

后端：

  1. 保留个人信息国家。
  2. 当前第三方 POA 绑定标记 superseded。
  3. POA 旧内容退出本轮有效状态，第三方地址资料只作为预填。
  4. 覆盖预填中的 POA 国家为个人国家，并清空旧证明文件 URL。
  5. 设置 requires_resubmission=true、method=manual，递增审核代次。
  6. 用户必须上传新证明后再次 saveinfo(mode=edit)，新内容进入人工待审。

如果同一次第三方认证同时覆盖 POI 和 POA，关联 POI 也要恢复待提交；只有服务端有明确同次认证关联时才执行，不能按“同会员、同 provider”猜测。

选择“更新个人信息国家并重置 KYC”

1POST /api/kyc/process/verification/poa_country_decision
2{
3  "decision": "use_poa"
4}

后端：

  1. 旧本人进行中流程标记终止，process_status=-2。
  2. 当前目标下的认证绑定全部失效。
  3. 创建新的 target_context_id，递增 target.generation。
  4. 将 target.process_id 置为 null，保存 personal_country_override=poa_country。
  5. 相同表单的旧值可以作为预填，但不能继承旧 kyc_status=9。
  6. 用户回到个人信息页重新正式提交；新流程在这次提交时才创建。

旧生效流程和会员当前国家在新整轮通过前保持不变。国家决策是“重置当前 KYC 目标”，不是会员自行选择新的监管规则。

3.8 问卷、客户协议和最后提交

问卷和客户协议仍使用 saveinfo(mode=edit)，审核方式从当前规则决定。协议字段由后端生成签署 PDF 并保存签署记录；前端只提交明确的同意值，不提交任意文件 URL 代替签署。

当用户完成一个步骤后，前端重新请求 myinfo，根据 steps[].status、ui_state、available_actions 渲染下一步。不要用“当前页面提交成功”直接跳到最终成功页，因为：

  • 第三方 passed 只是候选结果，必须正式提交。
  • 人工审核提交后仍是 kyc_status=1。
  • 整轮生效必须等待所有规则要求的表单本轮内容都为 9。

4. 从正式提交到整轮生效的表写入

4.1 saveinfo(mode=verification) 的事务边界

前端传当前 target_context_id、process_id、form_id、expected_version、request_id、verification_id。服务端在锁内重新核对目标和绑定，然后：

  1. 首次还没有流程时创建 t_kyc_process，source_type=1、process_status=1、effect_status=0。
  2. 旧的同表单当前记录 is_last=0，保留审核历史。
  3. 新增 t_kyc_user_content，写入 process_id、form_id、kyc_config_id、kyc_content、kyc_form_detail_snapshot、journey_id、is_last=1。
  4. provider_values 由服务端从绑定读取，不信任前端伪造的第三方资料。
  5. 完整且无需人工时写 kyc_status=9、kyc_audit_method=provider；姓名保留人工或证据不完整时写 kyc_status=1、kyc_audit_method=manual。
  6. POI/POA 文件投影到 t_customer_file；来源指向 kyc_user_content。
  7. 写入 t_kyc_process_log 的客户提交/自动通过事件。
  8. 绑定写 state=submitted、process_id、content_id，保存 receipts。

4.2 t_kyc_process_log 在 UI 里对应什么

它不是前端操作日志，而是流程业务事件账本。用户端动作中需要关注：

UI 动作 日志含义
正式提交个人信息/人工 POI/POA/问卷/协议 客户提交，operator_type=1
第三方资料正式提交且自动通过 系统自动审核，review_result=9
姓名保留当前姓名转人工 POI 转人工原因
保留个人国家并要求重交 POA POA 重提原因
采用 POA 国家重置流程 流程终止/重置原因
身份证件地址自动补齐 POA 系统回填和自动审核事件

name_preview、普通 refresh 和打开第三方 URL 不应单独伪造一条正式提交日志；它们是读取或控制状态动作。

4.3 整轮生效

只有当前规则需要的所有表单本轮 is_last=1 且 kyc_status=9，才执行：

  • 当前 t_kyc_process 改为完成/审核通过/生效，写 activated_at、ended_at、kyc_profile_snapshot。
  • 原生效流程改为失效，记录被新流程替代。
  • 最终个人信息姓名、居住国家、国籍、生日和监管快照投影到会员资料。
  • 刷新会员 KYC 总状态和汇总表。
  • 写流程激活日志并发送既有成功通知。

新流程尚未整轮通过时，旧生效资格仍由有效流程决定；不能因为新流程某张表处于待审就直接清空会员原有资格。

6. 前端实现时最容易出错的地方

  1. kyc_link 返回的 verification_id 必须原样保存；不能拿会员 ID、process_id 或 Sumsub applicantId 代替。
  2. business_id 只由后端生成和回调匹配，前端不拼接、不展示为可编辑字段。
  3. refresh 的 required_action=null 必须结合 state 判断；pending/null 和 rejected/null 是两种完全不同的 UI。
  4. POI passed 后不能直接进入下一张卡片，必须完成姓名确认并再次 saveinfo(mode=verification)。
  5. POA 国家分歧决策完成前，后续步骤必须禁用；即使用户手动调用接口，后端也会拒绝。
  6. name_confirm 或 poa_country_decision 成功后要使用响应中的最新 target_context_id、process_id、version，并重新调用 myinfo。
  7. 第三方认证回调写入的是 kyc_link_json 候选状态；前端不能把回调到达当成正式表单通过。
  8. 用户刷新页面时应从 myinfo.steps[].verification 恢复认证状态，不能只依赖前端内存。
  9. 历史详情是只读数据，history_incomplete=true 时不要用当前会员资料补齐缺失历史字段。

7. 结论

kyc_link_json 的作用不是保存一份“第三方结果文本”，而是把 UI 当前目标、每张表单的审核选择、每次第三方认证绑定、用户决策和幂等回执集中在会员维度保存。它保证了用户在刷新页面、回调迟到、切换人工/第三方、姓名确认和 POA 国家重置后，前端仍能恢复到正确的业务页面。

整条链路必须按下面的顺序理解：

1UI 读取目标
2→ 选择表单审核方式
3→ kyc_link 生成本地绑定
4→ 第三方完成审核
5→ 回调按 business_id 更新绑定
6→ refresh 返回下一动作
7→ 姓名/国家决策
8→ saveinfo 正式落库
9→ 所有表单通过后整轮生效
