KYC 2.20.1 身份信息与地址证明：前端串联及参数来源说明

整理日期：2026-11-13。面向 Web/App 前端。

依据：最新用户 API 接口文档第 3～9 节及第 14 节，并核对本地 gtcuser / test / 3e0105521 的参数接收和状态处理。本文是接口调用说明，不代表已对各供应商及环境完成真实认证验收。本次只补充文档。

1. 先分清“提交”发生在哪一步

用户做了什么 此时前端如何理解 下一步
人工填写 POI/POA，并且 saveinfo(mode=edit) 返回 submitted=true 已正式提交平台，按 status 展示待审或通过 刷新 context，按上下文读取步骤或只读详情
复用资料，saveinfo(mode=reuse) 返回 submitted=true 已正式提交本轮资料 同上；不能只展示历史通过状态而跳过提交
供应商页面显示“验证成功”或窗口关闭 仅是第三方页面行为，平台是否收到结果还未知 用本次 verification_id 请求 refresh
refresh.state=passed 平台已拿到第三方通过结果，但可能还未正式提交本轮表单 按 required_action 做姓名/国家处理，再正式 saveinfo(mode=verification)
name_confirm 成功 仅保存姓名选择，尚未正式提交身份表单 同一按钮操作自动续接 saveinfo(mode=verification)
refresh.state=submitted、submission_confirmed=true 第三方结果已经正式提交，仍可能处于人工待审 刷新整轮，以 myinfo.steps[].status 展示结果

前端不要把“第三方通过”“姓名确认成功”“本轮表单已通过”“整轮 KYC 已生效”当成同一件事。

所有本文接口均为 POST。完整地址为 https://{API_HOST} 加图中的完整 /api/... 路径。测试环境示例：https://test.gtctrader1203.top/api/kyc/process/refresh。鉴权、语言、设备 Header 沿用现有请求层。

所有接口先判断外层 response.code === 200，再读取 response.data。HTTP 200 不代表业务成功。下文 ctx/info/sw/link/r/preview/confirm/save/decision 均指相应成功响应的 data。

2. 页面先拿到什么，后续参数从哪里取

2.1 获取办理上下文和当前表单

  1. POST /api/kyc/process/context：无请求参数，发送 {} 即可，成功数据记作 ctx。
  2. ctx.permissions.can_continue=true 且有 ctx.current：调用 POST /api/kyc/process/myinfo，请求 { "process_id": ctx.current.process_id }。
  3. can_continue=true、current=null 且有 target：调用同一 myinfo，请求 { "target_context_id": ctx.target.target_context_id }。
  4. 没有办理入口时，不拿旧缓存 ID 或 effective.process_id 强行调用编辑页 myinfo，按第 9 节进入总览/只读详情。

myinfo 成功数据记作 info。从 info.steps 中定位当前实际表单 step。form_type=2 是身份信息 POI，form_type=5 是地址证明 POA；接口的 form_id 必须用 step.form_id，不能传数字 2/5 代替。

2.2 下列变量是本文图表的取值约定，不是新增接口字段

图中变量 实际参数/用途 准确来源和更新时机
T target_context_id 初始来自 info.target.target_context_id；应与刚读取的 ctx.target 同属一轮。国家重置后采用新目标，重新读取页面
P process_id 初始来自 info.process.process_id；首次未创建时为 null。正式提交后取返回的 process_id，不能继续传旧的 null
V expected_version 初始为 info.process.version；无流程时为 0。后续取同一当前流程最近一次有效业务响应 version，不能前端自行加一
F form_id 当前 step.form_id；POI/POA 各自独立，步骤 ID 不硬编码
C 可选 config_revision info.target.config_revision，是不透明字符串；只在接收此参数的接口原样传入
provider 第三方渠道 从当前 step.review_selection.channels[].value 选择，且 allowed_review_methods 必须包含 third_party；不能自行固定 sumsub
G selection_generation 新建链接时取 switch_method 返回的 sw.review_selection.generation；恢复页面时取当前 step.review_selection.generation
Q verification_id 新认证取 kyc_link 的 link.verification_id；页面恢复或同次认证关联 POA 时取该步骤自己的 step.verification.verification_id
E edit_context_id enter_edit / resubmitinfo 返回值；切换方式返回非空编辑上下文时也保留
B base_content_id resubmitinfo / switch_method 返回的旧当前内容 ID；不是历史复用来源 ID
S source_content_id step.reuse.source_content_id；只在当前允许复用时用于 mode=reuse，或作为合法编辑预填来源
rid_* request_id 前端为每个业务动作生成的唯一字符串，如 UUID；同一动作原样重试沿用原 ID，不同动作使用不同 ID

T/P/V/F/Q 必须属于同一会员、同一当前目标、同一表单的有效认证。前端不得混用旧目标和新流程，或把 POI 的 Q 用于 POA。

expected_version 是整条流程版本，不是每个表单独立版本。因此对同一流程的写操作应串行；POI 操作更新版本后，POA 要用新响应或重读页面后的版本。

2.3 按当前返回动作选路径

  • 人工填写：看 permissions、available_actions；必要时切换为 manual，再编辑/提交，见第 3 节。
  • 合法复用：reuse.available=true 且当前允许 reuse，走第 3.3 节。
  • 开始第三方：保存渠道 → 取得链接 → 打开链接 → 查询状态，见第 4 节。
  • 已有有效 verification_id：先用该 ID 查询/恢复，不为轮询重复切换方式、重复生成链接。
  • 已通过步骤只读，不为“继续下一步”重新发起认证。
  • POI 首次默认方式：只有同时满足 info.target.auto === 1、允许 third_party、存在可用渠道时默认展示第三方。POA 按自身步骤权限和渠道处理，不能直接套用 POI 默认值。

POI 的 country 是证件国籍；POA 的 country 是居住国家。不能拿 POI 国籍和个人居住国家直接做相等校验。

3.3 历史复用的请求链

只有 step.reuse.available=true 且当前允许 reuse 时使用。无需先 enter_edit，也不需要第三方链接、姓名确认或第三方 refresh。

 1// 各变量来源见第2.2节；以下是请求对象表达式，不是固定的测试数据。
 2await post('/api/kyc/process/saveinfo', {
 3  target_context_id: T,                       // info.target.target_context_id
 4  process_id: P,                              // 当前本人流程；首次为null
 5  form_id: step.form_id,                      // 当前要复用的具体表单
 6  expected_version: V,                        // 当前流程最新版本
 7  request_id: rid_reuse,                      // 本次复用动作唯一ID
 8  mode: 'reuse',
 9  source_content_id: step.reuse.source_content_id
10});

values/edit_context_id/verification_id 不需要传。config_revision 可选，传时取 C。成功后执行第 9 节刷新分流。复用 POA 同样受国家一致性校验；返回 POA_COUNTRY_MISMATCH 时不能通过修改前端预览值继续复用，应让用户进入编辑提供符合当前国家的新资料。

4.2 页面恢复、第三方窗口返回和同源绑定

重新请求 context 和按权限分流后的 myinfo，找到需要处理的 step：

1const Q = step.verification?.verification_id;
2if (Q) {
3  // 有当前绑定时先读它，不是重新switch_method/kyc_link。
4  const response = await post('/api/kyc/process/refresh', {
5    verification_id: Q
6  });
7  // 检查code后，按第5节处理response.data。
8}

必须保留 Q 与表单 F 的对应关系。verification_id 不是流程 ID、表单 ID、会员 ID、Sumsub applicantId 或第三方 externalUserId。前端不拼装业务号，不直接调用供应商回调。

认证链接过期或绑定被替代时，重读步骤，按当前允许动作开始新认证；不能继续使用旧 Q 做姓名确认或正式提交。

5. refresh 的每种返回，前端下一步具体做什么

POST /api/kyc/process/refresh 只传 { "verification_id": Q }。其余目标、流程、版本由返回提供，不能把别的接口字段塞进该请求。

r.state / r.required_action 前端展示 下一请求和参数来源
pending，action 通常 null 认证处理中 等待 r.retry_after 秒，再 refresh({verification_id:r.verification_id})
passed + poi_name_confirm_required 姓/名拆分确认；必要时显示姓名冲突双选 按第 6 节 name_preview → name_confirm → saveinfo
passed + submit_verification 附加校验已完成，可正式提交 saveinfo 的 T/P/F/V/Q 分别取 r.target_context_id/process_id/form_id/version/verification_id，mode=verification，生成独立 request_id
passed + poa_country_decision_required 展示个人居住国家与 POA 国家冲突 按第 7 节双选；决策成功后不再提交原绑定
rejected + nationality_rejected 证件国籍不在允许范围 展示 rejection_reason/document_country；重新读步骤后仅执行可用动作，不能靠姓名确认绕过
其他 rejected，action 可为 null 审核未通过 展示 rejection_reason；只有 can_request_check=true 才提供 Sumsub 重审；其他重新认证/人工操作以当前步骤权限为准
submitted 结果已经入本轮流程，未必通过 停止本次等待认证结果的轮询，按第 9 节刷新；人工审核阶段用 context/myinfo 读取实际状态
superseded/expired 本次认证不可继续办理 丢弃旧 Q 的操作入口，重新 context 分流和读取当前步骤
不符合已知组合，如 passed 但 action 意外为空 不推断通过或自动提交 重读页面；仍不一致时保留非敏感请求信息反馈后端

required_action=null 本身不是错误，也不是通过标志。 必须与 state 一起判断。尤其不能只写 if (!required_action) { 显示成功 }。

5.1 Sumsub 失败后的 request check

它是供应商重审，不是人工内容的 resubmitinfo。只在当前 can_request_check=true 且用户选择重审时调用：

1await post('/api/kyc/process/request_check', {
2  target_context_id: T,                   // 最新当前目标
3  process_id: P,                         // 最新当前流程；首次null
4  form_id: step.form_id,                 // 被拒绝绑定所属表单
5  verification_id: step.verification.verification_id,
6  selection_generation: step.review_selection.generation,
7  expected_version: V,                   // 当前流程版本
8  request_id: rid_recheck                // 本次重审动作独立ID
9});

不传 provider/applicantId/config_revision。成功返回包含当前 verification_id/state/required_action/version/request_check_status/retry_after。继续用该绑定调用 refresh，通过后仍要进入姓名/国家处理及正式提交。

preparing/sending/accepted/unknown 不换新 ID 反复发起重审。unknown 时保留原绑定继续查询或反馈核对；failed 明确失败后，用户显式重试再创建新动作。发送前 preparing 中断的恢复可沿用原请求 ID；不是每轮 refresh 都调用一次 request_check。

6. POI 通过后：姓名拆分 → 预检 → 确认 → 正式提交

6.1 完整参数流程图

入口是当前 POI 认证 r.state=passed 且 r.required_action=poi_name_confirm_required。图中每次写成功必须检查 code，失败停止依赖链。

6.2 前端按钮应该怎么实现

  1. 让客户确认 first_name/last_name；refresh 只提供完整 document_name，不能假定它额外提供可靠姓/名拆分字段。
  2. 调用 name_preview 验证拆分并取得是否与个人姓名冲突。姓和名都必填；拼接必须匹配证件完整姓名，具体归一化规则由服务端校验。
  3. 没冲突也要 name_confirm(decision=use_confirmed_name)；有冲突才提供两种选择，不能在无冲突时强行转 keep_current_name_manual。
  4. 用户最终点击确认后，前端串行完成 name_confirm 和 saveinfo，不额外要求客户再点一次“提交身份表单”。
  5. 仅在 saveinfo 正式提交成功后显示“已提交”；status=1 是待人工，status=9 是本步骤通过。

use_confirmed_name 会在正式提交时更新本轮个人资料；会员生效资料在整轮生效时同步。不能在 name_confirm 成功时就宣称会员生效姓名已经修改。

6.3 版本和幂等键示例

请求 使用版本 业务动作 ID 响应及下一步
name_preview 当前版本 3 不需要 request_id 返回 3，不推进版本
name_confirm preview.version=3 rid_name 示例返回 version=4
saveinfo(mode=verification) confirm.version=4 rid_poi_save，与上一个不同 示例返回 version=5；正式内容此时才产生

数字仅用于说明，不能硬编码。首次尚无流程时，确认成功仍可能 process_id=null,version=0，正式提交使用这个实际返回值。

如果确认成功而后续提交网络失败，保留 rid_poi_save 与完整原请求用于重放，不因重试而重新生成另一条认证。若用户修改姓名选择，则是新动作，应重新预检、生成新的确认/提交请求键。

7.2 国家决策接口的参数来源

接口： POST https://{API_HOST}/api/kyc/process/verification/poa_country_decision，处理第三方 POA 国家不一致，新接口。

参数 必填/条件 来源
process_id 本文建议显式传，尚无流程为 null 当前 POA refresh.process_id，必须是绑定对应的当前本人流程
form_id 必填 POA refresh.form_id；也可取 myinfo.blocking_action.form_id
verification_id 必填 POA refresh.verification_id；也可取同一阻断对象的 verification_id
decision 必填 用户选 keep_personal 或 use_poa
expected_version 当前流程必填；无流程 0 POA 当前 refresh.version；从阻断对象进入时使用当前 myinfo.process.version
request_id 必填 此次国家选择独立的业务动作 ID

请求里没有 target_context_id、config_revision。 这个接口从服务端当前目标解析，不能照抄其他写接口的所有公共字段。

从 myinfo.blocking_action 进入时，国家展示值为该对象的 personal_country/poa_country，默认项为 default_decision=keep_personal；流程/版本从同次 myinfo.process 取得。不要使用页面上另一个表单的认证 ID。

7.3 两种选择后，哪些值不能混用

返回字段 keep_personal use_poa
process_id 作出决策时的当前流程 原流程，不是重置后的新流程
version 当前流程决策后的版本 原流程终止后的版本，新目标提交不能用它
process_status 有原流程时为 1 有原流程时为 -2
target_context_id 当前目标 新目标 ID
next_process_id 当前流程或首次 null null，尚未创建新流程
next_version 后续办理版本 0
reset_form_ids POA 及可能关联的 POI 按实际返回处理；整轮都须重新读取

采用 POA 国家会终止本次本人流程、准备新目标，不是立即修改会员当前生效国家。旧生效档案继续按其有效性展示。

8. 同一次第三方认证同时拿到 POI 和 POA，前端怎么串

供应商一次认证可能产生两个本地绑定，它们对应不同 form_id、不同 verification_id。不是每个表单都必须再打开一次第三方链接，也不是一个 ID 可以提交两个表单。

  1. POI 回到平台后，用 link.verification_id 查询当前 POI。
  2. 按第 6 节处理姓名并正式提交；如果整轮已有 POA 国家冲突提示，也应按提示安排国家决策，不能忽略后续阻断。
  3. 每次正式提交/国家选择后重新读取整轮状态。POI 名字更新、POA 国家选择都可能改变其他表单，不能沿用提交前的 POA 缓存。
  4. 重新从 info.steps 找 POA 步骤：
最新 POA 状态 前端动作和参数来源
step.status=9，例如已被 POI 地址自动补齐 直接展示通过；不重复认证/提交。save.auto_passed_form_ids 只是提示，仍以重读结果为准
有 step.verification.verification_id 且尚未正式提交 refresh({verification_id:该POA自己的ID})，再按第 7 节处理
poa_country_decision_required 或 blocking_action 指向该 POA 用 POA 的 F/Q 与当前 P/V 执行国家决策；不能提交 POI 的绑定
没有可用绑定，也未自动通过 按该步骤当前可用动作人工填写、复用或开始独立第三方认证
国家选择后恢复待提交的关联 POI 按最新 reset_form_ids/steps/permissions 重做，不能保持页面旧通过标志

“POI 地址自动补齐 POA”需要配置和证据同时满足条件；前端不根据供应商页面有地址就自行认定 POA 通过。是否触发以正式提交响应和重读步骤为准。产品材料中开关与独立 POA 的既有口径冲突仍沿用主接口文档第 6.4 节的说明，本文不新增业务解释。

10. 失败、中断和重试：不要把串联做成重复提交

发生位置/返回 前端必须怎么接
refresh.pending 保留当前 Q 按 retry_after 查询，不重新生成链接或切换方式
姓名预检失败 提示修正用户确认的姓/名拆分；不发送 name_confirm/saveinfo
name_confirm 响应丢失 原参数、原 rid_name 重放；取成功回执再接正式提交
姓名确认成功、正式提交未发出 用确认返回的 process_id/version 和预先生成的 rid_poi_save 自动续接
第三方正式提交响应丢失 可先用同一 Q 的 refresh 查看 submission_confirmed；或原参数、原提交 ID 重放 saveinfo；然后重读页面
人工/复用提交响应丢失 原参数、原提交 ID 重放，成功后重读页面；不能直接再生成一次新提交
KYC_NAME_CONFIRM_REQUIRED 读取当前姓名/版本重新预检确认，新决策使用新请求 ID；不用为了姓名决策重做有效第三方认证
POA_COUNTRY_MISMATCH 人工/复用 POA 未提交成功；让用户提供与本轮个人国家一致的资料，不能走第三方国家双选来掩盖人工错误
KYC_POA_COUNTRY_DECISION_REQUIRED 读取当前 POA 及阻断信息，进入国家决策；不能用跳过弹窗直接提交后续表单
KYC_VERSION_CONFLICT 停止旧写请求，重读 context/myinfo，重新判断业务动作；不能仅把新版本填入旧请求自动重发
KYC_TARGET_CHANGED 关闭旧目标的编辑/认证操作，重读 context 再分流；context 本身失败则停止依赖链
KYC_PROCESS_NOT_EDITABLE 原流程可能已完成/终止，按最新 context 进入只读档案或新目标
KYC_REQUEST_REPLAY_MISMATCH 同一 ID 对应参数发生变化；停止自动重试，重读当前状态，确需新业务动作时使用新 ID
KYC_POA_RESUBMIT_REQUIRED 国家冲突保留个人国家后，必须上传新证明人工重提，不能拿旧URL或切第三方绕过
KYC_FIELD_REQUIRED/KYC_FIELD_INVALID/KYC_FILE_INVALID 修正字段/文件；不展示已提交。修改业务参数后是新动作，使用新提交 ID

原请求重放的 version/status/content_id 是原动作回执，不保证代表此刻最新状态；恢复后先重读页面再开展下一独立写操作。页面卸载后停止无用轮询，重新进入时由 context/myinfo 恢复当前绑定。

11. 前端联调时逐项确认

  • POI 人工：上传成功 → 正式提交 → status=1 展示待审，使用整轮刷新而非无绑定的第三方 refresh。
  • POI 第三方：窗口成功 → 同一 Q 查询 → 姓/名拆分 → 预检 → 确认 → 自动正式提交 → 整轮刷新。
  • 姓名一致：也调用 name_confirm(use_confirmed_name)；不一致：确认用户选项再串正式提交。
  • POA 人工/复用国家不一致：展示提交错误，不改变本地通过状态。
  • POA 第三方国家一致：使用该 POA 自己的 Q 正式提交；不额外做 POI 姓名确认。
  • POA 第三方国家不一致：双选参数取对应 POA，采用 POA 国家后改用新 T、null P、0 V重新开始。
  • 同一次认证同时获得 POI/POA：读取各自绑定和最新状态，既不共用 Q，也不无条件重新开两个认证链接。
  • 所有正式提交成功后：先 context 分流；已生效的流程用 history/detail，不拿完成的 ID 调 myinfo。
  • 同一流程的写操作串行，下一请求版本来自上一步实际响应；不同动作请求键不同，同动作重试保留原键。
