KYC 2.20.1 姓名确认前端对接与联调清单

本次按最小修改方案落实：复核已有用户 API，以新增行为验证固定两次调用的重试和回滚边界，补齐前端接入与真实环境验收步骤。后端未新增合并接口，未修改业务逻辑、第三方回调、SQL 或管理端。用户 App/Web 前端仓库未提供，因此本文不代表页面已接入或已验收。

gtcuser 分支：feature/v2.20.1/kyc_process-jalen；本次提交：84b2aa71b 补充KYC姓名确认串联验证。Hugo 文档只保存在本地，不提交。

后续收尾更新：b9e26dc26 修正了第三方正式提交重放返回的会员资格，新增 20 项真实资格查询行为检查。最新总结果见同目录《KYC-2.20.1用户API最终收尾复核-20261104.md》；下文保留姓名串联实施记录，App/Web 页面仍需接入。

1. 需求依据与边界

  • 禅道 #1089 下的用户 PRD FR-NM-13：保留当前姓名时回填第三方资料，直接提交人工审核并定位下一步骤。前端一次点击自动串联已有确认与正式提交接口，满足这一交互，不额外增加第二次确认。
  • 采用证件姓名时，后端正式提交才更新本轮个人信息；本轮整体验证通过后再投影到会员生效资料。姓名变化后的协议重签仍按已有步骤权限处理。
  • 范围文档 2.2.2 的独立 POA 优先前置条件与“关闭后人工审核”表述仍存在口径冲突。本次继续保持“开关只控制无独立 POA 时的 POI 地址替代”，没有将本轮执行授权视为产品对冲突的新确认。也不把独立第三方 POA 一律改成人工。
  • 复用按 FR-RU-01 及范围 2.2.1 的相同 form_id 执行。未增加跨 ID 迁移映射。

2. 前端接入点

所有路径均为 POST，使用既有登录鉴权；下文响应是项目统一包装内的 data，前端须先检查 HTTP 及业务成功状态。process_id/form_id/verification_id/content_id 均保持字符串，首次未提交时 process_id=null,expected_version=0。域名由各端当前 API 环境配置提供，不硬编码 staging/生产域名。

接口名称 完整 API 地址 本次使用方式
获取当前流程上下文 /api/kyc/process/context 读取当前目标、流程、版本、有效资格与权限
获取步骤详情 /api/kyc/process/myinfo 按服务端返回的顺序、状态和权限渲染页面
查询第三方认证状态 /api/kyc/process/refresh 判断姓名选择、正式提交或已提交；窗口关闭不表示成功
预检姓名拆分 /api/kyc/process/verification/name_preview 只读验证拆分，并判断是否显示姓名分歧选项
保存姓名选择 /api/kyc/process/verification/name_confirm 一次按钮操作的第一个写请求，只保存选择
正式提交表单 /api/kyc/process/saveinfo 同次按钮操作自动接续的第二个请求，正式提交 POI

2.1 预检与弹窗

在 refresh.state=passed,required_action=poi_name_confirm_required 时显示证件完整姓名与姓/名输入。调用“预检姓名拆分”：

1{
2  "process_id":"10001",
3  "target_context_id":"ctx-uuid",
4  "form_id":"12",
5  "verification_id":"verify-uuid",
6  "first_name":"SAN",
7  "last_name":"ZHANG",
8  "expected_version":3
9}

name_mismatch=true 时显示默认“更新个人信息姓名并自动通过”和可选“保留当前姓名并转人工审核”。自动通过仍以正式提交返回为准，资料不足可能待人工。false 时直接使用 use_confirmed_name，不显示双选。输入变更后需重新预检；KYC_NAME_CONFIRM_REQUIRED 时保持弹窗，不推进步骤。

示例假设本轮还有未提交步骤，所以 review_status=10；全部提交但待审时为 11。status=1 表示该 POI 已提交待人工，不是通过。示例 member_kyc_status=1 适用于没有旧生效档案的办理中客户；仍有旧生效档案时为 9，包括第三方提交回执重放。重放的 content/status/version 确认原操作，会员资格按当前状态只读计算；页面完整生效档案仍通过 context 重读。

成功后重读“上下文”和“步骤详情”，根据当前步骤顺序、blocking_action、available_actions 和 permissions 定位可继续步骤；整轮完成时显示完成页。不能简单固定跳到 POA，也不能把待人工当作整轮已通过。

2.3 串联代码示意

以下是交接示意，尚未写入 App/Web 项目。postData 代表现有请求层：校验业务成功状态并返回 data，失败抛出对应业务错误。

 1// 预检和用户选择完成后创建一次；retry 复用同一 op。
 2function createNameOperation(context, input, uuid) {
 3  return {
 4    busy: false,
 5    confirm: {
 6      process_id: context.process_id,
 7      target_context_id: context.target_context_id,
 8      form_id: context.form_id,
 9      verification_id: context.verification_id,
10      expected_version: context.version,
11      first_name: input.first_name,
12      last_name: input.last_name,
13      decision: input.decision,
14      request_id: uuid()
15    },
16    submitRequestId: uuid(),
17    submit: null
18  };
19}
20
21// 从同一个确认按钮调用；重试时不重新生成 request_id。
22async function submitConfirmedName(op, postData, reloadPage) {
23  if (op.busy) return;
24  op.busy = true;
25  try {
26    if (!op.submit) {
27      const confirmed = await postData(
28        '/api/kyc/process/verification/name_confirm', op.confirm
29      );
30      op.submit = {
31        process_id: confirmed.process_id,
32        target_context_id: op.confirm.target_context_id,
33        form_id: op.confirm.form_id,
34        verification_id: op.confirm.verification_id,
35        expected_version: confirmed.version,
36        request_id: op.submitRequestId,
37        mode: 'verification'
38      };
39    }
40    const saved = await postData('/api/kyc/process/saveinfo', op.submit);
41    if (saved.submitted !== true) {
42      return { needsAction: true, response: saved };
43    }
44    await reloadPage(); // context + myinfo，按实际状态显示通过或待人工
45    return saved;
46  } finally {
47    op.busy = false;
48  }
49}

调用层应区分下表错误，再决定“原操作重试”还是“重读页面”。按钮防连点期间禁止修改当前输入。只有客户重新选择姓名/决策、完成新的预检后，才创建新操作；不能在每次网络重试时生成新 ID。示意中的姓名参数仅保留在当前页面内存，不写日志或浏览器持久存储。

3. 故障与页面恢复

情况 需要执行的动作 成功判据/边界
姓名确认请求超时，尚未拿到响应 保留原确认参数与 ID，重放同一个 POST /api/kyc/process/verification/name_confirm 回执 request_replayed=true 时使用其返回版本；不得据此直接显示提交成功
姓名确认成功，正式提交未发送 用已得到的版本调用 POST /api/kyc/process/saveinfo 仍是同一次按钮操作；不再要求客户重新选一次
正式提交超时，结果未知 对同一认证调用 POST /api/kyc/process/refresh；也可重放原 saveinfo 参数与 ID submission_confirmed=true 或 submitted=true 才表示已提交；passed 单独不表示提交完成
正式提交事务回滚 保留姓名选择和原正式提交请求；恢复后原请求重试 本轮内容、文件、提交回执和版本不残留半成品；已成功的姓名确认不回滚
KYC_VERSION_CONFLICT 停止自动重试，重新读取 POST /api/kyc/process/context 与 POST /api/kyc/process/myinfo，显示流程已更新 不把新版本自动填回旧操作；恢复当前步骤后由客户继续
KYC_TARGET_CHANGED / KYC_PROCESS_NOT_EDITABLE 清除旧操作，重读上下文，回到当前目标或只读流程 旧确认回执不能恢复已经终止或替换的流程
KYC_VERIFICATION_PENDING 重读当前步骤与 POST /api/kyc/process/refresh 按服务器动作显示等待、重认证或当前审核方式；不能把失效认证继续提交
页面刷新、App 重启，原内存操作丢失 先读上下文、步骤，再查当前 verification_id 的 refresh submitted 显示已提交；passed + submit_verification 显示继续提交；passed + poi_name_confirm_required 重新确认
重读后为 passed + submit_verification 客户点击继续时，以当前目标/流程/版本发起正式提交 沿用服务端已存决策，不重复调用确认；恢复页面本身不自动写入
服务端返回 submitted=true,status=1 显示已提交、待人工，按服务端权限继续 禁止显示“已通过”，旧生效资格从 context 读取

若保留跨刷新恢复标识，只保存与当前登录会员、目标及认证绑定的非敏感请求 ID；登出或目标改变时清除。原参数丢失时不要猜测重放确认请求，也不要静默替换客户的姓名选择。

新增 tests/behavior/KycProcessNameFlowCheck.php，执行真实 Service、Hyperf Model/Repository 和 SQLite 事务；供应商结果使用隔离前置数据，不请求外部服务，也不读取业务连接。新增 46 项检查，基础提交脚本原有 357 项 同时通过，不将重复执行累计成新覆盖。
