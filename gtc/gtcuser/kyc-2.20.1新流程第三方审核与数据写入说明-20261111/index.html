KYC 2.20.1 新流程第三方审核与数据写入说明

整理日期：2026-11-11。代码依据：本地 gtcuser 分支 feature/v2.20.1/kyc_process-jalen，提交 f420fdc1b。

本次逐段核对新流程 Controller、KycProcessService、SumsubService、供应商客户端、IDWise 回调、Zoloz 定时任务、客户文件投影、总状态计算及相关 SQL。没有切换工作分支、修改业务代码、访问数据库或调用真实第三方接口。以下描述该代码版本的行为，不能据此认定 dev/test 已部署相同版本或某笔认证已处理成功。

本文专门解释 /api/kyc/process/* 新流程。已有《KYC第三方审核请求与回调流程》主要解释旧 /api/kyc/*，两者的正式落库时点不同。

1. 必须先分清三件事

  1. 第三方认证有了结果：认证绑定的 state=passed/rejected，结果保存在 t_kyc_member_other.kyc_link_json。
  2. 客户把结果正式提交到本轮表单：调用 saveinfo(mode=verification)，生成 t_kyc_user_content，绑定变为 submitted。
  3. 整轮 KYC 全部通过并生效：本轮必需表单的当前内容全部通过，更新 t_kyc_process、会员资料及生效档案。

这三个时点不能混为一谈。尤其是：

  • passed 不表示整轮 KYC 已完成，也不表示正式表单已经入库。
  • submitted 表示该认证结果已进入正式流程；如果客户选择保留姓名转人工，正式内容仍是待审。
  • provider_result_at 是绑定收到并采纳一次结果的本机记录时间，不是 Sumsub 原始审核时间，也不是整轮通过时间。

2. 全流程图

flowchart TD A["读取 context / myinfo<br/>确定目标、表单和可用渠道"] --> B["switch_method<br/>保存 third_party + provider 和认证代次"] B --> C["kyc_link 第一次事务<br/>控制 JSON 新增绑定，state=reserved<br/>生成 verification_id 和 business_id"] C --> D["调用 Sumsub 生成 WebSDK Link<br/>externalUserId=本次 business_id"] D --> E["kyc_link 第二次事务<br/>保存 URL，reserved 转 pending<br/>返回 verification_id + URL"] E --> F["用户打开本次 URL<br/>在第三方页面上传资料并认证"] F --> G["Sumsub 审核完成<br/>POST /api/kyc/kyc_webhook"] G --> H["验签、过滤完成事件<br/>按 externalUserId 找本次绑定<br/>检查目标、流程、渠道和代次"] H --> I["解析整体及具体步骤结果<br/>成功时拉取资料、步骤状态和图片"] I --> J["recordProviderCallback<br/>控制 JSON 更新 state、provider_result_at<br/>以及 provider_values / 原因等"] J --> K["前端 refresh<br/>按登录会员 + 同一个 verification_id 查询"] K --> L{"当前绑定 state"} L -- "pending" --> M["required_action=null<br/>按 retry_after 继续查询"] L -- "rejected" --> N["展示原因<br/>按能力重审、重新认证或切换人工"] L -- "passed：POI" --> O["name_preview → name_confirm<br/>拆分证件姓名并保存客户选择"] L -- "passed：POA" --> P{"居住国家一致？"} P -- "否" --> Q["poa_country_decision<br/>重交证明或重置本轮"] P -- "是" --> R["saveinfo，mode=verification"] O --> R R --> S["写正式内容、客户文件和流程日志<br/>绑定改 submitted 并关联 content_id"] S --> T{"本轮必需表单全部通过？"} T -- "否" --> U["继续其他步骤或等待人工审核"] T -- "是" --> V["整轮完成生效<br/>更新会员资料及档案快照<br/>原生效流程退出生效"]

图中为 Sumsub 主链路。IDWise 使用 referenceNo；Zoloz 的结果来自既有定时查询，详见第 11 节。

3. 各种 ID 分别解决什么问题

标识 谁生成 保存位置/含义 使用方
member_id 既有会员系统 当前会员；用户接口从登录态获取 后端确定认证归属
target_context_id 后端 待办理目标；原始 JSON 通常是 state.target.id 防止旧页面办理已经变化的目标
form_id 表单配置 t_system_form.id；POI 的类型为 2，POA 为 5 指向具体表单，不等于 form_type
selection_generation 后端 state.forms[目标ID:表单ID] 的当前审核选择代次 切换方式/渠道后隔离旧结果
verification_id kycLink() 生成 UUID state.verifications 中本次绑定的对象键 前端 refresh、确认姓名、正式提交
business_id kycLink() 生成 本次绑定内部字段，格式为 会员ID_8 加 16 位随机数字 传给 Sumsub 的 externalUserId，并用于回调精确关联
applicantId Sumsub Sumsub 的申请人 ID，结果入绑定时保存为 journey_id 后端拉步骤状态、图片、重审
attemptId Sumsub 第三方审核轮次；保存为 provider_attempt_id 尤其用于区分 request check 前后结果
request_id 前端每个业务动作生成 生成链接的绑定或 state.receipts 同一请求重试去重，不能代替 business_id
process_id 本轮首次正式提交时生成 t_kyc_process.id，也回写绑定 正式流程归属；生成链接时可以尚为 null
content_id 正式提交时生成 对应 t_kyc_user_content.kyc_id 正式表单及客户文件来源

最关键的对应关系是：

1前端持有 verification_id
2    ↓ 在当前会员的控制 JSON 里找到绑定
3绑定.business_id
4    = 生成链接请求的 externalUserId
5    = 同一认证回调的 externalUserId

externalUserId 不等于 verification_id，也不再只等于会员 ID。 前端无须传入或拼出 business_id，新 kyc_link 的响应也不返回它。

4. 节点一：生成绑定和认证链接

入口：POST /api/kyc/process/kyc_link。

4.1 前置条件

先从 context/myinfo 获得当前目标、表单、版本及允许渠道，并通过 switch_method 保存：

1method = third_party
2provider = sumsub
3selection_generation = 当前返回的 generation

渠道来自本轮目标规则的 t_kyc_setting.audit_method_json。新链接生成路径的 level_name 也从当前渠道配置读取，不应直接套用旧接口独立 POA 使用全局 location 的解释。

kycLink() 检查目标仍有效、表单属于规则且启用、表单为 POI/POA、渠道允许、所选渠道一致。有正式流程时还要求它属于本人 source_type=1、处于进行中且版本匹配；当前表单已通过时不能重新生成链接。

4.2 先在本地预留绑定

第一次事务锁定该会员的 t_kyc_member_other，向其 JSON 的认证集合新增一个对象。

此时没有新增正式 KYC 流程或内容。verification_id 是 JSON 对象键，并非数据库里一张独立认证表的主键。

4.3 再向 Sumsub 请求链接

本地预留事务提交后，在事务外调用：

1KycApiService::getWebSdkLink(本次 business_id, 当前渠道 level_name, 空 actionId, 当前语言)
2    → SumsubClient::getWebSdkLink()

供应商请求的核心内容：

1POST /resources/sdkIntegrations/levels/{levelName}/websdkLink
2     ?ttlInSecs=1800
3     &externalUserId={本次绑定的business_id}
4     &lang={规范化语言}

客户端沿用既有认证配置和 HMAC 签名。本路径直接申请 WebSDK Link，没有在这里先显式调用 createApplicant()。

该请求没有携带 Webhook URL。 审核事件发往哪个环境，依赖 Sumsub 账户的 Webhook 配置；不能从“链接由 dev 生成”直接推出“回调一定发到 dev”。

4.4 拿到链接再回写绑定

第二次事务将同一绑定的 url 保存，并把仍为 reserved 的状态改为 pending。Sumsub 初次生成链接时没有返回本地要保存的 applicantId，所以此时 journey_id 通常为空，之后解析回调资料时补充。

前端拿到的是 verification_id、provider、state、url、expires_at、process_id。只有这一组响应中的 URL 和绑定才是一对。

4.5 重复请求、重新认证和失败

  • 同一 request_id、相同目标/流程/表单/渠道/代次且绑定仍有效时，复用原绑定；已有链接直接返回。
  • 外部请求失败后保留本地预留信息。条件仍一致且未到期时，用原请求 ID 重试，沿用原业务号。
  • 主动发起新认证使用新请求 ID，新建绑定及业务号；同一目标、同一表单未提交且未失效的旧绑定被标为 superseded。
  • 原请求不能跨目标、渠道或代次恢复。过期/终态绑定不能继续作为生成链接的重放请求。
  • expires_at 表达链接有效期，不能把它当成“第三方必须在此时审核结束”的期限。该版 refresh 没有仅凭当前时间自动把 pending 改为 expired。

5. 节点二：客户打开链接完成第三方认证

客户在本次返回的第三方页面完成证件拍摄、活体、地址证明等配置要求。这一步的申请人、审核状态、OCR 资料、图片先存在供应商系统。

对 Sumsub 主链路而言，客户点击完成、关闭窗口或网页跳回系统，都不会因此直接把本地绑定改成 passed，也不会仅凭浏览器事件生成 t_kyc_user_content。

pending 在链接生成后已经存在，不足以证明用户已上传或 Sumsub 正在人工审核；它只是本地尚未取得可办理结果的状态。

客户打开旧链接完成的认证，产生的是旧链接所关联的业务号结果，不能拿来更新刚生成的新绑定。

6. 节点三：回调如何精确找到本次绑定

Sumsub 沿用旧服务器回调入口：

1POST /api/kyc/kyc_webhook

入口没有改成 /api/kyc/process/kyc_webhook。这是服务器间接口，依靠供应商签名验证来源，不使用会员 Bearer token。

6.1 先验签，再筛选完成事件

SumsubClient::callback() 对原始请求体计算 HMAC，与 x-payload-digest 比较，算法来自 x-payload-digest-alg。

Controller 只把下面的事件交给业务处理：

1type = applicantReviewed 或 applicantActionReviewed
2reviewStatus = completed

其他合法事件可以被接收，但不会进入本次审核结果处理。

6.2 通过 externalUserId 找会员和绑定

业务处理进入 SumsubService::handleSumsubReviewedWebhook()，读取回调的 externalUserId，然后调用 providerCallbackFormType(businessId, sumsub)。

后端用业务号中的会员前缀定位 t_kyc_member_other.member_id，再在该会员 JSON 中精确匹配：

1verification.business_id === callback.externalUserId

随后还要检查：

  1. 绑定属于当前 target_context_id。
  2. 绑定的 process_id 与当前目标一致；若已有流程，必须仍为本人进行中流程。
  3. 当前表单方式仍为 third_party，当前 provider 仍为 sumsub。
  4. 绑定的 selection_generation 等于当前表单选择代次。
  5. 绑定未提交、未失效，且还没有锁定通过/拒绝终态。
  6. 对 request check 还要核对重审请求及当前供应商审核轮次。

所以“externalUserId 一样”是必要条件，还不是全部条件。用户切换到人工或换了渠道后，晚到的旧通过结果不能覆盖当前办理状态。

新 _8 格式业务号即使找不到可用绑定，也会被识别为新流程业务并停止旧落库路径，避免误按会员维度写入其他正式表单。

6.3 收到回调的日志不等于绑定处理成功

Controller 在内部处理抛异常后会记录异常日志，之后仍可能返回成功响应。它也会对无需处理的事件返回成功。

因此必须分开核对“请求到达”“事件符合条件”“精确匹配绑定”“资料解析成功”“绑定实际更新”；只看到“收到 KYC 回调成功”不能证明这些步骤全部成功。

7. 节点四：解析结果并保存到哪里

7.1 Sumsub 不只是看一个 GREEN

整体 reviewAnswer=RED：记录拒绝及原因，不用某个子步骤 GREEN 覆盖整体拒绝，也不依赖成功补拉资料。

整体 reviewAnswer=GREEN：继续查询申请人资料与 requiredIdDocsStatus，按当前本地表单类型解析：

本地表单 对应 Sumsub 步骤 提取资料
POI，form_type=2 IDENTITY 及其数字后缀步骤 姓名、证件国家、证件类型、号码、生日、有效期、正反面图片等
POA，form_type=5 PROOF_OF_RESIDENCE 及其数字后缀步骤 居住国家、地址、邮编、日期及地址证明文件等

后端通过既有解析器把国家代码映射为本地国家值。图片按当前步骤的 imageIds 下载并交给既有上传组件保存，绑定中存图片/文件 URL，不把图片二进制塞进 JSON。

有整体 GREEN 但对应子步骤尚无可用结果、关键国家/姓名缺失，或查询解析异常时，仍可能保留 pending。对应子步骤明确 RED 则拒绝。

POI 还有平台国籍校验：证件国家必须能规范化，并在 t_country 中满足 is_nationality=1、deleted_at=0。不满足时绑定转拒绝，原因为 KYC_NATIONALITY_NOT_ALLOWED。

7.2 结果写入控制 JSON

KycProcessService::recordProviderCallback() 先锁会员行和 KYC 附属行，再次检查目标、流程、渠道和代次，更新同一认证对象：

JSON 字段 写入内容
state passed、rejected 或 pending
provider_result_at 当前 PHP time()，即本机采纳结果的记录时间
journey_id Sumsub applicantId
provider_attempt_id 已解析的审核轮次
provider_step 对应第三方步骤名称
provider_values 服务端解析的正式提交候选资料及图片 URL
document_name POI 证件完整姓名
document_country POI 证件国家
poa_country POA 证明中的居住国家
personal_country 处理 POA 时计算的本轮个人信息居住国家
rejection_reason 拒绝原因（有时才提供）

同时保存整份 kyc_link_json 并更新该行 update_time。这里列的是条件字段，不是每次回调都会补全所有字段。

provider_result_at 初次预留时没有写入；进入结果记录时，即使结果还是 pending，也可能写入。所以排查时要联合看 state、provider_values、provider_result_at，不能只凭一个非零时间判定通过。重复终态或失效结果不会正常推进它。

7.3 此时哪些表还没有写

对这条 Sumsub 新流程结果而言，回调处理不会直接创建 t_kyc_user_content，不会创建 t_kyc_process，不会把会员改成已认证，也不会仅因候选结果 passed 就记一条正式步骤自动通过日志。

recordProviderCallback() 对 t_member 的行锁是为了并发互斥，不表示这时修改了会员资料。

7.4 一次 Sumsub 认证同时覆盖身份和地址

代码允许解析同一次返回的另一个步骤；只有能够明确对应本轮唯一表单、没有已有内容或独立认证、没有人工选择及重提要求等冲突时，才创建关联候选绑定。

  • 独立 POA/POI 子步骤的关联候选仍先保存在控制 JSON，不因回调直接正式提交。
  • 没有独立 POA 步骤时，可以提取当前身份证件自己的居住地址，先保存 poi_address_result 候选，不能用证件签发国代替居住国家。
  • 身份含地址自动通过 POA 还要求规则 auto=1 且 poi_address_auto_pass=1。必须等 POI 完成姓名确认并正式通过、文件/必填字段完整、国家一致且不覆盖已有独立资料，才在同一提交事务里写 POA 内容、客户文件及相关日志。
  • 国家不一致时只保留候选，进入国家决策。

关联候选有自己的 verification_id，但可能通过 source_verification_id 引用原认证，而不直接拥有新的 business_id。不能强行要求每个关联候选都有一条独立供应商申请。

8. 节点五：refresh 查什么，为什么 required_action 会为 null

请求：

1POST /api/kyc/process/refresh
2Authorization: Bearer <当前会员token>
3Content-Type: application/json

1{
2  "verification_id": "<本次kyc_link返回的认证UUID>"
3}

8.1 查询路径

1当前登录会员
2  → t_kyc_member_other.member_id
3  → kyc_link_json 中 __process_v1.state
4  → verifications[请求的 verification_id]

它不会根据“某会员最近一张通过表单”来推断本次绑定通过，也不会扫描 t_kyc_user_content 找一条人工造的数据来替代供应商结果。

没有这个对象就报 KYC_VERIFICATION_NOT_FOUND；对象存在但目标、审核代次、方式、渠道或流程不再适用时，返回状态可被映射为 superseded，不继续提供确认/提交动作。

8.2 普通认证与补偿查询的边界

情况 refresh 实际处理
普通 Sumsub 新认证 主要读取本地绑定，等待 Webhook 更新；没有普遍地每次调用 Sumsub 查询
Sumsub 已发起 request check，pending 且不处于 preparing 复用供应商结果解析入口主动补查当前 applicant/审核轮次，可更新本地绑定
Zoloz reserved/pending 且已有 provider_business_id 读取已有 t_identify 查询结果，尝试补入绑定；不在这里主动调用 Zoloz
普通 IDWise 新认证 读取绑定，依赖其 Webhook 结果写入

因此，普通 Sumsub 认证如果回调始终未能更新该绑定，连续请求 refresh 也可能始终得到 pending。

8.3 required_action 是当前下一动作

有效绑定状态/条件 required_action 前端应做什么
pending null 按 retry_after=5 秒继续查询
普通 rejected null 看拒绝原因及允许动作；可用时 request check
POI 平台国籍拒绝 nationality_rejected 提示国籍不允许；不能用重审绕过
superseded/expired null 重读 myinfo，不继续操作旧绑定
passed，POI 姓名尚未确认或确认基准已变化 poi_name_confirm_required 执行姓名预检、确认
passed，POA 国家不一致/缺失 poa_country_decision_required 执行国家决策
passed，必要确认/校验已完成 submit_verification 调用 saveinfo(mode=verification)
submitted null 结果已正式提交，重读 myinfo 看实际表单审核状态

required_action=null 本身既不能说明通过，也不能说明失败，必须同时看 state。

refresh 不直接返回完整的 provider_values。它返回供前端办理的姓名、国家、原因、流程版本和下一动作，正式提交时服务端再从同一绑定取可信资料。

9. POI 通过后的姓名确认和正式提交

9.1 name_preview 只读预检

接口：POST /api/kyc/process/verification/name_preview。

客户提交拆分的 first_name、last_name，后端确认绑定 passed、目标/流程/渠道/代次有效、版本正确及国籍允许，然后核验：

  • 姓和名都不能为空。
  • 拼接后必须等于第三方证件完整姓名。忽略空白、大小写，允许姓/名拼接顺序互换；不移除中点、连字符或改写内部字符。
  • 再逐个比较拆分结果与本轮个人信息中的姓、名，返回 name_mismatch。

个人姓名优先读取同一 process 的个人信息内容，没有时才回退会员姓名。该接口不写数据库，不推进版本。

9.2 name_confirm 保存客户的选择

接口：POST /api/kyc/process/verification/name_confirm。

选择 decision 写入表单控制状态 后续正式表单结果
接受证件拆分姓名 use_confirmed_name name_confirmation=confirmed，保存拆分姓名、当前个人姓名比对基准，requires_manual_review=false 资料完整时可通过；正式 POI 提交时同步本轮个人信息姓名
保留当前个人姓名，转人工核验 keep_current_name_manual name_confirmation=manual_review，保留证件拆分，requires_manual_review=true，原因 poi_name_mismatch saveinfo 写人工待审内容

姓名一致时仍要确认，采用 use_confirmed_name；这时不能选择“不一致转人工”路径。

这些选择写在 state.forms[目标ID:表单ID]，并在 state.receipts 保存幂等回执。确认动作不会把认证绑定改为 submitted，也不会立刻覆盖 t_member.first_name/last_name。

已有流程时增加 t_kyc_process.version。若姓名不一致且采用证件姓名，本轮已经通过的协议内容会被置为拒绝并注明 KYC_CONTRACT_RESIGN_REQUIRED，要求重新签署；同时记录 contract_resign_required 流程日志。尚未创建流程时仅保存控制状态。

如果确认以后个人信息姓名又变化，refresh/saveinfo 会检查旧比对基准并要求重新确认，不能用旧确认覆盖新姓名。

9.3 saveinfo 才是正式入库动作

接口：POST /api/kyc/process/saveinfo，传 mode=verification 和同一个 verification_id，并携带当前目标、表单、版本及新的提交 request_id。

后端使用绑定的 provider_values，不采信前端自行上传的“第三方已通过”字段或篡改后的证件资料。重新核对绑定和姓名/国家条件后，在事务中处理：

  1. 如果本轮尚无 process，创建 t_kyc_process，source_type=1、process_status=1、effect_status=0，并把当前目标下未失效的预认证绑定关联到此 process。
  2. 如当前表单已有待审/拒绝内容，将原记录 is_last=0，保留历史证据。
  3. 新增 t_kyc_user_content：写 process_id、form_id、kyc_config_id、kyc_content、kyc_form_detail_snapshot、journey_id、is_last=1 等。
  4. 若可信资料和所需证明完整，且没有保留姓名转人工的选择，写 kyc_status=9、kyc_audit_method=实际provider、kyc_visit_time=当前时间。否则写 kyc_status=1、kyc_audit_method=manual；第三方 passed 不绕过本地资料完整性要求。
  5. 对有文件的 POI/POA，写/更新 t_customer_file：origin_table=kyc_user_content、origin_id=新内容ID，文件类型为 2身份证明/1地址证明，记录 files_json、status 和审核人等。POA 受既有文件额度及锁控制。
  6. 采用证件姓名时，同步本轮个人信息 t_kyc_user_content.kyc_content 的姓名；此时不直接改旧生效资料。
  7. 记录 t_kyc_process_log 的 client_submitted；真正自动通过时再记 third_party_approved。身份证地址补齐 POA 有 poi_address_filled、poi_address_approved。
  8. 更新过程版本、最近提交/审核时间和审核汇总状态；完成条件满足时激活本轮。
  9. 同一绑定改为 state=submitted，写 process_id、content_id；保存提交回执，防止同一请求重复写表单。

refresh.state=submitted、applied=true 只证明第 9 步已完成。 若走人工待审分支，表单仍为 status=1。实际状态应重新读取 myinfo.steps[].status。

9.4 整轮什么时候生效

仅当当前规则要求的所有表单都有本轮当前内容并且均为 9，才会：

  • 将本轮 t_kyc_process 改为 process_status=9、review_status=9、effect_status=1，写 activated_at、ended_at、kyc_profile_snapshot。
  • 将此前仍生效的完成流程改为 effect_status=0 并记录 superseded_by_process_id。
  • 将本轮最终姓名、居住国家、国籍、生日、地址、规则等投影到 t_member，写 KYC 已认证状态。证件号通过既有敏感字段服务处理，主表/影子字段的写法由该服务模式决定，不能简单理解为此方法直接写 identity 明文。
  • 将监管类型及 KYC 快照投影到 t_member_other；可用时同步证件图片。
  • 记录 process_activated 日志，事务完成后沿用既有成功通知。

saveinfo 完成后还会刷新会员 KYC 总状态与 t_kyc_member_summary 申请/审核汇总；存在 effect_kyc_id 列且认证状态为 9 时同步 t_kyc_member_other.effect_kyc_id。

如客户已有旧生效档案，新轮尚未完成不代表会员一定降为未认证；总状态计算优先保留有效通过资格。整轮资格与当前某一张表单的状态仍是不同层次。

10. POA 国家不一致与失败重审

10.1 POA 国家判断

第三方返回的 poa_country 与本轮个人信息国家经 t_country 规范化后比较，不只比较 t_member 的旧投影值。

国家一致才可进入正式提交；国家不一致时 required_action=poa_country_decision_required，调用：

1POST /api/kyc/process/verification/poa_country_decision
客户选择 decision 主要处理
保留个人居住国家，重新提交 POA keep_personal 当前 POA 退出可用状态，要求新证明，清除旧证明预填，切到人工重提并增加代次；仅同源关联的 POI 按规则一并要求重提，独立 POI 不因而重置
采用 POA 国家并重置 KYC use_poa 当前目标认证全部失效；已有本人流程终止，新建目标上下文，暂存 personal_country_override，process_id=null；各步骤重新正式提交

第二种选择不是此时立刻创建新 process 或直接更新会员有效国家；待新轮正式办理并最终通过后，才按新轮资料投影。原生效档案不在这一决策时点被覆盖。

人工 POA 提交时国家不一致直接报 POA_COUNTRY_MISMATCH，不会套用第三方双选后仍提交旧认证结果。

10.2 Sumsub request check

这是 POST /api/kyc/process/request_check，用于绑定 rejected 且服务端返回 can_request_check=true 的场景。

  • 不创建一笔新认证，也不换成新 externalUserId；复用该绑定或其源绑定的 business_id/applicant。
  • 先记录 recheck 状态及此前 attempt/reviewDate，再向 Sumsub 请求同一 applicant 的 /status/pending。
  • 成功受理后绑定回到 pending，等待本次新审核结果。超时等结果不确定情形记 unknown，不盲目重复发送。
  • 回调及 refresh 补查均核对当前 applicant、externalUserId、新审核轮次或更新的 reviewDate；旧 RED 通知不能直接把新轮判回失败。
  • 结果再次解析为 passed 后，继续姓名/国家确认及正式提交，不跳过上述业务步骤。
  • 平台 KYC_NATIONALITY_NOT_ALLOWED 拒绝不允许通过 request check 绕过。

13. 用一笔认证检查每个节点是否接上

假定本次响应给前端的绑定为 V1，对应服务端业务号 B1：

 1kyc_link：V1 → B1 → URL1
 2用户认证：打开 URL1
 3回调：externalUserId=B1
 4本地保存：verifications[V1].state=passed
 5          verifications[V1].provider_result_at=本次记录时间
 6          verifications[V1].provider_values=本次审核资料
 7refresh(V1)：passed + poi_name_confirm_required
 8name_preview / name_confirm：保存 V1 所属表单的姓名确认
 9refresh(V1)：passed + submit_verification
10saveinfo(V1)：写正式内容 C1，绑定变 submitted，关联 process_id=P1/content_id=C1
11myinfo：读取 P1 本轮表单的实际审核状态

异常时按此顺序区分：

  1. V1 根本不存在：没有生成绑定、登录会员不一致、目标控制数据已变化等，不能拿第三方交易号代替 UUID。
  2. V1 有，回调却是旧 B0：旧页面/旧链接产生的认证，不会自然更新 V1。单凭同一会员或同一数据库不能混用。
  3. 回调为 B1，V1 仍 pending：查完成事件、签名、匹配条件、资料拉取与步骤解析，不只看“收到回调成功”日志。
  4. V1 passed，但没有正式 content：如果客户还没姓名确认和正式提交，这是该设计允许的中间状态。
  5. V1 submitted，content 是待审：可能是保留姓名转人工或证据不足，不能把 applied=true 当审核通过。
  6. 手工向 t_kyc_user_content 插入一条 9：不会自动生成 V1/B1 的关联或更新绑定。它可能干扰当前内容、流程状态和后续提交校验，但不能替代真实第三方回调。
