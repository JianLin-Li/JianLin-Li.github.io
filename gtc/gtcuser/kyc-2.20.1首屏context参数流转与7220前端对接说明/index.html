Kyc 2.20.1首屏context参数流转与7220前端对接说明

2026-11-13 项目：gtcuser

KYC 2.20.1 首屏 context 参数流转与 #7220 前端对接说明

整理日期：2026-11-13。代码核对基线：gtcuser / feature/v2.20.1/kyc_process-jalen / d52946bc7。

本文说明前端进入 KYC 页面后，如何根据 context 返回结果选择下一接口，以及请求参数从哪个字段取得。此次只更新文档，不修改后端代码或数据库。

1. 先明确四类数据的用途

所有下文的 ctx 都指 /context 成功响应中的 response.data，不是整个响应包装。

1const response = await post('/api/kyc/process/context', {});
2if (response.code !== 200) {
3  // 停止依赖 context 的后续请求，沿用统一错误处理。
4  return;
5}
6const ctx = response.data;

POST /api/kyc/process/context 无请求参数，可以发送 {}。鉴权、语言、设备等 Header 沿用项目约定。

首屏字段 表示什么 如何使用
ctx.current 本人进行中的流程，正常为 source_type=1、process_status=1 进入当前表单时，把 current.process_id 作为 myinfo.process_id
ctx.target 服务端分配的可办理目标，首次正式提交前也可以存在 首次进入表单时，把 target.target_context_id 作为 myinfo.target_context_id；后续写操作也使用当前目标
ctx.effective 当前已生效的只读档案 查看详情时，把 effective.process_id 作为 history/detail.process_id
ctx.delegated 后台代客进行中流程提示 只展示提示；delegated.process_id 不传给本人办理接口，也不用于读取进行中代客详情
ctx.permissions.can_continue 是否存在本人可继续办理的流程或目标 决定是否提供办理入口；不表示所有步骤都可编辑
ctx.permissions.can_view_history 是否允许查看历史 决定历史入口；为 true 不代表一定有历史记录
ctx.member_kyc_status 会员整体认证资格 展示整体状态，不用它挑选 process_id 或决定步骤是否通过

current、target、effective、delegated 可以同时存在。例如旧档案继续生效，同时办理新目标。本人和代客也可以各有一条进行中流程。delegated.exists=true 不应关闭已存在的本人办理入口。

2. 下一请求的参数来源表

下列首屏请求没有 form_id、expected_version 等表单提交参数。

何时调用 下一接口（全部 POST） 请求体 请求值的来源
can_continue=true 且有本人进行中 current /api/kyc/process/myinfo { "process_id": "当前流程ID" } process_id = ctx.current.process_id
can_continue=true、current=null、target!=null /api/kyc/process/myinfo { "target_context_id": "当前目标ID" } target_context_id = ctx.target.target_context_id
点击当前生效档案，且 effective!=null /api/kyc/process/history/detail { "process_id": "生效流程ID" } process_id = ctx.effective.process_id
加载历史列表，且允许查看历史 /api/kyc/process/history { "page": 1, "page_size": 20 } 页码由前端分页状态提供；不传 context 中任何 ID
点击历史列表某一项 /api/kyc/process/history/detail { "process_id": "所点击的历史流程ID" } process_id = history.data.list[index].process_id
只有进行中代客流程、没有本人流程和目标 无本人办理请求 无 展示代客提示；可独立展示已有生效档案和历史

有当前流程时，myinfo 只传 current.process_id 就够了；如同时传 target_context_id，两者须来自同一次最新上下文。当前代码优先解析 process_id，不要把双传理解为服务端会额外核对两者一致性。

myinfo 也允许发送 {} 自动查找当前流程。为便于联调追踪，本文建议首屏根据 context 显式选取参数。不是后端禁止无参调用，而是前端不应在没有办理入口时仍无条件加载编辑页。

3. 首屏请求流程图：每个分支都标明参数来源

图中实线表示本人办理接口的分支。虚线表示独立展示区域，允许与本人办理卡片同时出现；不是必须把所有详情接口一次请求完。effective 有值时可以先只渲染卡片，用户点击后再请求详情。

can_continue=false 不等于历史为空。即使 current/target/effective 全为 null，也可能存在失效或本人已终止流程，应通过 history 判断历史列表，而不是直接隐藏所有档案。

4. 三种最常见情况的完整请求示例

4.1 首次办理：还没有 process_id

首屏关键返回示例：

 1{
 2  "current": null,
 3  "target": {
 4    "target_context_id": "ctx-new-example",
 5    "process_id": null,
 6    "kyc_config_id": 67
 7  },
 8  "effective": null,
 9  "permissions": {
10    "can_continue": true,
11    "can_view_history": true
12  }
13}

下一请求：

1POST https://test.gtctrader1203.top/api/kyc/process/myinfo
2Content-Type: application/json
3
4{
5  "target_context_id": "ctx-new-example"
6}

这里使用 context.data.target.target_context_id。kyc_config_id=67 是规则 ID，不是流程 ID，不能传给 myinfo.process_id。尚未创建正式流程是正常情况，不需要前端创建流程，也不能取其他历史流程 ID 补上。

4.3 已全部通过：#7220 账号对应的情况

上一轮只读数据库核对：测试账号 103111205@max.com，会员 730103832，流程 3827 为 source_type=1、process_status=9、review_status=9、effect_status=1，五张表单均通过。本节引用上一轮核对结果，本轮没有重新查询或修改该账号。

对应首屏应按以下关键字段理解；此处为依据已核对状态和当前代码整理的结构示例，不冒充本轮线上 HTTP 抓包：

5. myinfo 成功后，后续表单操作的参数从哪里来

先完成首屏分支，再处理表单。不把 context 字段和上一次页面缓存混用。下表适用于已进入本人办理页，具体接口的必填项仍以主接口文档为准。

后续请求参数 推荐来源 注意
target_context_id 最近成功的 myinfo.data.target.target_context_id 首屏初始来源为 context.data.target.target_context_id；目标重置后替换，不沿用旧值
process_id 最近成功的 myinfo.data.process.process_id 首次为 null；首次 saveinfo 成功后采用返回的新 ID，并重新读取页面
expected_version 最近成功的 myinfo.data.process.version，后续使用相应业务动作返回的新 version 尚无正式流程时为 0；前端不自行加一
config_revision 最近成功的 myinfo.data.target.config_revision 接口支持时原样回传，不自行构造
form_id 当前选中步骤的 myinfo.data.steps[index].form_id 不是 form_type、不是 content_id
edit_context_id enter_edit/resubmitinfo 返回值或当前步骤返回的编辑上下文 属于当前目标和当前表单
base_content_id enter_edit/resubmitinfo 返回的 base_content_id 用于当前内容重提，区别于历史来源 ID
source_content_id 当前步骤 reuse.source_content_id 或编辑入口返回值 只在对应复用/编辑场景使用
verification_id 当前步骤 verification.verification_id 或本次 kyc_link 返回值 /process/refresh 只接收该认证绑定 ID，不能传流程 ID

如果 myinfo 虽然返回当前步骤，但 target=null，不要猜目标 ID 或开放写操作。当前流程与目标上下文可能存在数据或部署问题，应反馈后端核对。

按钮应结合 steps[].ui_state、available_actions、permissions；有本人进行中流程不代表每张表单都能编辑。待审核和已通过步骤可能只读。

6. 审核完成、目标变化和页面刷新时，必须重新分流

后台可能在 context 成功后、myinfo 请求到达前完成审核。因此前端即使第一次参数选对，也可能收到 KYC_PROCESS_NOT_EDITABLE。这时重新读取 context，按最新状态切换只读档案即可，不能持续重试原 process_id。

推荐处理顺序：

 1myinfo 或写接口返回 KYC_TARGET_CHANGED / KYC_PROCESS_NOT_EDITABLE
 2    ↓
 3取消旧目标的未完成读取、轮询和后续自动操作
 4    ↓
 5使旧页面上下文失效，不把旧 ID 作为默认回退值
 6    ↓
 7POST /api/kyc/process/context，{}
 8    ↓
 9按本文流程图重新选择接口和参数
10    ├─ 有 current：myinfo.process_id = current.process_id
11    ├─ 仅有 target：myinfo.target_context_id = target.target_context_id
12    ├─ 无本人办理入口、有 effective：history/detail.process_id = effective.process_id
13    └─ 无本人办理入口：展示代客提示、历史或空态

恢复时先查一次 context。如果仍失败，停止自动恢复并显示可重试提示，不创建无限的 context → myinfo → 错误 → context 请求循环。旧异步响应晚到时，也不能覆盖重新加载后的新页面状态。

KYC_VERSION_CONFLICT 同样先重读当前上下文及页面；不要仅换新版本就自动重发旧业务请求。正式提交超时但结果未知时，保留原 request_id 和原参数以便按既有幂等契约查询/重放，不能为了“刷新页面”随意换 ID 重交。

如果 /context 本身返回 code=10000、message=KYC_TARGET_CHANGED，前端应停止依赖它的请求并反馈后端。该接口无业务请求参数，不能把它归因为传错 process_id；需要结合实际 Request URL、请求时间和 request-id 查服务端。

7. 原接口文档中容易误读的位置

主接口文档为 KYC-2.20.1用户API最新接口文档-20261105.md。

  • 第 3.1 节定义 context 字段；第 3.2 节规定 myinfo 只能显式读取本人进行中流程。
  • 第 7.1、7.2 节定义历史列表和只读详情。
  • 原第 8.1 节只列 context → myinfo，没有在请求顺序旁写出每个分支的参数来源，容易被误读为无条件连续请求。本次已补齐。
  • 第 9、10 节中的“重读 context/myinfo”应理解为“先 context，再按状态决定是否 myinfo”，完成后应切换历史详情，而不是继续请求旧编辑流程。

8. 前端联调验收

场景 应观察到的请求
首次尚未正式提交 context → myinfo，参数只取 target.target_context_id；无须已有 process_id
本人流程进行中 context → myinfo，参数取 current.process_id
当前流程待审核，后台尚未完成 刷新 context 后仍有 current，再用 current.process_id 读 myinfo；按步骤权限展示
后台全部审核通过 刷新 context 后没有 current/target，查看生效档案用 effective.process_id 调 history/detail
旧档案生效，同时有新目标 生效档案与新办理入口均展示；各自使用 effective.process_id 和 current.process_id/target_context_id
本人、代客流程同时存在 本人继续办理，代客单独提示；不会把 delegated.process_id 传给 myinfo
无生效档案，但有本人终止历史 history 返回记录；点击列表项 process_id 调 history/detail，仅展示实际保存部分
context 本身业务失败 不继续请求 myinfo，不用旧缓存补 ID；保留错误信息反馈
首屏与详情请求之间流程刚好完成 旧 myinfo 被拒后只做有界重读，切换只读；无无限循环

本说明核对了当前 Controller、Service 的目标解析和 Repository 的流程范围。没有在本轮执行线上 HTTP 抓包，也没有把文档说明当成 test 环境功能验收通过证明。
