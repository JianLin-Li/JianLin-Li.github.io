1. 结论与验收边界

修改前并非已经完整满足需求。最明显的遗漏是 PRD 新增 6.6：“个人信息被后台驳回重提，但本轮 POI 已通过”的姓名冲突处理。此前实现的“第三方 POI 首次通过后确认姓名”不能代替这个场景。

本次已在现有 Controller / Service 中补齐姓名重提双分支、POI 确认姓名的当前个人信息同步、POA 决策前的后续步骤阻断、保留国家后的新证明强制重传、更新国家后的重置预填，并修正普通表单审核配置和用户端整轮生效时的姓名、国家、规则、快照及首屏入口。没有新增业务类或表。

当前结论是：姓名、国家的用户 API 决策规则已补齐主要已确认场景，并通过隔离测试；整项 KYC 仍不能认定可直接上线。 第 7 节列出了协议签署、证件约束、客户文件、日志和回调边界等独立缺口。这些事项没有被本次测试覆盖，也没有被“单步 status 正确”自动解决。

4. POI 姓名：必须分清两种业务场景

4.1 第一次第三方 POI 通过

前端拿到可信第三方 passed 后，先确认国籍，再展示证件完整姓名及姓、名输入。用户可以调整拆分，但不能丢掉中点、连字符等字符。

调用顺序：

  1. POST /api/kyc/process/verification/name_preview：只读校验，返回按证件国籍拼接的双方姓名及 name_mismatch。
  2. 一致时不显示双选，确认后提交 name_confirm；不一致时默认“更新个人信息姓名”。
  3. POST /api/kyc/process/verification/name_confirm：use_confirmed_name 或 keep_current_name_manual，保存决策并返回新版本。
  4. 必须继续 POST /api/kyc/process/saveinfo，带该版本、相同 verification_id、mode=verification 和新的 request_id。不能把 name_confirm 成功当作 POI 已经正式提交。
选择 本轮个人信息内容 本轮 POI 内容 旧会员资料
采用确认的证件姓名 正式 POI 提交时同步确认后的姓/名 证据齐全则 9；缺字段/文件则人工待审 新整轮生效前不变
保留当前个人姓名 不变 保存用户确认的证件姓/名及第三方资料，1/manual 不变

name_confirm 与正式提交是两个已有写接口，本次没有改成新接口或一次重构；前端需要完成这个串联。第二个请求失败应停留当前页重试，不能先跳下一步。

4.2 个人信息驳回重提，而身份信息已经通过（新增 PRD 6.6）

例：本流程个人信息被后台驳回，用户本次输入 NEW / NAME，本流程已通过 POI 为 SAN / ZHANG。

首次提交仍是 POST /api/kyc/process/saveinfo(mode=edit)。服务端查本流程 is_last=1,status=9 的 POI：

  • 一致：正常重交个人信息，按规则决定自动/人工，POI 保持通过。
  • 不一致且未选：返回 submitted=false,required_action=personal_name_decision_required,name_conflict；内容、版本和回执均不变。
  • 选择 personal_name_decision=use_poi_name：个人信息用 SAN / ZHANG 重新提交，POI 保持通过。
  • 选择 personal_name_decision=keep_personal_name：保留 NEW / NAME；原 POI 9 记录保留但 is_last=0，新 POI 为 1/manual；旧第三方绑定失效，其余步骤不变。

前端弹窗默认“使用身份信息中的姓名”；失败保留填写内容和选项。此场景不调用第三方、不调用姓名拆分接口。POI 异常缺失姓名时直接阻断，不能把个人信息覆盖成空值。

5. POA 国家：前端动作与数据库变化

5.1 人工提交

POST /api/kyc/process/saveinfo 内比较本轮个人信息国家与 POA 国家。China/CN/CHN 统一识别为同一个国家，未知国家不猜测。不一致返回 POA_COUNTRY_MISMATCH，不创建新内容、不变更会员资料。

App / Web 应在国家字段后常驻显示“与个人信息居住国家需保持一致”，不使用仅悬浮提示。API 提供 country_consistency.personal_country/hint_key，文案需前端落实。

5.2 第三方不一致：保留当前国家

例：本轮个人国家 China，POA Germany，默认 keep_personal。

  1. POST /api/kyc/process/verification/poa_country_decision 保存决策。
  2. 第三方返回的地址等数据预填，POA 国家覆盖为 China，清掉旧证明文件；旧认证 superseded。
  3. 本轮 POA 恢复待提交；前端回到 POA，要求重新上传。
  4. POST /api/kyc/process/saveinfo(mode=edit) 使用返回的新版本和新请求 ID；旧证明不能直接复用，也不能混入新文件；不能切回第三方绕过。
  5. 新内容进入人工待审。此前步骤不变；关联 POI 的复合认证例外仍待可信关联方案。

国家决策完成前，myinfo.blocking_action 指向该 POA；按 sort,id 排在它之后的步骤为 blocked_by_poa_country。后端拒绝绕过 UI 直接办理这些步骤。

5.3 第三方不一致：使用 POA 国家

例：用户选 use_poa，采用 Germany。

数据位置 变化
旧进行中 t_kyc_process process_status=-2,effect_status=0,termination_reason=poa_country_reset；保留历史
__process_v1.state.target 新 UUID、目标代次递增、process_id=null,personal_country_override=Germany
原 target 对应认证 全部 superseded；旧绑定不可提交到新目标
新 target 表单状态 全部待提交；相同表单已通过资料只作为预填，不复制审核状态

t_member.country 与旧生效档案 新整轮生效前保持旧资料；这是沿用此前已确认的资格隔离方案

响应原 process_id/version 属于被终止的旧流程，新增 next_process_id=null,next_version=0，前端必须切换到新目标后从个人信息重新办理。国家不是监管选择：继续使用管理员原来指定的目标规则。

7. 尚不能作为“完整已上线功能”的事项

7.1 用户 API：协议正式签署链路缺失（上线阻断项）

证据：旧 app/Service/crm/KycService.php::saveInfo 对字段类型 agrement 生成签名 PDF，创建协议签署记录和安全活动记录；新 KycProcessService::validateSaveValues/saveInfo 仅筛选值、校验必填并保存，没有调用对应签署逻辑。

影响：协议步骤 status=9 或“要求重签”只代表流程状态，并不能证明生成了新姓名下的签署 PDF。前端传入任意非空值也不能被视为签署证据。

最小修补方案：仅在新流程协议步骤正式提交时调用既有 PDF 能力，签署资料从本轮个人信息读取；沿用 contract_agreements 及既有活动日志表，不新增协议体系。签署副作用必须绑定 request_id 和目标/流程，生成失败不允许推进步骤；事务外文件生成和事务内确认要有重试复用，禁止重复签署。历史未改协议的只读复用可保留；姓名变化后的重签须生成新记录。该项本轮尚未实施。

7.2 用户 API：证件唯一性与完整个人资料投影尚未等同旧逻辑

证据：旧提交调用 TMemberService::checkIdOfUserNum；新 validateSaveValues 不是完整的表单类型校验，当前新提交链没有这一校验调用。本轮只补了姓名、国家和规则/监管/档案投影，没有引入敏感证件写入、生日/地址/企业信息等全字段投影，也没有调用旧成功通知。

最小修补方案：在正式 POI 接收的可信资料及人工填写资料上复用既有证件数量/唯一性规则；全部通过时按字段白名单调用现有敏感信息服务，不直接明文写证件字段。个人信息作为姓名的权威来源，不能由 POI 的不一致姓名覆盖“保留个人姓名”的选择。成功通知应在事务提交后按流程幂等发送。不要直接调用旧 checkUserKycStatus 代替整个新流程生效，旧方法包含旧配置查询和外部通知。

需要补联调：个人信息被驳回后同时修改居住国家，而本轮 POA 已通过的组合场景；应确认要求阻断个人信息国家变更还是重置 POA。当前国家校验集中于 POA 提交/决策，不能把此逆向修改场景计为已验收。

7.3 用户 API 与管理端：客户文件目录 / POA 额度口径需要统一

证据：本轮新流程提交没有向 t_customer_file 写用户 POI/POA 来源目录；现有 AddressProofFileService 仍统计旧 t_address_proof 和历史 KYC 内容，而 Eric 最新 SQL 已将旧独立地址证明表标为废弃。管理端直接创建的 t_customer_file 附件不一定被用户侧旧统计覆盖。

影响：用户资料可能不出现在新管理端客户文件列表；两端文件数量显示和 15 份上限可能不一致。现有数量检查不能宣称已经和 Eric 的新文件体系联调通过。

最小修补方案：以 (member_id,origin_table,origin_id,file_type) 对新提交内容投影客户文件，资料状态与审核状态同步；保留 KYC 原始内容为证据。额度与后台统一到同一来源、删除/拒绝口径及客户锁；旧数据迁移后不能将旧表和新目录重复相加。新目录缺少新用户资料时先补该来源，不能靠补计数掩盖目录丢失。

这会涉及现有公共额度服务，按最小范围另行修补和独立回归；本轮未改共享统计，未执行迁移。

7.4 用户 API：流程业务日志未完整写入

证据：新用户流程 Service 尚未写 t_kyc_process_log，而 Eric SQL 定义了客户提交、系统自动审核等 operator_type，后台历史日志读取这张表。

最小修补方案：正式提交事务内追加当前步骤日志，自动通过与普通提交分清事件；姓名保留导致 POI 转人工、国家重置导致终止应记录原因。通过既有提交回执防重放，不记录证件号、原始供应商报文或完整输入资料。无需新建日志表。

7.5 Eric 管理端：人工最后一步通过后的整轮生效

本轮不改 gtc_admin、gtc_admin_vue。需要 Eric 验证：

  • 本人流程按 process_id + is_last 重算，不跨轮拼表单；全部通过才冻结和生效。
  • 最终姓名采用本轮个人信息，不能在“保留个人姓名”后被 POI 姓名覆盖；本轮姓名更新不应污染旧生效内容。
  • 整轮切换与会员资料、规则、监管、快照写入应在同一事务；文件目录、额度、日志保持同一口径。
  • source1/source2 并行时，实时生效档案与冲突基线变化要处理；本人完成不应静默编辑代客草稿。

用户侧当前已把确认姓名同步到本轮个人信息内容，避免管理端只见到旧内容，但这不等同于后台所有激活投影已经验证通过。

7.6 按用户既定指示保留的回调范围

本轮未修改 recordProviderCallback 及供应商回调控制器。以下仍不算完成：同次认证覆盖 POI+POA 的关联重置、身份含地址自动 POA、Sumsub 失败后的 request check、Zoloz 新流程接通。

复合认证必须有可信的同次认证标识和具体覆盖表单，不能按同会员、同供应商推断。旧 target / 旧 generation / 已终止流程的迟到回调，需用真实已脱敏样本验证不会恢复通过。

8. Eric 最新 SQL 的实际影响

本地比较 HEAD..origin/feature/v2.20.1/kyc_process，差异只有 scripts/v2.20.1/kyc_process.sql，没有额外 PHP 差异。本报告按本地已拉取的远程引用分析，不声称它之后远程不会更新。

本次 SQL 增量为：

  1. 给 t_address_proof 增加“废弃，现放客户文件表”的注释。注释不迁移数据、不自动改变任何旧统计代码。
  2. 补后台客户文件、资料日志、代客流程操作的菜单/权限项。
  3. 菜单 INSERT 改用 follow_crm_gtc.t_menu 硬编码库名。

因此这次 SQL 更新没有新增姓名或国家决策字段，本轮无需因此扩表。原有 process / user_content.process_id / customer_file / process_log 架构继续使用。

发版注意：这是包含历史建表、加列及固定 ID INSERT 的初始化脚本，不是可安全重复执行的增量脚本。staging 已有表时不能整份重跑。由 Eric 根据目标库已有结构和菜单记录整理实际待执行增量，并核实硬编码库名及菜单 ID 冲突。本轮没有合并该 SQL，也没有执行它。

server_id、uk_legacy_key 的去除沿用用户此前已确认的 Eric 决策，不重新当作本轮设计缺陷；代码/字典残留由 Eric 清理。

另外，当前 gtcuser 数据字典的 t_kyc_user_content 定义仍未列出业务代码已广泛使用的 is_last，也未列出流程维度复合索引。不能据字典缺失推断 staging 没有这些列；发版时应核对实际结构并由 Eric 同步最终字典。本轮没有读取 staging 结构。

10. 接下来按最小修改推进的顺序

当前姓名/国家补丁先由用户审核；提交由用户手动完成。建议 gtcuser 提交说明：KYC: 补齐姓名重提决策和POA国家校验。
