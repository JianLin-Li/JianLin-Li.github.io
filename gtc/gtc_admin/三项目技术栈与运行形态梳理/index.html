三项目技术栈与运行形态梳理

2026-10-27 项目：gtc_admin

GTC 三项目技术栈与运行形态梳理

梳理日期：2026-09-30。

分析对象：gtc_admin、gtc_admin_vue、gtcuser 当前本地工作区。

本次未修改业务代码，仅新增本分析文档。结论来自项目规范、依赖清单与锁文件、已安装依赖元数据、启动入口、配置、代表性业务调用链和数据字典。未启动服务、执行业务任务、连接数据库或第三方服务，也未验证生产部署。下文的“已配置”“代码存在”不等于生产已经启用。

1. 总体结论

三个项目组成管理前端、管理后端和客户侧业务后端。两个后端同时涉及 CRM、MT、资金、KYC、跟单、PAMM、返佣和风控，职责通过具体入口和调用链区分，业务名称并不互斥。

项目 主要定位 核心框架 运行形态 交付物
gtc_admin_vue CRM/交易管理后台前端 Vue 3、Vite 4、Ele Admin Pro、Ant Design Vue 浏览器 SPA；开发时由 Vite 提供服务 dist/ 静态文件
gtc_admin 当前管理后台的主要接口及历史批处理入口 ThinkPHP 8 体系，本地 YKD 定制框架 生产 Web/FPM 请求处理；另有 CLI、队列及历史任务入口 PHP 源码、Composer 依赖、本地包、配置和文件资源
gtcuser 客户侧 API、交易业务及异步处理后端 Hyperf 3.1、MineAdmin 3.0、Swoole PHP CLI 常驻进程，提供 HTTP、Socket.IO/WebSocket，并承载队列与定时任务 PHP 应用及依赖；仓库包含 Docker/Compose 配置

2. gtc_admin

2.1 技术栈及版本依据

  • PHP：根依赖声明 >=8.0.0，项目协作规范明确 Web/FPM 运行环境按 PHP 8.0 兼容。
  • 框架：依赖清单声明 ThinkPHP 8，但实际由本地 ykd/framework 提供 think\\ 命名空间。根 Composer 配置使用 replace，替代上游 topthink/framework；本地包和当前安装包的 App::VERSION 均为 8.0.0。
  • 多应用：topthink/think-multi-app，当前安装版本 v1.1.1。
  • ORM：Think ORM，当前安装版本 v3.0.33；同时存在 Db::name()、动态连接和自定义查询扩展。
  • 鉴权：tinywan/think-jwt v1.5.0，配合后台会话、角色节点、数据范围、IP 白名单及登录限制。
  • 缓存与队列：默认 Redis 缓存、Think Queue Redis 驱动，当前安装 Think Queue v3.0.10。
  • 文件及文档：Think Filesystem、本地 ykd/think-filesystem、OSS、Easy Excel、TCPDF、FPDI；另有本地 PDF 相关资源。
  • 外部集成：MT 远程接口、Salesforce、支付与 Udun 钱包、KYC、短信、邮件、AI 翻译等。

这里必须把“ThinkPHP 8 体系”与“原版上游框架”区分开。框架维护和依赖安装需要保留本地包，不能仅按照标准 ThinkPHP 项目重新安装或升级。

依据：composer.json、本地框架包、项目规范。

2.2 请求入口与运行过程

  1. Web 入口为 public/index.php，加载 Composer 自动加载，再执行 ThinkPHP HTTP 应用。
  2. 支持多应用，默认应用配置为 api，管理后台主要使用 admin。
  3. 显式路由较少，url_route_must=false，主要采用 /应用/控制器/方法 自动解析。
  4. 后台基类配合语言、跨域、登录中间件解析用户和权限，加载会员、MT server、系统配置和数据范围，执行节点权限检查和操作日志。
  5. 项目响应通常是 {code, message, data}，业务成功码通常为 0。

生产形态是 Web Server 将 PHP 请求转交 PHP-FPM，执行请求后返回响应。与 Hyperf 常驻应用相比，代码更新、请求状态生命周期及进程管理方式不同。

依据：Web 入口、路由配置、后台基类、登录中间件。

2.3 分层与业务模块

规范要求新增后台业务采用：

1app/admin/controller -> app/service -> app/admin/model

当前代码保留历史结构，控制器中仍有直接数据库查询、状态处理和业务编排；也存在 app/admin/service、app/api/model 等既有目录。规范描述的是后续开发边界，不能据此认为现有代码已全部完成三层拆分。

主要业务包括会员与团队、后台权限和菜单、MT4/MT5 账户与交易、出入金及内部转账、KYC 审核、IB/返佣、跟单/PAMM、风控规则、经营与交易报表、支付渠道、活动、内容和系统配置。

app/risk 具有交易同步、返佣计算、佣金钱包结算、跟单和报表等历史入口。维护这些流程时使用模块内 app/risk/service，应进一步核对任务调度来源及与 gtcuser 同类任务的实际分工。

2.4 数据与后台任务

  • 业务数据库以 MySQL 为主，数据字典使用 t_ 表名体系。
  • 数据库配置包含多个 MT4/MT5 报表连接及 SelectDB/ClickHouse 相关连接；有自定义 ClickHouseConnection 和 Builder。配置存在不代表每个连接当前都使用。
  • Redis 用于缓存、会话相关状态、队列等；队列配置默认连接为 Redis，业务队列消费需要独立运行消费者。
  • 存在 RabbitMQ 消费代码，以及 Workerman/Crontab 历史代码和配置。当前根依赖与安装元数据未确认对应库，因此不能直接认定这些入口可运行或已在生产启用。
  • app/command/workman.php 当前只输出启动文字，并未实际启动 Workerman。根目录 run.php 也不是已确认的服务入口。
  • 部分后台动作调用 gtcuser 内部接口，例如异步导出、审核通过后的信号开户及 AI 翻译刷新。

依据：数据库配置、队列配置、CLI 命令配置、历史 workman 命令。

3.1 技术栈及实际解析版本

这是 JavaScript 为主的 Vue 3 管理后台，使用 Vue SFC、Composition API、script setup，并非整体 TypeScript 项目。

其他主要能力包括 Less、ECharts、Day.js、Big.js、富文本/Markdown、图片处理、XLSX、PDF、二维码、拖拽和视频播放。开发工具包括 ESLint、Prettier、Terser、自动组件导入和 gzip 构建插件。

依据：package.json、package-lock.json。

3.2 运行形态与构建

  • 应用入口为 src/main.js，注册 Pinia、路由、权限和国际化，挂载到浏览器页面。
  • 路由实际使用 createWebHashHistory()，属于 /#/... 形式的 SPA；已导入 createWebHistory 不代表启用了 History 路由。
  • 本地开发通过 npm run dev 启动 Vite，监听 0.0.0.0，端口读取 VITE_APP_PORT，未设置时为 9000。
  • 开发代理分别转发 /api、/admin，目标读取 VITE_PROXY_API_URL、VITE_PROXY_ADMIN_URL。这两个目标可相同，也可不同。
  • API baseURL 来源为 VITE_API_URL。Vite 的开发代理不会自动成为生产静态站点的代理规则；生产需要正确配置 baseURL 或 Web Server 转发。
  • npm run build 生成 dist/，base='./'，产物可由 Nginx/静态托管服务部署；生产不要求运行 Node 应用服务器。
  • 构建使用 Terser、生产移除 console/debugger/注释，并生成符合阈值的 .gz 文件。服务端是否实际使用预压缩文件由 Web Server 配置决定。
  • npm run serve 会先构建再运行 Vite preview，用于预览，不应视为生产部署方式。

依据：Vite 配置、入口、路由、设置。

3.3 请求、权限和菜单链路

1views 页面 -> api 业务封装 -> utils/request.js -> 后端接口
2登录 token -> 用户 store 获取菜单/会员信息 -> 动态注册路由 -> 页面及按钮权限

统一请求层使用 Bearer Authorization，并携带 serverid、think-lang、X-Timezone、时区偏移等上下文，敏感密码请求还包含 RSA 公钥/nonce 处理。生产请求超时通常为 15 秒，开发模式配置为不设置超时。

前端登录调用 /admin/pub/login；菜单调用 /admin/menu/mymenu；用户信息调用 /api/member/info；公共配置调用 /api/pub/config。这些 /api/member/info 和 /api/pub/config 在 gtc_admin 中确有实现，且前端按成功码 0 判断。

因此，不能简单配置“所有 /admin 交给 gtc_admin，所有 /api 交给 gtcuser”。具体接口归属需要按调用方、响应契约和网关规则核对。

菜单主要来自后端，路由使用 import.meta.glob('/src/views/**/index.vue') 解析页面，Pinia 保存用户、菜单、权限及系统配置。前端权限控制应与后台节点权限和数据范围协作，服务端仍承担最终授权判断。

国际化入口显式注册 18 个语言集合。语言头映射与两个 PHP 后端的语言标识体系需要保持兼容；金额、精度、日期和时区工具也是报表及资金页面的重要公共依赖。

依据：请求封装、登录 API、布局 API、用户 store、国际化入口。

3.4 业务范围与测试

页面涵盖会员、资金、KYC、代理、返佣、MT 配置、交易记录、跟单、PAMM、风控、报表、支付、活动、系统、工单和通知等。多个业务有历史页面、备份或重复实现，目录存在并不代表页面已进入当前菜单。

tests/unit 当前有 4 个 Node node:test 测试文件，另有源码目录内的测试文件；package.json 未定义统一 test 脚本。可按具体测试通过 node --test 执行，现有测试数量不能证明全部页面覆盖。lint:eslint 带 --fix，会写入文件，本次未执行。

4. gtcuser

4.1 技术栈及 PHP 版本差异

  • 框架：Hyperf 3.1、MineAdmin 3.0；锁文件与当前安装元数据的 Hyperf 核心版本为 v3.1.42，MineAdmin 核心为 v3.0。
  • 运行引擎：Swoole，Composer 声明 ext-swoole >=5.0；声明依赖 PDO/MySQL、Redis 等扩展。
  • 数据层：Hyperf Database/Eloquent 风格模型、Query Builder、Repository、数据库连接池；配置包含读写/分析数据源、MT4/MT5 报表源及 TDengine。
  • 服务能力：依赖注入、PHP Attributes 路由、AOP、事件、异步队列、Crontab、连接池、缓存和常驻进程。
  • 鉴权与安全：MineAdmin JWT、客户侧 OAuth、Token 中间件、会话失效、内部 Token、请求来源检查、RSA 解密、设备授权和限流等。
  • 文件与外部集成：OSS/文件系统、邮件、短信、支付、OAuth、KYC、MT、PDF/Office、Lark、AI/OpenAI；有 Prometheus/metric 和 PostHog 相关能力。
  • 本地依赖：packages/* Composer path 包及 plugin/ MineAdmin 插件。

PHP 版本存在明确差异：项目规范和 Composer 根声明以 PHP 8.1 为基线，Dockerfile 也使用 8.1；但当前生产锁定依赖中，OpenAI client、Symfony 7、WebAuthn 等要求 PHP 8.2，当前 vendor/composer/platform_check.php 的门槛也是 PHP_VERSION_ID >= 80200，Compose 使用 8.2 镜像。

按当前依赖正常安装和加载，需要至少 PHP 8.2。后续业务代码仍应遵守仓库规定的 PHP 8.1 语法边界；运行版本与依赖版本的统一需要单独处理，不能把文档中的 8.1 当作当前锁文件已兼容的事实。

依据：composer.json、composer.lock、项目规范、Dockerfile、Compose。

4.2 常驻应用启动和端口

实际启动链路是：

1composer start -> 清理 runtime/container -> php bin/hyperf.php start
2bin/hyperf.php -> Composer autoload -> 插件初始化 -> DI ClassLoader -> 容器 -> Hyperf 应用

项目规范提到 public/index.php，但当前仓库没有该文件，也没有 public/ 目录。HTTP 请求由 Swoole HTTP Server 回调交给 Hyperf 处理，实际启动入口是 bin/hyperf.php。

监听项 当前代码配置 用途
HTTP 0.0.0.0:9505 API 请求
socket-io 0.0.0.0:9507 Socket.IO/WebSocket
9506 Compose 映射，当前 server.php 未注册对应业务监听 不能仅凭端口映射认定服务存在

server.php 使用 SWOOLE_PROCESS，启用协程，配置 CPU 相关 worker 数、4 个 task worker、请求数回收、异步 reload、PID 和日志。静态文件处理关闭，文件访问需要结合 Nginx/OSS 等方案。入口代码将 PHP 默认时区设为 UTC。

常驻进程的配置、容器和代码在启动时加载，代码发布后需结合缓存处理和 reload/restart。请求数据必须注意协程上下文隔离；数据库/Redis 连接池、各队列进程及后台任务共同占用资源。

依据：启动入口、服务配置。

4.3 分层、路由与接口类型

1app/Http/Admin 或 app/Http/Api -> app/Service -> app/Repository 或 app/Model

主要业务域包括 Trade、Cash、Commission、Follow、Pamm、Risk、SecurityPolicy、IbAccount、crm、member 等。历史代码并不全部严格遵循分层，某些控制器和 Model 仍直接承担查询或业务处理。

客户侧控制器位于 app/Http/Api/Controller，包含 V1/V2/V3、开放接口、OAuth2、内部接口、设备接口和 Socket.IO。多数使用 Attributes 显式注册路由；V1 常使用 /api/member 等未带版本号的前缀，V2/V3 则有 /api/v2、/api/v3，不能只按文件目录推断 URL。

MineAdmin 自带的管理接口目录也存在，但 disable_admin_manage 默认为 true，全局 RouterBlack 中间件据此拦截 admin/ 请求；注释明确说明当前使用旧版管理后台。具体环境是否覆盖此默认值未验证。

客户侧 API 成功码通常为 200，与 gtc_admin 常用的 0 不同。返回字段虽均常见 code/message/data，调用方仍必须按接口契约处理，不能直接互换。

依据：会员接口、中间件、后台访问开关、后台拦截、响应码。

4.4 队列、调度和 WebSocket

  • config/autoload/processes.php 注册 CrontabDispatcherProcess 和 AsyncQueue ConsumerProcess，随应用启动。
  • AsyncQueue 使用 Redis，配置普通、快速、高优先级、报表、安全事件、下载、邮件、风控等多个队列及不同进程数、并发和超时。
  • ASYNC_QUEUE_ENABLED 控制多项队列进程数，但部分下载队列固定为 1 个进程，因此它不是当前配置中所有队列的统一关闭开关。
  • Crontab 全局配置启用，但具体业务任务通常还受 APP_RUN_TASK 和任务自身开关控制。不能把“调度进程启动”理解为全部业务任务都会运行。
  • 通用异步任务以数据库任务记录保存入参、状态和重试信息，队列 Job 携带任务 ID 调用 Service 消费。
  • Socket.IO 具备加入会员房间、主设备确认授权、取消授权及向发起设备通知等实际业务逻辑。
  • app/Process/RemoteEventListenerProcess.php 的 Process 注解当前被注释，不能据文件存在认定 Redis remoteEvent 监听已启动。LogProcess 实现的是日志 Processor，也不是独立常驻进程。

这说明仅检查 HTTP 健康不足以判断系统功能正常，还需要确认队列消费、调度开关、任务状态、WebSocket 及外部依赖。

依据：进程注册、队列配置、通用任务 Job、任务开关、Socket.IO 控制器。

5. 三个项目的协作链路

5.1 管理后台登录和初始化

1Vue 登录页 -> /admin/pub/login -> gtc_admin 签发后台 token
2Vue 请求拦截器 -> 携带 Authorization/serverid/语言/时区
3Vue user store -> /admin/menu/mymenu + /api/member/info
4Vue 动态注册菜单路由 -> 打开对应管理页面

上述管理菜单和历史公共会员信息接口在 gtc_admin 中存在。gtcuser 客户侧有自己的 JWT/会话/OAuth 链路，不能假设两端 token 在所有接口中可以互用。

5.2 后台触发客户侧执行

已核对链路 gtc_admin 职责 gtcuser 职责
信号审核通过后的 MT 开户 审核入口及同步内部 HTTP 调用，远端失败会阻断成功结果 OptionController 调用信号开户服务，完成具体开户/绑定
导出下载 组织接口地址、参数、语言、表头等，调用下载中心并转换响应码 创建任务，投递 downloads 队列，后台生成文件；部分任务按提供的地址拉取数据
AI 内容翻译刷新 管理内容更新后通知内部接口，失败记录日志 内容翻译服务处理刷新与落库
通用后台任务 按内部任务契约传入类型、业务参数、幂等键等 CommonTaskController 创建任务记录并投递 AsyncQueue

内部调用依赖 REMOTE_EVENT_URL 和内部 Token 等配置名；gtcuser 使用 InternalTokenMiddleware 校验 Token 请求头。本文不记录任何配置值或凭证。

依据：内部 HTTP helper、开户派发、导出适配、OptionController、下载中心入口、通用任务入口。

5.3 共享数据结构与耦合

gtc_admin 数据字典包含 425 张表，gtcuser 包含 424 张表，其中 424 个表名重合；gtc_admin 额外有 t_admin_translation_kv。这里比较的是建表名称，不代表全部字段、索引和约束完全一致。

两个后端都覆盖 t_member、t_member_mtlogin、t_fund_detail、t_sale_commission、KYC、策略、权限、日志和报表等结构，说明存在较强的数据模型关联。物理库、读写库、分析库及 Redis 是否实际共用，仍需部署资料确认。

因此未来改动公共状态、敏感字段、金额口径、权限或表结构时，应同时核对两个后端；涉及大表还需要按各自数据字典和查询来源检查索引、分页及统计方式。本次没有新增或修改 SQL，也没有进行性能压测。

7. 待确认项与后续顺序

  1. 确认实际部署拓扑：取得 Web Server/网关规则，标注管理 /admin、历史 /api、客户侧 /api、内部接口及 WebSocket 的真实目标；确认域名、进程管理和文件服务。
  2. 确认运行和安装版本：核对 gtc_admin FPM 的 PHP 8.0、gtcuser 实际 PHP/Swoole、前端构建 Node；优先解决 gtcuser 8.1 文档/镜像与 8.2 依赖门槛的不一致，再处理端口和 Composer 配置差异。
  3. 确认任务责任和开关：列出 gtc_admin 历史批处理、外部 cron、Think Queue、RabbitMQ 与 gtcuser Crontab/AsyncQueue 的生产启用情况，检查同类资金/返佣任务是否存在重复执行风险。
  4. 确认数据拓扑和发布基线：核对两个后端的物理库、分析库、读写分离、Redis DB/prefix 以及字段/索引差异；再确定两个项目的 SQL 发布先后关系。
  5. 执行隔离环境联调：后台登录/菜单/会员信息、列表、导出、信号审核开户、KYC/资金相关状态同步、队列和 WebSocket。外部服务采用测试环境或 mock，按业务风险执行针对性测试。
