4. #3500 数据库迁移和发布 SQL

4.1 检查顺序

当前 t_kyc_regulatory_type 没有 title_en，禁止先执行引用 title_en 的 SQL。

  1. SELECT VERSION()；目标为 InnoDB、MySQL >= 5.7.6。低于版本要求直接阻断发布。
  2. 查询 information_schema.columns、information_schema.statistics，确认字段、生成列和索引。
  3. title_en 不存在时只检查中文重复、中文空值和既有索引，跳过英文查询。
  4. 增加 title_en。
  5. 字段存在后执行英文重复检查。
  6. 重复数据只生成清理清单，人工确认；不自动删除和覆盖。
  7. 清理完成后增加生成列和唯一索引。

中文预检查：

1SELECT TRIM(title) AS normalized_title, COUNT(*) AS cnt
2FROM t_kyc_regulatory_type
3WHERE deleted = 0
4GROUP BY TRIM(title)
5HAVING COUNT(*) > 1 OR normalized_title = '';

英文预检查：

1SELECT LOWER(TRIM(title_en)) AS normalized_title_en, COUNT(*) AS cnt
2FROM t_kyc_regulatory_type
3WHERE deleted = 0 AND TRIM(title_en) <> ''
4GROUP BY LOWER(TRIM(title_en))
5HAVING COUNT(*) > 1;

4.2 固定 DDL

迁移程序按字段、生成列、索引顺序逐条执行，发现同名对象定义不一致即阻断，不提供命名锁或临时替代方案。

 1ALTER TABLE t_kyc_regulatory_type
 2  ADD COLUMN title_en VARCHAR(100) NOT NULL DEFAULT ''
 3    COMMENT 'KYC监管类型英文原始名称' AFTER title;
 4

 6  ADD COLUMN title_active_norm VARCHAR(255)
 7    GENERATED ALWAYS AS (
 8      CASE WHEN deleted = 0 THEN TRIM(title) ELSE NULL END
 9    ) STORED
10    COMMENT '未删除监管类型中文唯一归一值',
11  ADD COLUMN title_en_active_norm VARCHAR(100)
12    GENERATED ALWAYS AS (
13      CASE
14        WHEN deleted = 0 AND TRIM(title_en) <> ''
15        THEN LOWER(TRIM(title_en))
16        ELSE NULL
17      END
18    ) STORED

20

生成列和预检查的归一化表达式完全一致。删除记录生成 NULL，允许历史名称复用；英文空值生成 NULL，允许多条历史空值。迁移通过 information_schema 判断幂等，不使用不兼容的 IF NOT EXISTS。

5. #3501 查询、权限和列表契约

5.1 输入解析

列表请求保留现有 keyword，新增 invite_code。邀请码输入支持：

  • 原始邀请码；
  • 正十进制客户 ID；
  • 完整邀请链接；
  • 普通 query 和注册页 hash query；
  • ref、invitation_code、invitationcode 参数。

多个别名值不一致返回参数错误；链接没有邀请码返回格式错误，不降级模糊查询；邀请码采用精确匹配。纯数字只按客户 ID 解析，不接受符号数字、科学计数法或混合空格。

keyword 支持客户 ID、昵称、邮箱、手机号模糊查询。客户 ID 分支使用参数绑定的数值条件；invite_code 与 keyword 同时存在时使用 AND，不把两个字段合并成 OR。

5.2 默认筛选、顶层和展开

  • 首次进入页面 user_type=agent。
  • 重置清空关键词、邀请码、用户层级、注册时间，并恢复 user_type=agent。
  • 客户类型仍支持全部、代理、直客。
  • 管理员无 parent_id、无精确邀请码/客户 ID 时，主列表只取 parent_id=0 的顶层用户。
  • 非管理员无 parent_id、无精确邀请码/客户 ID 时，主列表取 parent_id=当前登录会员 ID 的第一层，并继续使用 member_root_path 做数据范围限制。
  • 精确邀请码或客户 ID 用于定位目标会员时，可以返回命中会员本身，但必须通过 URL 权限和数据权限；不能因命中条件绕过权限。
  • 关键词、客户类型、用户层级、注册时间都必须在主列表中同时生效。
  • 传入 parent_id 只查询一层直接下级，但必须同时带上当前全部筛选条件；展开不能丢掉关键词、邀请码、客户类型、层级和时间范围。
  • 展开和收起不改写筛选条件；搜索、重置、刷新成功后清空 expandedRowKeys 和旧 children。
  • 固定保留 member.status=1，本期不定义 member_invalid。
  • 列表和明细默认排除当前登录会员；本人查询另立权限需求。

6.2 页面展示状态

页面公开状态只允许：

  • available：显示“可邀请”；
  • disabled：显示“已停用”。

页面公开停用原因只允许：

  • ib_disabled：邀请码自身 status=0；
  • platform_disabled：所有可用配置的 IB 总开关关闭。

只有 disabled 才展示原因。授权、开户配置、ACCOUNT_TYPE 和服务器规则仍按用户端真实 checkInvitationCode 计算，但作为后台内部 diagnostic_reason，不进入本期页面停用文案。配置异常的历史行保留并显示 --，不能自行新增 PRD 未定义的停用原因。

状态计算固定为：

  1. code.status=0：status=disabled，disabled_reason=ib_disabled。
  2. 至少有一条配置通过公开/授权、开户配置和 ACCOUNT_TYPE 校验，且存在一条未关闭的 IB 总开关：status=available。
  3. 存在配置但全部 IB 总开关关闭：status=disabled，disabled_reason=platform_disabled。
  4. 没有任何可用配置或配置校验失败：status=disabled，disabled_reason 为空并显示 --；具体失败原因只写入 diagnostic_reason。

后台内部规则与 gtcuser 对齐：

  • 非数字 code 必须存在且归属会员存在；
  • code.status=0 记录 ib_disabled；
  • 公开开户配置按 invent_code、status=1、allow_share=1 判断；
  • 非公开配置检查 member_agent_remark 授权；
  • 授权后必须存在 status=1 的开户配置；
  • t_ib_invite_link_config.global_enabled=0 记录 platform_disabled；无记录默认启用；
  • ACCOUNT_TYPE 不包含 account_type 记录 diagnostic_reason=config_invalid。

gtc_admin 不调用 gtcuser Service，不引入内部 HTTP；用同一组测试数据分别执行用户端 checkInvitationCode 和后台只读计算，防止规则漂移。

6.3 权限和副作用

明细请求顺序固定为：参数解析 -> URL 权限 -> 会员存在且 status=1 -> check_data_permission -> 非管理员排除本人 -> 验证 matched_invite_code -> 批量读取 code/config -> 计算状态。

查询前后 t_member_invent_code 数量和内容必须一致，不调用 IbService::getInviteCodeList，不触发自动补建邀请码。

7. #3501 前端实施和验收

修改 gtc_admin_vue/src/api/agent/index.js、gtc_admin_vue/src/views/agent/account/index.vue 及现有多语言资源。

  • 查询区新增邀请码输入；首次和重置默认代理。
  • 搜索、重置、刷新均显示 loading，按钮防重复提交；刷新保留所有条件。
  • 无查询结果显示“暂无符合条件的用户”。
  • 邀请码未找到显示“未找到对应邀请码持有人”并建议检查或重置。

  • 昵称区显示展开/收起图标、昵称、客户类型、客户 ID。
  • has_children=false 显示灰色不可点击占位图标；true 才可请求。

9. 发布、回滚和完成标准

9.1 发布顺序

  1. 备份表结构和重复数据清单，确认目标 MySQL 版本和索引。
  2. 按字段 -> 生成列 -> 索引执行 #3500 SQL；确认 #3501 依赖表和索引。
  3. 先发布后端兼容版本，确保 title_en 缺失/为空时可以回退。
  4. 发布前端和新明细接口。
  5. 灰度验证 API 字段、权限、状态、复制、空状态、EXPLAIN 和无写入副作用。
  6. 全量发布并保留迁移执行记录。

9.2 回滚

  • 先回滚前端，再回滚后台代码；旧代码读取 title 不受 title_en 影响。
  • 默认保留新增字段、生成列和历史英文数据，优先应用回滚，不执行破坏性 DROP。
  • 确认没有后续依赖后，才按索引 -> 生成列 -> title_en 逆序回滚。
  • #3501 只回滚本次新增且无其他版本依赖的索引，不删除历史邀请码和 t_ib_invite_link_config。
  • DDL 任一步失败立即停止，记录已完成步骤，不重复执行未确认的 DROP/ALTER。

9.3 完成标准

  1. DB：迁移顺序、幂等、重复检查、唯一索引、数据字典和依赖表完成。
  2. 后端 #3500：真实调用链、字段契约、错误字段、日志快照和回退完成。
  3. 后端 #3501：列表、明细、主邀请码、状态诊断、权限、批量查询和无副作用完成。
  4. 前端：默认代理、组合筛选、复制、状态、展开、空状态和公共列表能力完成。
  5. 测试：PHP 8.2.35/8.1 兼容、相关测试、契约测试、EXPLAIN、灰度和回滚记录齐全。
