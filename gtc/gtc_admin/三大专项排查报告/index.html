三大专项排查报告

三个专项的范围

本报告对应“连接与事务泄漏、N+1 查询、索引失效 SQL”三个专项，具体范围如下：

专项 排查内容 对应问题编号
连接与事务 事务未提交或回滚、提前返回和异常路径的事务闭合、长事务、连接占用及连接池配置风险 T01—T08、C01—C05
N+1 查询 列表、循环及批处理中的逐条查询，以及间接调用造成的重复读取；当前记录 45 个已复核的读取位置或调用路径，不代表 45 个独立接口 N01—N45
SQL 与索引使用 FIND_IN_SET、过滤列函数、前置通配模糊匹配、无界读取及缺少时间范围等可能增加扫描成本的 SQL 形态 S01—S15

判断边界：事务闭合缺口不等于已证实永久连接泄漏；存在重复读取不等于都能安全批量替代；某个条件不能有效利用索引，也不等于整条 SQL 完全不走索引。实际影响需要结合连接池数据、执行计划及慢查询 Profile 验证，MySQL/PolarDB 与 SelectDB 分别按对应引擎判断。

首次扫描：2026-10-13；全面扩展复核：2026-10-14
代码基线：master
方式：全项目关键词检索后，对高风险命中阅读上下文、Repository、Model、数据字典及连接池实现。本文为新生成的静态复核文档，不代表已穷尽全部路径。

本次仅更新文档，不修改业务代码，不连接生产服务，不执行资金操作或数据库迁移。未取得线上 SQL、EXPLAIN、连接池运行数据，不能据此宣称已复现线上泄漏或慢查询。

二、连接与事务

T01：结算退款存在未闭合事务分支

位置：app/Common/Lib/Transfer/Transfer.php:1080，subscribeFinish()；事务开启在 1092 行。

  • 开启事务后，$forword->status != 1 直接返回错误数组，没有 commit/rollback。
  • 写入 status=9 后，仅在 $amount > 0 的成功分支 commit。金额为零或负数时执行到闭包末尾，没有闭合事务，也没有明确业务返回。
  • 正常正金额成功和 Throwable 分支有闭合，不应误报为所有调用都会泄漏。

影响：事务残留到连接释放；状态更新可能被框架回滚；后续同协程操作可能落入残留事务。常驻任务中风险更大。

建议：明确非正金额业务规则；使用受控事务边界，使每个返回路径都结束本层事务。不得简单 commit 非正金额分支而改变资金规则。

验证：构造状态不等于 1、金额 0、负数、正常成功、下游抛异常；逐项断言事务层级恢复到调用前值、状态及资金变化符合规则。

T02：自动入金异常路径未统一回滚

位置：app/Common/Lib/Transfer/Transfer.php:127，despoitMt()；catch 在约 169 行。

事务内创建转账记录、扣款并调用 MT 远程 balance。部分显式失败分支已 rollback，但 catch(Exception) 本身只更新支付状态并返回。创建记录或远程调用等位置直接抛异常时，可能进入未回滚路径；catch 中的状态更新还可能一起被框架回滚。

建议：明确事务所有者，异常时只回滚本方法开启的层级，再记录独立的失败状态。远程结果未知不能直接重试扣款，必须按订单号对账。

验证：分别在创建记录、扣款、远程调用超时处注入异常；检查事务层级、支付状态落库及远程实际到账情况。

T03：系统资金流水手动事务缺少异常兜底

位置：app/Repository/crm/SystemMoneyLogRepository.php:79，addMoney()。

beginTransaction 后仅正常成功 commit、更新失败 rollback；查询、计算、写入直接抛异常时没有本地 catch/finally。该方法还可能嵌套在调用者事务内；外层只 rollback 一层未必回到入口层级。

建议：采用框架事务闭包或严格记录入口层级，统一异常传播。不要无条件 rollback(0) 破坏调用者的事务。

验证：独立调用和嵌套事务调用均注入异常，检查事务层级与资金原子性。

T04：MtServer 写入位于 try 保护范围外，且有重复回滚

位置：app/Model/Trade/MtServer.php:255。

beginTransaction 后创建 MemberMtForwardLog，之后才进入 try。创建失败不经过该方法 catch。远程失败分支先 rollback 再抛异常，catch 又 rollback；有外层事务时可能多回滚一层。

建议：把所有事务内语句放入同一受控边界，确保仅结束本层事务；保持远程资金处理的幂等和对账逻辑。

T05：会员余额更新未覆盖全部 Throwable

位置：app/Repository/member/TMemberRepository.php:506，catch 在 565 行。

正常返回分支已有 commit/rollback，但仅捕获 Exception，TypeError、ValueError 等 Error 不走该回滚分支。仅作为异常覆盖风险记录，不等同于已发生连接泄漏。

建议：对资金方法评估 Throwable 处理，回滚后按既有业务契约传播异常；用非法计算输入或受控异常桩验证。

C01：连接池上限与 Worker 数量放大

位置：config/autoload/databases.php:32，default 池：min_connections=10、max_connections=1000、wait_timeout=10 秒。

连接池按进程、连接配置分别建立。若 8 个 Worker 均使用该池，配置上限预算可达 8000；不是启动时立即创建 8000 条连接，也不是实际连接量证明。还需计入其他进程、实例、读写分离连接及数据库端限制。

建议：按峰值同时访问数据库的协程数、SQL 时延和数据库 max_connections 分配连接预算；先测池等待和活跃连接，再调小上限，不直接给所有池套同一个数值。

C02：事务中等待远程 MT 响应

位置：app/Common/Lib/Transfer/Transfer.php:134、app/Model/Trade/MtServer.php:278 附近。

远程请求发生在写入/扣款之后、提交之前。对方慢或超时会延长本地连接和锁持有时间。这属于长事务/连接占用风险，不是永久泄漏证据。

短期：核实远程连接/读取超时，记录事务耗时及订单号，避免无限重试。 长期：评估状态机、幂等请求、对账补偿，缩短本地事务；不能简单把远程调用移到事务外而忽略资金一致性。

T06：钱包提现事务没有统一异常出口（P1）

位置：app/Service/crm/PayService.php:2594，withdrawGtcWallet()；beginTransaction 在 2638 行。

创建提现记录、跟踪记录、余额变更、资金明细及审核步骤后，正常路径在 2661 行提交；业务失败返回分支在 2677 行回滚。但 2638 行之后并没有覆盖整个事务的 try/catch，之前的 try 只保护另一段插入。任一写入直接抛异常，都可能留下本层事务。余额 Repository 还会开启嵌套事务，不能假设外层回滚一次就足够。

处理：统一本方法拥有的事务边界，保留余额、提现单、审核步骤的原子性；失败记录是否独立提交必须明确。验证记录创建失败、余额异常、明细失败、步骤失败和外层已有事务的情形，检查资金、状态及事务层级。

T07：入金回调异常未回滚，且混合提交前后失败（P1）

位置：app/Service/crm/PayService.php:1555，payCallbackNext()；事务 1610，提交 1635，catch(Exception) 1750。

catch 只记录异常并返回 false，没有回滚。订单保存和余额变更抛错时存在事务闭合缺口；而提交之后还会调用 MT、写资金明细及统计，这些失败同样进入 catch。回调返回失败不能证明入金没到账，无条件重放可能造成重复资金处理。

处理：区分“提交前失败”“提交结果不明”“已提交、后续动作失败”，依据持久化订单状态做幂等和补偿。提交后的失败不能靠 rollback 撤销已提交资金。验证重复回调、并发回调、提交前后异常及远程结果未知，不只测 HTTP 返回码。

T08：订阅申请失败路径重复回滚（P1，嵌套时重点）

位置：app/Common/Lib/Transfer/Transfer.php:956，applySubscribe()。

971、998 行的失败分支先 rollback 再抛异常；1002 行 catch 再 rollback。独立调用时第二次可能无实际动作，但存在外层事务时可能结束不属于本方法的事务层级；内部 addMoney 的异常闭合问题还会放大层级判断难度。

处理：单一异常出口，每层仅结束自己开启的事务；不要统一 rollback(0)。验证两类业务失败、嵌套调用及内层写入异常，同时检查外层后续写入是否仍受外层事务保护。

C03：多连接配置共同占用连接预算（P2）

位置：config/autoload/databases.php。除了 default 的 1000，selectDB、bigdataDB 配置上限分别为 50；bw2_2gtc 为 20；多组 MT 配置为 50；ib_report2—5 为 200。config/autoload/redis.php:20 的 Redis 池上限为 100，也需要独立观测。

不能只用 default 的数字评估系统：同一物理数据库可能被多个逻辑连接名访问，各进程、队列消费者、实例还会分别持池。估算应为“实际启用进程 × 各目标连接池预算”的汇总，再加其他服务余量；并非所有池都会同时达到上限。

先按数据库目标归类，记录 Worker/消费者数量、活跃连接、等待时长、峰值 SQL 延迟，再调整上限。连接池等待超时与 SQL 执行超时是不同指标。

C04：部分外部请求没有总超时（P1/P2，按调用频率）

  • common/crm.php:118 的 getData：仅设连接超时，没有整个请求的 CURLOPT_TIMEOUT；会员 KeChat 认证服务存在调用。
  • app/Common/Lib/Withdraw/GtcOutPay.php:575 的 postData：同样只有连接超时。付款结果未知时应先对账，不能因为本地超时直接再付款。
  • app/Common/Lib/Zoom/ZoomBase.php:68,111：令牌及业务请求未看到连接/总超时设置。

连接建立成功后，对端持续不返回仍可能长期占用协程或消费者。同协程之前借出的数据库连接可能一直持有到协程结束，即使没有开启事务。设置连接及总超时、限制重试和并发，记录各阶段耗时；鉴权、支付和一般读取分别处理超时后果。

反例：common 的 postData 已有总超时；GtcPay 的 postData 有 300 秒总超时，属于超时较长而非缺失。不能把所有 curl 调用统一报成无超时。

C05：文件处理异常路径没有显式关闭（P3，条件风险）

app/Service/crm/MemberKeChatImportService.php:24 打开 CSV，循环处理后第 40 行关闭；中途异常没有 finally。app/Jobs/SystemDownloadJob.php:982 打开输出文件，1035 行正常关闭，但 1040 行 catch 重抛，异常路径未统一清理。导入还会累积整份文件数据，需看文件规模和 RSS。

建议使用 finally 管理句柄、按批处理大文件。PHP 资源析构可能最终释放句柄，所以这不是已证实的永久 FD 泄漏。测试连续异常批次的 FD/RSS 是否回落。SystemDownloadV2Job 和部分上传流已有 finally，不列为同类缺口。

框架兜底与判断边界

vendor/hyperf/db-connection/src/ConnectionResolver.php:63 在协程结束时 defer 归还连接。 vendor/hyperf/db-connection/src/Connection.php:107 在 release 时检查 transactionLevel，存在未结束事务则 rollback(0)，并记录：

1Maybe you've forgotten to commit or rollback the MySQL transaction.

因此本报告确认的是业务事务闭合缺口，不能据此断言连接永远不归还。协程未结束、长任务持续占用连接、异常回滚失败等需要运行数据验证。普通 ORM 查询未显式 close 不是自动构成泄漏。

本次抽查的 UaePassAuthService HTTP 请求设有超时并调用 curl_close；CSV 导入正常路径有 fclose，但异常清理仍有条件风险，见 C05。未将这些直接列为永久泄漏。

三、N+1 查询

N01：设备列表

位置：app/Service/member/TMemberService.php:3651，loginDevice()。

分页设备后 foreach 内逐个 MemberLoginLogRepository::findByFilter()，按会员、设备、成功状态、id 倒序查询；N 个设备约增加 N 条 SQL，另有在线状态查询依赖。

最近的空设备修复只增加 EXISTS 过滤，没有消除 N+1。数据字典已有 (member_id,device_id,login_status) 索引，应先核实测试/生产是否一致，不重复盲目加索引。

建议：在当前会员、当前页 device_id 范围内批量取每个设备最新成功记录；保留 PC/App、已退出设备及最新记录选择语义。不要先对全日志表 group by。

验证：1、10、20 个设备的 SQL 次数应近似固定；比较旧结果与新结果、分页 total、设备归属和在线状态。

补充正确性风险：当前查不到日志时将设备信息覆盖为空值再 continue，若 EXISTS 分页后日志被并发删除，仍可能保留空设备列表项；需另行处理并发一致性。App 缺失的实际数据原因未通过测试环境返回值验证，不能认定过滤空行已修好全部原 Bug。

N02：品种与收藏

位置：app/Service/Trade/TradeService.php:764。

图标已批量查询，但循环仍对每个 symbol/server_id 查询 Symbol，并对找到的品种按 login_id/symbol_id count 收藏。N 个品种最多约 2N 次额外 SQL。

建议：按同一 server_id 和 symbol 集合批量取品种，按同一 login_id 和 symbol_id 集合取收藏，内存映射。不要跨服务器只按 symbol 合并。

验证：100 个品种的数据库查询次数不随品种数线性增长，收藏状态及缺失品种返回保持一致。

N03：MT5 成交补订单时间

位置：app/Service/Cross/CrossMt5DealsService.php:105。

分页后按每条 PositionTicket 查询 CrossMt5Orders，N 条成交增加 N 次查询。

建议：仅针对当前页批量读取订单。还需核实 Ticket 是否跨 Server 唯一；批量映射必须保留真实业务复合键，不能扩大现有串服务器风险。

N04：PAMM 待审列表

位置：app/Service/Pamm/PammService.php:1600。

每条 OUTALLMONEY 且 check_status=1 的记录分别查 StrategyCopy 和 StrategyOther；符合条件的 K 条记录增加 2K 次查询，同策略信息可能重复查询。

建议：收集当前页 copy_id、strategy_id 批量取数据，计算仍沿用原金额精度规则。测试缺失持仓、缺失策略、不同状态及相同策略重复出现。

四、不可有效利用普通索引的 SQL 形态

这里区分“条件本身不能做普通 B-tree 范围定位”与“整条 SQL 完全不用索引”。其他等值条件仍可能有效，最终要看执行计划。SelectDB 需检查分区、Tablet、倒排索引和 Profile，不直接套用 MySQL B-tree 结论。

S01：转账候选人的层级和包含搜索

位置：app/Service/Cash/CashService.php:617,651。

FIND_IN_SET(?, path)，并有 nickname/email/loginid 的包含匹配，钱包候选直接 get，没有数据库分页上限。member_root_path 数据字典虽有 path FULLTEXT，但 FIND_IN_SET 不会因此自动使用全文索引。member_id 主键仍可用于连接。
