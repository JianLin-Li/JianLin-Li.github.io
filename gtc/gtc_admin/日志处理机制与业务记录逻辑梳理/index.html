日志处理机制与业务记录逻辑梳理

2026-10-27 项目：gtc_admin

日志处理机制与业务记录逻辑梳理

梳理范围：gtc_admin、gtcuser 两个项目。 结论依据：当前工作区源码、配置文件、模型/Repository、队列与定时任务定义、两项目 docs/数据字典.sql。 本文只描述源码中的现状，不读取生产日志、不连接生产数据库，也不把配置注释当作已发生的运行事实。

1. 先区分四类“日志”

系统中的“日志”实际上有四种用途，存储和可靠性不能混为一谈。

类型 目的 典型落点 是否业务事实
运行诊断日志 排查异常、接口调用、任务进度、外部服务返回 本地文件、Swoole 文件、Lark 否，可能丢失或被轮转
管理操作审计 记录后台谁在什么时间调用了什么操作 t_operation_log、t_system_operation_logs、t_modify_operation_logs、MineAdmin 两张日志表 是，但覆盖范围取决于注解/中间件
客户安全审计 登录、登出、入金、出金、转账、修改安全设置等 t_member_login_log、t_member_login_session、t_member_security_activity 是，通常与客户或会话关联
资金/交易业务流水 记录金额、资金方向、订单和结算结果 t_member_amount_log、t_fund_detail、t_member_forword_log、返佣/结算表 是，属于账务或交易数据，不应仅依赖文本日志

因此，Log::error()、logger()->error() 只能作为诊断证据；提现、入金、转账、余额变更等结果必须以对应业务表为准。

2. gtc_admin

2.1 技术栈与总链路

gtc_admin 是 ThinkPHP 应用，使用 think\\facade\\Log/PSR-3 风格 API，默认 file 通道；后台中间件、Service、Model 和部分旧控制器还会直接写数据库或 ./logs 文件。整体链路如下：

 1Controller / Service / Task
 2        |
 3        +-- think\\facade\\Log::record|info|error|write
 4        |       -> think\\Log -> think\\log\\Channel -> File driver
 5        |       -> runtime/<app>/log/YYYYMM/DD.log（默认）
 6        |
 7        +-- #[LogOperation]
 8        |       -> LogOperationMiddleware（请求成功返回后）
 9        |       -> t_operation_log
10        |
11        +-- #[SystemOperation]
12        |       -> SystemOperationMiddleware（前置校验、执行后记录）
13        |       -> t_system_operation_logs
14        |
15        +-- #[ModifyReason]
16        |       -> ModifyReasonMiddleware（成功且有变更）
17        |       -> t_modify_operation_logs
18        |
19        +-- 登录/会员/资金业务服务
20                -> t_member_login_log / t_member_login_session
21                -> t_member_detail_log / t_member_amount_log / t_fund_detail

2.2 ThinkPHP 文件日志

配置在 config/log.php：

  • 默认通道是 file，全局 close=false，没有配置级别白名单。
  • file.path 为空，由 localPackage/framework/src/think/log/driver/File.php 解析为 $app->getRuntimePath() . 'log'。
  • single=false 且 max_files=0 时，主文件名是 runtime/<应用运行目录>/log/YYYYMM/DD.log；月份目录和日期文件由框架创建。
  • 单文件达到 file_size（驱动默认 2 MB）时改名为带 Unix 时间戳的备份文件。max_files=0 表示不按数量清理，因此实际保留量取决于外部日志清理策略和磁盘空间。
  • 文本格式默认是 [%s][%s] %s，分别为时间、级别、消息；json=false。
  • zoloz 是独立 File 通道，路径为 app()->getRuntimePath().'logs/zoloz'，调用方式是 Log::channel('zoloz')。

写入时机由 localPackage/framework/src/think/Log.php 与 Channel.php 决定：

  1. Log::record() 把消息先放入当前 Channel 的内存数组。
  2. Web 请求下 realtime_write=false 会使 Channel 默认延迟写入；请求结束或框架保存日志时批量调用 save()。
  3. Log::write() 调用 record(..., lazy=false)，立即调用 File driver 的 save()。
  4. File driver 最终通过 error_log($message, 3, $destination) 追加写文件。

这意味着普通 record/info/error 在请求中途进程异常时可能尚未落盘，而 write 更适合需要立即看到的任务进度；二者都不是消息队列，也没有跨进程重试。

config/trace.php 只配置控制台 Trace，服务于调试输出，不是持久化业务审计。app/ExceptionHandle.php 继承 ThinkPHP Handle，业务异常、数据库异常和未捕获异常最终由框架报告逻辑写入错误日志；它对 BusinessException 和 DbException 主要负责响应格式，不负责建立业务审计记录。

2.3 普通业务诊断日志

代码中常见形式包括：

1Log::info('业务阶段完成', ['member_id' => $memberId]);
2Log::error('外部服务调用失败: ' . $e->getMessage(), ['order_id' => $orderId]);
3Log::write('定时任务进入下一阶段');
4Log::record(json_encode($payload), 'error');

典型来源：KYC、MT API、Saleforce、支付/提现、跟单、返佣、静态报表、风险策略、MQ 消费等。消息内容通常是中文描述加会员 ID、订单号、MT 登录号、返回码和异常消息；并非所有调用都带结构化上下文，也不是所有调用都做敏感字段脱敏。

2.4 旧式手写文件日志

历史代码绕过 ThinkPHP Logger，直接使用 file_put_contents(..., FILE_APPEND)。已确认的落点如下：

来源 路径模式 内容/用途
app/risk/controller/CommissionWalletSettlement.php ./logs/commission/YYYY-MM-DD-wallet.log 钱包返佣结算进度和上下文
CopyCommission.php ./logs/commission/YYYY-MM-DD-gtc-init.log GTC 跟单/返佣初始化
PammCommission.php ./logs/commission/YYYY-MM-DD-Pamm-init.log PAMM 初始化
TradeCommissionV2.php ./logs/commission/YYYY-MM-DD-init.log 返佣初始化
Member.php、CreditService.php、Credit.php ./logs/commission/YYYY-MM-DD-credit.log 赠金处理
app/risk/controller/Mt.php ./logs/leavger/YYYY-MM-DD.log 杠杆处理任务
app/api/model/MtApi.php ./logs/mt/YYYY-MM-DD-dllapi.log MT DLL API 调用
app/admin/controller/Timer.php ./logs/timer/YYYY-MM-DD.log 定时任务输出；同时 echo 到 CLI
app/service/InformationService.php ./logs/mail/YYYY-MM-DD-mail.log 邮件/短信发送流程参数和返回结果
app/api/controller/Notify.php ./logs/pay/YYYY-MM-DD.log 支付通知处理
app/service/XiaoTechService.php ./logs/xiaoe_tech/YYYY-MM-DD.log 外部服务调用

这些路径以 ./ 开头，依赖启动工作目录，和框架的 runtime 日志不是同一目录；文件创建权限、轮转、保留期和并发写入均由各方法自行承担。手写日志中可能出现完整请求参数、邮箱、订单或外部响应，不能按框架日志的脱敏能力推断其安全性。

2.5 后台通用操作审计：t_operation_log

注册顺序见 app/admin/middleware.php，LogOperationMiddleware 位于登录 IP 中间件之后。控制器方法使用 PHP 8 Attribute：

1#[LogOperation(
2    title: '业务名称',
3    logParams: true,
4    logResult: false,
5    recordIp: true,
6    recordDevice: true
7)]

实际逻辑：

  1. 先执行 $next($request)，拿到响应后才反射控制器方法上的 LogOperation。
  2. 没有注解直接返回，不产生记录。
  3. 通过 tinywan\\JWT::getCurrentId() 获取管理员 ID；取 ID 失败时回退为 1，这会造成审计归属风险。
  4. 读取管理员昵称、HTTP method、/admin/{controller}/{action}、反射缓存键、注解 title。
  5. logParams=true 时记录 $request->all()，仅对顶层 password、pay_password、token、卡号、CVV、有效期和 Google 验证码替换为 ******。
  6. logResult=true 时把 ThinkPHP Response 内容规范化为 JSON；非 JSON 响应会放入截断到 2000 字符的 _non_json_response。
  7. recordIp/recordDevice 打开时记录 IP、User-Agent、OS、浏览器、版本、设备类型和 IP 地区。
  8. OperationLog::create() 同步写 t_operation_log；写入失败只调用 Log::error()，不回滚业务响应。

数据字典中的 t_operation_log 字段包括 member_id、nickname、method、api、router、title、IP/设备字段、JSON 类型 request_params/response_params、remark 和时间戳。

边界：

  • 因为 $next 在前，业务抛异常时普通操作日志的保存代码不会执行；它不是完整的请求访问日志。
  • 它不记录所有接口，只记录加了 Attribute 的方法。
  • 脱敏只处理顶层键，嵌套数组、响应内容和字符串化 JSON 可能含敏感信息。
  • 当前实现计算执行耗时的起点在 $next 返回后，记录值接近零，不能作为真实接口耗时。
  • 模型字段白名单没有 remark，但中间件准备了 remark，需要以 ORM 实际行为和数据库结果继续核对。
  • operator() 关系使用 from_member_id，而数据字典字段是 member_id，列表关联可能不正确。

2.6 系统配置操作审计：t_system_operation_logs

SystemOperationMiddleware 处理 #[SystemOperation]：

1#[SystemOperation(
2    operationType: '风控',
3    configParam: '动态杠杆',
4    actionType: 'update',
5    remarkKey: 'remark',
6    recordResult: true,
7    requireGoogleCode: true
8)]

链路：

  1. 解析控制器和方法，读取 Attribute；没有 Attribute 时放行。
  2. 前置读取 remark，但当前 remark === '' 校验代码已注释，所以备注并非强制；requireGoogleCode=true 时仍强制校验 6 位 Google 验证码。
  3. 通过 SystemOperationLogService::captureBeforeSnapshot() 读取变更前快照。支持的快照对象包括角色、风险策略、自定义风控参数、提现限额规则、提现规则和登录 IP 访问规则。
  4. 执行真实业务。正常返回由 record() 写成功/失败结果；异常路径由 recordFailByException() 写失败记录后重新抛出原异常。
  5. 结果码严格为 0 或 999 才记成功 9，否则记失败 -1。
  6. change_data 优先读取响应中的 data.changed_fields；没有时比较前后快照。差异项包含字段、国际化键、旧值、新值，并递归排序 JSON 后比较。
  7. 去除请求中的 googleCode，补充 operation_type、配置项、动作、操作人、IP、UTC 操作时间、备注、扩展信息。
  8. SystemOperationLog::onBeforeInsert() 生成 SOL-YYYYMMDD-雪花ID，通过唯一索引保证唯一性。

表 t_system_operation_logs 有 uk_log_id、操作时间、操作人和操作类型索引。该表是配置变更审计，不应替代普通运行日志。

代码中还存在 Service 直接调用 SystemOperationLog::create() 的路径，例如支付状态、KYC 设置、国家配置、MT 服务器权限、风险组和 IB 邀请链接等；这些路径可能绕过统一中间件，但仍写同一张表。

2.7 账户风控修改审计：t_modify_operation_logs

ModifyReasonMiddleware 针对带修改原因 Attribute 的后台方法：

  • 前置校验管理员 Google 验证码，读取目标会员、MT 登录号、钱包余额和 MT 余额。
  • 业务成功后检查响应中的 changed_fields；为空时不写日志。
  • 记录操作人、会员 ID、MT 登录号、操作前钱包/MT 余额、IP、原因、UTC 操作时间、变更 JSON 和关联 ID。
  • ModifyOperationLog 自动生成 AOL-YYYYMMDD-雪花ID，并在 uk_log_id 冲突时最多重试三次；该 Trait 只解决编号碰撞，不是异步队列。

部分业务也会直接保存该模型，例如提现控制器和客户注册风险服务。数据字典说明该表用于账户风控项操作记录，索引覆盖操作时间、操作人、操作类型、会员 ID、MT 登录号。

2.8 登录与会话审计

后台登录入口 app/admin/controller/Pub.php::login() 在账号、角色、IP 白名单和 Google 验证器校验通过后写入 t_member_login_log，关键字段包括：

  • auth_source=ADMIN、会员/管理员 ID、Unix 时间、客户端 IP、完整 User-Agent、设备类型、OS/版本；
  • 国家、城市、国家代码、请求 URL；
  • 成功登录后生成会话/设备限制相关缓存，禁用会员时由 MemberLoginSessionService 批量锁定最多 500 条活动客户会话，并同步更新 member_login_log.logout_time 与结束原因。

共享表 t_member_login_log 同时服务 CUSTOMER 和 ADMIN。数据字典增加了 auth_source、channel、auth_method、failure_code、session_id、logout_time 等字段；session_id 有唯一索引，member_id/login_status、member_id/device_id/login_status 等索引支持审计查询。表中存在 token 字段，文档和接口应避免输出原始凭证。

MemberLoginLogService 主要负责分页筛选和展示 DTO，不在查询时补写日志；登录失败、成功和会话结束由实际认证/禁用流程写入。

2.9 会员详情与资金/交易日志

会员资料、状态、安全状态变更通过 Member::MemberDetailLog()/MemberService::memberDetailLog() 写 member_detail_log，内容包括：

1admin_id, member_id, before, after, func, type, field, status, created_at, updated_at

MemberDetailLogConstants 负责把状态值和字段名翻译为展示文本。它是字段变更事实，不是诊断文本。

资金与交易相关记录分为：

  • t_member_amount_log：会员钱包金额变更，通常和余额更新在同一业务事务/流程中写入；属于余额流水大表。
  • t_fund_detail：入金、出金、赠金、转账、返佣等资金明细，带类型、订单/会员、金额、币种、状态及 MT 去向。
  • t_member_forword_log 等转账表：记录内部/外部转账申请和状态；t_member_security_activity 或 OperationLogAspect 记录安全操作视角。
  • t_system_money_log：按业务类型汇总系统入/出及 MT 前后金额，不是逐笔审计表。
  • t_t_credit_record_log：用订单号+规则唯一键避免重复赠金，是幂等/处理证据。

后台提现、赠金、返佣控制器会同时写业务流水和 Log::write/error；发生冲突时应以业务流水、状态和幂等键核对，不能只查文本日志。

2.10 队列、MQ、定时任务与日志

gtc_admin 既有 ThinkPHP Queue，也有独立 RabbitMQ 消费入口：

  • app/service/InformationService.php::send() 默认 $queue=true，把邮件任务推到 \\app\\jobs\\controller\\MailJobs@send 的 Jobs 队列；写邮件过程还会写 ./logs/mail/YYYY-MM-DD-mail.log。
  • app/mq/controller/notify.php 声明 RabbitMQ direct queue 并消费消息，调用 Log::write() 记录消费者状态和消息体摘要。
  • app/admin/controller/Timer.php 是旧式 URL/CLI 定时控制器，白名单校验通过后执行统计、跟单、过期邮件等操作，并把进度写 ./logs/timer；它不是持久化调度器本身，实际触发依赖外部 cron、HTTP 或进程管理配置。
  • 风控返佣模块中的 sale_commission_wallet_queue 等数据库队列表是业务处理队列，带锁、重试、阶段和失败信息；这些是可查询的处理状态，不等同于 Log::info 文件日志。

队列任务应该把“投递、消费、成功、失败、重试”分别作为状态/日志记录；现有旧代码在不同模块的完整度不一致。

2.11 gtc_admin 日志风险与核对建议

  1. 框架延迟写日志和手写文件都可能在进程异常、磁盘满、权限错误时丢失；应确认生产 logrotate、备份和告警。
  2. ./logs 依赖工作目录，容器或 Supervisor 切换 cwd 后可能写到意外位置。
  3. 运行日志、审计表和资金流水混用名称，运维查询时容易误把诊断日志当成账务凭证。
  4. 普通操作审计在异常时不落库，成功/失败覆盖范围依赖 Attribute；高风险接口应优先使用系统操作/账户修改审计或明确的业务状态表。
  5. 参数脱敏不递归，手写日志和 Log::write(json_encode(...)) 可能泄露 token、密码、完整支付报文或第三方密钥。
  6. t_logger 当前只看到后台列表读取：Logger 通过 database.bigdata 查询 t_logger，按用户 ID、自然日、菜单 action_name 分页，页大小上限 100；在当前源码扫描中未找到明确写入入口，需继续向历史部署包/其他服务追溯，不能把它和 t_operation_log 视为同一张表。

3. gtcuser

3.1 技术栈与总链路

gtcuser 是 Hyperf + Swoole/Swow 风格常驻进程应用，使用 Monolog、Hyperf AsyncQueue、Hyperf Crontab、MineAdmin JWT/权限和 ORM。日志链路分为四层：

 1Controller / Service / Job / Task
 2        |
 3        +-- logger('channel')->info|warning|error
 4        |       -> LoggerFactory::get($name, $group='default')
 5        |       -> Monolog handler
 6        |       -> runtime/logs/debug-YYYY-MM-DD.log（default）
 7        |
 8        +-- 异常 Handler
 9        |       -> LoggerFactory::get('error')->error(...)
10        |       -> 默认 group 的 handler（除非显式传 group='error'）
11        |
12        +-- 管理端注解/事件
13        |       -> mine_user_operation_log / mine_user_login_log
14        |
15        +-- 客户接口注解/登录服务
16                -> member_security_activity
17                -> member_login_log / member_login_session
18                -> member_detail_log / modify_operation_logs / 资金流水

3.2 Hyperf/Monolog 文件日志

配置在 config/autoload/logger.php，格式为：

1%datetime%||%channel%||%level_name%||%message%||%context%||%extra%\n

已配置的 Logger group 和实际 handler：

group 文件 handler 级别 Processor/Lark
default runtime/logs/debug.log，RotatingFileHandler DEBUG 及以上 LogProcess；ERROR/WARNING/EMERGENCY 同步 Lark handler
error runtime/logs/error.log，RotatingFileHandler ERROR 及以上 LogProcess；同 Lark handler
sql runtime/logs/sql.log 配置为 ERROR，但查询订阅者调用 info，实际需以 Monolog 级别行为复核 无 processor
mt runtime/logs/mt.log DEBUG 及以上 无 processor
mt_lark runtime/logs/mt_lark.log DEBUG 及以上 无 processor；名称本身不代表发送 Lark
msg runtime/logs/msg.log DEBUG 及以上 无 processor
lark runtime/logs/lark.log INFO 及以上 用于 LarkWebhookService 自身 logger

RotatingFileHandler 按日期生成 debug-YYYY-MM-DD.log 等文件；配置没有明确 maxFiles 保留数量，长期保留仍依赖 Monolog 默认值和外部清理策略。Swoole 原生错误日志另由 config/autoload/server.php 的 OPTION_LOG_FILE 写入 runtime/logs/swoole.log，级别为 SWOOLE_LOG_WARNING。

关键语义来自 vendor/hyperf/logger/src/LoggerFactory.php 和 vendor/mineadmin/helpers/src/functions.php：

  • logger('pay') 调用 LoggerFactory->get('pay')，参数 $name='pay'、$group='default'；pay 是 Monolog channel 名，不会自动选择 pay.log。
  • 只有 LoggerFactory->get('sql', 'sql') 这种显式传第二个参数才会读取 sql group。
  • logger('error') 仍然默认使用 default group，所以异常处理器中的 get('error') 按当前源码会写 default handler 的 debug-日期.log，同时执行 default 的 Lark handler；它不会仅凭名字进入 error-日期.log。若生产有包装或覆盖 LoggerFactory，需要现场配置确认。
  • LogProcess 只在 default/error group 配置，sql、mt、msg 等专用 group 不经过该脱敏 Processor。

3.3 LogProcess 上下文和脱敏

app/Process/LogProcess.php 是 Monolog ProcessorInterface，不是 Hyperf Process，也不负责消费日志或写 Elasticsearch。它在 default/error group 中：

  1. 从 Context 读取 userInfo、headers、serverInfo。
  2. 从请求上下文读取 POST 数据。
  3. 计算客户端 IP，优先 X-Forwarded-For 首个值，其次 X-Real-IP，最后 remote_addr。
  4. 把 headers、client_ip、serverInfo、request、email、user_id 合并到 context，并把 serverInfo 放入 extra。
  5. 对 password、password_confirmation、fund_password、旧/新密码、authorization、cookie、set-cookie、x-api-key 做递归字段脱敏；敏感请求头直接删除。
  6. 数字索引 context 改名 p0/p1，数组/对象 JSON 字符串化，避免 Monolog/下游字段类型混乱。

AbstractController 会设置 headers 和 serverInfo；ApiTokenMiddleware 在 token 成功解析后设置 userInfo。Processor 不能保证对已经拼接到 message 字符串中的敏感值进行脱敏，专用 group 也没有 Processor；异常时 Processor 捕获错误并使用 PHP error_log() 后返回原记录。

3.4 Lark 告警链路

default 和 error group 注册 LarkWebhookHandler，只处理 ERROR/WARNING/EMERGENCY（具体还受 LARK_LOG_LEVELS 环境配置影响）：

1logger(...)->error()
2  -> Monolog LarkWebhookHandler
3  -> LarkWebhookService::pushLog()
4  -> Guzzle HTTP POST 到配置的 Lark webhook

LarkWebhookService 使用 10 秒 HTTP 超时，webhook 为空或请求失败时返回 false，不会抛出影响原业务的异常。它会调用 LoggerFactory->get('lark') 记录自身日志，正常落到 lark group 的文件 handler。

源码中还存在 app/Jobs/Security/SiteVisitLarkNoticeJob.php 等 AsyncQueue Lark 任务；这些是显式异步通知。LarkWebhookHandler 本身是同步 Monolog Handler，不是队列消费者，告警服务不可用时不能依靠该 handler 自动重试。

3.5 异常和 SQL 日志

app/Exception/Handler/AbstractHandler.php 的异常流程：

  1. handle() 先调用 report()，再生成业务响应。
  2. Debug 模式把格式化异常打印到 StdoutLoggerInterface，并把文件、行号、trace 放入调试响应上下文。
  3. 所有异常调用 LoggerFactory->get('error')->error($message, ['exception' => $throwable])。
  4. 响应统一补 Request-Id，便于用请求 ID 关联文件日志和安全审计。

config/autoload/listeners.php 注册 MineAdmin DbQueryExecutedSubscriber。它仅在 APP_DEBUG=true 时监听 QueryExecuted，把连接名、SQL 执行耗时和绑定值替换后的 SQL 写入 loggerFactory->get('sql')。绑定值被简单拼到 SQL 文本中，调试环境仍可能出现个人信息或敏感参数；生产关闭 APP_DEBUG 才不会记录全部 SQL。

3.6 MineAdmin 管理端操作日志

OperationMiddleware 不是全量 HTTP access log。它只对能从控制器方法解析到 Swagger Get/Post/Delete/Patch/Put Attribute 的接口，在真正 handler 执行前派发 RequestOperationEvent，字段为：

1userId, operation(summary), path, client IP, HTTP method

UserOperationSubscriber 收到事件后查管理员，再用 Coroutine::create() 调用 UserOperationLogService->save() 写 mine_user_operation_log，字段包括 username、method、router、service_name、ip、remark。Coroutine::create() 只是当前进程中的协程调度，不是 Redis 队列；进程崩溃时可能丢失，且中间件在业务执行前派发，所以不能证明请求最终成功。

管理员登录由 JWT UserLoginEvent 触发 UserLoginSubscriber，协程写 mine_user_login_log：username、IP、OS、browser、status（1 成功、2 失败），模型创建事件补 login_time。Repository 和管理控制器提供筛选、列表、删除接口。

表结构见 gtcuser/docs/数据字典.sql：

  • t_mine_user_login_log 有 username 索引，字段是管理员登录诊断/审计信息。
  • t_mine_user_operation_log 有 username 索引，保存后台操作路由和业务名称。
  • Namespace/Service 名称含 Logstash，但当前 Model/Repository 使用 Hyperf ORM 直接写关系型表，没有看到 Elasticsearch 客户端；不能据此认定已经写入 ES。

3.7 客户安全活动与 AOP 操作日志

OperationLogAspect 由 #[OperationLog] 方法 Attribute 触发，当前明确使用在：

  • PayController 入金、出金；
  • CashController 转账，按 type 区分内部/外部转账；
  • SocialTradingController、SecurityPolicyController 的若干客户安全/社交交易操作。

处理逻辑：

  1. 读取请求 body 和 member_id header，默认状态为失败 2。
  2. 调用真实方法；结果码为成功时状态改为 1，并从结果的 idField 提取关联业务 ID；非成功响应把 message 写入 remarks。
  3. 抛出异常时，业务异常写真实 message，普通异常写 System Error；错误码 10001 会抑制写入。
  4. finally 补 activity_type，并调用 MemberSecurityActivityService::createRecord()。
  5. Service 补充 IP、device-id、User-Agent；Repository 解析 IP 地区、OS、浏览器、版本后保存 t_member_security_activity。

该表字段包括会员、关联业务 ID/UUID、操作类型、终端、IP、国家城市、OS、设备、状态、浏览器、备注和时间，并有会员、创建时间、业务 ID/类型等索引。该日志是客户安全审计，不是通用请求日志。

注意：finally 中 transfer 缺少 type 时直接 return 一个失败 Result，可能影响原始返回/异常传播；这属于实现风险，应单独测试。

3.8 客户登录、会话和会员安全记录

MemberLoginLogService 是客户登录审计的核心：

  • UserLoginBeforeListener 识别密码认证、用户不存在/手机未验证/设备和 IP 风控等前置失败；已识别会员被锁定时写失败日志。
  • UserLoginAfterListener 处理密码错误、登录失败次数、锁定风控证据和成功/失败登录记录。
  • MemberLoginLogService::record() 统一补 auth_source=CUSTOMER、APP/WEB、客户端名称/版本、OS、设备展示值、设备标识哈希、认证方式、标准失败码等字段。
  • 成功登录时在同一数据库事务中锁定会员、解析 JWT 的 sid、写 member_login_log 和 member_login_session；账号被禁用或状态无效时抛出异常，不建立会话。
  • MemberLoginSessionService 负责刷新/结束客户会话，管理端禁用客户时使用共享表的行锁和有界批次同步结束日志。

数据字典中的 t_member_login_log 有 session_id 唯一键、IP/时间/会员+状态/设备索引；t_member_login_session 以 session_id 为主键，并有 (member_id, auth_source, ended_at) 索引。登录日志中的 token 只用于历史兼容/认证流程，管理接口展示层应避免返回原始 token。

3.9 会员资料、资金和交易业务记录

gtcuser 与 gtc_admin 共用多类业务表和数据库连接，写入点主要在 Service/Repository：

  • member_detail_log：会员资料、安全开关、代理关系等字段的 before/after；由 MemberDetailLog Model 或批量插入写入。
  • modify_operation_logs：账户风控、MT 账户修改原因和变更字段；App\\Model\\member\\ModifyOperationLog 与管理端使用同表。
  • member_amount_log：钱包金额变化；是大表，应按会员、时间、流水类型和主键范围查询。
  • fund_detail：入金、出金、赠金、转账、返佣资金去向及状态；FundChangesHistoryService 等服务用它生成资金历史。
  • member_forword_log、withdraw_refund_op_log 等：转账/退款/出金处理步骤和关联 ID。
  • mail_log、msg_log：通知发送结果，属于发送事实/供应商回执记录；详细邮件链路见已有《邮件功能技术架构与运行逻辑梳理》文档。

资金表、交易表和文本日志的职责不同：文本日志用于定位调用阶段，业务表用于重放状态、对账和审计；任何补偿任务都应以业务表状态和幂等键为准。

3.10 AsyncQueue、协程与定时任务中的日志

config/autoload/async_queue.php 配置 Hyperf AsyncQueue RedisDriver，主要 pool 包括 default、fast、height、security_event、lark 等；队列开关由 ASYNC_QUEUE_ENABLED 控制，各 pool 有进程数、并发数、超时和重试间隔。

当前日志相关行为：

  • 邮件、Lark 通知、风控事件、报表和外部同步等大量 Listener 使用 #[AsyncQueueMessage(pool: 'fast' 或其他)]，或者显式 pushQueue(new Job(...), ..., 'pool')。
  • Job 的发送前、成功、失败、跳过和重试通常用 logger('业务名') 写文件；邮件 Job 还更新邮件发送记录。
  • 管理端审计 Subscriber 使用 Coroutine::create()，不经过 AsyncQueue。
  • Hyperf\\Crontab\\Annotation\\Crontab 标记的 app/Task 由常驻进程定时触发，常见任务在开始、完成、跳过、异常、锁失败等阶段调用 logger('TaskName')。singleton=true、mutexExpires 用于单例/互斥，不等同于队列。
  • 例如返佣异常检测、短信滥用检测、MT 登录归档、转账待处理检查、PAMM/交易历史同步、佣金结算等 Task 都有独立 channel 名，但因未配置同名 logger group，通常仍落 default debug 文件；只有显式 LoggerFactory->get('mt') 等才会落到专用文件。

队列具备 Redis 持久化、重试与多进程消费能力；定时任务是触发器，通常在任务内查询业务表并更新状态。日志本身没有统一的任务执行表，需结合 Job 状态、业务表和对应 channel 文件排查。

3.11 gtcuser 日志风险与核对建议

  1. logger('error') 的 group/name 语义容易误判，实际文件落点必须按 LoggerFactory::get($name, $group) 核对。
  2. 只有 default/error group 使用 LogProcess；专用 group、直接拼接 message、Job/Task 参数可能绕过统一脱敏。
  3. Lark handler 是同步 HTTP 推送，失败仅返回 false；需要告警重试时应使用 lark AsyncQueue Job，并记录投递状态。
  4. MineAdmin 管理操作日志在业务 handler 前写入，且用协程直接 ORM 保存，无法证明业务成功，存在进程退出丢记录的窗口。
  5. 客户安全 AOP 只覆盖声明了 OperationLog 的接口；未加 Attribute 的入金、出金、转账或安全操作不会自动生成该表记录。
  6. SQL 日志仅在 Debug 开启，且把绑定值替换进文本；生产排查不能依赖 SQL 文件，开发环境也要避免使用真实敏感数据。
  7. 常驻 Swoole/队列/定时任务需要分别设置文件采集、轮转、保留和磁盘告警；Monolog 的日期轮转不等同于删除旧文件。

5. 建议的日志关联查询路径

5.1 请求/后台操作

  1. 先用请求时间、管理员 ID、IP、路由在 t_operation_log 或 mine_user_operation_log 查审计记录。
  2. 用同一时间窗口、请求 ID（gtcuser）或业务订单/会员 ID筛查文件日志。
  3. 若是配置变更，优先查 t_system_operation_logs 的 log_id、操作人和 change_data。
  4. 若是会员账户修改，查 t_modify_operation_logs、member_detail_log 以及业务主表最终状态。

5.2 登录/安全

  1. member_login_log 先按 member_id + create_time 或 session_id 查，区分 CUSTOMER/ADMIN。
  2. 再关联 member_login_session 的 ended_at/end_reason，确认是否真实建立和结束会话。
  3. 安全操作查 member_security_activity 的 activity_type + activity_id，再回到入金、出金、转账主表。
  4. 管理员登录单独查 mine_user_login_log，不要把客户失败登录和后台账号失败登录混在一起。

5.3 资金/交易

  1. 以订单号、会员 ID、MT login、时间范围和状态缩小 member_amount_log/fund_detail 大表范围。
  2. 以 fund_detail.type/type_id、转账单 ID、提现单 ID 关联业务状态。
  3. 文本日志只用于定位外部调用、重试和错误阶段；最终金额、状态和幂等结果以数据库事实为准。

6. 优先级改进建议

P0：先解决审计完整性和敏感信息

  1. 建立统一日志分类规范：诊断、审计、资金流水、通知回执分别定义字段和查询入口。
  2. 禁止在诊断日志中写原始 token、密码、支付卡信息和完整第三方报文；对手写文件和字符串化 JSON 做递归脱敏。
  3. 修正 gtc_admin 普通操作日志异常不落库、管理员 ID 回退 1、执行耗时计算位置和模型字段/关联字段问题。
  4. 核对 gtcuser logger('error') 的真实文件落点，必要时显式使用 get('error', 'error')，避免错误分流不符合预期。

P1：提高可检索性和可靠性

  1. 给每条请求、Job、Task、MQ 消息补统一 request_id/job_id/order_id/member_id，并在文件、Lark、业务审计表中保持同名字段。
  2. 管理操作审计改为业务成功后写入，或至少增加 started/succeeded/failed 状态和异常原因；协程写入改为可靠队列或事务外盒表。
  3. 对 Lark 同步 Handler 增加失败重试/降级计数，使用 AsyncQueue 发送告警；记录 HTTP 状态、重试次数和最终结果。
  4. 明确所有日志目录的容器挂载、权限、轮转、保留期、备份和磁盘告警，不依赖 max_files=0 或 Monolog 默认值。

P2：性能与运营

  1. 大表审计查询强制时间范围、会员/订单高选择性条件和分页；禁止全表 count/sum。
  2. 对 t_logger 的写入来源、库连接和保留策略做一次全链路追溯；确认它是否由其他服务/历史部署包写入。
  3. 统一 Task/Job 日志格式，至少包含开始、结束、处理数量、跳过数量、失败数量、耗时、游标和重试原因。
  4. 建立脱敏回归测试和日志落点检查，覆盖 default/error/sql/mt/msg/lark 等 Monolog group 以及两个项目的共享业务表。

7. 本次梳理的边界与验证方式

  • 本次未修改业务代码，只新增本文档。
  • 已静态阅读日志配置、ThinkPHP/Hyperf 日志驱动、异常 Handler、中间件、Attribute、Service、Model、Repository、队列/定时任务定义和数据字典关键表结构。
  • 未连接生产数据库、Redis、RabbitMQ、Lark、SMTP 或 MT 服务，因此没有验证生产环境实际目录、环境变量值、队列积压和日志保留天数。
  • 生产上线前应使用合成数据做一次验证：普通 record/write 落点、异常落点、注解成功/失败路径、客户登录会话事务、AsyncQueue 重试、Crontab singleton、Lark 失败降级和敏感字段脱敏。
