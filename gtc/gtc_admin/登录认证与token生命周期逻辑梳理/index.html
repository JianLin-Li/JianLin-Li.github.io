登录认证与 token生命周期逻辑梳理

2026-10-27 项目：gtc_admin

登录认证与 Token 生命周期逻辑梳理

梳理日期：2026-10-03。范围：当前本地 gtc_admin、gtcuser 源码及实际安装的相关依赖；补充 gtc_admin_vue 的后台凭证存储行为。

本文是源码分析结果，未修改业务代码。未读取 .env、证书、实际部署密钥、真实 Token 或生产日志，也未连接数据库、Redis 或外部认证服务。所有时间和用户数据示例均为虚构数据。文中默认值来自仓库配置，不能直接等同于线上运行值。

1. 核心结论

系统中至少存在四条需要区分的认证链路：

项目与认证域 主要入口 技术实现 访问令牌中用户 ID 的位置 刷新令牌形式
gtc_admin 管理后台 /admin/pub/login ThinkPHP、Tinywan think-jwt、Firebase PHP-JWT、HS256 extend.id JWT，结构与访问令牌相同，无用途声明
gtcuser CRM 客户登录 /api/pub/login，注册自动登录、第三方登录等 Hyperf/MineAdmin、自定义 Mine\Jwt\Jwt、Lcobucci JWT、HS256 jti JWT，通过 sub="refresh" 标识用途
gtcuser 自带管理端 /admin/passport/login MineAdmin Passport、同一个自定义 JWT 类，default 场景 jti JWT，通过 sub="refresh" 标识用途
gtcuser 独立 OAuth2 授权 /api/oauth2/token League OAuth2 Server、RSA RS256、Defuse Crypto sub；jti 为随机令牌 ID 加密的 JSON，不是 JWT

最重要的区别如下：

  1. token_type 是响应中固定的字符串 Bearer，用来提示客户端按 Authorization: Bearer <access_token> 携带凭证；它不是 Token 内部的随机字段，也不参与密码验证。
  2. gtc_admin 返回 expires_in；CRM 客户登录返回 expire_at 和 expire_time。客户侧的 expire_at 实际表示有效期秒数，expire_time 才是绝对到期时间戳。
  3. 后台有 JWT 固定截止时间和 Redis 滑动会话两套时钟。续 Redis TTL 不会改变已经签名的 JWT exp，并且当前滑动会话校验只覆盖数据库中 admin 或 scope 为真的账号及相关执行路径。
  4. 客户侧正常新登录会生成随机 sid，访问和刷新令牌共享该会话；数据库保存会话截止时间和刷新版本 version，JWT 中的 sv 用于刷新时阻止旧凭证重复轮换。
  5. 后台源码中 access_secret_key、refresh_secret_key 是相同的固定字符串默认值，默认有效期也相同。两种 JWT 没有用途声明：在生成的时间字段相同时，access_token 和 refresh_token 可以完全一致。本文不展示密钥内容。
  6. 后台依赖库提供刷新方法，但当前应用代码未发现调用该方法的业务刷新入口；不能因为响应有 refresh_token 就认为前端已实现自动刷新。

2. 统一理解字段和 JWT

2.1 响应字段与令牌内部字段

字段 所在位置 单位或格式 作用
access_token 登录/刷新响应；客户端存储 字符串 后续资源请求的认证凭证
refresh_token 登录/刷新响应；客户端存储 JWT 或 OAuth2 加密字符串 获取新访问令牌；一般不用于普通业务请求
token_type 后台 Tinywan、OAuth2 响应 固定 Bearer 指定请求头认证方案；CRM 普通登录不返回该字段
expires_in 后台 Tinywan、OAuth2 响应 秒数 后台为配置的访问有效期；OAuth2 为返回时剩余有效期
expire_at CRM、MineAdmin Passport 响应 有效期秒数 虽名为 at，当前源码并未赋绝对时间
expire_time CRM 登录/刷新响应 Unix 秒时间戳 time() + expire_at，给客户端估计截止时间
exp JWT 载荷 Unix 秒时间戳 服务端校验 Token 到期的核心标准声明
iat JWT 载荷 Unix 秒时间戳 签发时间；客户侧还与会员失效水位比较
nbf JWT 载荷 Unix 秒时间戳 最早可使用的时间
expires_at 客户会话表或 OAuth2 表 会话表为 Unix 秒；OAuth2 模型为日期时间 持久化生命周期截止时间，与响应 expire_at 不是同一字段
expires 客户 Redis Token 列表元素 Unix 秒时间戳 设备列表内某枚访问令牌的预计截止时间

服务端不会相信客户端自行提交的 expire_at、expire_time 或 expires_in 来决定是否登录。客户端把这些值改大，不能延长签名 JWT 的寿命。

2.2 JWT 是怎样组合出来的

两项目的 HS256 JWT 都采用三段结构：

1base64url(JSON(header)) . base64url(JSON(payload)) . base64url(signature)
2
3signature = HMAC-SHA256(
4    secret,
5    base64url(JSON(header)) + "." + base64url(JSON(payload))
6)

典型头部为 {"typ":"JWT","alg":"HS256"}。签名保护载荷不被篡改，不会加密载荷；拿到 Token 的人可以解码看到其中的邮箱、用户 ID 等字段。真正接受凭证前必须验证签名、有效期和业务失效状态。

OAuth2 的访问 JWT 使用 RS256：私钥签名、公钥验证；它的刷新凭证则对 JSON 做加密，不能套用上述三段 JWT 解释。

2.3 默认时间配置对比

认证链路 访问有效期 刷新有效期 额外时限
gtc_admin JWT_TTL，默认 7200 * 8 = 57600 秒，16 小时 JWT_REFRESH_TTL，默认同为 57600 秒 SESSION_EXPIRE 默认 3600 秒；JWT 时钟容差默认 60 秒
gtcuser CRM JWT_TTL，默认 3600 秒 JWT_REFRESH_TTL，默认 7200 秒 黑名单 JWT_BLACKLIST_TTL 默认 7201 秒；会话截止取刷新 JWT exp
gtcuser Passport 同上 同上 默认没有 CRM 的 sid 会话生命周期
gtcuser OAuth2 OAUTH2_ACCESS_TOKEN_TTL 默认 PT1H OAUTH2_REFRESH_TOKEN_TTL 默认 P1M 授权码默认 PT10M；静默登录票据默认 60 秒

P1M 是 PHP DateInterval 的一个日历月，不应直接解释为固定 30 天。CRM JWT 支持 <device>_ttl、<device>_refresh_ttl 覆盖，如 pc_ttl、app_refresh_ttl；当前仓库 JWT 配置未声明这些覆盖键，所以静态默认回退到通用 TTL。

配置证据：后台 JWT 配置、客户 JWT 配置、OAuth2 TTL 读取。

3. gtc_admin：管理后台登录

3.1 入口与密码验证

入口为 Pub::login()。主要流程：

  1. 读取登录参数；阿里验证码开关启用时，先验证 captchaVerifyParam。
  2. 当前仅开放邮箱密码登录；type == 1 的手机号登录直接返回“暂未开放”。
  3. 读取 login_error_count + md5(email)。失败次数达到 5 次拒绝登录；错误密码使计数增加并缓存 600 秒。
  4. 密码经过 encrpyt_password() 后与会员表密码字段匹配。当前算法是 md5(password + salt)，默认使用固定盐；本文不展示盐值。
  5. 检查账户状态、IP 白名单、member_other.admin_banned_login。超级管理员/范围管理员跳过普通角色限制；普通账号必须具有允许后台登录的角色。
  6. 插入 member_login_log，认证来源 auth_source = ADMIN。
  7. 启用 app.admin_google_auth 且账号为 admin/scope 时，校验 Google 验证码。
  8. 签发 JWT，写 Redis 会话及可选终端集合，返回结果。

审计时序需要特别注意：登录日志插入在 Google 验证码校验之前，也在 Token 签发之前。因此这一条日志不能单独证明二次验证已完成或客户端已经取得 Token；该写入也没有保存随后生成的访问令牌。

证据：密码 helper、后台登录审计写入、Google 校验及签发。

3.2 access_token 和 refresh_token 的实际字段

控制器构造如下业务数据，再交给 tinywan\JWT::generateToken($user)：

字段 来源 在 JWT 中的位置
id 会员 ID extend.id
name 会员 nickname extend.name
email 会员邮箱 extend.email
admin `member.admin

Tinywan 生成的公共载荷为：

JWT 声明 访问令牌 刷新令牌
iss config.jwt.iss，默认 think.tinywan.cn 相同
aud 同样取 config.jwt.iss 相同
iat 生成时 time() 复用公共载荷的值
nbf time() + config.nbf；仓库配置为 -1 相同
exp time() + access_exp 替换为 time() + refresh_exp
extend 上表四个业务字段 相同

这里没有 jti、sid、sv、sub="refresh"、密码或设备指纹声明。aud 也不是请求域名自动生成的。

虚构的访问 JWT 解码示例：

 1{
 2  "iss": "think.tinywan.cn",
 3  "aud": "think.tinywan.cn",
 4  "iat": 1800000000,
 5  "nbf": 1799999999,
 6  "exp": 1800057600,
 7  "extend": {
 8    "id": 123,
 9    "name": "Example Admin",
10    "email": "admin@example.invalid",
11    "admin": true
12  }
13}

访问签名读取 access_secret_key，刷新签名读取 refresh_secret_key。当前仓库两项是同一个固定字符串；在默认 TTL 相同且生成的 exp 相同时，两种令牌输入完全相同，签名也相同。若实际 TTL 被配置为不同值，或生成跨秒，则令牌字符串可能不同，但当前没有独立用途声明供解析器区分。

证据：业务字段、generateToken、generatePayload。

3.3 响应与 token_type、expires_in

控制器将 Tinywan 返回数组放在业务响应的 data 中：

 1{
 2  "code": 0,
 3  "message": "登录成功",
 4  "data": {
 5    "token_type": "Bearer",
 6    "expires_in": 57600,
 7    "access_token": "<访问凭证，占位符>",
 8    "refresh_token": "<刷新凭证，占位符>"
 9  }
10}
  • token_type 为库代码固定赋值，不从数据库读取，不在载荷中。
  • expires_in 为 access_exp 的秒数，不反映 Redis 当前剩余 TTL，也不是刷新令牌寿命。
  • 此入口不返回 expire_at、expire_time。
  • refresh_disable=false 所以生成刷新令牌；refresh_is_store=false 所以默认不将完整刷新令牌存入 Tinywan 的 Redis 存储。

3.4 生成后服务端存在哪里

同一缓存 admin_member_login_device_set_{memberId} fingerprint => {t: 登录时间, tk: md5(access_token)} 同为 SESSION_EXPIRE；限制终端数量、定位淘汰对象

该终端集合在登录/退出时维护，不能等同于每次请求都同步刷新的完整在线设备表；普通访问续期的是 Token 标记，集合 TTL 并未随之统一更新。

证据：会话和终端缓存写入、默认 Redis 缓存、Tinywan RedisHandler。

3.5 后台客户端如何保存

已核对对应的 gtc_admin_vue：

  1. src/api/login/index.js 调用 /admin/pub/login，成功后只将 res.data.data.access_token 交给 setToken()。
  2. 当前 setToken() 将凭证写入 localStorage.access_token，移除旧的 sessionStorage 同名值；getToken() 优先本地存储，兼容会话存储。
  3. “记住我”另存为 login_remember_persist 标记，不决定 JWT 的 exp，也不改变后端 Redis TTL。
  4. 多标签页模块维护页签登记和离开标记，下次加载可清理已关闭所有页签的登录态；浏览器存储本身没有后端 Token TTL。
  5. 请求拦截器添加 Authorization: Bearer <access_token>。
  6. 响应拦截器可以读取响应头 authorization 并替换本地凭证，但这仅代表前端有接收能力。本次后台登录/鉴权链路未发现常规请求自动签发新 JWT 并下发该响应头的实现。
  7. 上述登录路径没有保存 refresh_token、token_type 或 expires_in，也未发现使用后台刷新令牌的调用。

证据：前端登录、Token 存储、请求 Authorization、响应头替换能力、页签生命周期。

3.6 登录时和后续请求怎样验证 Authorization

用户名密码登录时：Pub 是登录校验跳过的控制器。登录依赖密码、验证码、账户/角色/IP 等校验，不要求客户端先有有效 Authorization。因此不要把“密码登录验证”和“后续凭证校验”混为一件事。

受保护请求时：存在 CheckLogin 中间件和 BaseController 构造逻辑两处校验。控制器构造涉及框架创建时机，不应将它们画成所有路由都严格按同一顺序执行的一条流水线；它们共同构成认证检查。

flowchart TD R[后台请求] --> E{是否登录校验跳过路径} E -->|否| H[取得 Authorization] H --> J[校验 JWT 格式、算法、签名和时间] J --> U[读取 extend.id] U --> M[查询当前会员状态、后台禁用、IP与权限] M --> A{当前数据库 admin 或 scope 为真} A -->|是且进入会话检查路径| C[校验 admin_user_token 标记并续 Redis TTL] A -->|否| P[后续节点与数据权限判断] C --> P E -->|是| X[执行对应开放逻辑]

具体行为：

  • CheckLogin 跳过 Pub、Kchart 以及其 notauth 中的 index/groups、index/server_list。BaseController 的跳过条件不同，不能由一个中间件的白名单推断接口最终完全免认证。
  • 受保护路径先要求请求头包含 Bearer ；Tinywan 的解析更严格：整个字符串按空格拆分必须恰好两项，第一项必须是大小写精确的 Bearer，Token 必须非空，字符串必须有两个 .。
  • Firebase 解码验证配置的算法和签名，以及时间声明；后台 leeway=60 为时间校验提供容差。nbf 配置为 -1，表示比签发时刻早一秒可用。
  • Tinywan 从验证后的 extend.id 得到用户 ID。当前实现虽然写了 iss/aud，但没有额外约束要求它们等于预期签发者/受众。
  • BaseController 按用户 ID 查当前 status=1 的会员，检查 admin_banned_login、IP 白名单、节点和数据权限；角色权限不是单靠 JWT 的一个布尔字段决定。
  • 数据库中当前 admin/scope 为真时，checkadmin() 要求 extend.admin 为真。普通角色后台账号走不同权限分支，不能把全部后台用户都视为这个布尔分支。
  • _logger() 会调用 refreshAdminTokenSession()，要求会话标记存在并重置 TTL；全局搜索也有专门调用。该方法对 admin=false 直接返回；_logger() 对 URI 含 get_notify 的请求提前返回，跳过这一处会话检查与续期。
  • 解析失败在中间件可能返回业务 code=401；基类失效通常返回 code=10002。这些 JSON 业务码不能不加区分地当作 HTTP 状态码。

证据：CheckLogin、基类会员与权限检查、严格请求头解析、签名验证、会话检查入口。

3.7 Redis 续期与 JWT 到期的关系

以虚构登录时刻 T 和仓库默认值为例：

1JWT 访问令牌固定截止：T + 57600 秒
2Redis 初始会话截止： T + 3600 秒
3
4若 T + 1800 秒的请求进入续期逻辑：
5Redis 新截止 = T + 1800 + 3600
6JWT exp 仍然 = T + 57600

对执行会话检查的账号/路径，Redis 提前过期会导致 JWT 尚未到期也不能使用；持续访问最多维持缓存，无法跨越 JWT 固定截止时间。普通角色或跳过该检查的路径不具备完全相同的空闲过期行为。

源码注释中的“加半小时”不是准确配置说明：实际使用 (int) env('SESSION_EXPIRE', 3600)，默认是一小时。

证据：refreshAdminTokenSession。

3.8 刷新、退出与其他签发路径

刷新能力：Tinywan 的 JWT::refreshToken() 从 Authorization 取刷新 JWT，使用刷新配置验证，可选比对 Redis 中保存的刷新令牌，然后替换 exp 并签发访问令牌。返回值只有 access_token，不会同时轮换刷新令牌，也不会自动写应用自己的 admin_user_token 标记。当前应用 app/ 中未发现该方法的调用，所以这是依赖库能力，不是已确认上线的后台刷新流程。

退出：Pub::logout() 优先读输入 token，然后读 Authorization 的 Bearer 凭证，最后读输入 access_token；删除对应会话缓存。若 JWT 仍能验证则定位用户，并按当前设备指纹移除终端集合项。它不建立 JWT 黑名单，也不统一撤销刷新凭证。因缓存校验范围有限，不能断言后台退出后同一 JWT 在所有后台账号和路径上都立即失效。

IP 拒绝分支：check_ip_list() 调用 JWT::deleteRefreshToken($token)，传入的是令牌字符串；依赖库实际期望用户 ID 并删除 JWT:REFRESH_TOKEN:{id}。因此这段代码不能作为刷新凭证已正确撤销的证据，当前刷新存储又是关闭的。

后台模拟客户登录：Role::demo_login() 通过内部调用访问 gtcuser 的 remoteDemoLogin，取得的是客户侧 JWT，不是 Tinywan 后台 JWT，见 4.8。

后台注册代码中的签发：Member.php 有一处调用 generateToken()，随后马上把 $token 置为空数组，最终返回空数据；不能把这段当成已向客户端交付的自动登录凭证。

证据：依赖库刷新方法、退出、IP 拒绝分支、模拟登录、注册签发后覆盖。

4. gtcuser：CRM 客户登录

4.1 实际生效的技术实现

普通客户登录使用 App\Http\Common\Lib\OAuth\OauthPassportService，JWT 场景名为 oauth。它的名称含 OAuth，但这里是项目自己的密码/第三方登录 JWT 契约，不能直接等同于第 6 节的 League OAuth2 Server。

config/autoload/annotations.php 将 Mine\Jwt\Jwt 映射到 app/Common/Lib/Jwt/Jwt.php，所以梳理必须以这份覆盖实现为准。Mine\Jwt\Factory 根据场景加载配置，最终使用 Lcobucci 的 JwtFacade 和项目时钟签发/解析。

签名算法为 HMAC SHA256（HS256）；密钥通过 InMemory::base64Encoded(env('JWT_SECRET')) 读取。同一仓库默认 default 和 oauth 场景使用同一个环境变量，客户访问和刷新令牌也使用同一个场景签名密钥。

配置声明了 claims.iss，但当前覆盖实现的构建方法没有读取并添加这些默认声明。因此实际客户 JWT 不能凭该配置断言包含 iss。

证据：类映射、实际 Jwt 实现、场景工厂、配置。

4.2 密码登录完整调用链

sequenceDiagram participant C as 客户端 participant P as PubController participant S as OauthPassportService participant J as 自定义 JWT participant R as Redis participant D as 登录日志/会话数据库 C->>P: 邮箱或手机号、密码、设备信息 P->>P: IP、地区、撞库防护及参数校验 P->>S: 前置事件检查后调用 login S->>S: 验证密码、检查设备数量 S->>J: 共享 email/sid/sv 签发 access 和 refresh S->>R: 写 login_token 列表 S->>D: 登录后事件写日志和 sid 会话 D-->>S: 同库事务成功 S-->>P: Token 对、expire_at、expire_time P-->>C: 业务响应

入口 PubController::login() 对应 /api/pub/login：

  1. 检查客户端 IP、地区规则、登录参数和撞库防护。type=0/1 对应邮箱/手机号密码登录；手机号经敏感信息登录服务解析。
  2. 查到用户后触发 OAuthBeforeEvent。监听器处理手机号验证状态、密码错误锁定及业务风控等。配置默认最大密码错误次数为 3 次，锁定时长 10 分钟，实际以运行配置为准。
  3. OauthPassportService::login() 调用会员 verifyPassword()；其最终使用 encryptPwd()，当前也是 md5(password + 固定盐)。
  4. 管理员重置的临时密码有单独分支：验证重置记录、状态和有效期，返回业务异常及 reset_token 要求改密，不会直接按普通登录返回访问/刷新 Token。
  5. 正常密码通过后，执行设备数量限制 loginSafe()，生成会话声明，签发 Token 对，缓存访问 Token 列表。
  6. 同步触发 OAuthAfterEvent，成功监听器将原始访问 Token 和 Token 对传给 MemberLoginLogService::record()。
  7. record() 在数据库事务中锁会员行，复核 status=1、banned_login!=1，创建登录日志和会话记录；失败登录不会创建会话。
  8. 返回 expire_at 和 expire_time。前置/密码/后置阶段的失败会按现有审计逻辑记录，不能把所有异常都理解为密码不正确。

证据：前置监听器、登录服务、会员密码验证、密码 helper、登录后监听器、同库写入。

4.3 客户 Token 精确载荷

MemberLoginSessionService::claims() 每次正常新登录返回：

1email = 用户邮箱
2sid   = bin2hex(random_bytes(16))，32 位十六进制随机字符串
3sv    = 整数 0

当前方法无条件添加 sid/sv。其旧注释“未开启时保留旧 Token 契约”与代码分支不一致，不能据注释推断正常登录缺少会话字段。

声明 access_token refresh_token 说明
iat 签发时间 各自签发时间 JwtFacade 自动补充，当前使用 Unix 秒序列化
nbf 各自签发时刻 各自签发时刻 默认没有后台那样的 -1 偏移
exp 签发时刻 + 设备访问 TTL 签发时刻 + 设备刷新 TTL 具体 TTL 由覆盖配置或通用配置取得
jti 字符串会员 ID 字符串会员 ID 当前把 ID 当用户 ID，不是随机唯一 Token ID
aud pc 或 app 同设备类型 用作设备类型；不是 OAuth2 的 client ID
email 用户邮箱 同邮箱 自定义字段在载荷根部
sid 本次登录的随机会话 ID 同一个 sid 两枚令牌关联同一持久化会话
sv 初始 0，刷新后增加 同一版本 刷新校验使用；普通 HTTP 访问不比对该版本

Lcobucci 构建/解析对象中 aud 为数组，单受众在 JWT JSON 编码时会统一成字符串。因此看到解码 JSON 的 "aud":"pc"，和服务代码取 claims()->get('aud')[0] 并不矛盾。

虚构访问 JWT 的载荷：

 1{
 2  "iat": 1800000000,
 3  "nbf": 1800000000,
 4  "exp": 1800003600,
 5  "jti": "123",
 6  "aud": "pc",
 7  "email": "member@example.invalid",
 8  "sid": "0123456789abcdef0123456789abcdef",
 9  "sv": 0
10}

虚构刷新 JWT 在上述业务字段基础上，将 exp 改为 1800007200 并加入 "sub":"refresh"。真实两次签发可能跨秒，不应假设两个 iat 永远完全一样。

不在正常客户 JWT 中的字段包括密码、原始手机号、角色列表、IP、设备实例 ID、auth_source、token_type、响应 expire_at/expire_time。审计表中的认证来源和设备详情不等于 JWT 声明。

证据：sid/sv 生成、访问构建、刷新构建、时间自动补充、单受众编码。

4.4 expire_at 和 expire_time 的实际作用

普通客户登录和刷新结果的核心数据形态是：

1{
2  "access_token": "<访问凭证，占位符>",
3  "refresh_token": "<刷新凭证，占位符>",
4  "expire_at": 3600,
5  "expire_time": 1800003600
6}

计算公式：

1expire_at   = jwt.getExpireTime(deviceType)       // TTL，秒
2expire_time = 返回组装时的 time() + expire_at     // 绝对 Unix 秒
3JWT exp     = JWT 签发时刻 + 对应 TTL             // 真正校验依据

expire_time 是返回组装时计算的，之前可能发生事件处理和数据库写入，所以它与 JWT exp 有小幅偏差的可能。客户端需要精确截止时间时，应以经过正确处理的 Token exp 为参照；服务端始终验证签名后的 exp。

CRM 返回中没有 token_type、expires_in，但约定仍可按 Bearer 请求头发送访问令牌。该 expire_time 描述的是访问令牌，不是刷新令牌或整段可刷新会话的寿命。

4.6 Authorization 如何验证

全局 HTTP 中间件会先处理 ApiTokenMiddleware，再进入具体路由和其认证要求。密码登录本身不要求已有有效访问令牌。

读取凭证优先级：

1Authorization 请求头
2    -> token 请求头
3    -> URL query 中的 token
4    -> 空字符串

有 Authorization 头时不会再回退读取后两种来源。基础提取方法是删除字符串中的精确 Bearer ，没有严格要求前缀一定存在：裸 JWT 放在 Authorization 也可能进入解析；小写 bearer 不会按同样规则被删除。推荐调用方统一发送标准格式，不能将当前宽松行为写成严格 Bearer 校验。

校验分层如下：

  1. parserAccessToken() 验证 HS256 签名、iat/nbf/exp（StrictValidAt，默认零时钟容差）、黑名单，并拒绝 sub="refresh"。
  2. ApiTokenMiddleware 对以上解析异常捕获后按匿名处理；签名解析得到用户 ID 后，再检查会员失效水位和持久化 sid 会话，这两项检查位于捕获块之外，失败会拒绝请求。
  3. 水位校验要求 iat 严格晚于 member_token_invalid_before:{id}。
  4. 有 sid 时要求会话存在、会员 ID 匹配、未结束、expires_at > now。无 sid 的历史令牌走兼容分支，由原有签名、黑名单和水位约束处理。
  5. 写入请求的 Token 属性、会员 ID 头及请求上下文用户信息。全局中间件会覆盖 member_id，不能靠客户端自报该头取得身份。
  6. 受保护路由的 TokenMiddleware 要求 member_id>0；其白名单仅在没有提交 Token 时允许匿名，提交无效 Token 会拒绝。
  7. 后续 Service 再执行账户状态、业务权限等检查；全局 Token 解析自身没有对每个请求都查询完整会员状态。

普通 HTTP 会话校验不比较 sv 与数据库 version。sv 防重放目前主要作用于刷新，不是每次访问都执行的版本失效机制。普通解析也未配置预期 iss 或设备/场景 aud 约束。

开放 Pub 登录/刷新路由没有普遍要求旧 Authorization 有效，但仍经过全局中间件：提交过期/签名错误 Token 可能降为匿名，提交能解析但会话已结束或水位已撤销的 Token 则可能提前被拒绝。客户端应避免在重新登录时无条件附带已撤销的旧凭证。

证据：HTTP 中间件注册、ApiTokenMiddleware、凭证提取、访问解析约束、受保护路由要求、会话有效性、失效水位。

4.7 刷新：两套入口必须分别看

A. /api/pub/refresh_token，开放刷新入口

请求体必须同时提供 refresh_token 和 access_token。适用于访问令牌已经到期、刷新令牌仍有效的情形。

执行流程：

  1. 解析刷新 JWT：签名、标准时间、黑名单。
  2. 有 sid 时，按 member_id + sid 查询登录日志当前 token，用 hash_equals() 比对传入的旧访问令牌。这允许旧 access 已过期，但要求是当前这一会话的凭证。
  3. 若旧访问令牌仍能解析，再校验它与刷新令牌的会员 ID 一致；解析旧 access 失败不会仅因过期直接禁止刷新。
  4. 服务层检查会员失效水位，并显式要求 sub === "refresh"。
  5. 有 sid 时，在数据库事务内锁会话行；检查未结束、未过期、会员匹配，并严格比较刷新 JWT 的 sv 和数据库 version。
  6. 将旧刷新 JWT 拉黑，签发新 Token 对；保留原 sid、邮箱和设备类型，sv 更新为 version+1。
  7. 更新会话 version 和 expires_at，新的截止时间取新刷新 JWT exp；把新 access 加入缓存列表。
  8. 控制器调用 removeTokenStr(oldAccess, false)：移除旧 access 的缓存列表项，能解析时拉黑旧 access，不结束共享会话。
  9. 更新登录日志 token 为新 access；迁移弹窗广告缓存；返回新凭证及 expire_at/expire_time。

这是一种“刷新令牌轮换 + 持久化版本”的实现。旧刷新 Token 即使在 Redis 黑名单到期后仍有 JWT 剩余寿命，也会因版本落后而不能再次刷新。每次成功刷新都会把会话截止重新推到新刷新令牌的 exp；当前这段逻辑没有按最初 created_at 限制整段会话的最长总寿命。

B. /api/member/refresh_token，会员受保护入口

该控制器类注册了 TokenMiddleware，因此需要有效的当前访问认证；请求体只要求 refresh_token。它调用相同的服务层刷新逻辑，所以仍执行 sub、会话和版本检查，但控制器后处理不同：

  • 没有公开入口的“传入旧 access 必须等于该 sid 的当前日志 Token”的绑定检查。
  • 按刷新令牌会员 ID 和当前请求访问 Token 更新日志；两者不属于同一日志时更新可能为空。
  • 没有调用公开入口的 removeTokenStr(oldAccess, false)，旧 access 不在此处移出列表或拉黑。
  • 普通 HTTP 又不比较访问 Token 的 sv，所以这个入口刷新成功后，原 access 可能继续有效直至自身 exp 或其他撤销条件生效。
  • 这个入口不能用于“当前 access 已过期”的正常续签场景。

不能用公开入口的行为描述覆盖全部刷新接口。

刷新中的事务边界

会话锁和版本更新在 MySQL 事务内，但 Redis 黑名单、列表写入发生在签发回调中，不随 MySQL 回滚；公开入口的登录日志 Token 替换又在服务层事务完成后执行。因此当前流程存在跨存储失败和并发窗口，应通过测试环境故障注入验证恢复能力，不能声称整个刷新过程在 Redis/MySQL 间完全原子。

无 sid 的旧令牌不走持久化版本校验，主要依赖黑名单、时间和水位，长期 TTL 配置调整时要单独考虑旧刷新 Token 重放。

证据：开放刷新入口、服务层刷新、行锁与版本、会员刷新入口、日志 Token 替换。

会话定时扫描为每分钟一次，要求 app_run_task 和 member_login_audit.expire_scan_enabled 同时开启，后者仓库默认 false。每批默认 500，Service 限制最高 1000；自然结束记录采用真实 expires_at，不是任务运行时间。鉴权到期检查不依赖任务是否开启。

Token 签发、上述登录会话记录和刷新核心流程在请求内完成；JWT 到期由请求时读取时间声明判断，不需要队列或定时任务来“删除 JWT”。定时扫描负责补记会话自然结束状态，不能代替实时鉴权。

失效水位默认以当前秒写入，要求新 Token 的 iat 大于该秒。仓库提供 waitUntilTokenCanBeIssued() 方法，但本次搜索未发现实际调用；密码重置/全量撤销同秒重新签发的边界需要验证，不能仅因方法存在就断言已解决。

WebSocket 与 HTTP 的差异

socket-io 注册 WebSocketAuthMiddleware。握手使用 query token，校验 JWT、会员失效水位、黑名单和当前会员状态；当前这份中间件未调用 MemberLoginSessionService::assertValid()。因此 HTTP 已依据 sid 拒绝的会话，不应推断 WebSocket 握手必然做了同样检查；已建立连接是否立即断开也不能从 HTTP 鉴权推导，应另行验证连接生命周期。

证据：客户退出、批量撤销、后台禁用客户、后台共享会话结束、自然到期任务、扫描配置、WebSocket 鉴权。

5. gtcuser：MineAdmin 自带管理端 Passport

这套管理端位于 gtcuser，与 gtc_admin 的 /admin/pub/login 属于不同代码和用户认证入口。

5.1 登录与声明

/admin/passport/login 使用 username/password，调用 App\Service\PassportService、UserRepository 和管理用户模型（mine_user 体系），选择 JWT default 场景。

调用自定义 Jwt 的普通构建方法，字段比客户登录少：

1access:  typ/alg 头部；iat、nbf、exp、jti=用户ID
2refresh: 同上，exp 使用 refresh_ttl，另有 sub="refresh"

默认没有 email/aud/sid/sv，也没有由覆盖实现加入的 iss。响应为 access_token/refresh_token/expire_at，expire_at 同样是 TTL 秒数；服务未返回 expire_time/token_type/expires_in。

正常服务登录没有将原始 Token 对写入 CRM member_login_session 或客户 Token 列表；登录事件不能等同于客户 sid 会话。该服务还存在 loginUser(TMember $user) 方法，但本次未发现其调用，应视为已有能力而非已确认的业务入口。

5.2 Authorization、刷新和退出

  • 普通管理端受保护路由使用 AccessTokenMiddleware，调用 default 场景解析器和 Passport 的 checkJwt()，核心为签名、时间、黑名单和拒绝刷新类型；用户/权限处理继续由管理端上下文及业务层执行。
  • /admin/passport/refresh 通过 RefreshTokenMiddleware 解析请求中的凭证，再调用 Passport refreshToken()，拉黑旧凭证并返回新 Token 对。
  • 当前刷新解析器只校验签名、时间和黑名单，没有要求 sub="refresh"；Passport 服务也没有补这个要求。 因访问和刷新使用同一密钥，有效访问 JWT 在实现层面也可能被当成刷新凭证接受。CRM 服务则有显式用途检查，两者不能混淆。
  • /admin/passport/logout 仅拉黑本次访问 JWT，不结束 sid 会话，也不关联撤销已经签发的 refresh。持有未过期刷新令牌仍可能获取新 access。
  • default/oauth 使用同一个签名密钥，解析器没有场景/预期受众约束；两个认证域都将用户 ID 放在 jti。跨场景误用的影响需结合用户存在性和权限中间件验证，不能宣称已完成利用验证，但应优先评估。

证据：管理登录入口、Passport 签发与退出、Passport 刷新、刷新中间件、刷新解析器。

6. gtcuser：独立 League OAuth2 授权

本节解释客户项目中另一组 token_type/expires_in/expire_time 来源，避免将它们错误归到 /api/pub/login。

6.1 授权入口与技术栈

主要入口：

入口 用途
/api/oauth2/login_ticket 已登录 CRM 用户申请绑定 client 的一次性静默授权票据
/api/oauth2/authorize、/api/oauth2/silent_authorize 授权流程，形成授权码/静默授权结果
/api/oauth2/token authorization_code 或 refresh_token grant 换取凭证
/api/oauth2/refresh_token 兼容入口，内部设 grant_type=refresh_token 后复用 token 入口
/api/oauth2/user 由 OAuth2Middleware 验证 OAuth2 access 并取得用户信息

工厂启用的是授权码 grant 和带会员状态复核的刷新 grant（各有启用配置），不能因为依赖包包含 PasswordGrant 文件，就认为系统通过 OAuth2 密码 grant 登录。

静默 login_ticket 为 lt_ + bin2hex(random_bytes(24))，缓存绑定用户和 client，默认 TTL 60 秒，消费时使用锁并删除。票据响应字段是 expire_in，既不是 expires_in 也不是客户登录的 expire_at；它不是最终访问 JWT。

证据：OAuth2 控制器、服务器工厂、票据服务。

6.2 access_token：RS256 JWT

库为令牌生成随机 ID，默认 bin2hex(random_bytes(40))，即 80 位十六进制字符串。访问 JWT 使用 RSA 私钥签名，声明如下：

声明 来源
jti 随机访问 Token ID，不是会员 ID
sub 用户 ID 字符串
aud OAuth2 client ID
iat/nbf 构建 Token 的时间
exp 访问实体的截止日期
scopes 获得的 scope 标识列表

头部为 typ=JWT/alg=RS256。这里没有 CRM 的 email/sid/sv。签名使用 OAuth2ServerOptions 指定的私钥，资源服务器读取公钥；不得与 JWT_SECRET 的 HS256 处理混用。

证据：随机 ID 生成、访问 JWT 构建。

6.3 refresh_token：加密 JSON

BearerTokenResponse 先构造：

1{
2  "client_id": "example-client",
3  "refresh_token_id": "<随机刷新令牌ID>",
4  "access_token_id": "<关联访问令牌ID>",
5  "scopes": ["example-scope"],
6  "user_id": 123,
7  "expire_time": 1800007200
8}

随后调用 CryptTrait::encrypt()。根据 encryption key 的类型，使用 Defuse Crypto 的 encrypt() 或 encryptWithPassword()；最终给客户端的是加密字符串。

这里的 expire_time 在加密刷新载荷内部，是刷新令牌的绝对截止 Unix 秒，与 /api/pub/login 响应中访问令牌的 expire_time 作用不同。这个刷新 Token 不能当 JWT 解码或用 HS256 parser 验证。

证据：响应及刷新载荷、Defuse 加解密。

6.4 响应与存储

OAuth2 成功结果是协议 JSON，并非普通 CRM 的同一 data 结构：

1{
2  "token_type": "Bearer",
3  "expires_in": 3600,
4  "access_token": "<RS256访问JWT>",
5  "refresh_token": "<加密刷新字符串>"
6}

expires_in = access_expiry_timestamp - time()，是输出时剩余秒数，可能略小于配置 TTL。库同时设置 Cache-Control: no-store 和 Pragma: no-cache。

模型逻辑表 保存内容 是否保存客户端收到的完整凭证
oauth2_access_tokens 随机 id、client/user、scopes JSON、revoked、expires_at 不保存完整访问 JWT
oauth2_refresh_tokens 随机 id、关联 access ID、revoked、expires_at 不保存完整加密刷新字符串

模型使用日期时间字段 expires_at，不是客户会话的 Unix 秒字段。实际物理前缀随 DB 配置；本次在当前数据字典中未定位到这两表定义，能确认的是模型和仓储契约，不能据此确认线上表、索引或迁移已部署。

证据：访问仓储、刷新仓储、访问模型。

6.5 Authorization 与刷新验证

资源请求由 ResourceServer + BearerTokenValidator 处理：

  1. 要求存在 Authorization 请求头；删除匹配的 Bearer 前缀后解析 JWT。实现没有单独对“缺少 Bearer 前缀但提供裸 JWT”做严格拒绝分支。
  2. 公钥验证 RS256 签名，LooseValidAt 检查提供的时间声明。
  3. 取 jti 查访问仓储，令牌不存在或 revoked=true 则拒绝。
  4. 将访问 ID、client ID、用户 ID、scopes 放入 request 属性和 OAuth2 上下文；这不是 CRM 的 jti 用户上下文。

JWT 中写了 aud=clientId，当前基础 validator 没有独立配置的预期 audience 约束；scope 信息被注入也不等于所有业务接口自动执行了所需 scope 判断。

刷新流程会验证 client、解密刷新字符串、检查 client 绑定、内部 expire_time、数据库刷新撤销状态；项目覆盖 grant 还复核会员当前是否允许 OAuth2 登录。新 scopes 不能比原 scopes 扩大。正常轮换撤销旧访问 ID 和旧刷新 ID，再写新实体并返回凭证。

这里没有 CRM 的 sid/sv 行锁机制；当前仓储方法展示的是逐条写入/更新，不能认定并发刷新天然等价于客户持久化版本保护，应单独验证。

全局 ApiTokenMiddleware 可能先尝试以 HS256 解析这个 RS256 Token 并降为匿名，OAuth2 路由随后用自己的中间件完成认证。所以不能把“CRM parser 不识别”理解为 OAuth2 请求必然非法，也不能把这两套 Token 任意替换。

证据：OAuth2 Bearer 验证、路由 OAuth2 中间件、刷新 grant、会员状态复核。

8. 已确认的差异、风险与处理顺序

以下是源码支持的关注点，并非本次已实施的修复或已验证的线上漏洞结论。

8.1 优先核实并处理认证边界

  1. 后台 access/refresh 缺少隔离：当前固定密钥默认值相同、TTL 默认相同、无用途声明。先在隔离环境确认相同 Token 条件，再设计不同用途/密钥和存量兼容策略。没有随机声明还可能导致同用户同秒登录得到相同 access；同设备重登逻辑先写新标记再清旧标记，键相同时应验证是否误清本次会话。后续改变配置必须评估历史 Token 立即失效的影响。
  2. Passport 刷新端缺少 refresh 用途检查：为刷新明确要求 sub=refresh，并验证 default/oauth 域之间的凭证误用；仅靠同一 HS256 密钥验证不足以区分账户体系。
  3. 后台退出和设备淘汰覆盖不一致：Redis 会话检查对普通角色及部分请求路径没有同等覆盖。先统一期望的后台认证边界，再验证所有账号类型的退出/空闲过期/终端淘汰行为。
  4. 客户两套刷新入口行为不一致：公开入口撤销旧 access，会员入口没有同样后处理。先确定刷新后旧 access 是否必须立即失效，并统一会话绑定和列表/审计更新规则。
  5. WebSocket 未同步 sid 校验：验证 access 已过期但 refresh 仍有效的设备被踢之后，旧握手 Token 的行为；同时明确已连接用户的撤销策略。

8.2 再完善故障、到期与存储

  1. MySQL/Redis 非同一原子事务：为登录、刷新持久化失败建立可复现测试，关注新 access 已缓存但会话未落库、旧 refresh 已拉黑但数据库回滚、日志 Token 未替换导致下次公开刷新匹配失败。
  2. 失效水位同秒签发：iat <= cutoff 会拒绝新 Token，等待方法尚未发现调用。测试密码修改后立即重新登录和批量退出后同秒重新签发。
  3. 原始凭证存储范围较大：客户登录日志、Redis 列表和黑名单键都包含可用原始凭证。明确必要性、访问控制、保留期限和脱敏方案；需要日志匹配时可评估哈希关联，但不能在本次分析中直接改契约。
  4. JWT 声明与配置不一致：客户 claims.iss 未加入、黑名单配置前缀未使用；后台 aud 复用 iss；设备 audience 未作为用途校验。统一文档和代码前需明确兼容范围。
  5. 旧/模拟令牌兼容路径：无 sid 的历史、模拟、MT 用途 Token 与正常客户会话的生命周期不同，不能只修正常新登录就宣称覆盖所有 Token。
  6. 审计口径：后台日志在 MFA 前写；客户会话到期扫描默认关闭。后台登录成功统计、客户“在线”展示应明确取哪一层事实。
  7. 密码存储：两项目客户/后台历史密码路径使用 MD5 加固定盐，需独立规划现代密码哈希兼容迁移；这不影响本文对当前 JWT 字段的判断。

8.3 查询与容量核验范围

本文没有新增 SQL，也未执行查询。现有登录核心查询多为用户 ID、sid 或 Token 的单对象定位；客户 session 查询有主键/唯一索引，到期扫描有 (ended_at, expires_at, session_id)，且批次有上限。

登录日志按原始 Token 查找有前缀索引，不能未经执行计划验证就认定对任意数量日志都高效；sid 定位有唯一索引，更明确。全量撤销按会员和批次执行；会话索引对排序/截止条件的具体覆盖以及 OAuth2 表结构仍需真实测试库 EXPLAIN、数据规模和运行配置核验。文档未对这些查询做性能修改。
