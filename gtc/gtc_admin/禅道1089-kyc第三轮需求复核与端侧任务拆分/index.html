禅道 #1089 KYC 第三轮需求复核与端侧任务拆分

分析日期：2026-10-27。依据：禅道 #1089、用户端详细 PRD、第三轮改动范围汇总，以及本地 gtc_admin、gtcuser、gtc_admin_vue 源码和 gtc_admin/docs/数据字典.sql。只做需求与实现方案分析，未修改业务代码、数据库或配置。未连接生产数据库；用户 App/H5 源码未在本地核实，Web 原型分支访问返回 404，因此用户端现状仅以 PRD、原型与客户 API 为依据。

1. 结论与范围边界

这不是给现有 KYC 加几个状态标签的改动。当前数据和大量接口以 member.kyc_id + member.kyc_status 表示一套 KYC；第三轮要求同一客户同时有一条办理中实例和一条生效实例，且所有表单提交、人工审核、第三方链接/回调、资格门禁、快照都按实例归属。应先交付实例模型和旧资格保持能力，再联调客户端复用及后置校验。

需求来源须分层理解：

层级 内容 本方案处理
#1089 + 详细 PRD 的 P0 双实例/监管切换、逐步骤复用、国籍与姓名后置校验、POA 国家一致性、历史详情/快照、迟到回调防污染 本次主链路，必须纳入两端拆分与联合验收
范围汇总明确列出的 KYC 关联项 管理端代客创建、审核列表、POI 含地址自动通过 POA、Sumsub request check、国家映射、动态记录、后台历史资料 纳入总方案，但逐项标出前置确认和与 #1089 的关系；不能仅因汇总建议 P1/P2 就忽略本期是否交付的决定
范围汇总标记“否，资料管理相关” 客户文件统一管理、上传/预览/删除 独立需求，不作为 #1089 核心流程的阻塞项；历史 KYC 文件只读展示仍属 #1089
PRD 的 Mock/多语言/埋点 Mock、异常态与历史样例为 P0；多语言 P1、运营埋点 P2 页面联调需要 Mock；多语言至少覆盖本期上线语言，埋点按发布范围确认

2. 现状证据与真正的改造点

现状 代码证据 对 #1089 的影响
t_member 只有 kyc_id、kyc_status、Iscertified，t_member_other 只有单份 kyc_regulatory_type_id 与 kyc_profile_snapshot 数据字典 中的 t_member、t_member_other 不能表达“新 B 办理中，旧 A 生效”。须明确这几个兼容字段的读写口径，不能把它们直接当成新流程状态
t_kyc_user_content 以自增 kyc_id 为表单提交记录 ID，含 form_id、kyc_config_id、步骤状态、审核时间和部分表单题目快照；目前无 instance_id，数据字典也未列该表的成员/实例组合索引 数据字典 不能用现有 kyc_id 冒充流程实例；历史按配置 ID 拼接会把同配置的多轮办理混在一起；新增实例关联与索引需评估
CRM 更改 KYC 目前禁止已通过客户变更，且立即写 member.kyc_id、member_other.kyc_regulatory_type_id 并刷新总状态 Kyc.php 与“任意时点切换、新流程未通过旧资格继续生效”正面冲突。不能只放开前端按钮
两端总状态服务都按 member.kyc_id 下最新表单重算 member.kyc_status/Iscertified CRM 状态服务、客户 API 状态服务 办理 B 时若直接改 member.kyc_id，资格会从 9 掉到 0/1/2；若保持 A，则 B 的表单与审核找不到正确当前配置。必须拆开“实例审核状态”和“会员生效资格”
客户提交以 member.kyc_id 写 kyc_config_id，且 member.kyc_status=9 直接禁止继续提交 KycService.php 已认证客户办理 B 要重构写入口、暂存、撤回、重提和表单读取；只改 saveinfo 不够
Sumsub 回调由 externalUserId 解析到会员，再按会员当前 kyc_id 找 POI/POA；业务 ID 只有 memberId 或 memberId_N，回调检查主要看步骤已通过/人工待审 SumsubService.php、KycService.php、业务 ID 旧回调可能落到新实例。业务 ID 后缀是重提序号，不是流程实例；需要持久的 attempt→instance/step 绑定与回调幂等、作废检查，不能仅靠前端传 instance_id
第三方 POI 通过后当前代码直接更新会员姓名/证件等并置步骤 9；POA 通过后会同步居住国家并置步骤 9 KycService.php、同文件 POA 后置校验和客户选择必须挡在“平台步骤通过”及有副作用的会员资料写入之前；旧实现顺序与 PRD 不一致
当前 myinfo 在会员认证状态为 9 时优先读取单份生效档案快照，且该快照的答案仍可能从实时表单记录读取；CRM 快照保存挑选已通过记录时未按本次实例约束 客户读取、快照注释、CRM 快照 不能直接用于多条不可变历史详情。要冻结每次实例的表单结构、答案、文件引用和审核结果；旧数据需定义降级展示
后台审核列表按会员总状态分页，默认 member.kyc_status=1，汇总表一会员一行 KycReviewListService.php、汇总表 A 生效、B 待审时会员总状态仍是 9，B 会从当前默认审核列表消失。列表主体/筛选应转为待审实例或明确双状态
资格门禁确实读取 member.kyc_status，例如客户 API KYC 中间件及支付/跟单相关服务 KycMiddleware.php、PayService.php 维持旧 kyc_status=9 是兼容发布的重要条件；监管/PSP/开户还要逐调用方审计，不能只检查 /api/member/info

3. 统一业务模型与状态转移（建议实现口径）

3.1 三条视图，不是三种互斥状态

current 是当前可办理/待审的实例，effective 是当前资格所依据的已认证实例，history 是供列表查看的实例集合，包含当前生效档案置顶及已失效、已终止实例。流程审核状态 in_progress/pending/rejected/certified/void 与生效状态是不同维度；certified 未必仍 effective，void 绝不能复活。每会员最多一个可办理实例和一个生效实例，允许二者并存。

建议有独立实例主记录：稳定 instance_id、member_id、目标监管与 KYC 配置、表单配置快照或版本、流程状态、当前/生效指针、created_at、approved_at、ended_at、void_reason、操作人与来源。表单提交记录与第三方 attempt 关联实例和步骤，编辑标记、复用来源、审核方式与决策结果落库。具体表名和字段类型以 Eric 的设计及发布 SQL 评审为准；但实例 ID 与提交记录 ID 必须区分。当前/生效唯一性须用数据库约束或会员级指针加事务锁保证，不能只在应用层先查再插。

事件 办理实例 生效实例 member.kyc_status/Iscertified 兼容值 关键约束
首次办理 建 A 无 随 A 审核状态更新，未通过不置 9 不重复创建 A
A 已生效，后台切到 B 建 B；A 仍保留 A 保持 9/1 B 与 A 可同监管/同配置但不同实例
B 步骤提交、待审、拒绝 只改 B/其步骤 A 保持 9/1 A 的资格、监管/PSP规则不因 B 的拒绝而改变
B 全部必需步骤经平台审核通过 B 变 certified 并成为生效 A 结束生效，留历史 仍为 9/1 同一事务切指针、记时间与快照；成功通知只发一次
B 未完成时再切 C B→void，建 C A 保持 9/1 B 的写入、人工审核、第三方链接和迟到回调全部失效
没有旧生效实例，当前实例拒绝/终止 按产品定义保留或新建 无 不得仍为 9/1 明确重新发起入口与时间字段

后台切换事务建议锁会员/实例指针行，校验版本后 void 旧 current、创建新实例、记录操作日志，提交后再发通知。全通过事务重新检查目标实例仍是 current、所需步骤最新版本全部通过、后置决策已完成，再完成 A→B 切换。跨 gtc_admin 与 gtcuser 的重试须幂等；两端不能各自维护一套不一致的“全通过”判断。

3.2 逐步骤复用的判定表

复用来源是当前生效档案中相同或明确兼容的表单步骤，不是任何历史通过行，也不是整条流程。PRD 评论说明个人转公司也可适用，但“兼容”必须由表单映射/字段规则定义，不能只按 form_type 猜测。

条件 新实例当前步骤 其他步骤
来源已通过、当前规则下资料完整合法、字段及资料未变化、用户未点过“修改” 用户确认并提交后直接继承通过；记录来源实例/步骤与复用决策 不变
来源未通过、缺字段/非法、新表单新增必填字段、或已进入编辑态 只预填兼容字段；新字段为空；编辑标记持久化；提交后按新规则重新审核 不变
点“修改”后又改回旧值 仍重新审核，不可恢复只读继承 不变
新增必填字段尚未补全 只读展示旧字段，提交不可用；“修改”后补全再提交 不变

服务端必须重新校验完整性、字段版本与编辑标记。协议签署、文件、身份证明等高风险字段不能简单复制引用后立即通过：需要按新监管规则确认复用资格与文件可读性。只有全部必需步骤通过且后置校验/选择已闭环，实例才可切为生效。

3.3 第三方审核后的平台关口

第三方拒绝：展示第三方原因，不做平台国籍/姓名校验。第三方通过：先保存带实例/attempt 归属的原始结果，平台实时读取允许国籍并做国家映射；国籍不允许则 POI 平台拒绝，展示“平台审核未通过”及原因，弹窗只有“确定”，随后允许重启第三方或使用原结果预填人工审核。国籍允许后，先由客户确认第三方姓名拆分，再比较个人信息姓名；字符组成须与第三方姓名一致，含 ·、- 等符号。匹配则 POI 自动通过；不匹配时默认“更新个人信息姓名”并通过，或“使用当前姓名”且直接提交预填资料进入人工待审。客户未作选择前不得把第三方 GREEN 写成平台已通过，也不得先覆盖会员姓名。

人工 POA 国家不一致时提交前阻断；第三方 POA 可先提交，发现不一致时进入必须解决的弹窗，解决前不能进入后续步骤。“保留个人信息国家”：POA 回待提交，第三方资料预填但国家改为个人信息国家，必须上传新的地址证明并转人工；若同一第三方覆盖 POI+POA，POI 也回待提交。“更新个人信息国家”：更新个人信息并把当前实例全部步骤重置待提交，从个人信息重来，兼容资料按复用规则预填；旧回调不得恢复状态。个人信息表单本身不显示 POA 一致性提示，只在 POA 国家字段常驻提示。

4. 用户端任务（Eric/客户端按此认领）

编号 任务与可见行为 依赖/验收
U1 档案资料总览：首次无生效/历史且仅一当前流程时直入表单；其余展示新监管入口、当前生效档案置顶、失效/终止历史；显示目标监管和办理状态；处理加载、空、错误与多设备刷新 依赖 overview 三视图返回；终止实例只读，不可继续提交；流程切换后刷新不得显示过期按钮
U2 历史列表/详情：按 instance_id 进入，只读渲染当时表单结构、值、文件和步骤审核状态；显示 created_at，生效展示审核时间、失效/终止展示结束时间；缺失字段保留为空；接口失败显示规定提示 不能从当前 myinfo/会员资料拼装历史；时间格式 YYYY-MM-DD HH:mm:ss，时区以接口约定为准
U3 单步骤只读/编辑复用：来源资料只读，提供“修改/提交”；新增必填字段时禁用提交并引导编辑；点击修改先调用服务端持久化标记；仅提交当前步骤，重新拉取步骤状态 编辑后刷新仍是编辑态；个人信息居住国家仅编辑态可改；提交成功不本地推断整条 KYC 通过
U4 POI 第三方结果页：区分第三方拒绝/平台拒绝/待姓名确认/人工待审；国籍拒绝按 PRD 单按钮弹窗返回方式选择；人工资料可编辑回填 错误码驱动状态，不通过文案猜分支；旧链接、void 或并发错误提示刷新当前实例
U5 姓名确认和差异弹窗：姓/名编辑、按国家规则展示全名、保留特殊字符、默认更新个人信息；另一选项直接系统提交人工审核并跳下一步骤 输入字符组成校验与服务端一致；等待提交响应，防重复点击；证件号等敏感原始结果不放持久前端存储
U6 POA 表单与差异处理：常驻国家提示；人工提交前拦截；第三方差异弹窗默认保留当前国家；两条选择路径按服务端返回的新步骤状态导航；强制重新上传证明 决策未完成锁后续导航；POI+POA 同源时正确显示 POI 重置；后退/刷新可恢复未完成决策
U7 Mock、语言和联调：覆盖 A 生效+B 待审、B void、完整/不完整快照、国籍拒绝、姓名不一致、POA 两条路径及多设备状态刷新 #1089 P0 Mock；本期上线语言补齐状态、时间、错误和按钮文案。用户端源码不可见，文件级估算待 Eric 核实

5. 后端任务（gtc_admin + gtcuser，含管理端接口）

编号 任务 主要落点/验收
B1 实例与步骤持久化：实例、有效/当前指针、配置版本/快照、表单提交记录外键、编辑/复用来源、第三方 attempt、生命周期时间；唯一性、事务与幂等 两端共享数据库与同一状态机契约；发布 SQL、数据字典、回填和回滚计划独立评审。t_kyc_user_content 现仅主键，实例/步骤查找须设计复合索引
B2 改写监管切换：已认证、办理中、待审任意时点可触发；锁定会员；作废旧 current、建新 current；旧 effective/资格/监管规则不变；记录管理员及原因 CRM setUserKyc 不再直接覆盖生效监管；管理端页面与日志/动态记录同步。权限与审计按既有后台约定
B3 生效资格和全通过：步骤最新版本、平台后置决策、配置快照共同决定实例是否全通过；一次事务切 effective，写 approved_at/ended_at 与历史快照；兼容写 member.kyc_status/Iscertified 重构两端状态服务、成功通知、member_other.kyc_regulatory_type_id 同步时点；扫监管、PSP、开户、支付、跟单等读点，不让 B 待审导致 A 资格丢失或提前套 B 规则
B4 客户 API：总览、实例详情、历史列表/快照、进入编辑、步骤复用提交、普通提交/暂存/撤回/重提、姓名确认与选择、POA 差异决策 gtcuser KYCController 与 KycService。所有变更操作绑定会员+当前 instance_id+步骤版本；非当前/void 返回稳定冲突码
B5 第三方回调和重试：Sumsub/IDWise/Zoloz 各入口绑定 attempt、instance、step、provider 身份；验签、去重、版本检查；迟到回调仅留审计，不改 current/effective 当前 memberId_N 只能找会员，须补可靠映射；失效链接尽量调用第三方作废，不能作废时本地硬拒绝。刷新轮询、人工审核和后台代客提交同受实例门禁
B6 平台附加校验：实时允许国籍、国家映射、姓名字符/国家拼接规则、人工资料回填；POA 双路径及 POI+POA 联动重置 第三方 GREEN 先进入 platform_review/待客户决定等中间状态；会员姓名/国家副作用与审核状态一起协调，失败可重试/回滚；特殊字符和空值有明确错误码
B7 历史快照与旧数据：每实例固定表单定义、字段值、文件引用、审核结果、监管配置、创建/审核/结束时间；历史只读；旧记录按可证明的配置与时间回填，不可确定时显式标记不完整 单份 kyc_profile_snapshot 不能覆盖多实例；旧记录无 created_at/ended_at 时不伪造审核时间；文件访问校验本人/授权后台角色，保留隐私和有效访问期限
B8 CRM 审核列表/详情：以 current 实例待审状态筛选，新增上传时间；默认“全部表单已提交且有待审”，未提交 与 待审核 分开；审核操作带实例/步骤版本 KycReviewListService 当前按会员 kyc_status 过滤会漏 A 生效+B 待审；汇总表按实例设计或另建投影，避免每页全量扫描明细。管理端 Vue API/页面联调
B9 管理端代客创建与历史资料：客户详情 KYC 资料 Tab，按实例展示历史和详情；创建时检查未完成实例，按步骤保存并可定位审核；与客户同时操作用版本冲突处理 范围汇总要求“取消/提交覆盖”二次确认，但覆盖已认证或新实例可能破坏资格，覆盖语义须先拍板；不能用前端确认代替服务端 CAS/锁。权限、操作人和审计明确
B10 范围汇总中的支撑项：KYC 设置的“POI 含地址自动通过 POA”仅 Sumsub 且无独立 POA 结果时使用；国家映射维护；Sumsub request check 能力调查和频率/权限控制 这些不是 #1089 主 PRD 的完整细则。第三方字段、request check 能否开放及收费/幂等先验证，再决定本期是否上线开关/入口；不能让自动 POA 绕过国家一致性关口

后台 Vue 是管理端交付，不等同于客户用户端；其 KYC 审核列表、设置、客户详情改动需与 B2/B8/B9/B10 同步拆任务。独立“客户文件统一管理”另开需求，不与历史 KYC 文件只读展示混淆。

6. 跨端接口契约（先约定再并行开发）

以下是建议响应语义，不是现有 API 的已实现字段。具体路由和字段命名由两端联调确定，旧接口的兼容期也应写进接口文档。

契约 必须表达的字段/行为
overview current_instance（可空）、effective_instance（可空）、history[]、会员资格状态、每实例审核状态/目标监管/开始和结束时间；当前生效档案在 history 中置顶但不重复计算
instance detail instance_id、lifecycle_status、effective_status、时间、监管/KYC 配置快照、按当时顺序的 steps[]；每步有表单定义/答案/文件/审核状态/复用来源/编辑标记。对外不返回原始第三方完整报文
step action 请求带 instance_id、form_id、step_version/幂等键和动作；响应给新步骤状态、实例状态、下一步及未决 decision；服务端校验登录会员、当前性、版本、必填与审核方式
provider attempt 服务端创建并持久化 attempt_id ↔ instance_id ↔ step_id ↔ channel ↔ provider_business_id；回调不信任客户端携带 ID，先验签后查 attempt；旧 attempt 已作废/已处理返回幂等成功但不落业务状态
错误码 区分 INSTANCE_VOID、INSTANCE_STALE、STEP_VERSION_CONFLICT、REUSE_INCOMPLETE、NATIONALITY_NOT_ALLOWED、NAME_CONFIRM_REQUIRED、POA_COUNTRY_MISMATCH、PROVIDER_REJECTED、HISTORY_UNAVAILABLE；具体数字码与 HTTP 码两端统一
时间与隐私 后端给统一时区的 ISO/时间戳及展示时区约定；前端按 PRD 展示秒。历史文件用受控访问 URL；接口不暴露证件号、原始人脸资料及不必要的第三方字段

7. 不能靠开发者自行猜的待确认点

按阻塞程度排序，建议产品、Eric、后台/客户端在联调前一起定稿：

  1. 生效规则口径：新 B 未通过时“监管/PSP/开户按 A”是所有读点一致的要求，但若客户选择更新姓名或居住国家，个人资料字段何时对支付、出金、合约、报表生效？须区分客户展示资料与资格依据；否则会出现 A 生效却被 B 的国家/姓名影响资金规则。
  2. current 与 history 状态：rejected 是否仍可继续作为 current 重提；void 详情用“已终止”还是统一“已失效”；未曾认证的 void 是否显示审核时间为空、结束时间为作废时间。PRD 详情字段只显式规定生效/失效，列表又要求终止流程。
  3. 表单兼容判定：PRD 主条款写“相同 form ID”，说明又有“兼容表单”，评论扩展到个人转公司。应确认兼容映射、必填/选项变化、上传文件/协议能否复用，以及来源究竟限定当前生效实例还是“历史最新已认证”。本文建议优先当前生效实例，不自动回溯更老档案。
  4. 姓名规则：范围汇总写“暂定只能修改姓名顺序”，详细 PRD 要求字符组成完全一致的姓/名拆分。以详细 PRD 为当前方案；需确认空格、大小写、Unicode 规范化、复姓/中间名、国籍拼接规则，以及“自动通过”前是否更新证件姓名和签署文件。
  5. POI/POA 自动联动：同一 Sumsub 审核同时覆盖两步时，POA 冲突会重置 POI；姓名确认尚未完成或 POI 已自动通过时具体重置顺序、图片保留与重传范围需确认。“证件含地址”字段和国家映射也未确认。
  6. 后台代客覆盖：范围汇总提出管理员与客户并发时“提交覆盖”。需定义能覆盖的实例/步骤、已生效档案是否永不覆盖、冲突对话所展示版本、管理员权限和审计；建议只允许对同一 current 实例做受控版本提交，任何资格变更走独立审批。
  7. 第三方 request check：Sumsub 是否允许客户触发、每次费用/次数、速率限制、失败重试和第三方 attempt 是否保持同一实例，范围汇总明确待确认。本期不可把入口当成既定 P0。
  8. 旧数据迁移：历史记录缺流程实例、创建/结束时间或完整字段快照时，如何归组、是否展示“资料不完整”、无法判定的记录是否允许复用；须以脱敏样本与数据量评估，不能按同 kyc_config_id 直接合并。
  9. 需求文本缺口：详细 PRD 的 FR-NA-17 仅写“第三方覆盖 POI 时或 POI+POA”，缺少动作/结果；其国籍章节编号也有 6.4/6.5 混用。需由产品补全“国籍拒绝时 POA 的处理、第三方两步骤结果是否一并作废”等行为，不能按残句实现。
  10. 范围归属：管理端代客创建、审核列表、POI 自动 POA、国家映射、客户文件统一管理是否同一个发布批次；汇总中的建议优先级与 #1089 PRD P0 并不完全相同，应拆独立验收单或在 #1089 明确子任务。范围汇总称“客户端历史仅展示已通过”，而详细 PRD/#1089 要求展示已终止实例；此处暂按更具体的 #1089 验收口径，待产品确认。

8. 联合验收与实施顺序

  1. 先定契约和数据迁移：确认上述口径、现网脱敏样本、两端单一状态机与表结构；做旧数据回填/不完整策略和回滚方案。不得先让 CRM 放开已认证客户改监管。
  2. 先交付 B1-B3/B5 基础链路：模拟 A 生效、建 B、B 拒绝、B 通过、B void、A 仍生效、重复/迟到回调；验证会员资格与监管/PSP/开户规则及成功通知一次性。然后开放用户端 U1/U3 的联调。
  3. 再交付逐步复用和历史 U2/B4/B7：覆盖同表单、兼容表单、个人转公司、新增必填字段、编辑又改回旧值、文件缺失、完整/不完整旧记录。每次提交断言其他步骤不变。
  4. 再交付平台后置校验 U4-U6/B6：第三方拒绝、国籍拒绝后两审核方式、姓名字符与两决策、POA 两决策、POI+POA 联动、刷新/多设备/并发/回调乱序。校验会员姓名与国家副作用发生的准确时点。
  5. 最后联调管理端 B8-B10 和非主链路项：A 生效+B 待审仍出现在审核队列；上传时间语义及旧数据空值；管理员代客与客户并发冲突；Sumsub 自动 POA 及 request check 仅在外部能力确认后开启。

测试至少覆盖：服务端状态机/事务幂等、两个后端相同资格口径、客户端接口契约、后台审核权限与数据范围、迟到回调、历史文件访问控制、旧记录兼容。灰度发布时建议新表/索引与回填先行，两端写入通过开关同步启用，旧接口保持读兼容；回滚不能删除已产生的新实例，只能关闭新入口并保留新数据可审计。t_kyc_user_content 尚无按 member_id + instance_id + form_id + 最新记录 的索引；历史列表必须按会员和实例过滤、分页，审核列表按可索引的实例状态/时间过滤后再批量取步骤，不做同步全表聚合。上线前用现网数据量和 EXPLAIN 验证，而非仅依赖结构推断。

本次验证边界：已核对需求原文、禅道摘要、范围汇总与上述主要代码链及数据字典；未运行接口/数据库测试，未验证生产版本、Sumsub 实际字段和用户端源码。本文是供两端对照的实施与验收基线，不代表待确认业务口径已获产品批准。
