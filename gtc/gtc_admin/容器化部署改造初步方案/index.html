容器化部署改造初步方案

2026-10-27 项目：gtc_admin

GTC 项目容器化部署改造初步方案

一、汇报结论

建议公司采用“Harbor 镜像仓库 + Jenkins 持续交付 + Docker Swarm 运行”的渐进式方案。

本方案不一次性引入 Kubernetes，不重写现有业务，不改变现有 API、域名、数据库和外部服务。三个项目分别构建镜像，先在 DEV 环境验证，再逐步推广到 TEST、UAT 和生产环境。

核心原则：

  • 镜像只包含代码和运行依赖，不包含环境专属配置、密码、Token、证书和私钥。
  • 继续使用现有 Jenkins，增加镜像构建、推送和部署步骤。
  • 继续使用现有 Docker Swarm，先解决 gtcuser 发布停服问题。
  • 环境配置放在部署服务器，由容器启动时只读加载。
  • 每个环境使用明确版本的镜像，不使用 latest。
  • 先完成最小闭环，再根据实际收益扩展高可用、监控和自动回滚能力。

二、现状概述

公司目前有三个相互配合的项目：

项目 当前技术栈 当前运行形态
gtc_admin PHP 8.0、ThinkPHP 8、Redis、MySQL、SelectDB/报表数据源、PHP-FPM 常规 PHP-FPM/Web 方式
gtcuser PHP 8.1、Hyperf 3.1、Swoole 5、Redis、MySQL、异步队列、定时任务、WebSocket Docker/Swarm，发布时存在短暂停服
gtc_admin_vue Vue 3、Vite、Pinia、Vue Router、Ant Design Vue、Ele Admin Pro、Less Jenkins 构建静态前端文件

当前 Jenkins 已按 DEV、TEST、STAGING 等视图组织任务，至少包含 CRM 后端、Vue 前端和 gtcuser API 任务。gtcuser 仓库已经存在 Dockerfile、Compose 和 Swarm 部署文件，但不同文件之间存在 PHP 版本、镜像和运行方式差异，需要统一生产模板。

生产和 UAT 的实际节点、Swarm 服务、Nginx、PHP-FPM、卷和计划任务仍需在实施前做一次只读盘点，避免把历史部署文件误认为当前线上配置。

三、改造目标

3.1 发布目标

将当前“Jenkins 工作目录拉代码、打包、传输代码、远程启动”的方式，逐步调整为：

1Git
2  -> Jenkins 拉取指定版本
3  -> 构建镜像
4  -> 推送 Harbor
5  -> 目标环境拉取指定镜像
6  -> 滚动更新容器
7  -> 健康检查

3.2 业务目标

  • gtcuser 发布时不再整体停服。
  • 版本可以追踪到 Git commit 和镜像 digest。
  • 出现问题时可以快速回滚上一版镜像。
  • DEV、TEST、UAT、生产使用相同构建产物，减少环境差异。
  • 保持现有接口路径、域名、数据库和前端调用关系不变。

四、目标架构

 1代码仓库
 2  |
 3  v
 4Jenkins
 5  | 代码检查、测试、构建镜像、镜像扫描
 6  v
 7Harbor
 8  | 保存不可变版本镜像
 9  v
10Docker Swarm
11  |-- gtcuser：Hyperf/Swoole 容器
12  |-- gtc_admin：PHP-FPM 容器
13  |-- gtc_admin_vue：Nginx 静态资源容器
14  v
15现有 Nginx/负载均衡/域名

Harbor 只负责镜像存储、权限、漏洞扫描和保留策略，不负责容器编排。第一阶段沿用现有 Swarm，不同时推进 Kubernetes 迁移。

五、三个项目的镜像方案

5.1 gtcuser

镜像内包含：

  • PHP 8.1 运行环境
  • Swoole、xlswriter 等扩展
  • Composer 生产依赖
  • gtcuser 业务代码

容器启动：

1php bin/hyperf.php start

HTTP 和 WebSocket 继续使用当前应用端口，由现有 Nginx 或负载均衡转发。

需要把队列消费者和定时任务与 Web 服务区分开，避免扩容 Web 副本后重复执行任务。第一阶段可以先保持现有行为，第二阶段再拆分为 Web、Worker、Cron 三类服务。

5.2 gtc_admin

新增 PHP-FPM 镜像，镜像内包含：

  • PHP 8.0 运行环境
  • Composer 生产依赖
  • ThinkPHP 业务代码

第一阶段保留现有 Nginx 入口，由 Nginx 将 PHP 请求转发到 PHP-FPM 容器，避免同时改动域名、路由和静态文件入口。

5.3 gtc_admin_vue

采用两阶段构建：

1Node 镜像构建 dist
2  -> Nginx 镜像提供静态文件

前端 API 使用相对路径，例如 /api，由不同环境的 Nginx 转发到对应的后台服务。这样同一个 Vue 镜像可以从 DEV 晋升到 TEST、UAT 和生产，不必因为 API 域名不同重新编译。

六、运行时配置方案

不把 .env 文件纳入 Git，也不把 .env 文件复制进镜像。

第一阶段采用最简单的服务器外置配置方式：

1/opt/gtc-config/dev/gtcuser.env
2/opt/gtc-config/test/gtcuser.env
3/opt/gtc-config/uat/gtcuser.env
4/opt/gtc-config/prod/gtcuser.env

容器启动时将对应环境配置只读挂载到应用约定位置，例如：

1/opt/www/.env

现有 gtcuser 的 Swarm 文件已经采用外部 Docker Config 注入 .env 的思路，可以在此基础上统一。生产环境的密码、Token、私钥等敏感值后续可单独迁移到 Docker Secret；第一阶段不强制建设配置中心。

配置文件要求：

  • 不进入镜像层。
  • 不进入 Git 仓库。
  • 不在 Jenkins 普通日志中打印。
  • 文件权限限制为部署用户可读。
  • 每个环境独立维护，禁止生产配置复用测试配置。

七、镜像版本规范

建议镜像名称如下：

1harbor.example.com/gtc/gtcuser:<git-sha>
2harbor.example.com/gtc/gtc-admin:<git-sha>
3harbor.example.com/gtc/gtc-admin-vue:<git-sha>

部署时固定使用 Git SHA 或镜像 digest，不使用 latest。

如果一次发布需要三个项目协同，应由 Jenkins 生成发布清单：

1release: 2026.09.30-001
2gtcuser: <image-digest>
3gtc_admin: <image-digest>
4gtc_admin_vue: <image-digest>

这样可以准确还原某次发布使用的代码版本。

八、Jenkins 改造方式

保留现有 Jenkins 任务和环境视图，先增加以下步骤：

  1. 拉取指定分支或 commit。
  2. 安装依赖并执行已有构建检查。
  3. 构建对应项目镜像。
  4. 扫描镜像中的高风险漏洞。
  5. 推送 Harbor。
  6. 记录 Git commit、镜像 tag 和 digest。
  7. 调用目标环境部署脚本。
  8. 检查容器状态和业务健康接口。
  9. 失败时保留上一版镜像并支持回滚。

第一阶段可以继续使用现有 Jenkins 页面任务；稳定后再把关键脚本迁移到仓库 Jenkinsfile，减少发布逻辑只存在于 Jenkins 页面中的风险。

九、环境规划

环境 用途 初步部署方式
DEV 开发联调 单机 Compose 或单节点 Swarm
TEST 测试验证 独立 Swarm stack 或独立主机
UAT 预发布验收 尽量复制生产部署方式
PROD 正式生产 独立 Swarm stack，逐步增加副本和滚动更新

各环境至少隔离以下资源：

  • 数据库和数据库账号
  • Redis 实例或逻辑库
  • OSS 路径或 bucket
  • MQ、短信、邮件和第三方回调
  • JWT、内部 Token、加密密钥
  • 域名、证书和 WebSocket 地址

十、对现有系统的影响

保持不变的内容

  • 现有 API 路径和返回结构
  • 现有数据库表和业务数据
  • 现有前端页面和接口调用方式
  • 现有域名和外部回调协议
  • 现有 Jenkins 作为发布入口
  • 现有 Swarm 作为第一阶段编排平台

需要新增或调整的内容

  • 三个项目的 Dockerfile 或多阶段构建文件
  • .dockerignore，禁止环境文件和敏感文件进入构建上下文
  • Harbor 项目、权限、机器人账号和保留策略
  • 各环境的 Swarm stack 文件
  • Jenkins 构建和部署步骤
  • 容器健康检查和回滚脚本
  • gtcuser 的滚动更新配置

十一、实施阶段

第一阶段：只读盘点和试点准备

  • 确认测试、UAT、生产服务器和 Swarm 节点。
  • 确认现有 Nginx、PHP-FPM、Supervisor、计划任务和卷。
  • 确认 Jenkins 三个核心任务的分支、构建目录和远程发布命令。
  • 建立 Harbor 项目和最小权限账号。

第二阶段：gtcuser DEV 镜像化

  • 整理现有 Dockerfile。
  • 固定 PHP/Swoole 基础版本。
  • 增加 .dockerignore。
  • 构建镜像并推送 Harbor。
  • 使用外部配置启动 DEV 容器。
  • 验证 HTTP、WebSocket、Redis、队列和日志。

第三阶段：gtc_admin 和 Vue DEV 镜像化

  • 新增 gtc_admin PHP-FPM 镜像。
  • 新增 Vue Nginx 静态资源镜像。
  • 保持现有 Nginx 域名和代理关系。
  • 验证登录、接口、上传、WebSocket 和静态资源。

第四阶段：TEST、UAT 和生产推广

  • 使用同一镜像 digest 逐环境晋升。
  • 逐步启用滚动更新。
  • 先低流量验证，再进行正式切换。
  • 保留旧部署方式和旧镜像作为回滚路径。

十二、主要风险和控制措施

风险 控制措施
环境配置错误 每个环境独立配置，部署前执行配置完整性检查
密钥进入镜像 .dockerignore、镜像层审计、敏感配置外置
gtcuser 多副本重复任务 初期保持任务副本为 1，后续拆分 Worker/Cron
WebSocket 连接中断 健康检查、优雅退出、验证断线重连和负载均衡
镜像启动失败 发布前启动检查，失败自动保留旧版本
数据库变更不兼容 数据库迁移独立执行，先兼容旧版本再切换代码
Harbor 或 Swarm 故障 保留旧镜像、旧 stack 文件和人工回滚命令

十三、验收标准

第一阶段至少满足：

  • 三个项目可以分别构建业务镜像。
  • 镜像中没有 .env、私钥、证书和真实 Token。
  • Harbor 可以按版本保存和拉取镜像。
  • DEV 可以通过指定镜像启动三个项目。
  • gtcuser 发布不再依赖传输源码到运行服务器。
  • Jenkins 能记录 Git commit、镜像 tag 和 digest。
  • 部署失败可以恢复上一版镜像。
  • 现有登录、核心 API、前端页面和 WebSocket 功能通过验证。

十四、最终建议

本项目不建议一次性进行大规模 DevOps 重构。建议先完成一个小闭环：

1gtcuser DEV
2  -> Docker 镜像
3  -> Harbor
4  -> Swarm 启动
5  -> 健康检查
6  -> 回滚验证

这个闭环验证成功后，再以相同模式处理 gtc_admin 和 gtc_admin_vue，最后推广到 TEST、UAT 和生产。这样改动集中、风险可控，现有系统仍然可以继续使用。

本方案为初步架构和实施建议，未包含生产环境实际节点、Jenkins 任务脚本和宝塔站点配置的最终确认；正式实施前需要完成一次只读资产盘点。
