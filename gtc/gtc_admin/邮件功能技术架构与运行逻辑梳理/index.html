邮件功能技术架构与运行逻辑梳理

2026-10-27 项目：gtc_admin

邮件功能技术架构与运行逻辑梳理

1. 文档范围与结论

本文基于 gtc_admin、gtc_admin_vue、gtcuser 当前源码、Composer/NPM 依赖、邮件相关数据字典和配置进行梳理，重点回答以下问题：

  • 邮件功能使用了哪些技术栈；
  • 邮件是否使用队列，队列如何分流；
  • 定时发送、延迟发送和批量发送分别如何触发；
  • 模板、语言、SMTP、日志和失败处理如何串联；
  • 三个项目在邮件功能中的边界是什么。

本次只新增分析文档，未修改业务代码，也未输出任何 SMTP 密码、Token、密钥或 .env 敏感值。

1.1 核心结论

  1. 系统存在两套后端邮件实现：
    • gtc_admin：ThinkPHP 8 + yzh52521/think-mail，底层由后台服务调用 SMTP；异步主要使用 topthink/think-queue 的 Redis 驱动，队列名为 Jobs。
    • gtcuser：Hyperf 3.1 + Swoole 常驻进程，业务发送主链路由自定义 EmailService 直接构造 Symfony Mailer；投递使用 Hyperf AsyncQueue + Redis，并按通知类型拆分 notify_normal、notify_all、fast 等队列。
  2. gtc_admin_vue 只负责邮件配置、模板、批量任务、会员手工发送和日志等管理页面，不直接连接 SMTP，也不执行队列消费或定时任务。
  3. 会员业务通知的推荐主链路是：业务代码构造 EventTrackEvent -> NotificationListener -> SendMemberEmailJob -> EmailService -> SMTP -> mail_log。
  4. 全员通知不是一次 SMTP 群发，而是先写 mail_batch_send，再按会员拆成单会员任务，批量投递到 notify_all 队列。
  5. gtc_admin 的延迟邮件使用 Think Queue 的 Queue::later；gtcuser 支持 AsyncQueue 的 delay，但当前发现的主要业务定时邮件是 Crontab 触发后立即入队，未发现业务代码直接调用 Mailable 的 later()。
  6. gtc_admin 的队列失败持久化配置为 none，多个 Job 在异常后直接删除任务；批量发送代码中 fail_num 的增加条件与变量语义疑似相反，需在生产环境核对。
  7. gtcuser 的邮件任务默认重试次数较少：SendMemberEmailJob 为 maxAttempts=1，NotifyAgentJob 为 2；发送异常通过异常传播交给 AsyncQueue，但失败补偿、死信和幂等策略仍需单独建设。

2. 三项目职责与运行形态

项目 运行形态 邮件职责 是否发送 SMTP
gtc_admin ThinkPHP 8、PHP 8.0 兼容的 Web/FPM；另有 Think Queue Worker 和历史 Timer/Workerman 代码 后台邮件管理、旧业务邮件、后台手工发送、批量任务、跨项目远程通知投递 是，InformationService 同步执行时连接 SMTP；默认业务调用通常先入 Jobs 队列
gtcuser Hyperf 3.1、Swoole 常驻进程 会员事件通知、全员通知、代理通知、密码通知、IB 定时通知、模板渲染和邮件日志 是，EmailService 直接使用 Symfony Mailer；SMTP 发送在 AsyncQueue Consumer 中执行

3. 技术栈与配置体系

3.1 gtc_admin 技术栈

composer.json 声明：

  • PHP >=8.0.0；
  • ThinkPHP ^8.0、Think ORM；
  • yzh52521/think-mail ^3.2；
  • topthink/think-queue ^3.0；
  • Redis Queue 连接；
  • 本地 ykd/framework 扩展。

邮件基础配置文件为 config/mailer.php，而 InformationService 构造时会按照 server_id 从 config_server 读取 SMTP 主机、账号、密码、端口和发件人名称，然后动态覆盖 mailer 配置。因此，旧业务链路的实际配置来源主要是 config_server，不能只看静态 config/mailer.php 判断线上配置。

队列配置文件 config/queue.php：

  • 默认驱动为 Redis；
  • Redis 队列默认名为 default；
  • 邮件 Job 在代码中显式使用 Jobs 队列名；
  • failed.type=none，没有可靠的失败任务持久化表。

3.2 gtcuser 技术栈

composer.json 声明：

  • PHP >=8.1；
  • Hyperf 3.1.*、Swoole >=5.0；
  • hyperf/async-queue 3.1.*、hyperf/crontab ^3.1、hyperf/event 3.1.*；
  • hyperf-ext/mail 本地包 packages/mail-master；
  • Symfony Mailer 由本地邮件包依赖和业务代码直接使用。

config/autoload/mail.php 支持 SMTP、AWS SES、Mandrill、Mailgun、Postmark、sendmail 和 log transport；全局配置由 MAIL_MAILER、MAIL_SMTP_DSN、MAIL_FROM_ADDRESS、MAIL_FROM_NAME 等环境变量提供。需要区分两条实现：

  1. 本地 hyperf-ext/mail 提供 Laravel 风格的 Mailable/F facade，并支持 ShouldQueue、queue()、later()；
  2. 当前核心业务使用的 App\Service\Common\EmailService 绕过该 Facade，直接通过 Transport::fromDsn()、Symfony\Component\Mailer\Mailer、Email 发送，并自行写日志。

AsyncQueue 配置为 RedisDriver。邮件相关队列主要有：

队列 典型用途 当前配置特征
notify_normal 普通业务通知、密码通知、代理通知、IB 通知 5 个进程、并发上限 10、消费超时 10 秒
notify_all 全员通知逐会员投递 3 个进程、并发上限 5、消费超时 10 秒
fast 快速通知；部分验证码/首笔入金通知 5 个进程、并发上限 10、消费超时 10 秒
default 其他耗时任务 不是邮件专用队列

config/autoload/processes.php 注册 ConsumerProcess，所以队列消费者是 Hyperf 常驻进程的一部分；CrontabDispatcherProcess 同时负责扫描 Attribute 定义的定时任务。

3.3 gtc_admin_vue 技术栈

前端为 Vue 3 + Vite，主要依赖 Vue Router、Pinia、Axios、Ant Design Vue、TinyMCE、XLSX/JSZip。邮件页面只封装 HTTP API，例如：

  • /admin/Mail.MailConfig/*：SMTP 配置列表、增改删、启停、连接测试；
  • /admin/mail/*：模板、批量任务、批量发送、批次详情；
  • /admin/Mail.TemplateImport/*：模板 ZIP 预览、确认、导入记录；
  • /admin/Logger/mail 或兼容日志接口：邮件发送日志；
  • /admin/Member/sendMail：会员详情页手工发送。

4. 数据模型

4.1 gtc_admin 数据表

表定义位于 gtc_admin/docs/数据字典.sql：

表 作用 关键字段/状态
t_mail_config 新邮件配置表 type：verification_code、system_notification、marketing、all；status：1 启用、0 停用、-1 删除；is_default 默认配置
t_mail_template 模板主表 name、title、content、type、mail_config_type、is_must_open；status：0 禁用、1 启用、-1 删除
t_mail_template_lang 模板语言内容 (template_id, lang) 唯一；default 作为默认语言
t_mail_log 发送日志 收件人、发件人、模板、正文、server_id、status、error_info
t_mail_batch_send 批量发送主任务 status：0 待推送、1 推送完成、2 推送失败、3 手动中断；send_num、fail_num
t_mail_batch_send_user 批次的会员明细 batch_id、member_id、email、send_time、status
t_mail_template_import_batch 模板导入批次 0 待确认、1 已导入、2 失败
t_mail_template_import_detail 导入逐行明细 新增/覆盖动作、语言 JSON、变量 JSON、错误 JSON

邮件日志所在数据库连接由后台日志控制器决定，当前 Logger::mail() 从 database.bigdata 连接读取 t_mail_log，不是简单地默认读取业务主库。

4.2 gtcuser 数据模型

gtcuser 的模型使用无前缀表名，例如 mail_template、mail_template_lang、mail_log、mail_batch_send；实际物理表名和前缀由数据库连接配置决定。主要模型为：

  • App\Model\crm\MailTemplate：启用状态的模板主记录；
  • App\Model\MailTemplateLang：多语言标题和正文；
  • App\Model\MailBatchSend：全员通知/批量通知任务和状态；
  • App\Model\crm\MailLog、MailLogRepository：成功和失败日志；
  • MailConfigRepository：按模板 mail_config_type 和权重选取邮件配置。

两个后端项目都出现邮件模板、批次和日志模型，实际部署时应确认它们是否共享同一 CRM 数据库、是否由数据库前缀映射到同一物理表，以及哪个项目负责写入哪类记录。

5. gtc_admin 邮件功能逻辑

5.1 通用发送入口

app/service/InformationService.php::send() 接受收件人、主题、HTML 正文、SMTP 元数据和 $queue 开关：

1queue=true  -> Queue::push(MailJobs@send, ..., 'Jobs') -> MailJobs::send -> send(..., false)
2queue=false -> 直接调用 yzh52521/think-mail 的 Mailer facade -> SMTP -> 写 t_mail_log

队列模式只表示“发送请求已入队”，不会在当前 HTTP 请求内确认 SMTP 已成功。同步模式会：

  1. 校验收件人；
  2. 解码 HTML entity；
  3. 调用 Mailer Facade 发送；
  4. 写入 t_mail_log，成功 status=1，失败 status=0 并记录 error_info；
  5. 返回发送结果。

sendMailByTemplate() 的流程为：

  1. 根据会员 ID 或邮箱定位会员；
  2. getUserLang() 从启用模板和语言表中选出语言内容，找不到指定语言时回退默认模板；
  3. replace_variable() 使用 $variable 形式的占位符进行字符串替换；
  4. 生成 SMTP 日志元数据，例如模板名、业务表名、业务 ID、服务器 ID；
  5. 调用 send()，默认仍为队列模式。

5.2 模板与语言

后台模板控制器 app/admin/controller/Mail.php 提供模板列表、新增、编辑、删除、启用/停用和详情；支持验证码、系统通知、营销等推送类型。is_must_open=1 的模板不能被停用。

模板导入由 MailTemplateImportService、MailTemplateImportParser 和 TemplateImport 控制器完成：

  1. 上传 ZIP；
  2. 读取 templates.xlsx 和对应 HTML 文件；
  3. 预览并生成导入批次、逐行明细；
  4. 确认后新增或覆盖主模板及 t_mail_template_lang 内容；
  5. 在导入记录中保留新增、覆盖、缺语言和错误信息。

5.3 SMTP 配置选择

后台 MailConfig 控制器维护 t_mail_config，允许按验证码、系统通知、营销和全部类型配置 SMTP，并限制只能有一个默认 all 配置。testConnection() 用原生 socket 测试主机和端口，465 端口按 SSL 连接，其他端口按普通 TCP 连接测试。

需要注意配置存在两个来源：

  • 旧 InformationService 的发送实现主要从 config_server 读取按 server_id 的 SMTP 参数；
  • 新 t_mail_config 的类型化配置主要由新模板/邮件服务体系使用，gtcuser::EmailService 会根据模板 mail_config_type 通过 MailConfigRepository 选择配置。

这意味着新增或修改配置时必须确认调用方使用的是哪一条链路，不能假定所有邮件都读取 t_mail_config。

5.4 普通业务邮件

gtc_admin 中有大量旧式直接调用，典型场景包括：

  • 注册激活、注册成功、忘记密码；
  • 登录验证码、修改登录/资金密码、提现验证码、Google 验证码；
  • 入金成功/驳回、出金、KYC 审核、MT 开户；
  • 跟单、活动、课程、文章、工单和代理相关通知。

这些调用大致分为两种：

  1. 直接 new InformationService(...)->sendMailByTemplate(...)，默认进入 Jobs 队列；
  2. 调用 remoteOption('option/memberAuditNotify', $data)，由 gtc_admin 通过跨项目接口把通知转给 gtcuser。

后台审核类、课程类和活动类代码中同时存在这两种方式，必须以具体调用点为准。

5.5 批量邮件

后台页面 sendemail/sendemail/index.vue 调用：

  • POST /admin/mail/batch_add 创建批次；
  • POST /admin/mail/batch_send 推送批次；
  • POST /admin/mail/batch_info 查看会员级明细；
  • POST /admin/mail/batch_delete 删除尚未推送的批次。

batch_add 支持全部客户、标签客户、指定客户和国家客户等筛选条件。batch_send 先查询收件人并把主批次从状态 0 改为状态 1，再为每个会员构造 Job：

1Mail::batch_send
2  -> 逐会员 Queue::push(MailJobs@fire, ..., 'Jobs')
3  -> MailJobs::fire
4  -> InformationService::send(..., queue=false)
5  -> SMTP
6  -> t_mail_batch_send_user + t_mail_log

MailJobs::fire 会增加 send_num 并写入会员明细；源码中 if ($res === true) { fail_num+1 } 与 status=$res===true?1:0 同时存在，前者看起来把成功结果记成失败数量，需核对 InformationService::send() 的真实返回约定后修正统计口径。

5.6 手工发送与日志

会员详情页的 src/components/member/sendemail.vue 调用后台 /admin/Member/sendMail。Logger::sendMail() 当前调用 InformationService::send() 时没有传 $queue=false，所以后台手工发送也会先进入 Jobs 队列，接口返回的是“已提交/已入队”语义，不能等同于 SMTP 已投递。

Logger::mail() 支持按邮箱和会员 ID 查询邮件日志，分页返回，并对验证码、密码和邮箱做脱敏。日志可用于判断 SMTP 阶段是否执行，但不能单独证明收件方已阅读邮件。

5.7 gtc_admin Job 行为

app/jobs/controller/MailJobs.php 有三个入口：

  • fire()：批量逐会员发送，同步调用 Mailer，更新批次和批次明细；
  • send()：普通邮件，同步调用 Mailer，异常时打印并删除 Job；
  • sendOfRemote()：调用 remoteOption('option/memberAuditNotify', $data)，最多检查两次尝试后删除。

大多数异常分支直接 $job->delete()，failed() 只保留调试输出，且 config/queue.php 的 failed driver 为 none。因此当前链路没有可靠的死信表、自动补偿或人工重放机制。

6. gtcuser 邮件功能逻辑

6.1 主发送服务

App\Service\Common\EmailService::send() 的流程如下：

  1. 收件地址为空时直接记录警告并返回；
  2. 未指定 serverId 时使用默认 MT Server；
  3. 标准化模板语言代码，例如 zhCn -> cn、zhTw -> tw、india -> in；
  4. 查询启用的 mail_template；
  5. 优先使用指定语言的 mail_template_lang，没有有效内容时回退 default；
  6. 根据模板的 mail_config_type 和配置权重选择 SMTP，找不到时回退 all，再回退按服务器读取的旧配置；
  7. 注入 webname、收件邮箱等通用变量；
  8. 用 $key 形式替换模板标题和 HTML 正文；
  9. 对 user_reset_mt4_pwd 等历史模板执行 HTML entity 兼容解码；
  10. 对日志变量和正文中的密码字段做脱敏；
  11. 构造 Symfony Transport、Mailer 和 Email，设置发件人、收件人、标题和正文；
  12. 成功写 mail_log.status=1，异常写 status=0 和截断的错误信息，并重新抛出异常。

createTransport() 对 SMTP socket 设置 8 秒超时，避免常驻 Worker 因连接长期阻塞。源码中 executeSend() 的日志 server_id 从邮件配置数组读取，而邮件配置选择前同时保留了 SMTP server_id 元数据，当前字段映射需要继续核对，存在日志服务器 ID 为空的风险。

6.2 事件通知主链路

大部分会员通知由 EmailNotificationEventService 构造 EventTrackEvent，事件由 NotificationListener 接收。监听器校验 member_id、templateDataMap 后创建 SendMemberEmailJob，再投递到 notify_normal：

 1注册/登录/KYC/资金/MT/跟单等业务
 2  -> EmailNotificationEventService::commonNotification()
 3  -> dispatchEvent(EventTrackEvent)
 4  -> NotificationListener::process()/execute()
 5  -> AgentEmailIsolationService 入队前过滤
 6  -> pushQueue(SendMemberEmailJob, 0, notify_normal)
 7  -> ConsumerProcess
 8  -> SendMemberEmailJob::handle()
 9  -> 发送前再次检查隔离状态
10  -> 查询会员、邮箱和语言偏好
11  -> EmailService::send()
12  -> Symfony Mailer -> SMTP -> mail_log

会员 Job 在执行时重新查询会员，因此邮箱、国家、首选邮件语言和代理隔离模式均可能以执行时的最新状态为准。不存在会员或邮箱时，若 Job 未显式设置备用邮箱，则跳过发送。

AgentEmailIsolationService 在入队前和发送前各检查一次，用于避免代理应用模式变化后仍发送被隔离的代理类邮件。

6.3 全员通知

approvedNotification() 对公告、直播、课程发布、活动和直播即将开始等枚举走全员通知：

  1. 查询启用会员数量；
  2. 写入 mail_batch_send，记录标题、事件值、人数和开始时间；
  3. 获取 notify_all Driver；
  4. 以 5000 条为查询块，逐会员创建 SendMemberEmailJob，通过 mailTaskId 关联批次；
  5. Job 执行时从 mail_batch_send.event_value 重新确定模板名，若批次状态为 3 则跳过；
  6. 全部 Job 推送完成后将批次状态写为 1，异常写为 2。

开发环境和本地环境对全员发送限制为固定会员 ID 列表，避免测试环境误发全量客户。

这里的批次状态“1”表示推送任务已完成，不表示每封邮件 SMTP 均成功；单封成功/失败仍应以 mail_log 为准。mail_batch_send 当前没有与每个 AsyncQueue Job 的最终结果自动回写的完整闭环，运维统计时需要同时查看批次和日志。

6.4 代理通知

代理设置相关场景通过 pushNotifyAgentJob() 投递 NotifyAgentJob 到 notify_normal。Job 执行时：

  1. 查询下级会员是否已配置规则；
  2. 查询其上级代理和邮箱；
  3. 再次执行代理邮件隔离检查；
  4. 向上级代理发送 SetRuleSuperiorAgent 模板；
  5. 向客服配置中的 NOTIFY_EMAIL 地址发送客服模板。

NotifyAgentJob::$maxAttempts=2，但客服地址是循环发送，部分成功/部分失败时没有独立的每个客服收件人的状态表。

6.5 后台密码通知和验证码

  • AdminMtPasswordEmailService 创建 SendMemberEmailJob，模板为 user_reset_mt4_pwd，投递 notify_normal；
  • 登录密码重置、MT 密码重置会把密码作为 Job 数据传递，但 EmailService 会对日志变量和正文做密码脱敏；
  • 邮箱验证码任务由 TMemberService 构造 Job，可指定新邮箱和无会员时的回退语言；
  • 首笔入金通知的部分路径使用 fast 队列，以降低验证码/关键通知等待时间。

6.6 远程通知入口

gtc_admin 的课程、文章、活动、审核等部分代码调用 remoteOption('option/memberAuditNotify', $data)；gtc_admin 也会把这个调用放入 MailJobs::sendOfRemote 延迟 Job 中。该接口将事件数据交给 gtcuser 的远程业务入口，再由 EmailNotificationEventService 或相应通知服务转成邮件 Job。

因此，看到 gtc_admin 代码没有直接 SMTP 调用并不代表没有邮件发送；需要继续沿 remoteOption 的接口路由、HTTP 客户端和 gtcuser 接收端核对实际部署地址与认证配置。

6.7 历史/备用实现

以下代码存在，但当前主业务是否仍使用需要通过调用关系和部署版本确认：

  • app/Repository/Remote/EmailRepository.php::_sendEmail() 标记了 #[AsyncQueueMessage(pool: 'fast')]，直接使用 Symfony Mailer 并写 MailLogRepository；它与 EmailService 的发送逻辑重复，疑似遗留或特定远程场景实现；
  • SendSystemEmailJob 已定义 maxAttempts=2，但 handle() 的实际发送代码整体注释，当前不能视为可用系统级邮件入口；
  • packages/mail-master 的 Mailable 支持 ShouldQueue、queue() 和 later()，但当前发现的业务邮件主要使用自定义 SendMemberEmailJob，不应把框架能力误写成业务已经使用。

7. 队列使用与定时/延迟发送

7.1 队列总表

项目 队列组件 Redis 邮件队列 消费形态 失败持久化
gtc_admin Think Queue 3 是 Jobs（代码显式传入） 独立 Queue Worker failed=none，无可靠 failed 表
gtcuser Hyperf AsyncQueue 3.1 是 notify_normal、notify_all、fast Swoole 常驻 ConsumerProcess 依赖 Driver 重试与 Job maxAttempts，未见完整死信/补偿闭环

7.2 gtc_admin 延迟发送

课程直播提醒

app/admin/controller/Course/ZoomMeeting.php::scheduleLiveReminder() 根据直播开始时间和提前量计算 delay：

  • delay > 0：Queue::later(delay, MailJobs@sendOfRemote, ..., 'Jobs')；
  • 已过提醒点但直播尚未开始：立即 Queue::push；
  • 直播已经开始：不再发送。

课程通常会分别安排提前 1 小时和 24 小时的通知，最终通过 sendOfRemote 将通知交给远程 gtcuser。

代理审核后的延迟提醒

app/admin/controller/Agent.php 中安排了 24 小时和 48 小时的 Queue::later，数据类型为 set_rule_superior_agent，最终也进入 sendOfRemote。该逻辑需要结合接收端幂等和业务状态判断，避免重复提醒。

跟单过期检查

app/admin/controller/Timer.php::check_follow_exprie() 扫描过期跟单配置并调用 sendMailByTemplate()。由于该方法默认 $queue=true，Timer 只负责发现到期记录，实际 SMTP 仍由 Jobs 队列完成。Timer 本身更像被外部计划任务或白名单 CLI 调用的控制器入口，不是 ThinkPHP Queue 的定时调度器。

7.3 gtcuser Crontab 定时邮件

Hyperf 的 Crontab 总开关在 config/autoload/crontab.php，具体任务通过 #[Crontab] Attribute 注册，并由 CrontabDispatcherProcess 调度。邮件相关任务包括：

任务 Cron 实际动作 邮件队列
app/Task/MailTask/IbSignTask.php 0 12 * * * 调用 IbService::unSignIbEmail()，按 500 条块扫描未签署 IB 协议的客户并创建通知 Job notify_normal
app/Task/MailTask/IbCommissionTask.php 0 12 * * * 调用 IbService::unCommissionIbEmail()，找出未配置佣金规则的代理及其上级并创建通知 Job notify_normal
app/Task/InvestorReportTask.php 20 0 * * * 主要计算投资者日报；当前源码未见直接发送邮件，不能归类为邮件发送任务 不适用
app/Task/CommonOptTask.php 每 60 秒 公共定时操作；是否间接触发邮件需按其具体分支和运行配置确认 视分支而定

IbSignTask 和 IbCommissionTask 的 isEnable() 依赖 BASE_CRONTAB；许多其他 Task 使用 TaskTrait::isEnable()，依赖 APP_RUN_TASK。当前 .env、.env.test、.env.staging 的开关值并不完全一致，生产是否真正执行必须以部署环境变量和进程启动参数为准。

7.4 延迟队列能力与实际使用边界

gtcuser 的 pushQueue($job, $delay, $queue) 支持传入延迟秒数；EmailNotificationEventService::pushNotifyAgentJob() 已保留 $delay 参数，具备延迟投递能力。框架邮件包的 Mailable::later() 也会把任务连同 delay 推入 AsyncQueue。

当前已确认的业务延迟主要来自：

  • gtc_admin 的 Queue::later 课程/代理提醒；
  • gtcuser 的定时任务触发后立即投递通知 Job；
  • 个别服务通过 pushQueue 传入 delay。

应以实际调用点为准，不能因为框架支持 later() 就推断所有模板邮件都按定时发送执行。

8. 模板、语言和变量渲染

8.1 模板选择

两套后端都采用“模板主表 + 模板语言表”：

1template name/code
2  -> 主模板 status=1
3  -> 指定语言 mail_template_lang
4  -> 无内容时回退 default
5  -> 替换 $variable
6  -> 生成 HTML Subject/Body

gtc_admin 的旧逻辑通常先根据会员国家/语言调用 getUserLang()；gtcuser 的新逻辑在 Job 执行时调用 translateDataMap()，优先会员的邮件语言设置，其次按国家语言，最后回退英文/default。

8.2 变量与翻译

gtcuser 的 translateDataMap() 支持：

  • ['is_trans' => true, 'key' => '...'] 形式的业务翻译变量；
  • 对严格匹配的 Y-m-d H:i:s 时间追加服务器 UTC 偏移提示；
  • 注入会员 username、nickname、realname 等变量；
  • 对密码、只读密码、资金密码等日志变量替换为 ******。

gtc_admin 的 replace_variable() 主要是简单字符串替换，业务代码通常先自行组装国家、时间、金额和链接等变量。

9. 日志、状态、失败与幂等

9.1 日志

  • gtc_admin：同步发送或 Queue Job 内部写 t_mail_log；后台日志接口分页查询并脱敏。
  • gtcuser：EmailService::executeSend() 成功/失败均通过 MailLogRepository 写 mail_log，同时写 EmailService、email-send、email-notify 等应用日志。
  • 日志记录的是 SMTP 客户端执行结果，通常不能证明远端邮箱服务商最终投递或用户打开。

9.2 失败处理

gtc_admin

  • 队列配置未启用 failed job 存储；
  • MailJobs::send() 和 fire() 异常后直接删除 Job；
  • sendOfRemote() 最多尝试后删除；
  • failed() 没有业务补偿；
  • 批量明细会记录 0/1 状态，但统计条件疑似有误。

gtcuser

  • SendMemberEmailJob 的 maxAttempts=1，发送异常会抛出；
  • NotifyAgentJob 的 maxAttempts=2；
  • EmailService 写失败日志后重新抛异常，让 AsyncQueue 决定重试；
  • 全员任务的“推送完成”只表示子 Job 已写入队列，不代表所有 SMTP 调用成功；
  • 未发现邮件专用死信表、失败重放命令和统一幂等键。

9.3 幂等风险

以下情况可能造成重复邮件或状态不一致：

  • 同一业务事件重复 dispatch；
  • gtc_admin 的 24/48 小时延迟 Job 与业务重试同时存在；
  • AsyncQueue 重试发生在 SMTP 已接受但应用未及时收到响应之后；
  • 全员批次只记录任务级状态，单会员 Job 缺少业务事件唯一键；
  • NotifyAgentJob 的 uniqueId 只保证序列化字段唯一，不等于数据库幂等约束。

12. 当前风险与待核对项

  1. 配置来源并存：gtc_admin 旧 config_server、t_mail_config 和 gtcuser 环境变量/类型化配置同时存在，需要形成明确的模板到 SMTP 配置映射表。
  2. 批量失败统计疑似反向：MailJobs::fire() 中 res===true 时增加 fail_num，需要核对发送返回值后修正。
  3. 失败任务不可追踪：gtc_admin failed queue 为 none，Job 异常多直接删除；生产故障后缺少可靠重放入口。
  4. 批次状态语义不足：gtcuser 全员任务状态 1 表示“子任务已推送”，不是“全部邮件已成功”；前端若显示为已发送容易误导运营人员。
  5. 重试与幂等不足：SMTP 超时、进程重启、远端接口响应丢失时可能重复发送；建议引入业务事件 ID、模板名、会员 ID 的唯一键或发送去重表。
  6. 日志敏感信息边界：gtcuser 已对模板密码变量脱敏，但异常信息截取 500 字符，仍应确认 SMTP 异常不会带出账号、DSN 或认证信息。
  7. 日志 server_id 映射需核对：EmailService::executeSend() 从 $config['serverId'] 读取日志字段，而类型化 t_mail_config 返回的 serverId 为 0，可能导致日志无法按 MT Server 追踪。
  8. 重复实现：EmailRepository::_sendEmail()、SendSystemEmailJob 和本地 Mailable 包能力与主 EmailService 并存，需通过生产调用链确认哪些仍在使用。
  9. 跨项目远程链路可观测性不足：sendOfRemote、remoteOption 和 gtcuser 接收端需要统一 request/task ID，否则很难关联后台操作、远程接口、邮件 Job 和 SMTP 日志。
  10. 定时任务环境开关不一致：BASE_CRONTAB、APP_RUN_TASK 在不同环境文件中取值不同，发布检查必须确认 Crontab Dispatcher、Consumer 和队列进程均已启动。
  11. 前端接口与旧页面并存：模板管理同时存在旧 messagetemplate 和新 newmessagetemplate 页面；批量邮件页和部分兼容 API 目录中存在历史页面，需在菜单权限中确认实际运营入口。
  12. 邮件内容和收件人缺少统一审计：直接正文发送、模板发送、远程通知分别写不同元数据，建议统一记录业务事件类型、任务 ID、来源项目和幂等键。

13. 建议的验证顺序

按以下顺序做线上或测试环境验证，能最快确认邮件全链路：

  1. 核对三个进程面：gtc_admin Queue Worker、gtcuser ConsumerProcess、CrontabDispatcherProcess 是否运行；
  2. 用测试 SMTP 和单个测试会员验证 notify_normal：检查 Job 入队、模板语言、SMTP 结果和 mail_log；
  3. 验证 gtc_admin /admin/Member/sendMail，确认接口返回与实际发送状态的时间差；
  4. 创建 2~3 人批量任务，核对 mail_batch_send、mail_batch_send_user、send_num、fail_num 和 t_mail_log；
  5. 在开发环境触发全员公告，确认固定测试会员限制、notify_all 投递和取消状态 3 的行为；
  6. 创建课程直播，分别测试提前 24 小时、提前 1 小时和已经开始三种时间分支；
  7. 手工执行或等待 IbSignTask、IbCommissionTask，确认 BASE_CRONTAB 开关、分块查询和 notify_normal 投递；
  8. 制造 SMTP 超时/认证失败，确认失败日志、重试次数、批次状态和是否产生重复邮件；
  9. 对 remoteOption('option/memberAuditNotify') 建立跨项目链路追踪，核实接收端、认证、模板枚举和日志关联；
  10. 最后核对 t_mail_config、config_server、MAIL_SMTP_DSN 三套配置在同一模板上的实际优先级。
