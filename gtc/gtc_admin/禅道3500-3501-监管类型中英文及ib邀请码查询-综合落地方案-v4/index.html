1. 对比结论与最终取舍

1.1 两份方案的优劣

维度 v3 方案 同事方案 v4 结论
需求边界和状态建模 对页面公开状态、内部诊断原因、直客 ID、主邀请码、筛选继承定义更严谨 把配置异常统一归为平台停用，页面语义过粗 采用 v3 的四段状态规则；内部诊断不外泄
数据库发布 生成列和唯一索引已固定，但缺少存储过程式阻断和重复执行细节 有 SIGNAL、信息架构检查和重复数据中止 采用同事的发布控制方式，生成列、索引名称统一为本方案唯一版本
#3500 接口校验 保存校验完整 增加只读 validate_name，便于前端分别定位字段 纳入 validate_name，但保存时仍由服务端和数据库最终校验
#3501 索引 曾建议 (member_id, groups)，缺少真实执行计划依据 建议 member_id 单列索引，符合主查询条件 采用单列索引；本需求不增加复合索引，后续性能问题另立任务
邀请码输入 支持多种链接和别名 明确原始码 255、完整 URL 2048、正整数规则 纳入全部边界和冲突规则
前端和测试 状态、筛选、展开逻辑较完整 复制、加载状态、空状态、账户类型名称和 node --test 更具体 合并为可验收清单
跨项目边界 明确 gtcuser 不改业务代码，并用契约测试对齐规则 方案描述较容易把 gtcuser 规则直接当作可调用 Service 固定为后台只读计算 + 同一数据集契约测试，不引入跨服务调用

1.2 最终判断

v3 在业务口径和风险边界上更优，同事方案在数据库施工细节、只读校验接口和测试颗粒度上更优。v4 合并两者优点，并冻结所有会导致开发人员自行决策的分支：

  • #3500 使用 title、title_en 原始字段；API 同时返回 name、name_en、title、display_name。
  • #3500 只保留一套生成列和唯一索引命名。
  • #3501 页面公开状态只有 available/disabled，停用原因只有 ib_disabled/platform_disabled；配置异常写内部诊断。
  • 主列表和展开接口共享全部筛选条件；展开只增加一层直属 parent_id 条件。
  • gtcuser 本期不改业务代码，不通过 HTTP 或共享 Service 被后台调用。
  • 发布脚本先预检查、再加字段、再检查英文重复、再建生成列和索引；重复数据通过 SIGNAL 阻断，脚本可重复执行。

4. #3500 字段、展示和接口契约

4.1 字段映射

含义 数据库 API
中文原名 title title
英文原名 title_en name_en
兼容当前语言展示值 不落库 name
统一展示值 不落库 display_name

列表和引用详情必须返回：

1id, title, name_en, name, display_name, description,
2status, deleted, updated_by, updated_by_id, update_time

编辑表单只回显 title 和 name_en。name、display_name 不能回写数据库。保存请求继续兼容旧字段 name 作为中文原名，并新增 name_en；Controller 在边界处转换为 title/title_en，Service 内部只使用原始字段名。

4.2 展示和回退

  • zh_CN、zh_TW、zh-cn、zh-tw 优先 title，为空回退 title_en。
  • 英文及其他非中文语言优先 title_en，为空回退 title。
  • 两者均为空显示 --，并限频记录数据异常。
  • 一个展示位置只显示一个 display_name，不拼接双语；编辑页同时显示两个输入框。
  • 历史英文为空时允许列表回退；编辑页提示补充英文并阻止再次保存为空。
  • 切换语言重新请求字典或重新计算展示值，不能把 display_name 当作原始中文保存。
  • 生成列和内部归一字段不进入 API。

4.3 保存和只读唯一性校验

保存接口必须在 Service 进行最终校验：

  • 两个字段去除首尾空格后均非空。
  • 中文最多 50 个字符，英文最多 100 个字符。
  • 中文和英文分别按归一值唯一，编辑排除当前 ID。
  • 英文允许常见缩写、括号和名称标点，不使用会删除英文标点的中文清洗函数。
  • 数据库唯一索引冲突按索引名映射到 name 或 name_en，表单保留输入并定位字段。

新增只读接口：

1POST /admin/kyc_regulatory_type/validate_name
2权限：复用 kyc_regulatory_type/view，不新增菜单
3请求：{ id?: int, name?: string, name_en?: string }
4响应：{ valid: bool, error_fields: string[], message?: string }

接口只做格式和唯一性读取，不写库；至少传入一个待校验字段。前端在输入停顿后调用并使用 error_fields=[name,name_en] 分别定位错误。该接口不能替代保存时的服务端校验、事务和数据库唯一索引。

5. #3500 数据库迁移和发布

5.1 固定前置条件

发布目标为 InnoDB、MySQL 5.7.6 及以上。低于该版本直接阻断。发布脚本不使用不兼容的 ADD COLUMN IF NOT EXISTS 或 CREATE INDEX IF NOT EXISTS。

发布文件固定为：

1gtcuser/scripts/v2.20.1/20261109_3500_kyc_regulatory_type_english.sql
2gtcuser/scripts/v2.20.1/20261109_3501_agent_invite_code_query.sql

gtc_admin 和 gtcuser 的 docs/数据字典.sql 在代码提交中同步更新；SQL 只放在表所属项目的版本脚本目录。

5.2 执行顺序

  1. 记录 SELECT VERSION()、引擎、表行数、字段和索引定义。
  2. 在 title_en 不存在时只检查中文空值和重复；不引用不存在的英文列。
  3. 检查 agent/account 菜单权限存在且有效；不得编造菜单 ID。
  4. 增加 title_en。
  5. 字段存在后检查英文空值和重复。
  6. 重复或空值发现后由发布人员生成清理清单并中止；不自动删除、覆盖或回填。
  7. 增加生成列。
  8. 增加唯一索引。
  9. 第二次执行整份脚本必须幂等，并验证索引定义没有漂移。

5.3 归一化和唯一约束

预检查口径必须与生成列完全一致：

 1-- 中文：未删除记录不能为空，且 TRIM 后唯一
 2SELECT TRIM(title) AS normalized_title, COUNT(*) AS cnt
 3FROM t_kyc_regulatory_type
 4WHERE deleted = 0
 5GROUP BY TRIM(title)
 6HAVING COUNT(*) > 1 OR normalized_title = '';
 7
 8-- 英文：未删除且非空，LOWER(TRIM()) 后唯一
 9SELECT LOWER(TRIM(title_en)) AS normalized_title_en, COUNT(*) AS cnt
10FROM t_kyc_regulatory_type
11WHERE deleted = 0 AND TRIM(title_en) <> ''
12GROUP BY LOWER(TRIM(title_en))
13HAVING COUNT(*) > 1;

固定 DDL 定义如下，名称不再变更：

 1ALTER TABLE t_kyc_regulatory_type
 2  ADD COLUMN title_en VARCHAR(100) NOT NULL DEFAULT ''
 3    COMMENT 'KYC监管类型英文原始名称' AFTER title;
 4
 5ALTER TABLE t_kyc_regulatory_type
 6  ADD COLUMN title_active_norm VARCHAR(255)
 7    GENERATED ALWAYS AS (
 8      CASE WHEN deleted = 0 THEN TRIM(title) ELSE NULL END
 9    ) STORED
10    COMMENT '未删除监管类型中文唯一归一值',
11  ADD COLUMN title_en_active_norm VARCHAR(100)
12    GENERATED ALWAYS AS (
13      CASE
14        WHEN deleted = 0 AND TRIM(title_en) <> ''
15        THEN LOWER(TRIM(title_en))
16        ELSE NULL
17      END
18    ) STORED
19    COMMENT '未删除监管类型英文唯一归一值';
20
21ALTER TABLE t_kyc_regulatory_type
22  ADD UNIQUE KEY uk_kyc_regulatory_type_active_title (title_active_norm),
23  ADD UNIQUE KEY uk_kyc_regulatory_type_active_title_en (title_en_active_norm);

实际发布脚本使用临时存储过程封装以上顺序：每个 DDL 前通过 information_schema.columns/statistics 判断对象是否存在；已存在对象必须核对类型、生成表达式、索引列和唯一性，定义不一致立即 SIGNAL SQLSTATE '45000' 停止；不存在对象通过 PREPARE/EXECUTE 执行。临时过程执行成功后删除。脚本不得自动删除旧索引，不提供命名锁备选分支。

生成列为 NULL 的记录不参与唯一约束，因此软删除记录可复用名称，英文空值可有多条历史记录；正常新增和编辑仍由 Service 的必填校验阻止空英文。

6. #3501 查询、权限和响应

6.1 输入解析

请求字段为 keyword、invite_code、user_type、level、register_time_start、register_time_end、parent_id、分页参数。邀请码支持原始码、正十进制客户 ID、普通 query URL 和 hash query URL；URL 别名为 ref、invitation_code、invitationcode。

解析规则固定如下：

  • 原始邀请码最多 255 字符，完整 URL 最多 2048 字符。
  • 数字输入只接受正则 ^[1-9][0-9]*$，按客户 ID 解析；拒绝 0、负数、符号、小数、科学计数法和混合空格。
  • 非数字原始输入按邀请码精确匹配，不做部分匹配；使用现有大小写不敏感排序规则。
  • URL 同时解析普通 query 和 hash 后的 query。
  • 同一 URL 中多个别名值不一致返回参数错误。
  • URL 形式明确但没有邀请码返回格式错误，不降级为关键词模糊查询。
  • keyword 支持客户 ID、昵称、邮箱、手机号的模糊条件；invite_code 与 keyword 同时存在时使用 AND。
  • 所有条件使用参数绑定；列表始终分页，禁止无条件全表读取。

6.2 默认层级、数据权限和展开

  • 首次进入页面和重置后 user_type=agent。
  • 重置清空关键词、邀请码、客户类型以外的层级和时间条件，并恢复代理。
  • 管理员在没有 parent_id 且没有精确邀请码/客户 ID 时主列表使用 parent_id=0。
  • 非管理员在同样条件下使用 parent_id=current_member_id，并继续执行现有 member_root_path 数据范围。
  • 精确邀请码或客户 ID 可定位命中会员及其允许范围内的后代，但仍叠加客户类型、关键词、层级、注册时间、status=1 和数据权限。
  • 传入 parent_id 只查询一层直属下级；展开请求携带当前全部筛选条件，再追加直属父级条件。
  • 主列表和明细默认排除当前登录会员，避免列表不可见但明细可见；本人查询不在本期范围。
  • 所有 URL 权限、角色权限和 check_data_permission() 均先于业务查询执行。

这是对管理员无条件主列表的明确行为调整，验收必须覆盖管理员顶层、非管理员第一层、关键词命中、精确定位和越权。

invite_code_count 去重后的邀请码数量
has_invite_code_detail invite_code_count > 1
can_copy_invite_code 有可复制邀请码或直客 ID 时为 true
has_children 当前页会员是否有状态正常的直属下级
children 初始为空数组，展开成功后填充一层

主要邀请码固定排序：

  1. 当前精确查询命中的邀请码优先；
  2. 有完整可用配置优先于缺失配置；
  3. account_register_setting.sort_order ASC，空值排末尾；
  4. create_time DESC；
  5. server_id ASC；
  6. account_register_setting_id DESC；
  7. code ASC 作为稳定兜底。

直客没有自有邀请码时使用 primary_invite_code=member.id、primary_invite_type=direct_member_id，页面显示“客户 ID”；代理邀请码显示“IB”。主列表不生成或写回任何邀请码。

parent_name 和 has_children 均按当前页会员 ID 集合批量查询，内存映射后回填，禁止逐行查询或逐行 count。对 parent_id/status 查询执行 EXPLAIN；本需求不增加会员表索引，执行计划和剩余风险写入验收记录。

约束：

  • 一个 code 对应多个服务器或开户配置时可以返回多行；同一 account_register_setting_id 只保留一行。
  • 无配置的历史 code 仍计数并返回空配置占位，排在有效配置之后。
  • 前端只展示 account_type_name，内部编码不得直接展示；服务器、邀请组、账户类型缺失保留行并显示 --。

  • 明细和主列表均提供复制按钮，复制只读取邀请码或直客 ID，不能读取密码、验证码、token，也不改变联系方式脱敏。

6.5 页面公开状态和内部诊断

公开字段只有：

  • status=available：页面显示“可邀请”；
  • status=disabled：页面显示“已停用”；
  • disabled_reason=ib_disabled：页面显示“IB停用”；
  • disabled_reason=platform_disabled：页面显示“平台停用”。

状态计算固定为：

  1. code.status=0：disabled + ib_disabled。
  2. 至少一条完整配置通过公开/授权、开户配置、ACCOUNT_TYPE 校验，且对应 IB 总开关存在一条未关闭：available。
  3. 存在配置但全部对应 IB 总开关关闭：disabled + platform_disabled。
  4. 没有有效配置或配置校验失败：disabled + disabled_reason=null，页面显示 --；具体原因写入内部 diagnostic_reason，不序列化到页面 API。

后台只读计算逐项对齐 gtcuser/app/Service/member/TMemberService.php::checkInvitationCode()：

  • 公开开户配置按邀请码、status=1、allow_share=1 判断；
  • 非公开配置检查 member_agent_remark 对邀请组的授权；
  • 授权后必须存在正常开户配置；
  • t_ib_invite_link_config.global_enabled=0 记录平台诊断；无配置记录按默认启用；
  • ACCOUNT_TYPE 不包含账户类型记录 config_invalid；
  • 授权失败记录 authorization_invalid；
  • 配置或服务器资料缺失保留历史行，页面原因保持 null，不新增产品未定义原因。

后台不调用 gtcuser Service，不调用有写入副作用的 IbService::getInviteCodeList()。使用同一组固定数据同时执行用户端校验和后台状态计算，契约测试只验证对外结果和诊断映射。

7. 前端实施与页面验收

修改 gtc_admin_vue/src/api/agent/index.js、gtc_admin_vue/src/views/agent/account/index.vue 和现有多语言资源：

  • 首次加载默认客户类型“代理”；重置清空关键词、邀请码、层级、时间并恢复代理。
  • 搜索、重置、刷新均有 loading 和防重复提交；刷新保留条件。
  • 邀请码输入支持原始码、客户 ID 和两类链接；解析错误、别名冲突和未找到归属分别提示。
  • 主列表昵称区域显示展开/收起图标、昵称、客户类型和客户 ID。
  • has_children=true 才允许展开；false 显示灰色不可点击占位图标，不发送请求。
  • 只有多邀请码显示“查看明细（N个）”；明细顶部显示昵称、用户类型、客户 ID、邀请码总数量。
  • 主列表和明细均提供复制；复制成功提示不泄露联系方式。
  • 页面状态只展示“可邀请/已停用”，停用原因只展示“平台停用/IB停用”，内部诊断不显示。
  • 无查询结果显示“暂无符合条件的用户”；邀请码无归属显示“未找到对应邀请码持有人”；链接无法解析显示格式提示；加载失败保留条件并支持重试。
  • 单字段缺失保留列位置并显示 --；服务器、账户类型、邀请组同样处理。
  • 展开请求继承当前关键词、邀请码、客户类型、层级、时间和数据范围；搜索、重置、刷新成功后清空 expandedRowKeys 和旧 children。
  • 旧请求不能覆盖新请求；分页、列设置、横向滚动、全屏和现有表格能力保持。

8. 测试、性能和发布验收

8.1 #3500 行为测试

  • 新增、编辑表单同时展示中文和英文；中文/英文空值、空格、超长、控制字符和重复分别定位。
  • 英文大小写重复、编辑排除当前 ID、软删除后复用。
  • validate_name 只读、权限复用、字段错误数组和保存时再次校验。
  • 并发新增/编辑由数据库唯一索引拦截，失败只影响当前请求。
  • 列表和详情均返回 name、name_en、title、display_name，映射稳定。
  • 中文、繁体、英文和其他非中文环境回退正确；双空显示 --。
  • KYC、客户、支付、监管配置、导出、引用弹窗、操作日志和审计快照均覆盖。
  • 语言切换不改变 ID、状态、关联；历史日志名称不随当前语言漂移。

8.2 #3501 行为测试

  • 首次/重置代理、全部/代理/直客筛选和所有条件 AND 组合。
  • 邀请码、正整数客户 ID、普通 query、hash query、别名冲突、非法链接和精确匹配。
  • 管理员顶层、非管理员第一层、精确命中后代、越权、本人查询和会员状态过滤。
  • 主邀请码命中优先、可用配置优先、稳定排序、复制和直客客户 ID 类型。
  • 多 code、多配置、同配置去重、无配置历史 code 和去重数量。
  • available/disabled、ib_disabled/platform_disabled 和诊断原因不外泄。
  • 账户类型业务名称、服务器/邀请组缺失占位、直接上级昵称。
  • has_children 批量计算、无下级禁用图标、展开一层且继承筛选。
  • 无结果、未找到邀请码、链接解析失败、加载失败、重试和旧请求覆盖。
  • 查询前后 t_member_invent_code 数量和内容相同；确认没有自动补建或其他写入。

8.3 数据库和性能检查

  • SQL 第一次执行、第二次执行均有日志；第二次不重复加字段、生成列、索引。

  • invite_code_count 在当前会员集合内去重，不对全表做无条件聚合。

9. 发布、回滚和完成标准

9.1 固定发布顺序

  1. 从三个 master 建分支，记录提交、数据库版本、表行数和索引。
  2. 在隔离库完整执行 #3500、#3501 SQL；同一脚本连续执行两次，核对幂等和 EXPLAIN。
  3. 先发布能兼容 title_en 缺失/为空的后台后端。
  4. 发布数据库字段、生成列、唯一索引和数据字典对应版本。
  5. 发布 #3500 前端、#3501 列表改造和明细接口。
  6. 灰度检查字段契约、权限、状态、复制、空状态、过滤继承、无写入副作用和日志。
  7. 全量发布并保存 SQL 执行记录、测试记录和回滚点。

9.2 回滚

  • 前端先回滚，后台代码后回滚；旧代码只读取 title，不受 title_en 影响。
  • 默认保留新增字段、生成列、唯一索引和英文数据，优先代码回滚，不执行破坏性 DROP。
  • DDL 任一步失败立即停止，记录已完成步骤；不得重复执行未经确认的 DROP/ALTER。
  • 只有在确认没有后续版本依赖后，才按唯一索引 -> 生成列 -> title_en 逆序回滚。
  • #3501 只回滚本次新增且无其他版本依赖的 member_id 索引；不删除历史邀请码和 t_ib_invite_link_config。
  • 数据清理和英文回填使用独立可审计脚本，不写入回滚脚本。

9.3 可发布完成标准

  1. DB：前置检查、字段、生成列、索引、幂等、重复阻断、依赖表和两份数据字典完成。
  2. #3500：中英文原始字段、API 字段、唯一校验接口、真实引用链、日志快照和回退完成。
  3. #3501：输入解析、组合筛选、权限、主邀请码、状态分层、明细、批量查询和无副作用完成。
  4. 前端：默认代理、复制、状态、客户类型/ID、展开、禁用图标、空状态和公共列表能力完成。
  5. 测试：PHP 8.2.35/8.1、前端行为、契约、并发、权限、SQL 二次执行和 EXPLAIN 记录齐全。
  6. 未满足任一项不得标记为可发布。

10. v4 对遗漏项的闭环说明

v4 补入了 v3 中缺少或不够具体的内容：validate_name、原始码和 URL 长度、正整数规则、存储过程 SIGNAL、单列 member_id 索引、菜单权限预检查、账户类型业务名称、复制与页面 loading、无下级禁用图标、完整空状态、昵称区客户类型/客户 ID、明细 user_type 和 matched_invite_code 服务端验证。

v4 修正了同事方案中的关键风险：配置/授权/ACCOUNT_TYPE 失败不再全部伪装为“平台停用”；公开原因保持产品定义的两种值；主列表和展开不丢筛选条件；主要邀请码字段、直客 ID 类型、去重数量、历史缺失配置和无写入副作用均有固定契约；gtcuser 不引入本期业务代码和跨服务依赖。

v1、v2、v3、对照评审和同事方案均保留为历史材料；本文件作为后续开发、测试、发布和验收的唯一执行基线。
