禅道1115 需求与3500 3501 v2方案对照评审

2026-11-13 项目：gtc_admin

禅道 1115 与 3500-3501 v2 落地方案对照评审

评审日期：2026-11-09
需求来源：https://chan.fxconfig.com/index.php?m=story&f=view&storyID=1115
对照方案：禅道3500-3501-监管类型中英文及IB邀请码查询-综合落地方案-v2.md
对照基线：gtc_admin、gtc_admin_vue、gtcuser 当前 master
本文只做需求和方案评审，不修改业务代码。

1. 结论

v2 已覆盖数据库迁移顺序、监管类型中英文数据模型、name/name_en 接口验收、真实后端调用链、邀请码只读查询、权限、批量查询和跨项目状态对齐等主要风险，整体方向可继续使用。

但 v2 还不能原样作为最终开发验收文档。禅道 1115 的 PRD 对页面默认值、主列表邀请码字段、复制操作、状态原因、组合筛选和刷新行为有明确要求，v2 有几处遗漏或实现口径超出需求。建议修订后再拆分开发。

2. 必须修正的问题

2.1 P0：停用原因和状态模型超出 PRD

禅道需求只定义两种展示状态：

  • 可邀请；
  • 已停用。

停用原因只要求区分：

  • 平台停用；
  • IB 停用。

v2 在第 3.5、6.3 节把 authorization_invalid、config_invalid 也放进用户可见的 disable_reasons，并把用户端注册校验的所有失败原因直接变成后台状态。这样会出现状态标签和 PRD 不一致的问题，也可能让一个正在展示的有效邀请码因历史开户配置变化显示成未定义原因。

建议最终契约拆成两层：

  1. 页面展示字段只返回 status=available/disabled，前端文案固定映射为“可邀请/已停用”。
  2. disabled_reason 只允许 ib_disabled/platform_disabled，且只有 status=disabled 时返回；启用状态不返回停用原因。
  3. 用户端注册规则的授权、开户配置和 ACCOUNT_TYPE 结果保留为后台内部诊断字段或日志，不进入本期页面验收字段。若产品要求显示这些原因，应先扩展禅道需求和原型。
  4. 当邀请码自身 status=0 时优先返回 ib_disabled；平台总开关关闭时返回 platform_disabled。多开户配置的 code 只有在所有可用配置都被平台停用时才返回 platform_disabled。

这样既满足 PRD 的两种状态，也保留后台与用户端注册规则对齐所需的只读计算。

2.2 P0：主列表没有完整定义“主要邀请码”展示

PRD 明确要求：

  • 主列表默认显示主要邀请码；
  • 查询命中具体邀请码时优先显示命中码；
  • 邀请码可复制；
  • 显示可邀请/已停用状态；
  • 多邀请码显示“查看明细（N个）”；
  • 直客显示客户 ID，并标识为客户 ID 类型的邀请码；
  • 没有可展示邀请码时显示占位。

v2 只有 invite_codes 摘要和 invite_code_count，没有冻结主列表的具体响应字段和主要邀请码选择规则，开发仍需要自行决定。

建议新增明确字段：

字段 规则
primary_invite_code 当前展示的主要邀请码；命中码优先，否则按可用配置、sort_order、创建时间和 ID 稳定排序
primary_invite_status available 或 disabled
primary_invite_disabled_reason 仅 disabled 时返回 ib_disabled/platform_disabled
primary_invite_type agent_invite_code 或 direct_member_id
invite_code_count 去重后的 code 数量，不是明细行数
can_copy_invite_code 当前页面字段始终为 true；复制不改变联系方式权限
has_invite_code_detail invite_code_count > 1

直客没有自有推广码时，primary_invite_code 应展示其客户 ID，primary_invite_type 返回 direct_member_id，并使用“客户 ID”标签；代理显示“IB”标签。

2.3 P0：默认客户类型和重置行为遗漏

PRD 要求首次进入页面默认客户类型为“代理”，点击重置后也恢复为“代理”。v2 的列表口径没有写入默认值，也没有前端重置验收。

应在前后端同时冻结：

  • 初次请求 user_type=agent；
  • 重置清空关键词、邀请码、用户层级、注册时间，并恢复 user_type=agent；
  • 仍允许用户手动切换“全部、代理、直客”；
  • 对现有 URL 或保存筛选状态不做隐式恢复，避免首次打开受旧状态影响。

2.4 P0：展开查询不应丢失当前筛选条件

v2 第 3.3 节写明展开不继承新的关键词，只按 parent_id 查询。PRD 同时要求“用户需同时满足所有查询条件后才展示”，并要求展开/收起不改变当前查询条件。

建议改为：

  • 主列表和展开接口都接收同一份关键词、邀请码、客户类型、层级和注册时间条件；
  • 展开额外增加 parent_id，并只取一层直接下级；
  • 关键词命中邀请码时，主列表命中会员仍可展示；展开后的子项也按同一条件过滤；
  • 展开或收起不能清空、改写或绕过当前筛选；
  • 新搜索、重置、刷新成功后清空 expandedRowKeys 和旧 children，避免旧结果混入新列表。

如果产品确认“展开是结构浏览，不受搜索条件过滤”，应把该例外写回禅道需求；当前 PRD 文本不支持 v2 的隐式忽略。

3. 需要补齐的验收细节

3.1 关键词必须包含客户 ID

PRD 要求关键词支持客户 ID、昵称、邮箱、手机号模糊查询。当前 master 的 Agent::account() 只对 email、nickname、username 做模糊匹配，未直接查询 member.id。

方案应明确：

  • 纯数字且未被邀请码字段解析为链接参数时，邀请码条件按会员 ID 精确命中；
  • 普通 keyword 的数字也要支持会员 ID 查询，避免只匹配 username；
  • keyword 的 ID 分支使用数值比较或经过参数绑定的字符串前缀策略，不拼接原生 SQL；
  • invite_code 与 keyword 同时存在时按 AND 处理，不能把两个输入合并成 OR。

3.2 账户类型必须返回业务名称

PRD 要求账户类型展示业务名称，不展示内部编码。v2 的 JSON 示例仍是 account_type=standard，没有明确 account_type_name 的来源和字段契约。

建议返回：

  • account_type：内部值，仅供后端或调试，不直接展示；
  • account_type_name：从现有账户类型字典或配置映射出的业务名称，缺失显示 --；
  • 前端只展示 account_type_name。

服务器名称、邀请组名称和账户类型名称都应在明细接口中批量映射，不能逐行查询。

3.3 复制邀请码和联系方式脱敏

PRD 明确要求邀请码支持复制，复制不得解除邮箱、手机号脱敏。v2 写了联系方式权限保持不变，但没有把复制按钮、复制成功/失败提示和安全验收列为页面行为。

前端应增加：

  • 主列表主要邀请码复制按钮；
  • 明细每行邀请码复制按钮；
  • Clipboard API 失败时提示用户手工复制；
  • 复制只读取 code，不读取或展示邮箱、手机号；
  • 联系方式继续调用现有 MemberEmailPhone 和脱敏逻辑。

3.4 所属用户必须是直接上级

PRD 要求所属用户只展示直接上级昵称，顶层用户展示空值占位，不展示祖先路径。v2 只保留了 parent_id 查询，没有把这一点列入验收。

列表和展开行都应通过当前记录的 parent_id 批量映射直接上级昵称：

  • parent_id=0 或找不到上级：--；
  • 不读取 member_root_path.path 拼接祖先链；
  • 不能在循环内逐行查询上级昵称。

3.5 刷新、加载和通用列表能力

PRD 要求搜索、重置、刷新期间显示加载状态，避免重复提交；搜索完成后重置展开状态；还要求不影响分页、列设置和全屏能力。v2 只写了空状态和加载失败，没有把以下内容加入验收：

  • 搜索按钮防重复提交；
  • 刷新保留当前全部筛选；
  • 列表分页、列设置、横向滚动和全屏入口保持现有公共组件能力；
  • 旧请求返回不能覆盖新请求；
  • 无结果、邀请码无归属、链接无法解析、请求失败分别显示对应提示；
  • 搜索成功后清空展开行和 children。

4. #3500 仍需优化的契约

4.1 名称字段的展示和编辑语义要写得更硬

PRD 把 name 定义为中文名称、name_en 定义为英文名称；当前后台旧接口的 name 又承担当前语言展示语义。v2 通过 title 表示中文原名、name 表示展示值来兼容旧接口，这个方向可行，但必须在 API 文档和前端 DTO 中明确：

  • 列表/详情 name 是展示字段；
  • title 是编辑回显用的中文原名；
  • name_en 是编辑回显和验收用的英文原名；
  • 保存请求的 name 仍表示中文原名，不能把列表返回的英文 name 当作保存值；
  • 业务关联始终使用 ID。

如果产品坚持 name 必须永远表示中文原名，则应取消 v2 的展示语义，另增 display_name，不能让同一字段在不同接口含义不一致。

4.2 重复错误必须按字段区分

PRD 要求：

  • 中文重复：监管类型名称已存在；
  • 英文重复：英文监管类型名称已存在；
  • 重复时分别定位对应字段，不关闭表单。

v2 第 5 节写的是统一返回“名称已存在”，不足以直接验收。Service 应根据应用层查重和唯一索引名称分别返回错误字段，例如 name 或 name_en；前端保留输入并定位对应控件。

4.3 历史英文为空时的编辑提示

PRD 要求历史记录英文为空时，编辑表单提示管理员补充，保存仍必须通过必填校验。v2 只写了回退和必填，没有写提示文案、字段高亮和接口缺失时的行为。

前端应在 title_en 为空时显示补充提示并将英文字段标记为必填；接口缺失 name_en 时按空值处理，不能把展示 name 复制到英文输入框。

4.4 统一展示需要明确“不同时显示中英文”

需求要求同一位置只展示当前语言对应的一个名称。v2 说使用当前语言展示值，但没有把不同时显示双语写入组件验收。列表、筛选项、KYC 选择器、客户资料和引用弹窗均应只渲染一个 display_name，编辑表单才同时显示两个输入字段。

5. v2 中可以保留的设计

  • 先查 information_schema，再增加 title_en，再做英文重复检查，最后创建唯一索引。
  • 生成列和唯一索引的固定定义，以及阻断式幂等检查。
  • title/title_en 原始值与展示值分离，列表和详情均返回 name/name_en。
  • KycSetting、Pay、Member、SystemOperationLogService、Logs 等真实调用链改造。
  • t_ib_invite_link_config 作为必需依赖，缺少配置时默认启用。
  • 以 t_member_invent_code 为历史邀请码主表，不调用用户端自动补建邀请码。
  • invite_code_count 按去重 code 计算，items 可以按开户配置展开。
  • matched_invite_code 服务端验证、URL 权限和数据权限双重校验。
  • 当前页批量计算 has_children，避免 N+1。
  • gtc_admin 与 gtcuser 使用规则对齐和契约测试，而不是跨项目直接调用 Service。

6. 修订后最低验收清单

#3500

  • 中文字段标签为“监管类型名称（中文）”，英文标签为“监管类型名称（英文）”。
  • 新增/编辑均展示两个输入，历史英文为空时明确提示补充。
  • 中英文空值、长度、唯一性和并发冲突分别定位到对应字段。
  • 列表和详情返回 name、name_en，API 文档说明 name/title/display_name 的含义。
  • 中文环境、英文及其他非中文环境只展示一个当前语言名称，回退规则正确。
  • KYC、客户、支付、监管配置、导出、引用弹窗和日志全部使用同一展示方法。
  • 名称更新不改变 ID、状态和业务关联，日志记录中英文旧值和新值。

#3501

  • 初始 user_type=agent，重置后恢复 agent。
  • invite_code 精确查询支持邀请码、客户 ID、普通 query/hash 邀请链接。
  • keyword 支持客户 ID、昵称、邮箱、手机号，并与其他条件按 AND 组合。
  • 主列表有主要邀请码、状态、复制、多邀请码明细入口和直客 ID 类型。
  • 页面状态只展示可邀请/已停用；停用原因只展示平台停用/IB 停用。
  • 账户类型展示业务名称，服务器/邀请组/缺失字段显示占位。
  • 所属用户只显示直接上级昵称，顶层显示占位。
  • 展开只展示一层直接下级，并继承当前筛选；搜索/重置/刷新清空旧展开状态。
  • 无下级禁用图标、无结果、未找到邀请码、链接解析失败和加载失败均有明确提示。
  • 主列表和明细邀请码都可复制，复制不改变联系方式脱敏。
  • 分页、列设置、全屏和现有公共列表行为不回归。

7. 最终建议

先按本文 P0 项修订 v2，再把 P1 验收细节写入接口文档和前端任务。尤其要在开发前冻结“主要邀请码如何选择”和“配置失效是否属于页面停用原因”两个口径，否则后端状态计算和前端文案仍会出现返工。
