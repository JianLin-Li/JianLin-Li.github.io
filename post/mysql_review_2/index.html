一、MySQL 主从复制是什么？

MySQL Replication 的核心思想非常简单：

主库发生数据变化 → 写入 Binlog → 从库读取 Binlog → 写入 Relay Log → 从库执行这些日志中的事务。

官方定义也是类似的：Source 将数据库变更记录到 Binary Log，Replica 请求并读取这些 Binary Log，然后在自己的数据库上重新执行这些变化。默认情况下复制是异步复制。(MySQL开发者专区)

最基本的架构：

 1                 ┌──────────────────┐
 2                 │     MySQL 主库    │
 3                 │     Source       │
 4                 │                  │
 5                 │  Client          │
 6                 │    │             │
 7                 │    ▼             │
 8                 │  InnoDB          │
 9                 │    │             │
10                 │    ▼             │
11                 │  Binary Log      │
12                 └────────┬─────────┘
13                          │
14                          │ 网络
15                          │ Binlog
16                          ▼
17                 ┌──────────────────┐
18                 │     MySQL 从库    │
19                 │     Replica      │
20                 │                  │
21                 │  I/O Receiver    │
22                 │       │          │
23                 │       ▼          │
24                 │   Relay Log      │
25                 │       │          │
26                 │       ▼          │
27                 │  SQL/Applier     │
28                 │       │          │
29                 │       ▼          │
30                 │     InnoDB       │
31                 └──────────────────┘

二、为什么需要主从复制？

主从复制最常见的用途有：

用途 说明
读写分离 主库负责写，从库负责读
数据备份 从库可以作为备份数据源
高可用 主库故障后可以提升从库
灾备 从库部署在另外服务器/机房
查询扩展 多个从库分担查询压力
报表查询 BI、统计报表从从库读取
数据同步 不同服务器保持数据同步
故障切换 主库故障时切换到 Replica

例如 ERP/MES/WMS 系统中：

 1                 ERP 应用
 2                    │
 3           ┌────────┴────────┐
 4           │                 │
 5          写                 读
 6           │                 │
 7           ▼                 ▼
 8      ┌─────────┐       ┌─────────┐
 9      │ MySQL-01│──────▶│ MySQL-02│
10      │  主库   │ Binlog │  从库   │
11      └─────────┘       └─────────┘
12                             │
13                             ▼
14                         BI/报表

四、Binlog 是什么？

Binlog：

Binary Log，二进制日志。

它记录 MySQL 中发生的、需要复制的数据库变化。

例如：

1INSERT INTO user
2(id, name)
3VALUES
4(1, '张三');

执行之后：

1MySQL
2  │
3  ├── 修改 InnoDB Buffer Pool
4  │
5  ├── 修改数据页
6  │
7  └── 写 Binlog

Binlog 可以理解成：

“主库做过什么事情的操作记录。”

五、Binlog 记录什么？

例如：

1UPDATE employee
2SET salary = 15000
3WHERE id = 100;

如果使用 Row Based Replication：

1Table: employee
2Primary Key: 100
3
4Before:
5salary = 12000
6
7After:
8salary = 15000

而 Statement Based Replication 更接近：

1UPDATE employee
2SET salary = 15000
3WHERE id = 100;

所以 Binlog 有不同的格式。

六、Binlog 三种格式

MySQL 主要有：

1STATEMENT
2ROW
3MIXED

1. STATEMENT

记录 SQL。

例如：

1UPDATE account
2SET money = money - 100
3WHERE id = 1;

Binlog 更接近：

1UPDATE account
2SET money = money - 100
3WHERE id = 1;

优点：

  • 日志量较小

缺点：

  • 某些 SQL 在不同环境执行可能产生不同结果

七、ROW

ROW 记录的是：

数据行发生了什么变化。

例如：

1UPDATE employee
2SET salary = 15000
3WHERE id = 100;

Binlog 实际记录的是行变化。

可以理解为：

1employee
2id = 100
3
4salary:
512000
6  ↓
715000

目前生产环境通常更推荐：

1binlog_format=ROW

八、MIXED

根据具体 SQL 自动选择：

1安全 SQL → STATEMENT
2
3不安全 SQL → ROW

不过在现代 MySQL 生产环境，通常直接使用：

1binlog_format=ROW

会更简单、稳定。

九、Relay Log 是什么？

这是理解主从复制非常关键的一点。

主库：

1Binlog

从库：

1Relay Log

流程：

 1主库
 2
 3Binlog
 4  │
 5  │ 网络
 6  ▼
 7从库
 8
 9Relay Log
10  │
11  ▼
12Applier
13  │
14  ▼
15数据库

官方架构也是：

Source 的 binary log → Replica 本地 relay log → Replica 应用。(MySQL开发者专区)

所以：

Binlog ≠ Relay Log

传统的一主一从：

18          │ Database      │

十二、I/O Thread 到底干什么？

MySQL 8.0 新术语叫：

Receiver Thread

它主要负责：

1连接 Source
2      ↓
3读取 Binlog
4      ↓
5写入 Relay Log

也就是说：

I/O Thread 不负责真正执行 SQL。

这是非常容易搞错的地方。

十三、SQL Thread 到底干什么？

传统复制：

1Relay Log
2    ↓
3SQL Thread
4    ↓
5执行事务

现代多线程复制：

1Relay Log
2    ↓
3Coordinator
4    ↓
5Worker 1
6Worker 2
7Worker 3
8Worker 4
9...

因此：

Coordinator 负责调度，Worker 负责执行。

MySQL 官方对多线程 Replica 的描述也是：设置 replica_parallel_workers > 0 后，会使用指定数量的 Worker Threads，同时存在一个 Coordinator Thread 从 Relay Log 读取事务并调度给 Worker。(MySQL开发者专区)

十四、为什么需要多线程复制？

假设：

主库每秒：

11000 TPS

从库只有一个 SQL Thread。

假设从库执行能力：

1700 TPS

那么：

 1主库：
 2
 31000 TPS
 4  │
 5  ▼
 6Binlog
 7  │
 8  ▼
 9从库
10
11700 TPS

每秒积压：

11000 - 700 = 300

于是：

11秒     300
210秒    3000
31分钟   18000

最终：

1Seconds_Behind_Source
2越来越大

多线程就是为了提高：

Replica Applier 的吞吐能力。

十五、MySQL 多线程复制结构

现代 MySQL：

 1                   Relay Log
 2                       │
 3                       ▼
 4                ┌─────────────┐
 5                │ Coordinator │
 6                └──────┬──────┘
 7                       │
 8          ┌────────────┼────────────┐
 9          ▼            ▼            ▼
10      Worker 1      Worker 2     Worker 3
11          │            │            │
12          ▼            ▼            ▼
13       Txn A          Txn B        Txn C
14          │            │            │
15          └────────────┼────────────┘
16                       ▼
17                    Commit

例如：

1事务：
2
3T1
4T2
5T3
6T4
7T5
8T6

如果事务之间没有依赖：

1Worker1 → T1 → T4
2Worker2 → T2 → T5
3Worker3 → T3 → T6

于是并行执行。

十六、但是不是所有事务都可以并行？

不是。

这是理解 MySQL MTS 最重要的地方。

假设：

1T1:
2UPDATE account SET money = money - 100 WHERE id = 1;
3
4T2:
5UPDATE account SET money = money + 100 WHERE id = 1;

T2 和 T1 都修改：

1account.id = 1

如果：

1T1
2T2

乱序执行：

1T2
2T1

可能导致最终结果与主库不同。

所以：

MySQL 必须识别事务之间的依赖关系。

十七、LOGICAL_CLOCK

现代 MySQL 多线程复制最重要的参数之一：

1replica_parallel_type

主要有：

1DATABASE
2LOGICAL_CLOCK

生产环境通常重点关注：

1replica_parallel_type=LOGICAL_CLOCK

MySQL 官方说明，LOGICAL_CLOCK 根据事务之间的依赖关系决定哪些事务可以并行执行；同时可以配合 Source 端的 binlog_transaction_dependency_tracking 改善并行化判断。(MySQL开发者专区)

十八、LOGICAL_CLOCK 是怎么工作的？

假设主库：

1T1
2T2
3T3
4T4

其中：

1T1 和 T2 无依赖
2T3 依赖 T1
3T4 和 T2 无依赖

那么从库可以：

1Worker1 → T1 → T3
2
3Worker2 → T2 → T4

而不是：

1Worker1 → T1
2Worker1 → T2
3Worker1 → T3
4Worker1 → T4

这样才能提高吞吐。

十九、为什么叫 LOGICAL_CLOCK？

可以把它简单理解成：

MySQL 给事务建立一个“逻辑上的先后关系”。

不是简单地：

1T1 → T2 → T3 → T4

而是识别：

1T1 ───────→ T3
2
3T2 ───────→ T4

那么：

1T1 与 T2

可以并行。

二十、binlog_transaction_dependency_tracking

这是进一步优化多线程复制的重要参数。

Source 端可以配置：

1binlog_transaction_dependency_tracking=WRITESET

或者：

1binlog_transaction_dependency_tracking=COMMIT_ORDER

它决定 MySQL 如何判断事务依赖关系。

常见理解：

1COMMIT_ORDER
2     │
3     ▼
4根据提交顺序推断依赖
5
6WRITESET
7     │
8     ▼
9根据事务实际修改的数据判断依赖

例如：

1T1 修改：
2
3user.id=1
4
5T2 修改：
6
7user.id=2

通过 Write Set 可以知道：

1T1
2 │
3 └── user.id=1
4
5T2
6 │
7 └── user.id=2

二者没有冲突：

1T1 ──┐
2     ├── 可以并行
3T2 ──┘

二十一、GTID 是什么？

GTID：

Global Transaction Identifier

也就是：

全局事务唯一标识符。

例如：

13e11fa47-71ca-11e1-9e33-c80aa9429562:1

可以理解成：

1Server UUID : Transaction Number

例如：

1aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:100

表示：

1服务器 UUID
2+
3事务编号 100

二十二、为什么生产环境强烈建议 GTID？

传统复制：

1Binlog:
2
3mysql-bin.000005
4Position:
5
6123456

切换主库的时候需要考虑：

1File
2Position

比较麻烦。

GTID：

1GTID = 3e11...:100

从库知道：

1我已经执行到：
2
33e11...:100

下一步：

1继续获取：
2
33e11...:101

因此：

GTID 极大简化了主从切换、故障恢复和重新搭建 Replica。

1Transaction

3    ▼

6    ▼
7Binlog

二十四、搭建一个完整的一主一从

下面开始真正搭建。

假设：

1MySQL-01
2IP: 192.168.10.101
3角色：Source
4
5MySQL-02
6IP: 192.168.10.102
7角色：Replica

端口：

13306

二十五、主库配置

修改：

1/etc/my.cnf

或者：

1/etc/mysql/my.cnf

加入：

1[mysqld]
2
3server-id=101
4
5log-bin=mysql-bin
6
7binlog_format=ROW
8
9binlog_expire_logs_seconds=604800

其中：

1server-id=101

非常重要。

主库和从库必须不同。

二十六、从库配置

 1[mysqld]
 2
 3server-id=102
 4
 5log-bin=mysql-bin
 6
 7relay-log=relay-bin
 8
 9binlog_format=ROW
10
11read_only=ON
12
13super_read_only=ON
14
15relay_log_recovery=ON

其中：

1server-id=102

必须和：

1101

不同。

官方要求 Source 和每一个 Replica 使用唯一的 server_id。(MySQL开发者专区)

二十七、为什么从库也建议开启 Binlog？

很多人认为：

从库只负责复制，不需要 Binlog。

其实生产环境经常建议：

1log-bin=mysql-bin

原因包括：

1主从级联
2故障切换
3级联复制
4备库继续作为其他节点 Source

例如：

1          Source
2             │
3             ▼
4         Replica1
5             │
6             ▼
7         Replica2

Replica1 必须能够继续产生 Binlog。

二十八、创建复制账号

在主库：

1CREATE USER 'repl'@'192.168.10.102'
2IDENTIFIED BY 'MyReplication@123';
3
4GRANT REPLICATION REPLICA
5ON *.*
6TO 'repl'@'192.168.10.102';

如果你的 MySQL 版本/环境仍使用旧权限名称，也可能看到：

1GRANT REPLICATION SLAVE
2ON *.*
3TO 'repl'@'192.168.10.102';

MySQL 8.0 新文档已经采用 Source/Replica 新术语，但历史 SQL 中仍经常看到 REPLICATION SLAVE。(MySQL开发者专区)

三十四、配置 Source

在 Replica 执行：

1CHANGE REPLICATION SOURCE TO
2    SOURCE_HOST='192.168.10.101',
3    SOURCE_PORT=3306,
4    SOURCE_USER='repl',
5    SOURCE_PASSWORD='MyReplication@123',
6    SOURCE_AUTO_POSITION=1;

然后：

1START REPLICA;

官方文档中，GTID 模式下可以使用：

1SOURCE_AUTO_POSITION = 1

而不是手工指定：

1SOURCE_LOG_FILE
2SOURCE_LOG_POS

(MySQL开发者专区)

三十五、查看复制状态

执行：

1SHOW REPLICA STATUS\G

2
3Replica_SQL_Running: Yes

三十六、MySQL 8.0.26 前后的字段变化

这个在实际工作中非常容易遇到。

以前：

1SHOW SLAVE STATUS

以及：

1Slave_IO_Running
2Slave_SQL_Running

新版本：

1SHOW REPLICA STATUS

以及：

1Replica_IO_Running
2Replica_SQL_Running

同样：

旧：

1CHANGE MASTER TO

1CHANGE REPLICATION SOURCE TO

官方从 MySQL 8.0.23 开始推荐新的 Source/Replica 语法；旧语法是兼容历史环境的重要知识点。(MySQL开发者专区)

四十二、replica_parallel_type

推荐：

1replica_parallel_type=LOGICAL_CLOCK

表示：

根据事务依赖关系进行并行执行。

另外：

1DATABASE

是按照数据库进行并行。

例如：

1DB1 → Worker1
2DB2 → Worker2
3DB3 → Worker3

这种模式限制比较明显。

如果你的业务所有数据都在：

1erp

数据库：

1erp

那么：

1DATABASE

几乎没有并行空间。

所以现代环境通常更关注：

1LOGICAL_CLOCK

四十三、replica_preserve_commit_order

建议：

1replica_preserve_commit_order=ON

为什么？

假设主库：

1T1
2T2
3T3

从库：

1Worker1 → T1
2Worker2 → T2
3Worker3 → T3

执行速度：

1T3 最快
2T2 第二
3T1 最慢

如果允许：

2T2 commit
3T1 commit

就可能和 Source 的提交顺序不同。

所以：

1replica_preserve_commit_order=ON

确保最终提交顺序与 Source 保持一致。

MySQL 官方也说明，该设置用于保证并行事务最终提交顺序与原始事务顺序一致。(MySQL开发者专区)

五十一、Write Set 的意义

假设：

1T1:

1T1 ────── Worker1
2          │
3T2 ────── Worker2

则：

1T1 → user.id=1

存在冲突：

六十六、MTS Gap 是什么？

多线程执行时：

1T1
2T2
3T3
4T4

可能出现：

1Worker1 → T1 ✓
2
3Worker2 → T2 ✓
4
5Worker3 → T3 ERROR
6
7Worker4 → T4 ✓

那么：

1T1 ✓
2T2 ✓
3T3 ✗
4T4 ✓

出现：

MySQL 官方特别指出，多线程 Replica 在 Coordinator 停止、Applier Worker 出错或 mysqld 异常关闭等情况下可能出现事务执行间隙；这时数据库状态可能暂时处于 Source 从未出现过的中间状态。(MySQL开发者专区)

六十七、MTS Gap 如何处理？

可以使用：

1START REPLICA UNTIL SQL_AFTER_MTS_GAPS;

这个机制的意义：

让多线程 Replica 继续执行，直到事务之间的 Gap 被消除。

官方文档也专门提供了 SQL_AFTER_MTS_GAPS 用于处理多线程复制中的 Gap。(MySQL开发者专区)

八十五、主从复制性能优化思路

不要一上来就：

1replica_parallel_workers=64

正确思路应该是：

 1发现延迟
 2    ↓
 3判断 IO 慢还是 Apply 慢
 4    ↓
 5如果 Apply 慢
 6    ↓
 7检查 CPU / Disk / Lock
 8    ↓
 9检查单线程还是多线程
10    ↓
11配置 MTS
12    ↓
13检查事务依赖
14    ↓
15优化 SQL / 索引

八十六、复制性能优化的几个层次

可以按照下面的层次理解：

 1第一层：
 2网络
 3
 4第二层：
 5Binlog IO
 6
 7第三层：
 8Relay Log IO

所以：

复制延迟不一定是“主从复制配置”的问题。

八十七、一个非常典型的生产问题

例如：

1Source：
2
3TPS = 5000
4
5Replica：
6
7TPS = 3000

观察：

1Relay Log
2越来越大

此时：

1I/O Thread：正常
2SQL/Applier：慢

那么：

1网络没问题
2Binlog没问题

重点应该：

1MTS
2 ↓
3Worker
4 ↓
5锁
6 ↓
7IO
8 ↓
9CPU

而不是：

1重新配置 Source

八十八、事务过大也会导致复制延迟

例如：

1BEGIN;
2
3INSERT 100万条数据;
4
5COMMIT;

这个事务：

1T1

非常大。

即使：

1replica_parallel_workers=32

也未必能够：

1T1拆成32个Worker

因为：

一个事务内部通常不能简单地被多个 Applier Worker 拆开执行。

所以：

1大事务

往往是复制延迟的重要来源。

八十九、生产环境特别注意“大事务”

例如：

1UPDATE 500万条

不要：

1UPDATE xxx
2SET ...
3WHERE ...;

一次提交。

可以考虑按照业务允许的方式：

110000
210000
310000
4...

拆分批次。

当然，是否能拆分必须考虑：

1业务原子性
2锁
3数据一致性

不能为了复制性能随便拆事务。

九十、主从复制和备份的关系

主从：

1数据复制

备份：

1数据恢复

二者不是一回事。

即使：

1Source
2 ↓
3Replica

正常。

如果误执行：

1DROP DATABASE erp;

那么：

1Source DROP
2   ↓
3Binlog
4   ↓
5Replica
6   ↓
7DROP

主从会一起删。

所以：

Replica 不能替代真正的备份。
