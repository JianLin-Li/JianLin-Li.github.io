gtc敏感信息加密方案

2026-08-17 · 15 分钟阅读 · gtc  ·
分享到:

某个表敏感字段加密 推荐采用“应用层可逆加密 + HMAC-SHA256 盲索引 + 统一会员敏感字段读写服务 + 影子列分阶段迁移”

第一轮方案提词

现在有个新需求，下面是我归纳的当前的一些现状和已知或者已决定的事项

  1. 新需求要求把数据库表t_member中敏感的字段phone和identity进行加密处理，我刚看了下这两个字段在数据字典中的定义分别是phone varchar(30) CHARACTER SET utf8 NOT NULL DEFAULT '',identity varchar(50) CHARACTER SET utf8 DEFAULT NULL COMMENT '身份ID'，需求要求加密后，以前的各个业务不能受影响，比如现有 hideListEmailPhone()、详情页手机号脱敏和 KYC 列表脱敏可以继续保留，但必须保证它们拿到的是解密后的值，而不是密文，但是phone和identity加密后不再保留前缀/包含搜索，这个需要把老的逻辑改造。

  2. phone按照数据库最终保存的完整手机号，避免同一个手机号因为区号拼接方式不同导致查不到，identity当前允许字母和数字，且数据库比较可能受大小写不敏感影，

  3. t_member表由于现有的字段已经非常的多了，加密敏感字段方案中需要考虑把新增的影子列或者过渡字段放入t_member_other表中，

  4. phone和identity采用可逆加密，加密算法采用最优的方案

  5. phone 和 identity 分别使用独立的密钥，独立的盲索引 HMAC 密钥

  6. 密钥加入项目的.env文件中，后端统一密钥格式、编码方式和版本号，但是需要设计密钥轮换和旧版本解密策略，

  7. HMAC-SHA256 盲索引 phone和identity的密钥分别独立 生成的hash 用于精准查询

  8. 需要统一一个加密/索引适配层服务，这个就写入crm后台代码库中，如果其他代码库项目有需要加解密则需要在crm后台项目中设计调用接口的形式来加解密敏感字段，统一负责包括和不限于以下功能： 8.1 手机号、证件号规范化； 8.2 加密和解密； 8.3 HMAC 索引生成； 8.4 查询条件生成； 8.5 批量解密； 8.6 密钥轮换； 8.7 密文损坏或解密失败处理。 8.8 供其他项目加解密phone和identity的接口 8.9 按主键游标批量回填历史数据

  9. 需要考虑日志、缓存已有的业务逻辑对于phone和identity加密后的处理

  10. 外部接口如果涉及phone和identity字段，则使用解密后的

    以上几点是我提出来的，有可能并不全面，基于这个需求，帮我分析以及影响范围进行深度评估，比如改动的代码库都有哪些，然后综合考虑出一套改动最小、影响最小的最优方案，需要慎重考虑以前的老业务逻辑，方案的交付步骤，以及每个交付步骤需要的详细流程，不要遗漏接口兼容和回归验证。

不要做任何改动，只出方案，我需要核对你出的方案，再继续做决定

‼️️‼️第一轮具体方案

一、结论

这不是单纯修改 t_member.phone、t_member.identity 两列，而是一次跨两个后端、一个前端、多个数据副本和外部系统的迁移。

推荐采用：

先确认威胁模型并补齐数据库/备份保护，再建设 CRM 统一敏感字段适配层，先迁移所有读写入口，最后启用 t_member 密文存储和 HMAC 精确查询。

不建议直接把明文替换为密文后再逐个修业务，因为当前大量代码使用：

  • phone、identity 直接 where
  • LIKE '%phone%'
  • select m.phone
  • $member->phone
  • 日志、缓存、KYC JSON、短信记录和 MT 外发
  • 前端默认假设后端返回的是脱敏明文

二、已确认的影响范围

t_member_other 具有唯一的 member_id，可放置盲索引和迁移元数据：数据字典.sql

密文长度会超过现有字段长度，因此必须先扩大字段，建议使用 ASCII 编码的 varchar(512) 或等效二进制字段。不能继续使用 varchar(30)/varchar(50)。

需要重点处理的明文副本包括：

  • t_kyc_user_content.kyc_content：KYC JSON 中包含手机号、证件号：数据字典.sql
  • t_logger.postdata：数据字典.sql
  • t_member_detail_log.before/after：数据字典.sql
  • t_member_idcard.idcardnum：数据字典.sql
  • t_activity_user.identity：数据字典.sql
  • t_member_reg_apply.phone：数据字典.sql
  • t_member_request_log.request_body：数据字典.sql

  • KYC 审核手机号和证件号重复校验：Kyc.php

  • 全局搜索、代理、跟单、提现、报表、Salesforce、风险同步等还有多处直接 LIKE 或 field(...phone...)。

  • 验证码缓存使用 md5(phone)：TMemberService.php
  • 身份证绑定限制按 identity 查询：TMemberService.php
  • 请求日志保存整个请求体：TMemberService.php

因此，gtcuser 不能继续直接查询或更新加密后的 t_member.phone、identity。需要增加 CRM 内部敏感字段客户端，至少替换 Repository 的手机号/证件号查询和写入路径。

  • 详情仍返回现有格式

  • 前端绝不能收到密文
  • 手机号搜索从“包含搜索”改成“完整号码精确搜索”
  • 清理前端 console.log(record.phone) 等敏感日志

三、推荐加密方案

1. 算法

PHP 8.0 优先使用 libsodium：

  • XChaCha20-Poly1305-IETF
  • 每次加密随机 nonce
  • 自带认证标签，可检测篡改
  • 密文格式建议：
1enc:v1:<key_id>:<nonce_base64url>:<ciphertext_base64url>

AAD 绑定：

1crm-member|field|member_id|normalize_version

这样可以防止把某个会员的密文复制到另一个会员或另一个字段。

如果生产有强制 FIPS 要求，再评估 AES-256-GCM；不能使用没有完整认证保护的 AES-CBC，也不应使用 RSA 作为数据库字段加密算法。

2. 密钥

手机号和证件号分别使用四组完全独立的密钥：

  • phone encryption key
  • phone HMAC key
  • identity encryption key
  • identity HMAC key

密钥统一使用：

  • 原始 32 字节随机值
  • Base64url 编码
  • 明确的 key_id 和版本号
  • current/previous key ring

新数据只使用 current key；读取时根据密文中的 key_id 使用旧密钥解密；轮换完成后再批量重加密。

密钥只存在 CRM 的部署环境或密钥管理系统中。.env 只能作为注入方式，不能放入数据库、前端或仓库。当前几个项目存在被 Git 跟踪的环境样例文件，正式实施前应先做 secret scan、清理样例和必要的密钥轮换。

3. 规范化

手机号不能再简单依赖 $d_code . $phone。

统一规则：

  • 使用 libphonenumber 解析
  • 输入可能是国际格式，也可能是区号加本地号码
  • 输出统一为完整 E.164 格式，例如 +<country><national_number>
  • 区号缺失、国家不明确、号码不合法时拒绝自动写入，进入人工处理
  • d_code 可以继续保留用于界面和外部供应商，但不再作为手机号唯一身份依据

gtcuser 当前已有 giggsey/libphonenumber-for-php 依赖：composer.lock

证件号统一：

  • trim
  • 只允许 ASCII 字母和数字
  • strtoupper
  • 空值继续保持 NULL 或空字符串语义
  • 重复判断与 HMAC 使用同一规范化结果
  • 迁移时必须统计大小写冲突，不能因为数据库原有大小写不敏感而静默合并账号

4. t_member_other 影子字段

建议增加：

  • phone_hmac
  • identity_hmac
  • phone_hmac_key_version
  • identity_hmac_key_version
  • phone_migration_status
  • identity_migration_status
  • phone_last_error_code
  • identity_last_error_code
  • phone_migrated_at
  • identity_migrated_at

盲索引使用 HMAC-SHA256，建议存 BINARY(32) 并建立普通索引，不建立唯一索引，因为现有业务允许一个手机号或证件号绑定多个账号。

查询时由服务计算 current/previous 版本的 HMAC：

1WHERE member_other.phone_hmac IN (?, ?)

所有查询参数必须绑定，不能拼接 SQL。

如果会员数量很大、member_other 当前行数很少，需先评估为所有会员补建副表记录带来的空间和写入压力。若不可接受，再单独建立紧凑的 t_member_sensitive_index 表，但默认仍可先使用 t_member_other，符合现有架构。

四、统一适配层职责

CRM 中新增统一服务，建议放在 app/service 下，并由控制器、Repository、KYC、短信、MT 和外部接口统一调用。

至少提供：

  • normalizePhone()
  • normalizeIdentity()
  • encryptField()
  • decryptField()
  • buildPhoneHmac()
  • buildIdentityHmac()
  • buildExactMemberQuery()
  • batchDecryptMembers()
  • writeMemberSensitiveFields()
  • rotateKeys()
  • backfillByMemberIdCursor()
  • handleDecryptFailure()

读取策略：

  • 密文格式合法：解密并返回明文
  • 旧版密文：使用旧 key 解密
  • 迁移期间的旧明文：兼容读取，并补写 HMAC
  • 密文损坏、未知版本、认证失败：不返回密文，记录错误码和会员 ID，列表显示脱敏/异常状态，关键业务返回通用错误

不要通过全局 ORM accessor 对每一行做网络解密，否则会造成 N+1 请求和 Hyperf 长驻进程中的性能问题。应在 Repository 或列表服务中批量读取和批量解密。

五、内部接口设计

CRM 是唯一持有敏感字段密钥的系统。

建议新增仅内网可访问的接口：

1POST /internal/sensitive/member/resolve

用途：手机号/证件号精确查询，只返回 member_id，不返回密文。

1POST /internal/sensitive/member/reveal

用途：按会员 ID、字段和业务用途返回明文，必须经过服务权限和审计。

1POST /internal/sensitive/member/batch-reveal

用途：列表页、批量同步、报表等批量解密，限制批次大小。

1POST /internal/sensitive/member/write

用途：注册、修改手机号、修改证件号，由 CRM 完成规范化、加密、HMAC、事务更新。

接口要求：

  • 独立服务账号，不复用普通用户 token
  • HTTPS，最好 mTLS
  • 时间戳、请求 ID、签名和防重放
  • IP 白名单、调用方 scope、超时、熔断、重试
  • 每次 reveal 记录调用方、会员 ID、字段、用途、操作人和请求 ID
  • CRM 不可用时，敏感业务 fail closed，不能退回直接查密文
  • 旧客户端仍提交原始手机号/证件号，由服务端兼容处理

六、详细交付顺序

阶段 0：决策和数据盘点

先确认：

  • “数据库被盗”是数据库文件/备份泄露，还是数据库账号逻辑导出
  • 是否覆盖 SelectDB、ETL、CDC、日志、缓存、OSS、报表和外部供应商
  • 生产是否允许 CRM 作为内部解密服务
  • 会员总量、空手机号、非法号码、国家缺失、重复值、大小写冲突
  • member_other 缺失行数量
  • 现有外部项目和 SQL 账号是否能禁止直接读敏感列

如果只是防数据库文件、快照和备份泄露，TDE、磁盘加密、加密备份、KMS 分离和 DB 权限收紧是低改动基础措施。字段级加密不能防止已取得应用主机、应用密钥或高权限 DB 账号的人读取明文。

阶段 1：冻结协议和测试向量

先确定：

  • 密文 envelope 格式
  • key ID 和版本规则
  • Base64url 编码
  • 手机号、证件号规范化版本
  • HMAC 输入域分离格式
  • 错误码
  • 内部 API 请求和返回 JSON
  • current/previous 轮换规则

使用测试密钥建立固定测试向量，禁止使用生产密钥做开发测试。

阶段 2：只加数据库结构

先执行可回滚的加法变更：

  • 扩大 t_member.phone、identity
  • 增加 t_member_other 盲索引和迁移字段
  • 增加普通索引
  • 更新数据字典
  • 检查变更锁表时间和复制延迟

此阶段不切换读写，不改变业务含义。

阶段 3：先上线适配层，保持明文模式

适配层先支持：

  • 明文读取
  • 明文规范化
  • HMAC 补写
  • 明文/密文双读
  • 统一错误处理
  • 统一日志脱敏

先把 CRM、gtcuser 的所有敏感读写入口切到适配层，但数据库仍保存明文。这样可以先验证业务调用链，不把加密风险和代码改造风险叠加。

阶段 4：迁移查询和展示

必须改造：

  • 所有手机号/证件号精确查询为 HMAC 查询
  • 所有 LIKE '%phone%'、LOWER(phone) 删除
  • 列表先分页取会员 ID，再批量解密，再调用 hideListEmailPhone()
  • 详情和 lookmemberinfo 按权限解密
  • BaseController 默认不加载敏感字段
  • gtcuser Repository 特殊处理 phone/identity
  • 不能让任何接口返回密文

手机号模糊搜索应改成完整手机号精确搜索；证件号也只支持完整精确搜索。前缀和包含搜索在随机密文 + HMAC 方案下无法继续支持。

阶段 5：迁移写入

所有新增和修改入口统一调用写入服务：

  • 后台新增会员
  • 后台修改会员
  • saveImportInfo
  • saveNew
  • API 注册
  • API 换绑手机号
  • KYC 审核和第三方 KYC 回调
  • MT 同步回写
  • 修复脚本和后台命令

写入必须在一个事务中完成：

  1. 锁定会员行
  2. 规范化手机号/证件号
  3. 计算 HMAC
  4. 生成随机密文
  5. 更新 t_member
  6. 更新 t_member_other
  7. 记录不含明文的审计信息

重复绑定检查需要按 HMAC 查询，并对同一个 HMAC 使用分布式锁或数据库锁，避免并发绕过绑定上限。

阶段 6：日志、缓存和副本治理

必须同步处理：

  • LogOperationMiddleware 增加 phone、identity 脱敏
  • member_detail_log.before/after 不再保存原值
  • member_request_log.request_body 删除或掩码敏感字段
  • t_logger.postdata 不再记录完整值
  • Redis 验证码 key 改用 HMAC 或会员 ID，不再使用 md5(phone)
  • 短信日志改为会员 ID、HMAC 或掩码手机号
  • SMS abuse 查询改为会员 ID/HMAC
  • 清理 loginfo、调试日志和前端 console 中的手机号
  • 新写入的 KYC JSON、活动、MT 申请记录禁止继续保存明文副本
  • 对历史 KYC JSON、短信日志、申请记录明确选择加密、掩码、删除或保留在 TDE 保护范围内

阶段 7：历史数据回填

按会员主键游标执行，不使用深分页：

1id > last_id
2ORDER BY id ASC
3LIMIT batch_size

每批流程：

  1. 读取 id、phone、identity、d_code、country
  2. 判断明文、旧密文、空值或损坏值
  3. 规范化
  4. 生成 HMAC
  5. 加密
  6. 短事务更新主表和副表
  7. 保存 checkpoint
  8. 记录成功、跳过、失败、人工处理数量

失败记录只保存错误类型和会员 ID，不保存原始敏感值。迁移必须支持断点续跑和幂等。

阶段 8：灰度和切换

推荐顺序：

  1. 测试库回填
  2. 生产影子校验
  3. 单品牌/小比例会员灰度
  4. 新写入全部加密

阶段二：冻结加密、规范化和接口契约

2.1 固定加密协议

新增统一适配层，协议版本固定为 v1：

  • 算法：PHP 8.0 可用的 libsodium XChaCha20-Poly1305-IETF。
  • 每次加密生成随机 nonce。
  • 认证标签由 AEAD 生成。
  • AAD 至少绑定：
    • 字段名：phone 或 identity。
    • member_id。
    • 规范化版本。
  • 密文格式：
1enc:v1:<key_id>:<nonce_base64url>:<ciphertext_base64url>

密文使用 ASCII 字符集和二进制安全比较，不依赖数据库大小写排序规则。

2.2 固定规范化规则

手机号：

  1. 去除首尾空格。
  2. 使用统一的电话号码解析库。
  3. 转换为完整 E.164 格式，例如 +8613800138000。
  4. 国家码缺失或有歧义时返回明确错误，不自动补国家码。
  5. HMAC 只对规范化后的完整号码计算。

identity：

  1. trim。
  2. 转换为大写。
  3. 只允许 ASCII 字母和数字。
  4. 空值保持 NULL，不把 NULL 转为空字符串。
  5. HMAC 只对大写后的规范化值计算。

因此，数据库大小写不敏感不会影响 identity 的精确匹配，查询统一使用 HMAC 结果。

2.3 固定盲索引规则

phone 和 identity 使用不同的 HMAC-SHA256 密钥。

建议存储：

1v1:<64位小写十六进制摘要>

字段建议：

  • phone_hmac_index varchar(80) CHARACTER SET ascii COLLATE ascii_bin
  • identity_hmac_index varchar(80) CHARACTER SET ascii COLLATE ascii_bin

分别建立普通索引，不设置唯一约束，因为一个手机号或证件号可能绑定多个会员账号。

密钥轮换期间，查询层需要根据当前版本和允许读取的旧版本生成多个候选 HMAC，使用 IN (...) 查询，完成回填后再停用旧版本。

2.4 固定内部 API 契约

CRM 作为唯一密钥持有方。其他后端不得持有加密密钥，也不能直接解密数据库字段。

建议新增内部接口：

接口 用途
POST /internal/v1/member-sensitive/query 根据 phone 或 identity 精确查询会员 ID
GET /internal/v1/member-sensitive/{memberId} 按权限获取已解密值或脱敏值
PUT /internal/v1/member-sensitive/{memberId} 规范化、加密、写入 t_member 和 t_member_other
POST /internal/v1/member-sensitive/decrypt-batch 批量解密，限制批量大小和调用权限
POST /internal/v1/member-sensitive/validate 校验和规范化输入，不返回密钥
POST /internal/v1/member-sensitive/rotate 受控密钥轮换和重加密任务

接口要求：

  • mTLS 或服务间签名认证。
  • 权限分为 query、decrypt、write、batch、rotate。
  • 每次请求带调用方、用途、幂等号和 trace ID。
  • 响应不返回密钥。
  • 失败不能返回原始密文作为可展示值。
  • 不记录请求中的 phone、identity 明文。
  • 批量解密接口必须限制会员数量、字段数量和调用频率。

    • t_logger、短信日志、请求日志、活动记录、KYC JSON 和证件审核记录都要单独盘点。

  4. 备份和导出：

    • 迁移前备份必须加密并限制访问。
    • 导出、临时 CSV、人工下载文件纳入清理和留存期限。
    • 生产备份不能因为回滚需要而长期保留明文副本。

9.1 增加运行开关

9.2 灰度顺序

  1. 数据库兼容结构阶段

    • 只增加字段、索引和状态列。
    • 业务仍使用旧明文。
    • 验证 DDL、复制和索引。

  2. 双读阶段

    • 读取时识别明文和 enc:v1。
    • 新代码可以解密密文。
    • 搜索同时尝试 HMAC 和旧数据精确查询。
    • 模糊搜索暂时只对未迁移旧数据保留。

  3. 加密写入阶段

    • 所有新建、修改、KYC、换绑数据直接写密文和 HMAC。
    • 不再产生新的明文。
    • CRM 负责 t_member 与 t_member_other 的事务性写入。
    • gtcuser 不能直接更新敏感列。

  4. 历史回填阶段

    • 使用 CRM CLI，例如 app/command/MemberSensitiveBackfill.php。
    • 查询方式：
1WHERE id > :last_id
2ORDER BY id ASC
3LIMIT :batch_size
  • 每批独立事务。
  • 已是当前版本密文的跳过。
  • 明文记录先规范化，再加密、生成 HMAC、更新状态。
  • 规范化失败或数据异常的记录进入错误队列，不覆盖原值。
  • 使用 WHERE id = ? AND phone = :old_value 或行锁处理并发更新。
  • checkpoint 持久化，支持 --from-id、--to-id、--batch、失败重试和断点续跑。
  • 不能使用深分页，也不能执行全表无条件一次性 UPDATE。
  1. 全量切换阶段
    • 验证所有可写入口均已加密。
    • 验证明文行数为零或全部进入已审批异常清单。
    • 切换为 hmac_only 精确查询。
    • 禁止手机号和 identity 前缀、包含搜索。
    • 保留旧版本解密能力，但不再保留旧明文查询代码。

9.3 回填验收

必须完成：

  • t_member 行数与回填成功数一致。
  • phone 非空记录都有 HMAC。
  • identity 非 NULL 记录都有 HMAC。
  • HMAC 索引无异常重复丢失。
  • 随机抽样解密值与迁移前基线一致或符合已批准的规范化结果。
  • 迁移前后精确查询结果集合一致。
  • 解密失败记录均有错误码和人工处理状态。
  • 回填期间无明文新写入。

阶段十：密钥轮换

轮换不是一次性替换 .env，按以下流程执行：

  1. 生成新的 phone 加密密钥和 HMAC 密钥。
  2. 旧密钥进入 previous key ring。
  3. 新写入使用新版本。
  4. 读取同时支持 current 和 previous。
  5. 使用主键游标重加密旧版本密文并重算 HMAC。
  6. 验证旧版本记录数归零。
  7. 等待备份、缓存和消息队列保留期结束。
  8. 再撤销旧密钥。
  9. 保留轮换审计记录，但不能记录密钥内容。

phone 和 identity 的密钥必须始终独立轮换，不能共用一把密钥。

阶段十一：回滚和停止条件

11.1 回滚原则

  • 双读阶段可以通过开关切回旧读路径。

  • 如需恢复旧系统，必须：
    1. 停止加密写入。
    2. 使用受控备份或 CRM 解密脚本恢复明文。
    3. 验证恢复结果。
    4. 再切换旧版本程序。
  • 恢复出来的明文只能存在于受控回滚窗口，不能作为长期状态。

出现以下任一情况，暂停灰度或回填：

  • 解密失败率超过批准阈值。
  • 迁移前后精确查询结果不一致。
  • 发现新的明文写入来源。
  • 会员详情、KYC、登录或注册出现敏感字段错误。
  • 数据库锁等待、复制延迟或接口延迟超过基线。
  • 内部接口出现未授权调用或明文日志。
  • HMAC 计算结果与测试向量不一致。
  • 回填错误队列持续增长且无法自动恢复。

下面是根据你新增决定重新收敛后的执行方案。当前仍然是方案设计，未修改代码、数据库、配置或 .env。

先明确一个关键结论：

  • t_member.phone、t_member.identity 的字段结构暂不修改，不扩容、不加索引、不删除。
  • 新增加密值和盲索引全部放到 t_member_other。
  • 最终切换完成后，t_member.phone 保留字段但不再保存业务手机号，按现有字段约束保存为空字符串；t_member.identity 保存为 NULL。

  • 其他表中名为 phone、identity 的字段不迁移、不加密、不改查询逻辑。

一、最终数据结构

1. t_member 保持原结构

不执行以下操作：

  • 不修改 phone varchar(30)。
  • 不修改 identity varchar(50)。
  • 不新增索引。
  • 不删除字段。
  • 不把密文写回 t_member。

最终状态：

1t_member.phone     = ''
2t_member.identity  = NULL

这意味着所有直接查询 t_member.phone 或 t_member.identity 的旧代码必须在最终切换前清理完毕。

2. t_member_other 只增加 5 个字段

建议字段如下：

字段 建议类型 含义
phone_ciphertext varchar(255) CHARACTER SET ascii COLLATE ascii_bin NULL 手机号加密值，保存完整规范化手机号
identity_ciphertext varchar(255) CHARACTER SET ascii COLLATE ascii_bin NULL 证件号加密值，保存去首尾空格后的原始大小写形式
phone_hmac_index varchar(70) CHARACTER SET ascii COLLATE ascii_bin NULL 手机号精确查询盲索引
identity_hmac_index varchar(70) CHARACTER SET ascii COLLATE ascii_bin NULL 证件号精确查询盲索引
sensitive_state tinyint unsigned NOT NULL DEFAULT 0 本行敏感字段迁移状态

sensitive_state 建议定义：

10 = 未处理或 member_other 行缺失
21 = phone、identity 均已处理，空值也视为已确认
32 = 数据异常，需要人工处理
43 = 解密或密文校验失败

不增加单独的版本字段，因为：

  • 密文自身携带 v1、v2 等版本。
  • HMAC 索引自身携带版本前缀。
  • 失败详情写入 CRM 任务日志和监控，不再增加错误描述字段。

索引：

1KEY idx_phone_hmac_index (phone_hmac_index)
2KEY idx_identity_hmac_index (identity_hmac_index)

两个索引都不能设置唯一约束，因为同一个手机号或证件号允许绑定多个会员。

二、加密协议和测试向量

1. 加密算法

PHP 8.0 已内置 libsodium，不增加 Composer 依赖，使用：

1sodium_crypto_aead_xchacha20poly1305_ietf_encrypt()
2sodium_crypto_aead_xchacha20poly1305_ietf_decrypt()

选择：

  • XChaCha20-Poly1305-IETF。
  • 随机 nonce。
  • 自带认证标签。
  • 支持 AAD。
  • PHP 8.0 可直接使用。
  • 不自行实现 AES、随机数或 MAC 拼接。

2. 密文格式

1enc:v1:<key_id>:<nonce_base64url>:<ciphertext_base64url>

例如：

1enc:v1:phone-2026-01:<nonce>:<ciphertext>

key_id 只表示版本和用途，不包含密钥内容。

3. AAD 格式

固定为：

1crm-member-sensitive|member_id=<id>|field=<phone|identity>|normalizer=v1

作用：

  • 防止手机号密文复制到 identity 字段。
  • 防止一个会员的密文复制到另一个会员。
  • 防止规范化版本变更后误解密。
  • 防止密文被跨业务复用。

4. 规范化和加密值的区别

为减少历史业务显示变化：

手机号

  • 加密值：保存完整规范化手机号。
  • HMAC：对完整规范化手机号生成。
  • API 兼容输出：根据原有接口约定拆分成 phone 和 d_code。
  • 内部服务同时保留 phone_e164，供短信、登录和查询使用。

identity

  • 加密值：保存 trim 后的原始大小写形式，避免页面显示被强制改成大写。
  • HMAC：对 strtoupper(trim(identity)) 生成。
  • 因此 abc123 和 ABC123 查询结果一致，但详情页可以继续展示原始大小写。

5. 测试向量

在 CRM 中新增固定文档：

1docs/security/member-sensitive-crypto-v1.md

测试向量必须包含：

  • 固定测试 key。
  • 固定 nonce。
  • 固定 member_id。
  • 固定字段名。
  • 固定规范化版本。
  • 明文。
  • AAD。
  • 预期密文。
  • 预期 HMAC。
  • 篡改密文后的失败结果。
  • 使用 phone 密钥解密 identity 的失败结果。
  • v1 密文使用 v2 密钥解密的失败结果。

生产环境 nonce 必须随机；固定 nonce 只能用于测试向量。

三、手机号规范化方案

现有代码存在两种手机号处理方式：

  • CRM 管理端保存时会把 d_code . phone 写入 t_member.phone。
  • 详情页又会根据 d_code 把区号从 phone 中剥离。
  • gtcuser 登录和验证码逻辑同时依赖 phone、d_code。
  • CRM 短信服务还存在针对 +86、+ 的特殊处理。

因此不能直接把所有历史值简单执行 +、去空格或纯数字化。

规范化输入

适配层统一接收：

1raw_phone
2d_code
3country
4source
5member_id

处理顺序：

  1. 去除首尾空格。
  2. 如果 raw_phone 已经以完整国际区号开头，禁止再次拼接 d_code。
  3. 如果 d_code 存在，则清理 + 后与本地号码组合。
  4. 如果 d_code 缺失，则尝试从明确的 country 映射国家区号。
  5. 国家或区号无法唯一确定时，不自动猜测。
  6. 使用现有项目已有的电话号码库进行解析和有效性校验。
  7. 通过校验后转换为 E.164。
  8. 只对 E.164 结果生成 HMAC。

分类处理

情况 处理
phone='' 且无区号 不生成 phone 密文和 HMAC，标记为已确认空值
合法完整国际号码 正常规范化、加密、生成 HMAC
本地号码且 d_code 明确 拼接后验证，成功后正常处理
d_code 缺失但国家明确且唯一 允许自动补全，但生成审计记录
国家和区号都缺失 不自动猜测，标记人工处理
字符非法、长度非法、解析失败 不迁移该条，保留 t_member 明文，标记异常
同一号码不同拼接方式 规范化后生成同一个 HMAC
同一号码绑定多个账号 全部保留，不使用唯一索引

特别注意：无法确认国家或区号的号码不能强行转换，否则可能把两个不同国家的号码转换成错误的同一个号码。

四、identity 规范化方案

当前管理端已有：

1^[a-zA-Z0-9]{1,50}$

执行规则：

  1. trim。
  2. 保留字母和数字限制。
  3. 加密前保存原始大小写形式。
  4. HMAC 前统一 strtoupper。
  5. 历史数据如果包含非字母数字字符，标记异常，不自动删除或截断。
  6. 大小写冲突不视为数据损坏，而视为同一个匹配值。
  7. 继续执行现有 ID_OF_USER_NUM 绑定数量限制。

例如：

1abc001
2ABC001

两条数据的 HMAC 相同，但可以继续绑定多个会员；是否允许新增绑定，仍由原有账号绑定上限决定。

  • 所有 CRM 敏感读写入口已迁移。
  • gtcuser 不再直接访问 t_member 敏感字段。

  • Vue 接口回归通过。
  • 登录、注册、KYC、短信、MT 回归通过。

  1. 停止旧 t_member 敏感字段写入。
  2. 将业务写入切换为只写 t_member_other。
  3. 分批将已完成记录的：
    • t_member.phone 更新为空字符串。
    • t_member.identity 更新为 NULL。
  4. 清空前暂停直接 SQL 写入任务。
  5. 清空完成后执行全库检查，确认没有新明文写入。
  6. 保留字段，不删除结构。

‼️️‼️重要概念

HMAC-SHA256 盲索引 概念

HMAC-SHA256 盲索引

“HMAC-SHA256 盲索引”可以理解为：为敏感字段生成一个只有系统能计算、但不能反向还原原文的精准查询指纹。

以手机号 13800138000 为例：

1手机号原文：13800138000
2系统密钥：K_phone_v1   // 保存在 KMS/密钥服务中，不放数据库
3盲索引：HMAC-SHA256(K_phone_v1, "13800138000")

数据库中可以保存：

1phone_ciphertext     = 加密后的手机号
2phone_search_hash    = 上面生成的 HMAC 值

phone_search_hash 是 32 字节二进制值，也可以使用 64 位十六进制字符串保存。它不能解密出手机号，但同一个手机号在同一个密钥下会生成相同的值。

查询时，不再这样查询：

1WHERE phone = '13800138000'

而是由应用先计算盲索引：

1$phone = normalizePhone($inputPhone);
2$searchHash = hash_hmac('sha256', $phone, $phoneKey, true);

再查询：

1SELECT *
2FROM t_member
3WHERE phone_search_hash = :search_hash
4LIMIT 1

查到记录后，应用使用自己的密钥解密 phone_ciphertext，继续发送短信、展示掩码手机号或执行后续业务。

完整流程如下：

1用户输入手机号
2    ↓
3统一格式化，例如去空格、统一国家区号
4    ↓
5使用应用密钥计算 HMAC-SHA256
6    ↓
7用盲索引做等值查询
8    ↓
9取出密文并由应用解密

证件号 identity 也可以采用同样方式，但建议使用独立密钥：

1phone   -> K_phone_v1
2identity -> K_identity_v1

这样做有几个重要特点：

  1. 支持精准查询

    注册重复校验、找回密码、后台按手机号查询、证件号去重等 = 查询都可以继续支持。

  2. 不能支持普通模糊查询

    例如：

    1phone LIKE '%1380%'
2phone LIKE '138%'

    盲索引无法支持这类查询。需要改成完整手机号精准搜索，或者额外设计前缀索引，但后者会泄露更多信息。

  3. HMAC 不是加密

    盲索引不能还原手机号，所以它只能解决“怎么查”的问题。若数据库中仍保存明文 phone，数据库泄露时明文仍然会暴露。

    因此完整方案通常是：

    1phone       -> AES-GCM 等可逆加密
2phone_hash  -> HMAC-SHA256，用于精准查询

  4. 为什么不用普通 SHA256

    手机号和证件号的格式空间相对有限，攻击者可以准备大量候选号码进行字典匹配：

    1SHA256("13800138000")
2SHA256("13800138001")
3SHA256("13800138002")
4...

    HMAC 多了一个不在数据库中的密钥。只有拿到应用密钥，攻击者才能有效验证候选值。因此密钥必须放在 KMS、独立密钥服务或受保护的运行环境中，不能和数据库备份放在一起。

  5. 盲索引本身仍会泄露相等关系

    如果两条记录的 phone_search_hash 相同，攻击者可以知道它们对应同一个手机号，虽然不知道具体号码。因此还需要考虑重复账号、日志、缓存、数仓同步等其他泄露面。

对当前项目而言，盲索引不是单独替换字段就能自动兼容旧逻辑。所有手机号、证件号的写入和精准查询，都需要统一经过一个加密/索引适配层；但它可以保留原有“输入明文、精准查询、应用内解密”的业务体验。
